A profile page needs a user from the network. You could keep an `isLoading` flag in state and branch on it. With Suspense, the component reads the data as if it were already there.

```jsx
function Profile({ userPromise }) {
    const user = use(userPromise); // no isLoading, no effect
    return <h1>{user.name}</h1>;
}

export default function Page({ userPromise }) {
    return (
        <Suspense fallback={<Spinner />}>
            <Profile userPromise={userPromise} />
        </Suspense>
    );
}
```

`Profile` never mentions a spinner. Yet the spinner shows while the promise is pending, and the profile replaces it later. Nothing in your code asks React to render again.

This guide shows the machinery behind that. A pending promise interrupts the render, the nearest boundary catches the interruption, and a listener on the promise brings the content back. Then it covers what shapes the reveal: where boundaries go, pre-warming, a 300ms throttle, and transitions that keep the old screen.

> Current as of React 19.2 and 19.3. `use` and Suspense for data are stable in React 19, and notes mark where 19.2 and 19.3 differ.

## 1. What suspending means

How does React know `Profile` is not ready, when `Profile` returns nothing special? It never checks a flag. It simply tries to use the data.

### The short version

A component suspends when it reads something that is not ready, such as a pending promise passed to `use`. React cannot finish that component, so it abandons its render. It shows the nearest `<Suspense>` boundary's fallback instead, and it listens to the promise. When the promise resolves, React renders the boundary's content again, and this time `use` returns the value.

So a Suspense fallback is temporary by design, because promises settle. An error boundary's fallback, by contrast, stays until you reset it. Every behavior in this guide refines one loop: interrupt, show a fallback, listen, retry.

### Interrupting a render with an exception

JavaScript has one way to leave a function halfway through: throw. React uses exactly that. This simplified teaching version runs in Node.

```js
// Simplified teaching version: suspend, catch at a boundary, retry.
const SuspenseException = new Error("not a real error");
let suspendedOn = null;

function use(promise) {
    if (promise.status === "fulfilled") return promise.value;
    if (promise.status === undefined) {
        promise.status = "pending";
        promise.then((value) => {
            promise.status = "fulfilled";
            promise.value = value;
        });
    }
    suspendedOn = promise;
    throw SuspenseException; // interrupt this render
}

function renderBoundary(children, fallback) {
    try {
        return children();
    } catch (thrown) {
        if (thrown !== SuspenseException) throw thrown; // a real error
        const promise = suspendedOn;
        promise.then(() => console.log("retry:", renderBoundary(children, fallback)));
        return fallback;
    }
}

const userPromise = new Promise((resolve) => setTimeout(() => resolve({ name: "Ada" }), 100));
const Profile = () => `<h1>${use(userPromise).name}</h1>`;

console.log("first:", renderBoundary(Profile, "<Spinner />"));
```

```text role="output"
first: <Spinner />
retry: <h1>Ada</h1>
```

`use` sees a pending promise, remembers it and throws. The boundary catches the throw, returns the fallback, and calls `.then` on the promise. About 100ms later the promise resolves, the boundary renders again, and `use` finds `status` set to `"fulfilled"`.

That is why <Mark kind="marker" wraps>a fallback is temporary: the promise it waits on settles</Mark>, and React is listening when it does.

### Declarative loading

Compare the version without Suspense, where every component owns its own loading state.

```jsx
// Without Suspense: the component tracks loading itself.
function Profile({ id }) {
    const [user, setUser] = useState(null);
    useEffect(() => {
        fetchUser(id).then(setUser);
    }, [id]);
    if (user === null) return <Spinner />;
    return <h1>{user.name}</h1>;
}
```

The data fetching guide calls this pattern the wrong tool for server state. With Suspense, the loading logic moves out of the component and into the boundary. You declare it once: while anything in here is not ready, show this.

### Try it

This browser exercise needs no data library. `lazy` suspends while a component's code loads, and the delay makes the fallback easy to see.

```jsx
import { lazy, Suspense } from "react";

const Chart = lazy(() => new Promise((resolve) => setTimeout(() => resolve(import("./Chart.jsx")), 1500)));

export default function App() {
    return (
        <Suspense fallback={<p>Loading chart…</p>}>
            <Chart />
        </Suspense>
    );
}
```

You should see the fallback for about 1.5 seconds, then the chart. Your component holds no loading state at all.

## 2. Catching a suspension: the nearest boundary

Suspense and error boundaries both catch something thrown during render and show a fallback. That resemblance is not a coincidence. They are one mechanism with one branch.

Three internal words help here. A fiber is React's object for one component instance, and each fiber points to its parent.

Begin work is the step where React renders one fiber on its way down the tree. To unwind is to walk back up from a fiber that threw, parent by parent, until React reaches a boundary that can handle the throw.

### The short version

When rendering a component throws, React catches the value in its work loop, in `throwException`. It checks what was thrown. A thenable, meaning any object with a `.then` method, is a suspension. It goes to the nearest `<Suspense>` boundary above the component. Anything else is an error, and it goes to the nearest error boundary.

React does not search for the boundary at that moment. It tracks the nearest boundary on a stack while it renders. The boundary then renders a second time in the same pass, now with its fallback. Content that was already on screen stays mounted but hidden, so its state survives.

### One catch, one branch

The branch is a single type check. This version runs in Node.

```js
// Simplified teaching version of the branch in throwException (ReactFiberThrow.js).
function classify(thrown) {
    const isThenable = thrown !== null && typeof thrown === "object" && typeof thrown.then === "function";
    return isThenable ? "suspend: nearest <Suspense>" : "error: nearest error boundary";
}

console.log(classify(new Promise(() => {})));
console.log(classify({ then() {} }));
console.log(classify(new Error("fetch failed")));
```

```text role="output"
suspend: nearest <Suspense>
suspend: nearest <Suspense>
error: nearest error boundary
```

| Thrown value | Caught by | The fallback lasts | What happens next |
|---|---|---|---|
| A thenable | The nearest `<Suspense>` | Until the promise settles | React listens and retries |
| An `Error`, or anything else | The nearest error boundary | Until you reset it | Nothing, since an error does not fix itself |

<MarginNote note="errors take this same path up the tree">

The unwind is the same for both, and so is "show a fallback". Only the boundary kind and the follow-up differ. That is why one component can sit inside both kinds of boundary, as section 10 shows.

</MarginNote>

### The handler stack

```js
// Simplified teaching version of the Suspense handler stack (ReactFiberSuspenseContext.js).
const handlers = [];
const nearest = () => handlers.at(-1) ?? "none";

handlers.push("Outer"); // beginWork enters <Suspense name="Outer">
handlers.push("Inner"); // and then <Suspense name="Inner">
console.log("Detail suspends, caught by:", nearest());
handlers.pop(); // Inner switches to its fallback
handlers.push("Outer"); // a fallback reuses the handler above it
console.log("Inner's fallback suspends, caught by:", nearest());
```

```text role="output"
Detail suspends, caught by: Inner
Inner's fallback suspends, caught by: Outer
```

As begin work enters each `<Suspense>`, React pushes it onto a stack, and pops it on the way out. The top of the stack is always the nearest boundary, and `getSuspenseHandler()` in `ReactFiberSuspenseContext.js` reads it.

It works like `try/catch`. The boundary that catches is the nearest one above the component, never a sibling or a descendant. A fallback is like a `catch` block, so a suspension inside it goes to the next boundary out. The error path is older and still walks up from fiber to parent to find a class error boundary.

### The boundary renders twice

```js
// Simplified teaching version of updateSuspenseComponent (ReactFiberBeginWork.js).
function updateSuspenseComponent(boundary) {
    const showFallback = (boundary.flags & DidCapture) !== 0;
    boundary.flags &= ~DidCapture;
    if (!showFallback) {
        return renderChildren(boundary); // attempt 1: the real content
    }
    hideContent(boundary); // an Offscreen child in "hidden" mode
    return renderFallback(boundary); // attempt 2: the fallback
}
```

The first attempt renders the children. When one suspends, `throwException` flags the boundary with `ShouldCapture`. React then unwinds back up, and `unwindWork` swaps that flag for `DidCapture` and returns the boundary to begin work. The second attempt renders the fallback, and the half-built content is thrown away, never committed.

If the content was already visible, React does not unmount it. It hides the DOM with `display: none`, so state survives. It cleans up layout effects in the hidden tree and runs them again on reveal. A tree that suspended before it ever mounted keeps no state, so its retry starts from scratch.

### No boundary at all

```jsx
// No <Suspense> above Profile: the first render shows nothing until the data arrives.
root.render(<Profile userPromise={userPromise} />);
```

What if nothing above the component is a `<Suspense>`? In a `createRoot` root, React 19 keeps the previous screen and waits for the data, even for a click. On the very first render, nothing appears until the data arrives.

React 18's legacy roots threw "A component suspended while responding to synchronous input" here. React 19 removed legacy roots from `react-dom`, so you will not see that error.

### Try it

Run this in a React 19 app with an error boundary component, such as the one in the error boundaries guide.

```jsx
const ok = new Promise((resolve) => setTimeout(() => resolve("loaded"), 1000));
const bad = new Promise((_, reject) => setTimeout(() => reject(new Error("failed")), 1000));

function Flaky({ promise }) {
    const data = use(promise); // pending: Suspense. Rejected: the error boundary.
    return <p>{data}</p>;
}

// <ErrorBoundary><Suspense fallback={<p>Loading…</p>}><Flaky promise={ok} /></Suspense></ErrorBoundary>
```

With `ok`, you should see "Loading…" for a second, then "loaded". Swap in `bad`, and the loading state gives way to the error fallback, which stays.

## 3. How a component suspends in React 19

You never write `throw` in a component. So what actually suspends, and why does an innocent-looking `fetch` loop forever?

### The short version

Three things suspend a component in React 19: `use(promise)`, a `lazy` component whose code has not loaded, and Suspense-ready libraries. `use` and `lazy` do not throw your promise. They store it and throw an internal `SuspenseException`, which React swaps back for the promise.

React also writes a `status` field onto the promise, so a later render can read the value without waiting. That only works if the same promise comes back. A promise created during render is new on every retry, so the component suspends forever. Cache the promise per input, or let a library do it.

### use reads a promise

```jsx
function Comments({ show, commentsPromise }) {
    if (!show) return null;
    const comments = use(commentsPromise); // fine after an early return
    return comments.map((c) => <p key={c.id}>{c.text}</p>);
}
```

`use` is stable in React 19. Unlike other hooks, it can run inside conditions and loops, and it can also read context. If the promise rejects, `use` throws the reason to the nearest error boundary. Here is what it does with a promise.

```js
// Simplified teaching version of trackUsedThenable (ReactFiberThenable.js).
function use(promise) {
    if (promise.status === "fulfilled") return promise.value;
    if (promise.status === "rejected") throw promise.reason;
    if (promise.status === undefined) {
        promise.status = "pending"; // first sight: tag the promise
        promise.then(
            (value) => Object.assign(promise, { status: "fulfilled", value }),
            (reason) => Object.assign(promise, { status: "rejected", reason }),
        );
    }
    suspendedThenable = promise; // the work loop reads this back
    throw SuspenseException;
}
```

Why throw a stand-in instead of the promise? The thrown value must never reach your code. The real exception's message starts "Suspense Exception: This is not a real error!", and it asks you to rethrow it. So never call `use` inside `try/catch`, because a `catch` would swallow the suspension.

### A resolved promise still suspends once

```js
const done = Promise.resolve("ready");
let seen = "nothing yet";
done.then((value) => (seen = value));
console.log("right after .then:", seen);
await null; // let one microtask run
console.log("one microtask later:", seen);
```

```text role="output"
right after .then: nothing yet
one microtask later: ready
```

A `.then` callback always runs later, so no code can read a native promise's value right away. That is why React tags promises with `status`. A brand-new promise suspends at least once, even when it has already resolved. A library that sets `status` to `"fulfilled"` itself lets `use` return at once.

### lazy and libraries

```jsx
const Settings = lazy(() => import("./Settings.jsx")); // the module needs a default export

<Suspense fallback={<Spinner />}>
    <Settings />
</Suspense>;
```

The first render of `Settings` starts the dynamic `import()`. While the chunk downloads, the lazy wrapper throws its pending promise, and React converts it, "as if we called use()", says its source. The lazy object keeps that one promise, so code splitting needs no cache from you.

Data libraries such as TanStack Query (`useSuspenseQuery`) and Relay cache promises by query key. You treat the data as always present. TanStack Query v5 still suspends by throwing the promise itself. React 19 supports that older path, which its source labels deprecated, but `use` is the API for your own code.

| Way to suspend | What it waits for | Who keeps the promise stable |
|---|---|---|
| `use(promise)` | Any promise | You: create it outside render, or cache it |
| `lazy(() => import(...))` | A code chunk | React, inside the lazy object |
| `useSuspenseQuery` and similar | Data | The library's cache, keyed by query |
| `throw promise` | Anything | You, and only libraries still do this |

### The cache requirement

```js
function fetchUser(id) {
    return new Promise((resolve) => setTimeout(() => resolve({ id }), 50));
}

// Uncached: every render makes a new promise.
const first = fetchUser(1);
const retry = fetchUser(1);
console.log("uncached, same promise?", first === retry);

// Cached: one promise per id.
const cache = new Map();
function fetchUserCached(id) {
    if (!cache.has(id)) cache.set(id, fetchUser(id));
    return cache.get(id);
}
console.log("cached, same promise?", fetchUserCached(1) === fetchUserCached(1));
```

```text role="output"
uncached, same promise? false
cached, same promise? true
```

Now put each version inside a component.

```jsx
// Loops: a new promise on every render, so every retry suspends again.
function Profile({ id }) {
    const user = use(fetchUser(id));
    return <h1>{user.name}</h1>;
}

// Ends: the same promise per id, so the retry reads it resolved.
function CachedProfile({ id }) {
    const user = use(fetchUserCached(id));
    return <h1>{user.name}</h1>;
}
```

The retry runs `Profile` again, which calls `fetchUser` again and gets a new pending promise. It suspends, its promise resolves, and the cycle repeats. <Mark kind="underline" wraps>A fresh promise on every render suspends forever</Mark>, and it is the most common Suspense bug.

React helps a little in development. Sometimes React replays a component within the same render, as section 4 shows. Suppose the replay gets a different promise from the same `use` call. React then logs "A component was suspended by an uncached promise" and reuses the first promise.

A retry is a new render, so a network fetch usually loops with no warning. If a root suspends over 100 times with no boundary to show, React throws an error naming a likely cause: an async Client Component.

### Try it

The later exercises share this small cache. It runs in Node too.

```js
// A tiny promise cache for the exercises: the same key gives the same promise.
const promiseCache = new Map();
function cached(key, ms, value = key) {
    if (!promiseCache.has(key)) {
        promiseCache.set(key, new Promise((resolve) => setTimeout(() => resolve(value), ms)));
    }
    return promiseCache.get(key);
}

console.log(cached("user-1", 50) === cached("user-1", 50));
console.log(await cached("user-1", 50));
```

```text role="output"
true
user-1
```

Now compare a loop and a fix in a React 19 app. Render each one under `<Suspense fallback={<p>Loading…</p>}>`.

```jsx
let fetches = 0;
function fetchUncached(id) {
    fetches += 1;
    console.log("fetch", fetches);
    return new Promise((resolve) => setTimeout(() => resolve({ name: `User ${id}` }), 500));
}

function Looping({ id }) {
    const user = use(fetchUncached(id)); // a new promise on every render
    return <h1>{user.name}</h1>;
}

function Settled({ id }) {
    const user = use(cached(`user-${id}`, 500, { name: `User ${id}` }));
    return <h1>{user.name}</h1>;
}
```

With `Looping`, a new "fetch" line should appear about every 500ms, and the fallback never leaves. You will probably not see the uncached promise warning, because no replay happens. With `Settled`, the name appears after about 500ms.

## 4. Coming back: pings and retries

The data arrives. Nothing in your code calls `setState`. How does React find out, and which render brings the content back?

Three scheduling words appear here, and [the scheduler guide](/articles/react-scheduler-and-lanes-internals) covers them in depth. A lane is React's priority label for an update, stored as one bit in a number.

A time-sliced render works in pieces of about 5ms, so the browser can handle input in between. A lane expires when it has waited too long, and React then finishes it in one unbroken pass.

### The short version

React listens to the promise a component suspended on. It attaches up to two listeners. A ping listener goes on during the render. If that render never committed, as when a transition kept the old screen, the ping marks its lanes as ready to try again.

A retry listener goes on when a fallback commits. When the promise resolves, it gives the boundary a retry lane, one of four lanes React cycles through for Suspense. Retry lanes are time-sliced and never expire. Either way, the component runs again, reads the resolved promise, and the content replaces the fallback.

### Two listeners

React <Mark kind="circle">never polls</Mark>. Both paths start from the same moment in `throwException`.

```js
// Simplified teaching version of throwException's Suspense path (ReactFiberThrow.js).
function onSuspend(root, boundary, promise, renderLanes) {
    boundary.flags |= ShouldCapture; // show the fallback in this pass
    boundary.retryQueue.add(promise); // the commit will attach the retry listener
    promise.then(() => {
        root.pingedLanes |= renderLanes; // ping: these lanes may now succeed
        ensureRootIsScheduled(root);
    });
}
```

The retry listener waits for the commit, because it only matters once a fallback is on screen.

```js
// Simplified teaching version of attachSuspenseRetryListeners and retryTimedOutBoundary.
function commitFallback(root, boundary) {
    for (const promise of boundary.retryQueue) {
        promise.then(() => {
            const retryLane = claimNextRetryLane(); // one of 4 retry lanes
            markRootUpdated(root, retryLane); // pendingLanes |= retryLane
            ensureRootIsScheduled(root);
        });
    }
}
```

| Question | Ping | Retry |
|---|---|---|
| When React attaches it | During render, in `attachPingListener` | At commit, once the fallback shows |
| Where React keeps it | `root.pingCache`, keyed by promise and lanes | The boundary's retry queue |
| What it does on resolve | Marks the original lanes as pinged | Schedules a new retry lane on the boundary |
| When it matters | The render never committed | A fallback is on screen |

### Retry lanes

```js
// Simplified teaching version of claimNextRetryLane (ReactFiberLane.js).
const RetryLane1 = 1 << 22;
const RetryLanes = 0b1111 << 22; // bits 22 to 25
let nextRetryLane = RetryLane1;

function claimNextRetryLane() {
    const lane = nextRetryLane;
    nextRetryLane <<= 1;
    if ((nextRetryLane & RetryLanes) === 0) nextRetryLane = RetryLane1; // wrap after 4
    return lane;
}

for (let i = 0; i < 5; i++) {
    console.log("retry", i + 1, "gets bit", Math.log2(claimNextRetryLane()));
}
```

```text role="output"
retry 1 gets bit 22
retry 2 gets bit 23
retry 3 gets bit 24
retry 4 gets bit 25
retry 5 gets bit 22
```

A retry is an ordinary update on a lane, so it goes through normal scheduling. The scheduler guide shows how `getNextLanes` skips suspended lanes until a ping and then picks them up.

Retry lanes sit below the transition lanes. Their renders are time-sliced, so a click can interrupt them. They never expire, because the source says retries must always be sliced.

### A last look before unwinding

A time-sliced render, such as a transition or a retry, does not unwind the moment something suspends. It yields to the main thread once. If the promise settled meanwhile, React replays the component as if nothing happened.

```js
// Simplified teaching version of renderRootConcurrent's suspended branch (React 19.2).
if (reason === SuspendedOnImmediate) {
    reason = SuspendedAndReadyToContinue;
    yieldToMainThread(); // give a cached promise a chance to settle
} else if (reason === SuspendedAndReadyToContinue) {
    if (promise.status === "fulfilled") replaySuspendedUnitOfWork(fiber); // no fallback
    else throwAndUnwindWorkLoop(fiber); // unwind and show the fallback
}
```

Blocking renders, such as those from clicks and timers, skip this step and unwind at once.

A thrown promise from an older library also unwinds at once. React's source says it keeps "the old behavior" there and always unwinds, because replays can cause infinite ping loops. The retry also explains the cache rule again. It re-runs the component, so it ends only if the component reads the same, now-resolved promise.

### Try it

Drop this into a React 19 app without StrictMode, so each render logs once.

```jsx

    console.log("Profile renders");
```

## 5. Where boundaries go: placement and nesting

One boundary at the top of the page hides the header behind a spinner. A boundary around every widget makes the screen pop like popcorn. Where should boundaries go?

### The short version

A boundary's fallback replaces everything below it that suspends. So where you put a boundary decides how much of the screen one loading state covers. One boundary around the whole page hides the header and navigation, which needed no data. A boundary around every small piece makes the screen arrive in fragments, a popcorn UI.

The usual answer is a shell, the layout that needs no data, outside any boundary, plus one boundary per region with its own data. Nesting adds order. An outer boundary reveals its content while an inner one still shows its fallback, so the page arrives in stages.

### Too high and too low

```jsx
// Too high: the header waits for the slowest panel.
<Suspense fallback={<PageSpinner />}>
    <Header />
    <Feed />
    <Sidebar />
</Suspense>
```

If anything here suspends, the user sees a full-page spinner and loses all context. The header could have rendered at once. The opposite mistake wraps every element, and each one reveals at its own moment.

| Placement | What the user sees | Cost |
|---|---|---|
| One boundary at the top | A full-page spinner, then everything | Ready parts wait, and context is lost |
| A boundary around every element | Pieces popping in at random | Flicker, layout shift, "is it done yet?" |
| A shell, plus one boundary per data region | Layout at once, then regions fill in | You must choose the regions |

### The shell pattern

```jsx
<Layout>
    <Header />
    <Nav />
    <Suspense fallback={<FeedSkeleton />}>
        <Feed />
    </Suspense>
    <Suspense fallback={<SidebarSkeleton />}>
        <Sidebar />
    </Suspense>
</Layout>
```

<MarginNote note="the shell paints first, slow parts wait">

The header, navigation and layout need no data, so they sit outside every boundary and appear at once. Each slow region gets its own boundary and a skeleton shaped like its content.

</MarginNote>

Match boundaries to data dependencies. A region with its own fetch can be ready on its own, so a local fallback for it is a coherent loading state. Error boundaries follow the same instinct, and the two often sit around the same regions. Regions that share data, or must appear together, can share one boundary.

### Nesting stages the reveal

```jsx
<Suspense fallback={<PageSkeleton />}>
    <PageFrame>
        <Suspense fallback={<DetailSkeleton />}>
            <Detail />
        </Suspense>
    </PageFrame>
</Suspense>
```

Suppose `PageFrame` needs page data and `Detail` needs slower data.

1. `PageFrame` suspends and reaches the outer boundary, which shows `PageSkeleton`. The inner boundary does not exist yet.
2. The page data arrives. The outer boundary retries, and `PageFrame` renders its children.
3. `Detail` suspends and reaches the inner boundary, now the nearest. The frame shows with `DetailSkeleton` inside it.
4. The detail data arrives, and the inner boundary retries.

<GuideFigure figure="su-nesting" />

The outer region does not wait for the inner one. Each level reveals as soon as its own data is ready, so the user watches structure arrive first. If the outer data is slower, the inner content cannot reveal first, because `Detail` does not render until its parent does.

Flatter structure, with sibling boundaries, reveals regions independently of each other. Nesting says something more: this sits inside that, and the outer part may show first.

Nest to match real containment, such as a page holding a section holding a detail. Deeper nesting suits layered data, where each fetch needs the one before. Too many stages bring back the popcorn feel, and each reveal is a retry that section 7's throttle spaces out.

## 6. Siblings and pre-warming

Two components fetch their own data, side by side in one boundary. The first suspends. Does the second one's fetch start now, or only after the first resolves?

### The short version

When one sibling suspends, React 19 stops rendering that boundary's content and commits the fallback at once, so the user sees it sooner. Stopping early would delay the other siblings' fetches, a waterfall.

So React then schedules a second render on a retry lane, called pre-warming. That render visits the skipped siblings only to start their work, such as `use` calls and lazy imports, and React discards its output.

Independent siblings therefore still fetch in parallel. Pre-warming cannot help a child of the component that suspended. That child does not exist until its parent renders.

### The question

```jsx
<Suspense fallback={<Spinner />}>
    <FeedA /> {/* use(getFeed("a")) suspends first */}
    <FeedB /> {/* use(getFeed("b")): when does this fetch start? */}
</Suspense>
```

Each feed starts its fetch during render, through a cached getter. If React never rendered `FeedB` until `FeedA` resolved, fetch B would start late. Two 1-second fetches would take 2 seconds instead of 1.

### Commit first, then pre-warm

```js
// Simplified teaching version of throwAndUnwindWorkLoop (ReactFiberWorkLoop.js, React 19.2).
if (isPrerendering) {
    unwindUnitOfWork(fiber, { skipSiblings: false }); // visit siblings to start their work
} else {
    unwindUnitOfWork(fiber, { skipSiblings: true }); // reach the fallback fast
    boundary.flags |= ScheduleRetry; // claim a retry lane when the boundary completes
}
```

| Step | Render | What happens |
|---|---|---|
| 1 | The normal render | `FeedA` suspends. React skips `FeedB` and commits the fallback. |
| 2 | Completing and committing | The boundary claims a retry lane as it completes. The commit marks that lane suspended. |
| 3 | The pre-warm render | `getNextLanes` picks a suspended lane that is not yet "warm". `FeedB` renders and starts fetch B. |
| 4 | Still the pre-warm | React throws the output away and marks the lane warm. |
| 5 | The real retry | When the data arrives, a ping or retry renders the content for real. |

The pre-warm render is time-sliced, so it never blocks input. When a render cannot commit anyway, as in a transition that keeps the old screen, React skips the extra pass. It turns the current render into the pre-warm and visits the siblings right there. React 19.2 and 19.3 have no flag for this, so it is always on.

So <Mark kind="marker" wraps>independent siblings in one boundary still fetch in parallel</Mark>. Siblings in one boundary also reveal together, which makes them the documented pattern for "load in parallel, show at once".

### A short history

From legacy Suspense in React 16 and 17 through React 18, React rendered every sibling before it committed the fallback. Fetches ran in parallel, but the fallback appeared later, and developers relied on that parallelism.

The React 19 release candidate skipped the siblings with no second pass. Parallel fetches turned into waterfalls, and the community pushed back. React 19.0 shipped pre-warming, which keeps the fast fallback and the parallel fetches.

### Waterfalls pre-warming cannot fix

```jsx
function Author({ id }) {
    const author = use(getAuthor(id)); // fetch 1
    return <Posts authorId={author.id} />; // Posts cannot render until fetch 1 resolves
}
```

`Posts` is a child of the component that suspended, not a sibling. It does not exist until `Author` renders, so its fetch waits. When the second fetch truly needs the first one's result, the wait is a real data dependency. When it does not, start both fetches higher up.

A third cause is structure. The components may not be siblings in the same boundary after all, or a nested boundary may change when one of them renders.

```jsx
function AuthorPage({ id }) {
    const authorPromise = getAuthor(id); // cached getters: both fetches start now
    const postsPromise = getPosts(id);
    return (
        <Suspense fallback={<Spinner />}>
            <Author promise={authorPromise} />
            <Posts promise={postsPromise} />
        </Suspense>
    );
}
```

## 7. The 300ms reveal throttle

The data arrives in 40ms, yet the spinner stays up for about 300ms. Two panels finish 100ms apart, yet they appear together. React is doing this on purpose.

### The short version

Showing and hiding a fallback has its own cost: a spinner that flashes for 40ms looks like a glitch. React 19 does not skip the fallback for an urgent update. It commits the fallback at once, then throttles the reveal.

`FALLBACK_THROTTLE_MS` is 300. React records the time of every commit where a fallback appears or disappears. A render made only of retries waits until 300ms after that time.

Retries that finish during the wait join the same commit, so nearby boundaries reveal together. A fallback is skipped only by a transition, or when a time-sliced render finds the data ready.

### The rule in code

```js
// From finishConcurrentRender in ReactFiberWorkLoop.js, React 19.2 (simplified).
if (includesOnlyRetries(lanes)) {
    const msUntilTimeout = globalMostRecentFallbackTime + FALLBACK_THROTTLE_MS - now();
    if (msUntilTimeout > 10) {
        root.timeoutHandle = scheduleTimeout(commitRootWhenReady, msUntilTimeout);
        return; // hold the reveal
    }
}
commitRootWhenReady();
```

`markCommitTimeOfFallback`, called during commit, sets `globalMostRecentFallbackTime` whenever a boundary flips either way. React skips a wait under 10ms. Inside `act`, React's test helper, React commits at once, so tests never wait out the throttle.

### Watching the numbers

```js
// Simplified teaching version of the retry throttle in ReactFiberWorkLoop.js.
const FALLBACK_THROTTLE_MS = 300;
let mostRecentFallbackTime = 0;

function commitTimeForRetry(readyAt) {
    const wait = mostRecentFallbackTime + FALLBACK_THROTTLE_MS - readyAt;
    const commitAt = wait > 10 ? readyAt + wait : readyAt;
    mostRecentFallbackTime = commitAt; // a fallback disappears: the clock restarts
    return commitAt;
}

mostRecentFallbackTime = 0; // the fallback appears at 0ms
console.log("data at 40ms, content at", commitTimeForRetry(40), "ms");
console.log("next reveal ready at 450ms, commits at", commitTimeForRetry(450), "ms");
console.log("next reveal ready at 900ms, commits at", commitTimeForRetry(900), "ms");
```

```text role="output"
data at 40ms, content at 300 ms
next reveal ready at 450ms, commits at 600 ms
next reveal ready at 900ms, commits at 900 ms
```

The first reveal waits for the 300ms mark. The second is ready 150ms after it, so it waits until 600. The third arrives late enough to commit at once.

<GuideFigure figure="su-throttle" />

### What the throttle does and does not do

| Situation | What React does |
|---|---|
| An urgent update whose data arrives in 40ms | Commits the fallback now, the content at about 300ms |
| Three boundaries ready within 300ms of each other | Reveals all three in one commit |
| Data that takes 2 seconds | Shows the fallback until then, and the throttle adds nothing |
| A transition that re-suspends visible content | Shows no fallback at all (section 8) |
| A test inside `act` | Commits at once |

<MarginNote note="a short wait beats a flashing spinner">

The cost of a loading state is not only the wait. It is also the jolt of showing and hiding it. React trades a little reveal latency for fewer, calmer visual changes.

</MarginNote>

The constant is built in, and you cannot set it per boundary. It smooths small timing differences, but it cannot fix many boundaries spread over seconds. That is a design problem, solved with placement and nesting.

The React 18 Working Group called this "placeholder throttling". React 18.3 used 500ms and throttled only retries that still left a fallback on screen.

Some updates outside a transition would have hidden visible content. For those, it also waited a "just noticeable difference" timeout before showing the fallback. Measured from the event, it waited until a mark such as 120ms, 480ms or 1,080ms. React 19 has no such timeouts.

### Try it

## 8. Transitions keep the old screen

A master-detail view shows one item's details. You click another item, the new details suspend, and the old details vanish behind a spinner. This is the most common Suspense frustration, and transitions fix it.

### The short version

By default, an update that makes visible content suspend again hides that content and shows the fallback. For a first load that is right, since nothing was there. For an update it is jarring. Wrap the update in `startTransition`, and React handles the suspension differently.

If showing a fallback would hide content already on screen, React does not commit. It keeps the old screen, waits for a ping, and renders the new screen on a transition lane. `isPending` stays true meanwhile, so you can dim the old content. New boundaries inside the transition still show their fallbacks at once.

### The default hides content

```jsx
// A plain update: the visible Detail suspends again, so the fallback replaces it.
<List items={items} onSelect={(id) => setSelectedId(id)} />
```

The user sees the old details, then a skeleton, then the new details. React cannot know in general that hiding is unwanted. For a first load, the fallback is exactly right.

### Wrapping the update

```jsx
function Master({ items }) {
    const [selectedId, setSelectedId] = useState(items[0].id);
    const [isPending, startTransition] = useTransition();

    return (
        <>
            <List items={items} onSelect={(id) => startTransition(() => setSelectedId(id))} />
            <Suspense fallback={<DetailSkeleton />}>
                <div style={{ opacity: isPending ? 0.6 : 1 }}>
                    <Detail id={selectedId} />
                </div>
            </Suspense>
        </>
    );
}
```

The update now gets a transition lane, which is low priority and interruptible. When `Detail` suspends, the old details stay, dimmed by `isPending`. The new details render in the background and swap in once ready.

<GuideFigure figure="react-transition-fallback" />

### The visible-content rule

```js
// Simplified teaching version of shouldRemainOnPreviousScreen (ReactFiberWorkLoop.js).
// Retries have one more case, skipped here.
function decide({ hasBoundary, onlyTransitions, boundaryWasVisible }) {
    if (!hasBoundary) return "keep the old screen (nothing can show a fallback)";
    if (onlyTransitions && boundaryWasVisible) return "keep the old screen, wait for the data";
    return "commit the fallback now";
}

console.log("click, visible boundary:", decide({ hasBoundary: true, onlyTransitions: false, boundaryWasVisible: true }));
console.log("transition, visible boundary:", decide({ hasBoundary: true, onlyTransitions: true, boundaryWasVisible: true }));
console.log("transition, new boundary:", decide({ hasBoundary: true, onlyTransitions: true, boundaryWasVisible: false }));
console.log("no boundary at all:", decide({ hasBoundary: false, onlyTransitions: false, boundaryWasVisible: false }));
```

```text role="output"
click, visible boundary: commit the fallback now
transition, visible boundary: keep the old screen, wait for the data
transition, new boundary: commit the fallback now
no boundary at all: keep the old screen (nothing can show a fallback)
```

React decides per boundary: would showing this fallback hide something visible? `ReactFiberSuspenseContext.js` tracks the outermost boundary that is not on screen yet, in a variable named `shellBoundary`. Everything above that boundary is already visible.

When React keeps the old screen, it marks the transition's lanes as suspended and commits nothing. It waits with no timeout until a ping arrives. A transition does not wait for all content, only long enough to avoid hiding what is visible. So <Mark kind="marker" wraps>transitions are how you update or navigate without hiding content</Mark>.

| Update | Was the boundary visible? | Result |
|---|---|---|
| A click or a timer | Yes | The content hides, and the fallback shows |
| A transition | Yes | The old screen stays until the data arrives |
| A transition | No, it is new | Its fallback shows at once |
| Any update, with no boundary above | Not applicable | The old screen stays, or nothing shows on first load |

### Resetting with a key, and routers

Sometimes the new content is truly different, like another user's profile. Showing the old user while the new one loads would mislead. A `key` tells React this is new content, so the boundary resets and shows its fallback.

```jsx
<ProfilePage key={userId} />
```

Routers that integrate with Suspense wrap navigations in transitions for you. The rule for your own code: wrap any update that changes visible Suspense content in a transition. That covers navigation, filters, tabs and selection. Keep the bare fallback for first loads.

The React 18 Working Group called this a "delayed transition". `<ViewTransition>` can animate updates from `startTransition`, `useDeferredValue` and Actions, and a Suspense reveal from fallback to content. It is stable in React 19.3 and experimental in 19.2.

## 9. useDeferredValue and Suspense

A search box filters results as you type. The input must update on every keystroke, so you cannot wrap its `setState` in a transition. The results still should not flash a fallback. `useDeferredValue` handles that case.

### The short version

`useDeferredValue` applies the transition idea to a value you do not set yourself. When the value changes, React first renders urgently with the old deferred value, so the input stays current. Then it renders again in the background with the new value, on a deferred transition lane.

If that background render suspends, React keeps showing the old results instead of a fallback, and it retries when the data arrives. Comparing the value with its deferred copy tells you the results are stale. It does not save network requests. Inside a transition it returns the new value and spawns nothing.

### A search page

```jsx
function SearchPage() {
    const [query, setQuery] = useState("");
    const deferredQuery = useDeferredValue(query);
    const isStale = query !== deferredQuery;

    return (
        <>
            <input value={query} onChange={(e) => setQuery(e.target.value)} />
            <Suspense fallback={<p>Loading…</p>}>
                <div style={{ opacity: isStale ? 0.5 : 1 }}>
                    <Results query={deferredQuery} />
                </div>
            </Suspense>
        </>
    );
}
```

On the first load, the boundary is new, so its fallback shows. After that, each keystroke updates the input at once. `Results` keeps the old query until the background render with the new one completes.

### Under the hood

```js
// Simplified teaching version of useDeferredValue on update (ReactFiberHooks.js).
function updateDeferredValue(value, previousValue) {
    if (includesOnlyNonUrgentLanes(renderLanes)) {
        return value; // already a background render: use the new value
    }
    requestDeferredLane(); // spawn a later render on a deferred lane
    return previousValue; // this urgent render keeps the old value
}
```

The spawned render uses a deferred transition lane. Inside hidden content, such as `<Activity mode="hidden">`, it uses `OffscreenLane` instead, the low-priority lane React keeps for hidden work. It contains only transition-like lanes, so section 8's visible-content rule applies, and the visible results stay. A new keystroke interrupts it and restarts with the latest value.

The background render does not reduce network traffic. Each keystroke can still start a request. A cache makes going back instant, since earlier queries are already stored.

React 19 adds an `initialValue` argument.

```jsx
const deferredQuery = useDeferredValue(query, ""); // the first render uses ""
```

The first render uses `initialValue`, and React then renders again in the background with `query`. Without it, the first render does not defer at all.

| | `startTransition` | `useDeferredValue` |
|---|---|---|
| What you control | The state update | Only the value you receive |
| The urgent part | Whatever runs outside the callback | The render that uses the old value |
| The background render | A transition lane | A deferred transition lane |
| The pending signal | `isPending` | `value !== deferredValue` |
| Hides visible content? | No | No |

## 10. Suspense with error boundaries

An async region has two ways to be unfinished: still loading, or failed. Suspense answers the first. Without an answer for the second, one failed request can take down the whole app.

### The short version

A promise you read can be pending or rejected. Suspense handles pending and ignores errors, so pair it with an error boundary around the same region.

Put the error boundary outside and Suspense inside. A pending read reaches Suspense first and shows its loading fallback. A rejected read throws its reason past Suspense to the error boundary, whose fallback stays until reset.

Without any error boundary, React 19 unmounts the whole root and reports the error. Resetting renders the region again. Drop the rejected promise from your cache first, or `use` throws the cached rejection at once.

### The pattern

```jsx
<ErrorBoundary fallback={<ErrorState />}>
    <Suspense fallback={<LoadingState />}>
        <Profile />
    </Suspense>
</ErrorBoundary>
```

| State | What `Profile` does | Who catches it | What the user sees |
|---|---|---|---|
| Pending | Suspends | The inner `<Suspense>` | `LoadingState`, then a retry |
| Failed | Throws the rejection | The outer error boundary, past Suspense | `ErrorState`, until a reset |
| Success | Renders | Nobody | The profile |

<MarginNote note="one throw path, two catchers">

Both boundaries wrap the same subtree, and each catches its own kind of thrown value. That is section 2's single branch, turned into a pattern.

</MarginNote>

The error boundary sits outside because Suspense lets errors pass. A thrown promise stops at the inner `<Suspense>`, while an error keeps going to the outer boundary. Place one such pair per independent region, matching data dependencies. Some libraries and frameworks bundle the pair, but underneath it is the same two boundaries.

### Recovering from a failure

```jsx
function retry() {
    userCache.delete(id); // drop the rejected promise
    resetErrorBoundary(); // render the region again, which fetches again
}
```

A reset renders the subtree again, so it suspends, shows the loading state, and then succeeds or fails. If the cache still held the rejected promise, `use` would read `status` as `"rejected"` and throw at once. That produces a reset loop with no real retry.

With no error boundary at all, React 19 reports the error through the root's `onUncaughtError` option and unmounts the root.

```js
const root = createRoot(container, {
    onUncaughtError(error) {
        reportToService(error); // nothing caught it, and the root is gone
    },
});
```

Two more details belong to the error boundaries guide. In a concurrent render, React retries once synchronously before it shows an error boundary. On the server, a Suspense boundary also catches render errors. React sends its fallback HTML, and the client tries that part again.

### Try it

This exercise tests recovery. The first request fails, and later ones succeed.

```jsx

            setTimeout(() => (fail ? reject(new Error("offline")) : resolve("Ada")), 500),
        );

    }

}

}
```

You should see loading, the error, then loading and "Ada" after the click. Remove the `delete` call, and "Try again" should fail at once. Remove the error boundary, and the whole root should disappear.

## 11. Suspensey stylesheets, images and fonts

Data is not the only thing that can make content unready. Content revealed before its stylesheet loads flashes unstyled, and images can pop in after a reveal. React 19 can wait for these too.

### The short version

In React 19, a `<link rel="stylesheet">` with a `precedence` prop holds back a reveal until the file loads. In a transition, React keeps the old screen and delays the commit. In an urgent update, the nearest boundary shows its fallback instead. React gives up after 60 seconds.

Images and fonts wait only inside a `<ViewTransition>`, and only in non-urgent renders. Images wait up to 800ms, and new fonts and on-screen images up to 500ms during the animation. Unlike data, these resources block the commit, not the render, so React can finish rendering while they load.

### Stylesheets

```jsx
function Docs() {
    return (
        <>
            <link rel="stylesheet" href="/docs.css" precedence="default" />
            <article className="docs">…</article>
        </>
    );
}
```

React hoists the link into the document head and orders it by `precedence`. Until the file loads, React will not reveal content that depends on it.

```js
// Simplified teaching version of preloadResourceAndSuspendIfNeeded (ReactFiberCompleteWork.js).
if (!stylesheetLoaded(resource)) {
    if (shouldRemainOnPreviousScreen()) {
        fiber.flags |= ShouldSuspendCommit; // the render finishes, the commit waits
    } else {
        suspendCommit(); // like a suspension: the nearest fallback shows
    }
}
```

At commit, React skips a stylesheet whose `media` query does not match.

```jsx
// Print styles never match on screen, so they never hold a transition's commit.
<link rel="stylesheet" href="/print.css" media="print" precedence="default" />
```

When a fallback shows because of a stylesheet, React schedules a retry right away, since the render itself had no data to wait for.

### Images and fonts

```jsx
<ViewTransition>
    <img src={photo.url} width={800} height={600} alt="" />
</ViewTransition>
```

Inside a `<ViewTransition>`, a transition's commit waits for this image to load and decode. React estimates the download size from `width` and `height`. If the images on the way are larger than it can fetch in about 500ms, it waits only 50ms.

| Resource | When React waits | Longest wait | How to opt out |
|---|---|---|---|
| A stylesheet with `precedence` | Any update | 60 seconds | Leave out `precedence` |
| An `<img>` inside `<ViewTransition>` | Transition, retry and idle renders | 800ms, or 50ms when there is too much to download | `loading="lazy"`, or an `onLoad` prop |
| New fonts and on-screen images | While a view transition starts | 500ms | None |

`<ViewTransition>` is stable in React 19.3, so this applies there. In stable 19.2, images never hold back a commit, because `<ViewTransition>` exists only in experimental builds.

### Try it

```jsx
function App() {
    const [show, setShow] = useState(false);
    return (
        <>
            <button onClick={() => startTransition(() => setShow(true))}>Open docs</button>
            <Suspense fallback={<p>Loading docs…</p>}>{show && <Docs />}</Suspense>
        </>
    );
}
```

## 12. SuspenseList (experimental)

Cards in a feed each have their own boundary, and each reveals when its data arrives. Card 3 can appear before card 1, which looks chaotic. React has a component for ordering reveals, but you cannot ship it yet.

### The short version

Sibling boundaries reveal in whatever order their data arrives. `SuspenseList` would coordinate them. `revealOrder` picks `forwards`, `backwards`, `together` or `independent`, and `tail` decides how many pending fallbacks show.

It is not in stable React. Stable `react` 19.2 and 19.3 do not export it at all. Only experimental builds export it, as `unstable_SuspenseList`, and its defaults changed between 19.2 and 19.3. For production, one shared boundary gives you "together", and nesting gives you an order. The throttle from section 7 smooths timing, but it never imposes an order.

### Coordinating siblings

```jsx
// Experimental builds only.
<unstable_SuspenseList revealOrder="forwards" tail="collapsed">
    <Suspense fallback={<CardSkeleton />}>
        <Card id={1} />
    </Suspense>
    <Suspense fallback={<CardSkeleton />}>
        <Card id={2} />
    </Suspense>
    <Suspense fallback={<CardSkeleton />}>
        <Card id={3} />
    </Suspense>
</unstable_SuspenseList>
```

| Prop | Value | Effect |
|---|---|---|
| `revealOrder` | `forwards` | Top to bottom: a card waits for the ones above it |
| `revealOrder` | `backwards` | Bottom to top |
| `revealOrder` | `together` | All at once, when all are ready, like `Promise.all` for the reveal |
| `revealOrder` | `independent` | Each as it resolves, the behavior with no list |
| `tail` | `collapsed` | Only the next pending fallback shows |
| `tail` | `hidden` | No fallbacks for items not yet revealed |
| `tail` | `visible` | Every pending fallback shows |

React 19.2's experimental build warns that both defaults are changing. It also warns that `backwards` will change and suggests `unstable_legacy-backwards`. In the 19.3 source, `tail` defaults to `hidden` and the order to `forwards`. SuspenseList also still has open edge cases, which is part of why it stays experimental.

### The stable alternative

```jsx
<Suspense fallback={<FeedSkeleton />}>
    <Card id={1} />
    <Card id={2} />
    <Card id={3} />
</Suspense>
```

One boundary reveals its whole subtree at once, which is `together`. Pre-warming keeps the three fetches parallel.

### Try it

```jsx
function Card({ id, ms }) {
    return <article>{use(cached(`card-${id}`, ms, `Card ${id}`))}</article>;
}

// <Suspense fallback={<FeedSkeleton />}>
//     <Card id={1} ms={300} /> <Card id={2} ms={900} /> <Card id={3} ms={600} />
// </Suspense>
```

Use the `cached` helper from section 3. All three cards should appear together at about 900ms. On an experimental build, try `revealOrder="forwards"` and watch them fill in order.

## 13. Streaming SSR and selective hydration

On the server, Suspense does a second job. It decides how HTML streams to the browser and how the page becomes interactive. Frameworks handle this for you, so this section stays short. The [Server Components guide](/articles/react-server-components-internals) covers streaming in depth.

### The short version

On the server, each Suspense boundary is a seam in the HTML stream. React sends the shell and each pending boundary's fallback first.

Then it streams each boundary's content as its data resolves, with a small script that swaps it into place. Since 19.2, React batches those streamed reveals briefly to match the client throttle. It stops batching if load time nears 2.5 seconds.

On the client, boundaries also split hydration, the step where React attaches its event handlers to the server's HTML. React hydrates each boundary separately. A boundary the user clicks hydrates at once, and one the user hovers jumps ahead on `SelectiveHydrationLane`.

### Streaming

```jsx
export default function Page() {
    return (
        <Layout>
            <Suspense fallback={<CommentsSkeleton />}>
                <Comments />
            </Suspense>
        </Layout>
    );
}
```

The first bytes carry the layout and `CommentsSkeleton`. The comments' HTML arrives later in the same response, and an inline script puts it in place of the skeleton.

```html
<!-- Simplified teaching version of one streamed response. -->
<main>…layout…<div id="slot">Loading comments…</div></main>
<!-- …later, in the same response… -->
<div hidden id="comments">…comments…</div>
<script>/* move #comments into #slot */</script>
```

The user gets a fast first paint, and slow regions fill in. Before 19.2, each streamed boundary revealed the moment it arrived. Batching now groups nearby reveals.

### Selective hydration

Boundaries let React hydrate in pieces, not all at once. A ready boundary does not wait for a slow one. If the user interacts with a region that has not hydrated, React hydrates that region first.

| Interaction with an unhydrated boundary | What React does |
|---|---|
| A click or key press | Hydrates that boundary synchronously, then handles the event |
| A hover or focus | Schedules its hydration on `SelectiveHydrationLane`, ahead of other boundaries |
| Nothing | Hydrates boundaries as their code and data become ready |

Hydration mismatches, which React treats as recoverable errors, and `hydrateRoot` itself belong to the Server Components guide.

### Try it

In a Next.js App Router project, make this the home page.

```jsx
import { Suspense } from "react";

async function Slow() {
    await new Promise((resolve) => setTimeout(resolve, 2000));
    return <p>Slow content</p>;
}

export default function Page() {
    return (
        <Suspense fallback={<p>Loading…</p>}>
            <Slow />
        </Suspense>
    );
}
```

Run the dev server and stream the response in a terminal.

```bash
curl -N http://localhost:3000/
```

The fallback HTML should print at once, and "Slow content" about 2 seconds later, in the same response.

## 14. Debugging Suspense

Something is wrong. A boundary loads forever, a navigation blanks the page, or requests line up one after another. Each symptom points to one mechanism in this guide.

### The short version

Most Suspense bugs fall into a few patterns. A boundary that loads forever usually reads a new promise on every render. Content that vanishes behind a spinner on navigation is missing a transition.

A fallback that lingers for about 300ms is the throttle working. A request waterfall comes from a real dependency or a parent-child fetch. A crash on a failed fetch means no error boundary.

React DevTools can force any boundary into its fallback, so you can test it without slow data. The Performance panel's Suspense track shows fallbacks and reveals.

### Symptoms and causes

| Symptom | Likely cause | Fix |
|---|---|---|
| Loads forever, requests repeat | A new promise on every render (section 3) | Cache the promise by input |
| Content vanishes on navigation or filtering | No transition (section 8) | `startTransition` or `useDeferredValue` |
| The spinner stays about 300ms for fast data | The reveal throttle (section 7) | Nothing, it is intended |
| A fallback flashes over visible content | An urgent update re-suspended it (section 8) | Wrap the update in a transition |
| Requests run one after another | A dependency, a child fetch, or components that are not siblings in one boundary (section 6) | Start independent fetches higher up, and check the boundary structure |
| A failed fetch removes the whole app | No error boundary (section 10) | Pair every boundary with one |
| `SuspenseList` is undefined | Stable React does not export it (section 12) | One shared boundary |
| The page stays on old content forever | Suspended with no boundary (section 2) | Add a `<Suspense>` above |

### Tools

| Tool | What it shows |
|---|---|
| React DevTools Components tab | Suspended components, and a toggle to force a boundary into its fallback |
| Performance panel, Scheduler track | A Suspense subtrack for fallbacks and reveals, and Transition work |
| Network tab | Parallel requests versus a waterfall, and how fast data arrives |
| React DevTools Profiler | Each render, including the retry when a promise resolves |

```js
performance.mark("detail-requested");
const detail = await getDetail(id);
performance.measure("detail data", "detail-requested");
```

A measure like this lines up your data timing with React's Suspense track.

### Try it

Take one Suspense problem in your app and classify it with the symptom table before you change code. Then open `ReactFiberThrow.js` and find this check in `throwException`.

```js
if (value !== null && typeof value === 'object') {
    if (typeof value.then === 'function') {
        // This is a wakeable. The component suspended.
    }
}
```

Follow both branches. One leads to a Suspense boundary, and the other to an error boundary.

## The whole thing in one list

1. A component suspends when it reads a promise that is not ready, and `use` interrupts its render.
2. React catches the suspension and shows the nearest `<Suspense>` above, which it tracks on a stack during render.
3. A promise must stay the same across renders, or every retry suspends again forever.
4. A ping retries a render that never committed, and a retry lane re-renders a boundary showing its fallback.
5. Put the shell outside boundaries and one boundary around each data region, and nest them for a staged reveal.
6. React 19 commits the fallback first, then pre-warms skipped siblings so their fetches run in parallel.
7. Reveals wait until 300ms after the last fallback change, so fast data never flashes and nearby reveals batch.
8. A transition never hides visible content behind a fallback, but new boundaries inside it still show theirs.
9. `useDeferredValue` keeps old results on screen while the new ones load in the background.
10. Pair each boundary with an error boundary, since Suspense handles loading and lets failures pass.
