Type into a search box that filters 5,000 rows, and each keystroke asks React for two things. The letter must appear at once. The list can take a moment, but it must never freeze the input.

```jsx
function Search() {
    const [text, setText] = useState("");
    const [query, setQuery] = useState("");

    function handleChange(event) {
        setText(event.target.value); // the input must update now
        startTransition(() => {
            setQuery(event.target.value); // the 5,000 rows can wait
        });
    }

    return (
        <>
            <input value={text} onChange={handleChange} />
            <SlowList query={query} />
        </>
    );
}
```

Two `setState` calls sit in one handler, yet React treats them very differently. The first commits before the browser's next turn. The second renders in pieces of about 5ms and gives way if you type again. Nothing in the code says "5ms" or "give way".

This guide shows the two mechanisms that supply both. The scheduler cuts work into slices and hands the **main thread** back to the browser. **Lanes** turn "urgent" and "can wait" into bits that React compares in one instruction. By the end you can follow any update from its event to its render.

> Current as of React 19.2 and 19.3. The scheduler and the lane model have been public since React 18, and lanes have been internal since React 17.

## 1. Why React needs a scheduler and lanes

Why can't React just render every update at once? Because "all at once" is exactly what freezes a page.

### The short version

A render that runs to completion holds the browser's one main thread, so the page cannot paint or answer input until it ends. Before concurrent rendering, React rendered every update that way. Concurrent React can work in slices of about 5ms instead, because fibers make a render resumable.

That raises two questions, and React answers them with two mechanisms whose jobs sound alike. The scheduler decides when React works, and it knows only time. Lanes decide which update goes first, and they know only priority. Urgent work such as a click still renders in one go. Only work that can wait, like a transition, is sliced.

### One thread, one long task

Paste this into the console of any page, then try to scroll.

```js
function busy(ms) {
    const end = performance.now() + ms;
    while (performance.now() < end) {}
}

busy(300);
console.log("done");
```

For 300ms the page cannot scroll, paint or answer a click, because one main thread does all of that, one job at a time.

At 60 frames per second the browser has roughly 16ms per frame. A 50ms render means about three frames with no paint and no input, a stutter developers call **jank**. The Performance panel flags any task over 50ms as a long task. That limit still leaves time to answer input within 100ms, where people notice delay.

### What synchronous React did

React renders through a work loop. It does one fiber's work at a time, a **unit of work**. Before concurrent rendering, that loop ran over the whole affected tree and committed in one run.

```js
// Simplified teaching version: a render that cannot stop.
function renderSync(root) {
    let unit = root;
    while (unit !== null) {
        unit = performUnitOfWork(unit);
    }
    commitRoot(root);
}
```

Small updates finish inside a frame. A large one cannot pause for an urgent click or an animation frame. <Mark kind="marker" wraps>It holds the main thread for that whole time</Mark>.

The old stack-based reconciler simply could not stop mid-render. Debouncing and memoization cut how often or how much React rendered, but could not make a necessary large render non-blocking.

### Cooperative scheduling

```js
// Simplified teaching version: the same loop, now able to pause.
function renderConcurrent() {
    while (workInProgress !== null && !shouldYield()) {
        workInProgress = performUnitOfWork(workInProgress);
    }
    if (workInProgress !== null) {
        resumeLater(renderConcurrent); // come back after the browser's turn
    }
}
```

This is **cooperative scheduling**: work until the 5ms slice is used up, yield, then resume. Fibers make it possible, because React builds the work-in-progress tree one fiber at a time and keeps a pointer to where it stopped.

"Cooperative" means neither side can force the other. An operating system can preempt a thread, but nothing preempts JavaScript on the main thread. So React checks the clock and yields by choice, as in classic cooperative multitasking.

The payoff: a big list rendered in a transition goes in 5ms slices, so typing stays smooth. And a render that can stop can also be abandoned when something urgent arrives.

### Two questions: when and which

Several updates can be pending at once: a click, a big transition, a Suspense retry, an idle update. React must do urgent work first and interrupt low-priority renders. It splits this between two mechanisms whose names both sound like "priority and timing", though their jobs differ.

| Question | Mechanism | Knows about | Knows nothing about |
|---|---|---|---|
| When should React work, and when should it pause? | The scheduler | Time, the frame budget, the event loop | What the work is |
| Which pending work goes first? | Lanes | Priority, and which updates are pending where | Time |

The scheduler runs, measures, stops and resumes chunks. Lanes label updates so React can compare and combine them cheaply.

```js
// Simplified teaching version of one update's journey.
const lane = requestUpdateLane(fiber); // section 6: label the update
root.pendingLanes |= lane; // it joins the pending set
queueMicrotask(() => {
    const renderLanes = getNextLanes(root); // section 7: pick the batch
    if (includesSyncLane(renderLanes)) {
        renderSync(root); // urgent: renders now, never sliced (section 8)
    } else {
        scheduleCallback(priorityFor(renderLanes), () => {
            render(root, renderLanes); // sliced only for transition-like lanes (section 5)
        });
    }
});
```

`renderLanes` is the set of lanes one render pass processes. A click's `SyncLane` work never reaches the scheduler, and only transition-like work is sliced.

Lanes govern what renders and whether to interrupt. The scheduler governs when it runs and yields. Concurrent rendering is the two together, since lanes alone would block on a big render and the scheduler alone would not know what is urgent.

<MarginNote note="the question to ask about any scheduling symptom">

When something feels slow or out of order, ask first whether it is about timing or priority. Timing belongs to the scheduler. Which update ran first belongs to lanes.

</MarginNote>

## 2. The scheduler: a min-heap of timed tasks

React hands its render work to the scheduler. What is it, and how does it pick the next task?

### The short version

The scheduler is its own npm package, `scheduler`, a small cooperative task runner that knows nothing about React. A task is a callback plus one of five levels. Their timeouts are -1ms, 250ms, 5s, 10s, and about 12 days for Idle. The scheduler adds the timeout to the current time to get an **expiration time**.

Tasks sit in a **min-heap** ordered by that time, so the soonest-expiring task runs first. As time passes, an old low-priority task becomes the soonest, so it cannot starve. A callback can return a function meaning "not finished". That is how one long render spans many slices.

### Five levels, five timeouts

```js
// How React calls the scheduler package.
import {
    unstable_scheduleCallback as scheduleCallback,
    unstable_NormalPriority as NormalPriority,
} from "scheduler";

scheduleCallback(NormalPriority, () => {
    console.log("ran");
});
```

A scheduler **task** is a callback plus a priority level.

| Level | Timeout | Meant for |
|---|---|---|
| `ImmediatePriority` | -1ms, already expired | The most urgent work. React 19 uses it only as a rare fallback. |
| `UserBlockingPriority` | 250ms | The user is waiting, as with input |
| `NormalPriority` | 5,000ms | Ordinary work |
| `LowPriority` | 10,000ms | Work that can wait |
| `IdlePriority` | 1,073,741,823ms, about 12.4 days | Work for when nothing else is pending. The source says it never times out. |

Immediate does not mean synchronous. Its task is expired from birth, so it tops the heap and skips the yield check. It still waits for the next **macrotask**, a new task on the event loop. React 19 uses it only in edge cases.

The scheduler is <Mark kind="circle">deliberately generic</Mark>, which keeps timing apart from fibers, lanes and reconciliation. It is also why React has two priority systems, which meet in section 8.

### One number for priority and age

```js
// Simplified teaching version of unstable_scheduleCallback.
const TIMEOUT = { Immediate: -1, UserBlocking: 250, Normal: 5000, Low: 10000, Idle: 1073741823 };

let now = 0; // a fake clock, so the example is repeatable
const taskQueue = []; // a min-heap, shown next

function scheduleCallback(priority, callback) {
    const task = { callback, expirationTime: now + TIMEOUT[priority] };
    push(taskQueue, task);
    return task;
}
```

Watch an old Normal task meet a new urgent one.

```js
now = 0;
scheduleCallback("Normal", () => console.log("old normal")); // expires at 5000
now = 4900;
scheduleCallback("UserBlocking", () => console.log("new click")); // expires at 5150
```

The old Normal task now runs first. One number unifies priority and starvation prevention, because a waiting task's deadline only gets nearer.

### The min-heap

```js
// Simplified teaching version of SchedulerMinHeap.js.
function push(heap, task) {
    heap.push(task);
    let i = heap.length - 1;
    while (i > 0) {
        const parent = (i - 1) >> 1;
        if (heap[parent].expirationTime <= task.expirationTime) break;
        [heap[parent], heap[i]] = [heap[i], heap[parent]];
        i = parent;
    }
}

function peek(heap) {
    return heap[0] ?? null;
}

function pop(heap) {
    const top = heap[0];
    const last = heap.pop();
    if (heap.length > 0) {
        heap[0] = last;
        let i = 0;
        while (true) {
            const left = 2 * i + 1;
            const right = left + 1;
            let smallest = i;
            if (left < heap.length && heap[left].expirationTime < heap[smallest].expirationTime) smallest = left;
            if (right < heap.length && heap[right].expirationTime < heap[smallest].expirationTime) smallest = right;
            if (smallest === i) break;
            [heap[smallest], heap[i]] = [heap[i], heap[smallest]];
            i = smallest;
        }
    }
    return top;
}
```

A min-heap gives O(log n) insertion and O(1) access to the most urgent task. The real heap sorts by `sortIndex` and breaks ties by task id, so equal deadlines run in arrival order. A second heap, `timerQueue`, holds delayed tasks until their start time.

### The run loop and continuations

```js
// Simplified teaching version of workLoop in Scheduler.js.
function workLoop(startTime) {
    let task = peek(taskQueue);
    while (task !== null) {
        const expired = task.expirationTime <= now;
        if (!expired && now - startTime >= 5) break; // slice used up: yield
        const continuation = task.callback(expired);
        if (typeof continuation === "function") {
            task.callback = continuation; // not finished: keep the task
            return true; // and yield at once
        }
        pop(taskQueue);
        task = peek(taskQueue);
    }
    return task !== null; // more work means "resume me later"
}
```

A returned function means "not finished, here is the rest", and the scheduler yields at once, whatever time is left. React's render task works this way, at a priority derived from its lanes. When the callback learns its task expired, React finishes without yielding.

### Try it

Paste the blocks above into the console, then run this.

```js

taskQueue.length = 0;
scheduleCallback("Low", () => console.log("low"));
scheduleCallback("UserBlocking", () => console.log("user blocking"));
scheduleCallback("Normal", () => console.log("normal"));

```

```text role="output"
normal

```

## 3. Yielding: MessageChannel and shouldYield

Yielding sounds simple: stop, let the browser run, come back. But what brings React back, and how does it know when to stop?

### The short version

After each slice, the scheduler posts a message to itself on a `MessageChannel`. The browser delivers it as a new task, so pending input, and a paint if a frame is due, can run first. The handler then runs the next slice.

`shouldYieldToHost` ends a slice after 5ms, or right after React asks for a paint. React's render loop calls it between units of work. The alternatives fail. Browsers clamp nested `setTimeout(fn, 0)` calls to about 4ms. A microtask runs before the browser gets any turn. `requestIdleCallback` may not fire for long stretches under load.

### Posting a message to yourself

This console snippet shows the yield-and-resume shape.

```js
const channel = new MessageChannel();
let chunksLeft = 3;

channel.port1.onmessage = () => {
    console.log("run one chunk");
    chunksLeft -= 1;
    if (chunksLeft > 0) channel.port2.postMessage(null);
};

channel.port2.postMessage(null);
```

```text role="output"
run one chunk
run one chunk
run one chunk
```

Posting on one port of a `MessageChannel` fires a `message` event on the other, delivered as a macrotask. Between tasks, the browser can handle input and render.

### Why MessageChannel

Measure how long each kind of "come back" takes.

```js
function measure(label, schedule) {
    let count = 0;
    let last = performance.now();
    const gaps = [];
    function tick() {
        const t = performance.now();
        gaps.push(t - last);
        last = t;
        if (++count < 20) schedule(tick);
        else console.log(label, (gaps.slice(5).reduce((a, b) => a + b) / 15).toFixed(2), "ms");
    }
    schedule(tick);
}

const port = new MessageChannel();
measure("setTimeout", (fn) => setTimeout(fn, 0));
measure("MessageChannel", (fn) => {
    port.port1.onmessage = fn;
    port.port2.postMessage(null);
});
```

On most machines `setTimeout` settles near 4ms per hop, and `MessageChannel` stays well under 1ms. The scheduler's source gives this as its reason, preferring `MessageChannel` "because of the 4ms setTimeout clamping". A microtask is faster still, but it never lets the browser in.

```js
// A "yield" through microtasks freezes the page like busy(500).
let n = 0;
function chunk() {
    busy(5);
    if (++n < 100) queueMicrotask(chunk);
}
chunk();
```

| Option | What goes wrong | Why |
|---|---|---|
| `setTimeout(fn, 0)` | About 4ms of idle waiting per 5ms slice | Browsers clamp nested timers |
| `queueMicrotask` or a promise | The browser never gets a turn | Microtasks drain before the browser renders or reads input |
| `requestIdleCallback` | Work can starve under load | It fires only when the browser judges itself idle |
| `requestAnimationFrame` | Work is tied to frames | It fires right before a paint, about every 16ms |
| `MessageChannel` | Nothing | A new task, promptly, with no clamp |

React did not start here. Early Fiber builds scheduled in the style of `requestIdleCallback`, and later aligned to `requestAnimationFrame`. Around 2019 the scheduler moved to a plain `MessageChannel` loop with a 5ms slice.

A yield does not guarantee a paint. At 60fps a frame is due about every 16ms, so most 5ms yields only give the browser a chance to handle input.

### The loop: performWorkUntilDeadline

```js
// Simplified teaching version of performWorkUntilDeadline in Scheduler.js.
const channel = new MessageChannel();
const port = channel.port2;
let startTime = -1;

channel.port1.onmessage = function performWorkUntilDeadline() {
    startTime = performance.now();
    const hasMoreWork = workLoop(startTime); // run tasks until the slice is used
    if (hasMoreWork) port.postMessage(null); // queue the next slice as a task
};
```

The real code stores no deadline. It compares the time since `startTime` with `frameInterval`, which is 5, and `unstable_forceFrameRate(fps)` can reset it to `Math.floor(1000 / fps)`.

<GuideFigure figure="sc-slices" />

`MessageChannel` is not the first choice everywhere. The host setup takes the first option that exists.

```js
// Simplified teaching version of the host setup in Scheduler.js.
let schedulePerformWorkUntilDeadline;
if (typeof setImmediate === "function") {
    schedulePerformWorkUntilDeadline = () => setImmediate(performWorkUntilDeadline); // Node.js, jsdom, old IE
} else if (typeof MessageChannel !== "undefined") {
    schedulePerformWorkUntilDeadline = () => port.postMessage(null); // browsers and workers
} else {
    schedulePerformWorkUntilDeadline = () => setTimeout(performWorkUntilDeadline, 0); // accepts the clamp
}
```

`setImmediate` wins where it exists because it runs earlier, and because an open `MessageChannel` would keep Node.js alive.

### shouldYield: the link to the render loop

```js
// Simplified teaching version of shouldYieldToHost in Scheduler.js.
let needsPaint = false;
const frameInterval = 5;

function shouldYieldToHost() {
    if (needsPaint) return true; // React asked for a paint
    return performance.now() - startTime >= frameInterval;
}
```

React imports it as `shouldYield` and calls it between units of work.

```js
// React's render loop in ReactFiberWorkLoop.js, React 19.2.
function workLoopConcurrentByScheduler() {
    while (workInProgress !== null && !shouldYield()) {
        performUnitOfWork(workInProgress);
    }
}
```

This is how an interruptible render actually interrupts. React sets `needsPaint` through `requestPaint()` after a commit, so the new UI shows soon. The scheduler dropped its old pending-input check in 2023, and React 19 never calls `isInputPending`.

A separate `workLoopConcurrent` yields every 25ms for transitions, but only behind the `enableThrottledScheduling` flag, off in open source builds. In a trace, stable React's loop chops the main thread into roughly 5ms pieces.

### Try it

Render about 3,000 moderately expensive items, update them inside `startTransition`, and record with 4x CPU throttling. You should see slices of about 5ms with gaps. Make the same update from a click without `startTransition`, and you should see one long task, because a click's update is never time-sliced.

## 4. Lanes: priorities as bits

React must also rank updates: a click, a transition, a retry. How does it label them so it can compare labels fast?

### The short version

A lane is one bit in a 31-bit integer, and each bit position stands for one priority or kind of work. An update gets one lane. A set of lanes, typed `Lanes`, can have many bits set. Bits make every question one instruction: `&` tests membership, `|` adds, `& ~` removes, and `lanes & -lanes` finds the most urgent lane.

Each fiber stores `childLanes`, the union of lanes pending below it. One AND per fiber tells React whether it can skip a whole subtree. A single priority number cannot do that. Lanes replaced such a number, the expiration time, in React 17.

### Bits as a set

Run this in the console. The values are the real ones from React 19.

```js
const SyncLane = 0b0000000010;
const DefaultLane = 0b0000100000;
const TransitionLane1 = 0b0100000000;

let pendingLanes = 0;
pendingLanes |= TransitionLane1; // a transition is waiting
pendingLanes |= SyncLane; // then a click arrives

const show = (n) => n.toString(2).padStart(10, "0");
console.log(show(pendingLanes)); // union
console.log((pendingLanes & SyncLane) !== 0); // membership
console.log(show(pendingLanes & -pendingLanes)); // most urgent lane
console.log(show(pendingLanes & ~SyncLane)); // remove the click
```

```text role="output"
0100000010
true
0000000010
0100000000
```

Why bits and not a priority number from 1 to 31? React performs set operations on priorities constantly, and each bitwise operator does one in a single instruction.

```js
// Simplified teaching versions of helpers in ReactFiberLane.js.
const includesSomeLane = (a, b) => (a & b) !== 0; // is this update in the batch?
const mergeLanes = (a, b) => a | b; // add to the pending set
const removeLanes = (set, subset) => set & ~subset; // mark lanes as handled
const isSubsetOfLanes = (set, subset) => (set & subset) === subset;
const getHighestPriorityLane = (lanes) => lanes & -lanes;
```

The real helpers are almost exactly these one-liners, and they run on the hot path of every render.

### Why lanes & -lanes finds the most urgent lane

```text
           lanes   0100000010
          ~lanes   1011111101
-lanes = ~lanes+1  1011111110
  lanes & -lanes   0000000010
```

In two's complement, `-x` equals `~x + 1`, which keeps the lowest 1 and flips every bit above it. The AND keeps only that bit, and because urgent lanes sit on low bits, it is the most urgent lane.

### Why 31 lanes

JavaScript bitwise operators work on signed 32-bit integers.

```js
console.log(1 << 30); // 1073741824
console.log(1 << 31); // -2147483648, the sign bit
```

The source sets `TotalLanes = 31` without saying why. The likely reason is that its code compares lanes with `>` and loops `while (lanes > 0)`, which break on negative values. V8's fast 31-bit small integers are another common explanation. The React 18 Working Group put it simply: 31 levels, because that is how many fit in one bitmask.

### childLanes: skipping whole subtrees

Every fiber carries `lanes`, for its own updates, and `childLanes`, the union of lanes pending below it. Scheduling an update ORs its lane into each ancestor's `childLanes`.

```js
// Simplified teaching version of the bailout check in beginWork.
function canSkipSubtree(fiber, renderLanes) {
    return (fiber.lanes & renderLanes) === 0 && (fiber.childLanes & renderLanes) === 0;
}
```

When nothing below matches `renderLanes`, React skips the whole subtree, a bailout. The check runs at every fiber, so it must be one cheap instruction.

<MarginNote note="why bits beat a single number">

A single priority number cannot say "this subtree has work at priorities 3, 7 and 12" in a form you can AND against. A bitmask can, because each priority keeps its own bit.

</MarginNote>

### Before lanes: one expiration number

```js
// The old model, simplified: one number per update.
update.expirationTime = currentTime + timeoutForPriority;
// No cheap way to ask: "is there transition work AND retry work below this fiber?"
```

In React 16's experimental concurrent work, an update's priority was its expiration time: the longer it waited, the higher its priority. That handled one linear notion of priority. It could not keep an urgent update, an in-progress transition and a Suspense retry in separate streams that do not block each other.

Andrew Clark's "Initial Lanes implementation" landed in May 2020 and shipped inside React 17.0. React 18 made the features built on lanes public. Lanes kept expiration only as a safety net (section 9).

Predict each line, then run it.

## 5. The React 19 lane layout

Which bit means what? React 19 assigns all 31 bits, and their order is the priority order.

### The short version

Lane constants live in `ReactFiberLane.js`, and a lower bit means a higher priority. React 19 puts `SyncHydrationLane` on bit 0 and `SyncLane` on bit 1. Input-continuous, default and gesture lanes follow, then 14 transition lanes, 4 retry lanes, idle and offscreen lanes, and `DeferredLane` on bit 30.

Ranges let React track several transitions or retries separately. Two facts from this layout drive the rest of the guide. Sync, InputContinuous and Default renders are blocking and never time-sliced. Transition, retry, idle and offscreen renders are time-sliced, and a more urgent lane can interrupt them.

### The layout

An Action is a transition whose callback is `async`. Hydration is React attaching its handlers to HTML the server already rendered. Hydration twins sit one bit below their lane and serve hydration at that priority.

`flushSync(fn)` runs `fn` and renders its updates synchronously before it returns.

| Lane | Bit | What uses it | Blocking or sliced | Expiry (section 9) |
|---|---|---|---|---|
| `SyncHydrationLane`, `SyncLane` | 0, 1 | Clicks, key presses, `flushSync` | Blocking, in a microtask (section 8) | 250ms |
| `InputContinuousHydrationLane`, `InputContinuousLane` | 2, 3 | `mousemove`, `scroll`, drag | Blocking | 250ms |
| `DefaultHydrationLane`, `DefaultLane` | 4, 5 | Timers, network responses | Blocking | 5s |
| `GestureLane` | 6 | Experimental gesture transitions | Blocking | 250ms |
| `TransitionHydrationLane` | 7 | Hydration in a transition | Sliced | 5s |
| 10 transition update lanes | 8 to 17 | `startTransition`, Actions | Sliced | 5s |
| 4 transition deferred lanes | 18 to 21 | `useDeferredValue` | Sliced | 5s |
| 4 retry lanes | 22 to 25 | Suspense retries | Sliced | Never |
| `SelectiveHydrationLane` | 26 | Hydrating a boundary the user hovers or focuses | Sliced | Never |
| `IdleHydrationLane`, `IdleLane` | 27, 28 | Work for when nothing else is pending | Sliced | Never |
| `OffscreenLane` | 29 | Hidden `<Activity>`, prerendering | Sliced | Never |
| `DeferredLane` | 30 | A marker, never rendered alone | n/a | Never |

`NoLane` is `0`, the "no work" sentinel. `<Activity mode="hidden">` keeps a subtree mounted but hidden, and React prerenders it at `OffscreenLane`. The layout and the `lanes & -lanes` trick were designed together, so the most urgent lane is always the lowest set bit. You never assign lanes yourself, but the layout shows how urgently React treats your work.

React 18 put `SyncLane` on bit 0 and `OffscreenLane` on top. It already had the InputContinuous, Default, transition, selective hydration and idle hydration lanes. React 19 added `SyncHydrationLane`, `GestureLane` and `DeferredLane`, and cut transition lanes from 16 to 14 and retry lanes from 5 to 4.

### Ranges, and where 19.2 and 19.3 differ

```js
// Simplified teaching version of claimNextTransitionUpdateLane.
const TransitionLane1 = 1 << 8;
const TransitionUpdateLanes = 0b1111111111 << 8; // bits 8 to 17
let nextTransitionUpdateLane = TransitionLane1;

function claimNextTransitionUpdateLane() {
    const lane = nextTransitionUpdateLane;
    nextTransitionUpdateLane <<= 1;
    if ((nextTransitionUpdateLane & TransitionUpdateLanes) === 0) {
        nextTransitionUpdateLane = TransitionLane1; // wrap around after 10
    }
    return lane;
}
```

A range lets React track several transitions or retries independently. React 19.2 still renders all pending transition update lanes together, but can suspend, ping and entangle each one. React 19.3 turns on `enableParallelTransitions` and picks only the most urgent transition lane, so one slow transition no longer holds back another.

### Blocking lanes and time-sliced lanes

The "Blocking or sliced" column comes from one line in `performWorkOnRoot`.

```js
// From performWorkOnRoot in ReactFiberWorkLoop.js, React 19.2 (simplified).
const shouldTimeSlice = !forceSync && !includesBlockingLane(lanes) && !includesExpiredLane(root, lanes);

const exitStatus = shouldTimeSlice
    ? renderRootConcurrent(root, lanes) // yields about every 5ms
    : renderRootSync(root, lanes); // runs to the end
```

So a `setState` in a `setTimeout` gets `DefaultLane` and renders in one blocking pass, not in slices. An expired lane also turns slicing off, as does `forceSync`, set when the scheduler reports that the render task timed out.

## 6. Giving an update its lane

You call `setState`, and nothing on the call says how urgent it is. So where does the lane come from?

### The short version

`setState` does not render. It creates an update, queues it on the fiber, and asks React to schedule the root. `requestUpdateLane` in `ReactFiberWorkLoop.js` picks the lane from the context the call runs in. Inside a transition, the update gets a transition lane.

Otherwise React reads the update priority the event system set while dispatching. A click gives `SyncLane`, and a `mousemove` gives `InputContinuousLane`. With no React event, React checks `window.event`. Only when that is empty, as in a timer or a promise callback, does the update get `DefaultLane`. So one `setState` can land in different lanes.

### The three checks

React picks the lane at the moment `setState` or `dispatch` creates the update.

```js
// Simplified teaching version of requestUpdateLane (ReactFiberWorkLoop.js)
// and resolveUpdatePriority (ReactDOMUpdatePriority.js).
function requestUpdateLane(fiber) {
    if (isRendering && workInProgressRootRenderLanes !== NoLanes) {
        return pickArbitraryLane(workInProgressRootRenderLanes); // a render-phase update
    }
    if (currentTransition !== null) {
        return requestTransitionLane(); // 1. inside a transition
    }
    return resolveUpdatePriority(); // 2 and 3: the event, or the default
}

function resolveUpdatePriority() {
    if (currentUpdatePriority !== NoLane) return currentUpdatePriority; // set by React's dispatcher
    const event = window.event;
    if (event === undefined) return DefaultLane; // timer, promise, network response
    return getEventPriority(event.type); // a native listener
}
```

In React 19 an event priority is a lane value. The `window.event` fallback covers code outside React's dispatcher.

```js
// Neither callback runs inside a React event handler.
button.addEventListener("click", () => setCount((c) => c + 1)); // window.event is a click: SyncLane
setTimeout(() => setCount((c) => c + 1), 0); // window.event is undefined: DefaultLane
```

| Where `setState` runs | What React finds | Lane |
|---|---|---|
| Inside `startTransition`, `useTransition` or an Action | A current transition | A transition lane |
| A React `onClick` or `onKeyDown` handler | Discrete update priority | `SyncLane` |
| A React `onMouseMove` or `onScroll` handler | Continuous update priority | `InputContinuousLane` |
| A native `addEventListener` click handler | `window.event` is a click | `SyncLane` |
| `setTimeout`, a promise callback, a network response | Nothing at all | `DefaultLane` |
| During render | A render-phase update | A lane from the current render |
| A legacy `ReactDOM.render` root, React 18 and earlier | Legacy mode, removed in React 19 | Always `SyncLane` |

The order is fixed: transition first, then the event, then the default.

<MarginNote note="the same setState can land in different lanes">

The lane belongs to the moment, not to the state. One setter called from a click, a transition and a timer gets three different lanes.

</MarginNote>

### From a click to a lane

Why is `setState` in `onClick` urgent?

```js
// Simplified teaching version of React's discrete event dispatch.
function dispatchDiscreteEvent(nativeEvent) {
    const previous = currentUpdatePriority;
    currentUpdatePriority = DiscreteEventPriority; // equal to SyncLane in React 19
    try {
        dispatchEvent(nativeEvent); // runs your onClick
    } finally {
        currentUpdatePriority = previous;
    }
}
```

Inside your handler, `requestUpdateLane` reads that discrete priority and assigns `SyncLane`. The event guide sets the priority, and this is where it becomes a lane. `startTransition` works the same way.

```js
// Simplified teaching version of startTransition.
function startTransition(callback) {
    const previous = currentTransition;
    currentTransition = {};
    try {
        callback(); // every setState in here hits check 1
    } finally {
        currentTransition = previous;
    }
}
```

So "mark this update as non-urgent" means "assign a transition lane". Every transition inside one event shares a lane, so distinct lanes come only across events. Updates made while an async Action is pending reuse its lane. Suspense retries skip this path and use `requestRetryLane`.

In the opening search box, the input update gets `SyncLane` and the results a transition lane, so React renders the input first.

### After the lane: ensureRootIsScheduled

The lane travels with the update. It decides the update's batch, whether its render can be interrupted, and whether it is time-sliced.

1. The event fires, and React's dispatcher sets the priority.
2. Your handler calls `setState`, and `requestUpdateLane` assigns a lane.
3. React queues the update and adds the lane to `fiber.lanes`, each ancestor's `childLanes`, and `root.pendingLanes`.
4. `ensureRootIsScheduled`, in `ReactFiberRootScheduler.js`, queues a microtask.
5. That microtask picks lanes and runs or schedules the render, as section 8 shows.

In short, <Mark kind="underline" wraps>events assign priority, lanes carry it, the scheduler runs it</Mark>.

## 7. Choosing the batch with getNextLanes

Several lanes can be pending at once. Which go into the next render, and what happens when a more urgent one arrives mid-render?

### The short version

Each root keeps `pendingLanes`, the union of lanes with unrendered work. Before a render, `getNextLanes` picks the most urgent group. In React 19.2, pending Sync, InputContinuous and Default lanes come out together, as do all transition update lanes. Idle work waits for everything else.

A lane is suspended when its render threw a promise for data that is not ready. React skips it until a ping, the signal that the data arrived. The chosen set is `renderLanes`, and other lanes stay pending. If a strictly more urgent lane arrives mid-render, React throws the half-built tree away and starts the urgent one.

### A toy getNextLanes

```js
// Simplified teaching version of getNextLanes and getHighestPriorityLanes (ReactFiberLane.js, React 19.2).
const SyncLane = 0b10;
const InputContinuousLane = 0b1000;
const DefaultLane = 0b100000;
const SyncUpdateLanes = SyncLane | InputContinuousLane | DefaultLane; // 42
const TransitionUpdateLanes = 0b1111111111 << 8; // bits 8 to 17
const TransitionLanes = 0b11111111111111 << 8; // bits 8 to 21
const NonIdleLanes = (1 << 27) - 1;

function getHighestPriorityLanes(lanes) {
    const urgent = lanes & SyncUpdateLanes;
    if (urgent !== 0) return urgent; // the urgent group, together
    const lowest = lanes & -lanes;
    if (lowest & TransitionUpdateLanes) return lanes & TransitionUpdateLanes; // 19.2: all transitions
    return lowest; // simplified: one lane otherwise
}

function getNextLanes(root, wipLanes) {
    const pending = root.pendingLanes;
    if (pending === 0) return 0;
    const nonIdle = pending & NonIdleLanes;
    const pool = nonIdle !== 0 ? nonIdle : pending; // idle waits for everything else
    const candidates = pool & ~root.suspendedLanes || pool & root.pingedLanes;
    if (candidates === 0) return 0;
    const next = getHighestPriorityLanes(candidates);
    if (wipLanes !== 0 && wipLanes !== next) {
        const nextLane = next & -next;
        const wipLane = wipLanes & -wipLanes;
        const defaultOverTransition = nextLane === DefaultLane && (wipLane & TransitionLanes) !== 0;
        if (nextLane >= wipLane || defaultOverTransition) return wipLanes; // keep going
    }
    return next;
}
```

Try it with a default update and a transition both pending.

```js

```


React renders `DefaultLane` now and leaves the transition for later. Urgent work jumps ahead every time React chooses.

### pendingLanes and renderLanes

The real signature is `getNextLanes(root, wipLanes, rootHasPendingCommit)`, and it has a few rules the toy skips.

- Suspended lanes are skipped until a ping marks them as pinged, meaning their data is ready.
- When every candidate is suspended, React may pick lanes it has not prerendered yet, to warm their data.
- Idle work waits until all other work is done, even suspended work.

An update is included if and only if its lane is in `renderLanes`, and the `childLanes` check compares against the same set. Other updates stay in `pendingLanes`, like the transition update in section 6.

React 17's first lanes code also added expired and entangled lanes here. In React 19.2, expiration switches time slicing off (section 9), and entangled lanes join when the render starts (section 10).

### Interruption

Yielding through `shouldYield` is what lets the click run at all, and `getNextLanes` decides to switch. A `DefaultLane` update never interrupts a transition. A source comment explains why: continuous input should interrupt transitions, but default updates should not.

## 8. Where lanes meet the scheduler

Lanes have chosen a batch. How do 31 lanes become one of five scheduler levels, and why does a click skip the scheduler entirely?

### The short version

`ensureRootIsScheduled` in `ReactFiberRootScheduler.js` adds the root to a list and queues one microtask. There, `scheduleTaskForRootDuringMicrotask` marks starved lanes, those waiting past their deadline (section 9), calls `getNextLanes` and decides how to run the batch. A batch with `SyncLane` gets no scheduler task. React renders it at the end of the microtask, before the browser's next turn.

Any other batch is reduced to an event priority, mapped to a scheduler level, and passed to `scheduleCallback`. Discrete and continuous map to UserBlocking, default and transitions to Normal, idle to Idle. Two systems exist because the scheduler is generic and five levels are too coarse for rendering.

### Two layers, two priority systems

The generic scheduler has five levels for any work. The reconciler's 31 lanes are built for rendering, transitions, retries and set operations. Lanes would cost the scheduler its generality, and five levels are too coarse for the reconciler.

So the systems are not redundant. `UserBlockingPriority` and `InputContinuousLane` express one idea, urgent continuous input, in two vocabularies.

### The microtask step

```js
// Simplified teaching version of ReactFiberRootScheduler.js, React 19.
function ensureRootIsScheduled(root) {
    addToScheduledRoots(root);
    if (!didScheduleMicrotask) {
        didScheduleMicrotask = true;
        queueMicrotask(processRootScheduleInMicrotask);
    }
}

function processRootScheduleInMicrotask() {
    didScheduleMicrotask = false;
    const now = performance.now();
    for (const root of scheduledRoots) {
        scheduleTaskForRootDuringMicrotask(root, now);
    }
    flushSyncWorkAcrossRoots(); // renders any SyncLane work right here
}
```

In React 19, scheduling a root creates no scheduler task right away, and ten `setState` calls in one handler still queue one microtask. The decision happens inside it.

```js
// Simplified teaching version of scheduleTaskForRootDuringMicrotask.
function scheduleTaskForRootDuringMicrotask(root, now) {
    markStarvedLanesAsExpired(root, now); // section 9
    const nextLanes = getNextLanes(root, wipLanesFor(root));
    if (nextLanes === NoLanes) return;
    if (includesSyncLane(nextLanes)) return; // flushed at the end of the microtask
    const priority = toSchedulerPriority(lanesToEventPriority(nextLanes));
    root.callbackNode = scheduleCallback(priority, performWorkOnRootViaSchedulerTask.bind(null, root));
}
```

`flushSync` also renders `SyncLane` work, at once.

### The translation

```js
// Simplified teaching version of lanesToEventPriority (ReactEventPriorities.js).
function lanesToEventPriority(lanes) {
    const lane = lanes & -lanes;
    if (lane <= DiscreteEventPriority) return DiscreteEventPriority; // SyncLane and its twin
    if (lane <= ContinuousEventPriority) return ContinuousEventPriority;
    if (lane & NonIdleLanes) return DefaultEventPriority; // Default, transitions, retries, selective hydration
    return IdleEventPriority;
}
```

`lanesToEventPriority`, in `ReactEventPriorities.js`, reduces the batch to the event system's tiers. In React 19 those tiers are lane values: Discrete is `SyncLane`, Continuous is `InputContinuousLane`, Default is `DefaultLane`, Idle is `IdleLane`, and `NoEventPriority` means none. React then maps the tier to a scheduler level.

<MarginNote note="the one place the two systems touch">

This table is the whole bridge. The scheduler never sees a lane. React hands it one of five levels, and only for work that is not sync.

</MarginNote>

| Lanes in the batch | Event priority | Scheduler level | How the render runs |
|---|---|---|---|
| `SyncLane` | Discrete | None, the scheduler is skipped | End of the microtask, blocking |
| `InputContinuousLane` | Continuous | `UserBlockingPriority` | Scheduler task, blocking |
| `DefaultLane` | Default | `NormalPriority` | Scheduler task, blocking |
| Transition, retry and selective hydration lanes | Default | `NormalPriority` | Scheduler task, time-sliced |
| Idle hydration, `IdleLane`, `OffscreenLane` | Idle | `IdlePriority` | Scheduler task, time-sliced |

React 18 mapped discrete priority to `ImmediatePriority`. React 19 maps discrete and continuous to `UserBlockingPriority`, because sync work now uses microtasks. In both versions, `SyncLane` work never really reached this table.

### The scheduler task

```js
// Simplified teaching version of performWorkOnRootViaSchedulerTask.
function performWorkOnRootViaSchedulerTask(root, didTimeout) {
    const originalTask = root.callbackNode;
    const lanes = getNextLanes(root, wipLanesFor(root));
    if (lanes === NoLanes) return null;
    performWorkOnRoot(root, lanes, didTimeout); // didTimeout forces a sync render
    scheduleTaskForRootDuringMicrotask(root, performance.now());
    return root.callbackNode === originalTask
        ? performWorkOnRootViaSchedulerTask.bind(null, root) // a continuation: more slices
        : null;
}
```

React 18 called this callback `performConcurrentWorkOnRoot`. `performWorkOnRoot` picks a blocking or sliced render, which checks `renderLanes` at each fiber and, when sliced, `shouldYield` after each unit.

## 9. Expiration: no lane waits forever

"Highest priority first" sounds fair until urgent work never stops. What keeps a transition from waiting forever while the user types?

### The short version

Pure priority order can starve low-priority work. If urgent updates keep arriving, a transition keeps getting interrupted and restarted. So each pending lane gets a deadline: 250ms for Sync, InputContinuous and Gesture lanes, and 5 seconds for Default and transitions. Retry, idle and offscreen lanes never expire.

On each scheduling pass, `markStarvedLanesAsExpired` moves lanes past their deadline into `expiredLanes`. In React 19 an expired lane does not jump the queue. The next render that includes it turns time slicing off. Input cannot interrupt it, so the stale work commits, at the cost of one brief stall.

### How starvation happens

Picture continuous typing while a transition renders the results.

```text
t = 0ms     the transition render starts: 250ms of work, in 5ms slices
t = 100ms   a keystroke gets SyncLane, and the transition restarts
t = 200ms   another keystroke, another restart
t = 300ms   and again: the transition never reaches its end
```

The user sees every keystroke, but the list never updates.

### A toy markStarvedLanesAsExpired

Each lane gets an expiration time, a real-time deadline, when it first becomes pending.

```js
// Simplified teaching version of markStarvedLanesAsExpired and computeExpirationTime (ReactFiberLane.js).
const NoTimestamp = -1;
const SyncLane = 0b10, InputContinuousLane = 0b1000, DefaultLane = 0b100000, GestureLane = 0b1000000;
const TransitionLanes = 0b11111111111111 << 8; // bits 8 to 21
const RetryLanes = 0b1111 << 22; // bits 22 to 25

function computeExpirationTime(lane, now) {
    if (lane & (SyncLane | InputContinuousLane | GestureLane)) return now + 250;
    if (lane & (DefaultLane | TransitionLanes)) return now + 5000;
    return NoTimestamp; // retry, idle, offscreen: never expire
}

function markStarvedLanesAsExpired(root, now) {
    let lanes = root.pendingLanes & ~RetryLanes;
    while (lanes > 0) {
        const index = 31 - Math.clz32(lanes);
        const lane = 1 << index;
        const expirationTime = root.expirationTimes[index];
        if (expirationTime === NoTimestamp) {
            if ((lane & root.suspendedLanes) === 0 || (lane & root.pingedLanes) !== 0) {
                root.expirationTimes[index] = computeExpirationTime(lane, now); // start the clock
            }
        } else if (expirationTime <= now) {
            root.expiredLanes |= lane; // waited too long
        }
        lanes &= ~lane;
    }
}
```

Default and every transition lane share 5 seconds, so the windows follow priority only roughly. Retry lanes never expire, because the source says they must always be time-sliced. Deadlines live in `root.expirationTimes`, one slot per lane.

The clock starts lazily. The check runs on every scheduling pass, before React chooses lanes, or as its source comment puts it, every time React yields.

```js
const T1 = 1 << 8;
const root = { pendingLanes: T1, suspendedLanes: 0, pingedLanes: 0, expiredLanes: 0, expirationTimes: new Array(31).fill(NoTimestamp) };

markStarvedLanesAsExpired(root, 0); // the clock starts: T1 expires at 5000
markStarvedLanesAsExpired(root, 4999);
console.log(root.expiredLanes === T1); // false
markStarvedLanesAsExpired(root, 5000);
console.log(root.expiredLanes === T1); // true
```

### What "expired" changes

`getNextLanes` in React 19.2 never reads `expiredLanes`, so an expired lane does not move ahead of more urgent ones. It acts through the switch from section 5.

```js
// The expired check inside performWorkOnRoot, React 19.2.
const shouldTimeSlice =
    (!forceSync && !includesBlockingLane(lanes) && !includesExpiredLane(root, lanes)) ||
    checkIfRootIsPrerendering(root, lanes); // prerendering suspended content is always sliced
```

A render with an expired lane runs to completion, so no keystroke can interrupt it. Low-priority work is <Mark kind="marker" wraps>deferred, but only up to a deadline</Mark>, and that bounds the delay any update can see.

This is the scheduler's expiration ordering from section 2, applied to lanes: priority sets the initial urgency, and elapsed time sets a deadline. Both layers face the same starvation risk. When the render task itself has expired, the scheduler passes `didTimeout`, and React renders synchronously.

Before lanes, expiration was the whole priority mechanism. Now it is the safety net: the bitmask decides the normal order, and expiration puts a deadline on it.

<GuideFigure figure="sc-starvation" />

Expiration rarely fires, because normal deferral resolves well inside 5 seconds. When it does, a long-deferred transition suddenly renders synchronously with a brief jank, trading a moment of responsiveness for guaranteed completion.

## 10. Entanglement: lanes that render together

Splitting work by priority makes React responsive. But some updates must not be split. What stops React from showing half of a change?

### The short version

Lanes let React render related updates in separate passes. If two updates that belong together land in different passes, the screen can show one without the other, a form of tearing. Entangling lanes says "if one renders, render the others too".

The root keeps an `entangledLanes` set and a per-lane `entanglements` array. When a render starts, `getEntangledLanes` adds every lane entangled with the chosen ones. React 19 entangles transition updates on the same hook queue and the lane `useDeferredValue` spawns. The source calls this "best effort". React will not throw away a render in progress just to honor a new entanglement.

### What goes wrong without it

The rendering guide defines **tearing**: one visible UI showing two versions of state, because different parts rendered against different values. If two updates that must apply together land in different batches, the user sees such an in-between state.

### A toy entanglement model

```js
// Simplified teaching version of markRootEntangled and getEntangledLanes (ReactFiberLane.js).
function markRootEntangled(root, entangledLanes) {
    root.entangledLanes |= entangledLanes;
    let lanes = entangledLanes;
    while (lanes) {
        const index = 31 - Math.clz32(lanes);
        root.entanglements[index] |= entangledLanes; // each lane remembers its partners
        lanes &= ~(1 << index);
    }
}

function getEntangledLanes(root, renderLanes) {
    let result = renderLanes;
    let lanes = root.entangledLanes & renderLanes;
    while (lanes > 0) {
        const index = 31 - Math.clz32(lanes);
        result |= root.entanglements[index]; // bring the partners along
        lanes &= ~(1 << index);
    }
    return result;
}
```

React calls `getEntangledLanes` from `prepareFreshStack`, which starts a fresh render. Its result, `entangledRenderLanes`, is what the render processes.

```js
const A = 1 << 8;
const B = 1 << 9;
const root = { entangledLanes: 0, entanglements: new Array(31).fill(0) };

markRootEntangled(root, A | B);
console.log(getEntangledLanes(root, A) === (A | B)); // true: B comes along
```

<GuideFigure figure="sc-entangle" />

The figure's two transitions split into separate passes. In 19.2 that happens only when one of them is suspended, but 19.3's parallel transitions make it common.

### Where React 19 entangles

| Case | Where | Why |
|---|---|---|
| Transition updates on the same hook or class queue | `entangleTransitionUpdate` | They share a source, and only the latest event matters |
| The lane `useDeferredValue` spawns | `markSpawnedDeferredLane` | The deferred render stays paired with its cause |
| Updates inside one async Action | A shared lane from `requestTransitionLane` | The Action's updates commit together |

### Best effort

React applies entanglements after it checks for partial work. So it will not throw away a render in progress to honor an entanglement that arrived mid-render. Entangled lanes usually render together, but not always.

That is the trade-off. Lanes <Mark kind="marker" wraps>split for responsiveness, entangle where splitting would break consistency</Mark>, and give up a little flexibility for it. Bits express independent priorities, and entanglement expresses required togetherness, a consistency constraint. You will rarely touch this most internal mechanism.

### Try it

Extend the toy with a third lane, entangled with `B` only.

```js

markRootEntangled(root, B | C);
console.log(getEntangledLanes(root, A).toString(2));
```

Predict the output first. The toy brings in `B` but not `C`, which is entangled with `B`, not `A`. The real `markRootEntangled` widens partner sets as entanglements chain, so React would bring in `C`. Change the toy so it does.

## 11. Lanes in disguise: the concurrent features

You never touch a lane. You use batching, `startTransition`, `useDeferredValue` and Suspense. How do they map onto the machinery?

### The short version

The concurrent features are friendly handles on lanes. Batching happens because updates from one context share a lane and React renders later, in a microtask or task. A transition is an update on a transition lane: below the click, sliced into 5ms pieces, and interruptible. `isPending` is a separate urgent update that renders first.

`useDeferredValue` spawns a second render on a deferred transition lane. A Suspense retry renders on a retry lane once the data resolves. Every handle feeds the same rules: pick the top group, block or slice, expire, entangle. That shared core is why the features compose well.

### Batching

```jsx
setTimeout(() => {
    setCount((c) => c + 1);
    setFlag((f) => !f);
    setName("Ada");
}, 0);
// createRoot (React 18 and later): one render. Legacy roots: three.
```

The concurrent features you use are <Mark kind="circle">lanes in disguise</Mark>. All three updates get `DefaultLane`, one bit in `pendingLanes`, so they render in one pass. The shared lane is only half of React 18's change. Legacy roots rendered such updates at once on `SyncLane`, while `createRoot` waits for its microtask or task, so updates pile up first.

In React 19, separate batches mostly mean urgent versus transition, since Sync, InputContinuous and Default render as one group. Updates split across ticks also render separately. [The hooks guide](/articles/react-hooks-and-effects-internals) covers batching in full.

```jsx
async function save() {
    setStatus("saving"); // renders in this event's microtask
    await api.save();
    setStatus("saved"); // a later tick, so a later render
    setDirty(false); // batched with "saved"
}
```

### Transitions and isPending

A transition lane ranks below the click that started it and is not blocking. So it renders second, in slices, and an urgent update can preempt it. `isPending` is not read from the lanes. It is its own optimistic state.

```js
// Simplified teaching version of startTransition inside useTransition (ReactFiberHooks.js).
function startTransitionFromHook(setPending, callback) {
    runWithPriorityAtLeast(ContinuousEventPriority, () => {
        setPending(true); // optimistic and urgent: the spinner shows first
    });
    const previous = currentTransition;
    currentTransition = {};
    callback(); // your updates get a transition lane
    currentTransition = previous;
    // isPending reverts to false when the transition commits
}
```

### useDeferredValue

The input that drives a deferred value still updates at once. The render with the new value then runs on a deferred lane, which is time-sliced and interruptible, the same machinery as a transition.

```js
// Simplified teaching version of useDeferredValue on update (ReactFiberHooks.js).
function updateDeferredValue(value, previousValue) {
    if (includesOnlyNonUrgentLanes(renderLanes)) {
        return value; // already a background render: use the new value
    }
    requestDeferredLane(); // spawn a later render on a deferred lane
    return previousValue; // this urgent render keeps the old value
}
```

The spawned render uses a `TransitionDeferredLanes` lane, or `OffscreenLane` while prerendering. All `useDeferredValue` hooks in one render share a lane, and the `DeferredLane` marker stops a waterfall, so only the first level of nesting defers. The hooks guide covers the API.

### Suspense: pings and retries

React has two paths back from a suspended render, and [the Suspense guide](/articles/react-suspense-internals) covers the rest. If the render suspended without committing, as in a transition that keeps the old screen, a ping marks the original lane as pinged.

```js
// Simplified teaching version of pingSuspendedRoot (ReactFiberWorkLoop.js).
thenable.then(() => {
    root.pingedLanes |= root.suspendedLanes & suspendedLane; // the same lane, now marked ready
    ensureRootIsScheduled(root);
});
```

If the boundary already committed its fallback, a retry listener gets a new lane instead.

```js
// Simplified teaching version of resolveRetryWakeable and retryTimedOutBoundary (ReactFiberWorkLoop.js).
thenable.then(() => {
    const retryLane = requestRetryLane(boundaryFiber); // claims one of 4 retry lanes, cycled
    markRootUpdated(root, retryLane); // root.pendingLanes |= retryLane
    ensureRootIsScheduled(root);
});
```

Retry lanes are time-sliced, never expire, and govern how the content is revealed. So "show a fallback, then reveal" means suspend, get a retry lane when the data resolves, and render that lane.

Click this button once and read the console.

```jsx

    const [value, setValue] = useState(0);
```

## 12. Debugging and observing scheduling

When an interaction feels wrong, how do you tell which mechanism is involved, and which tool shows it?

### The short version

Start in the Performance panel, because scheduling is about the main thread. A long unbroken task over 50ms during an interaction is a blocking render: Sync, InputContinuous or Default lanes, or an expired lane. Work cut into 5ms pieces means time slicing is working.

React 19.2 adds Performance Tracks to Chrome. The Scheduler ⚛ track shows each render's priority on Blocking, Transition, Suspense and Idle subtracks. The Components ⚛ track shows which components rendered and for how long. The React DevTools Profiler adds why each one rendered. Most symptoms map to one mechanism in this guide.

### Reading a trace

Record an interaction with 4x CPU throttling, so hidden problems show up.

| Pattern in the trace | What it means | What to check |
|---|---|---|
| One unbroken task over about 50ms | A render that did not yield | During an interaction, this work usually belongs in a transition |
| Work cut into roughly 5ms pieces | Time slicing works | Nothing. The gaps are where the browser handles input and sometimes paints |
| Input delayed behind React work | React blocks when it should yield | Whether that work is on an urgent lane, or expired |

You can label your own work so it lines up with React's tracks.

```js
performance.mark("filter-start");
const rows = filterRows(allRows, query);
performance.measure("filter rows", "filter-start");
```

### The tools

Performance Tracks appear automatically in traces of development builds. Profiling builds, from `react-dom/profiling`, show the Scheduler track too.

| Tool | What it shows |
|---|---|
| Main thread flame chart | Long tasks, slices, paints |
| Scheduler ⚛ track | Each render on a priority subtrack, with its phases |
| Components ⚛ track | Render and effect time per component |
| React DevTools Profiler | Which components rendered, and why |
| React DevTools Timeline profiler | Scheduled updates labeled by lane |

The Blocking subtrack is the quickest check for heavy work outside a transition. The Scheduler track also marks cascading updates, which can make React restart.

### Symptoms and mechanisms

| Symptom | Likely mechanism | What to do |
|---|---|---|
| A heavy update freezes the UI | It is on a blocking lane | Wrap it in `startTransition` |
| A transition still janks | An update escaped to an urgent lane, or one unit is too slow | Move the update inside, or make it cheaper |
| A deferred update renders late with a stall | Expiration turned slicing off | Usually fine, unless urgent load starves it often |
| Related updates show an inconsistent frame | Not in one lane or entangled, or your own bug | Put them in one transition |
| Expected batching renders several times | Urgent versus transition, or split across ticks | Make them in one event, before any `await` |

Time slicing helps when a render has many units of work, but it cannot split one giant computation inside a component. That is a render-cost problem, and the fix is to make that unit cheaper. An escaped update is common with async transitions.

```jsx
// Escaped: the update after await runs outside the transition.
startTransition(async () => {
    const data = await fetchResults(query);
    setResults(data);
});

// Fixed: wrap the update after the await again.
startTransition(async () => {
    const data = await fetchResults(query);
    startTransition(() => setResults(data));
});
```

After the `await`, the code is outside `startTransition` and `window.event` is gone, so the first `setResults` gets the blocking `DefaultLane`. Wrapping it again puts it back on the Action's lane.

## The whole thing in one list

1. The scheduler decides when React works, and lanes decide which work goes first.
2. The scheduler runs tasks from a min-heap ordered by expiration time, with five levels from -1ms to about 12 days.
3. It yields every 5ms by posting a `MessageChannel` message, because `setTimeout` clamps and microtasks never yield.
4. A lane is one bit of 31, lower bits are more urgent, and `lanes & -lanes` finds the most urgent lane.
5. `requestUpdateLane` picks a lane from context: transition, then the event, then `window.event`, then `DefaultLane`.
6. `getNextLanes` picks the most urgent group, and only a strictly more urgent lane restarts a render in progress.
7. Sync work renders at the end of a microtask, while other work becomes a scheduler task at UserBlocking, Normal or Idle.
8. Sync, InputContinuous and Default renders block, while transition, retry, idle and offscreen renders are time-sliced.
9. Expiration after 250ms or 5s turns time slicing off, and best-effort entanglement keeps related lanes in one render.
10. Batching, transitions, `useDeferredValue` and Suspense retries are all handles on these same lane rules.
