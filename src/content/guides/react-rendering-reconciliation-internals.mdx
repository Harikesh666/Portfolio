Type one letter into this search box and the cursor jumps out of the input. Type another and it happens again.

```jsx
function SearchPage() {

    function SearchBox() {
        return <input value={query} onChange={(e) => setQuery(e.target.value)} />;
    }
```

Nothing here deletes the input. Yet React destroys it and builds a new one on every keystroke, and focus goes with it. The cause is the way React decides what changed between two renders.

This guide shows that decision from the inside. It covers elements, the linear-time diff, the **fiber** objects that let React pause, and the two phases that apply a change.

## 1. What rendering is

You change some state, and the right part of the screen updates. How does React know which DOM nodes to touch? And why is "React is fast" only half true?

### The short version

React's job fits in one line: `UI = f(state)`. Your component returns a description of the screen. When state changes, React calls it again for a new description. It then <Mark kind="marker" wraps>compares the new description with the old one and changes only the DOM that differs</Mark>. That comparison is **reconciliation**.

An exact comparison of two trees costs about O(n³). So React uses two rules about UIs that make it O(n), linear in the number of nodes. It never reads the live DOM to compare. Each update then runs in two phases: **render** plans the change, and **commit** applies it to the DOM (section 9).

### Why not rebuild everything?

```js
// The simplest way to keep a screen in sync: throw it away and redraw.
function render(state) {
    document.body.innerHTML = "";
    document.body.append(buildWholeUI(state));
}
```

| Problem | What goes wrong |
|---|---|
| DOM work is slow | Creating nodes, layout and paint are among the slowest things a browser does |
| The DOM holds state you never stored | Uncontrolled input text, scroll position, focus, selection, video position and canvas pixels vanish with the node |
| Animations live on nodes | A recreated node restarts or loses its CSS transition |
| It does not scale | The cost grows with the whole app, not with the size of the change |

Given an old description and a new one, find a small set of DOM changes and apply them correctly and fast. That is reconciliation.

### Linear, not perfect

```text
exact tree diff     about n³ steps    3,000 nodes → 27 billion steps
React's heuristic   about n steps     3,000 nodes → 3,000 steps
```

Finding the fewest edits between two arbitrary trees is the tree edit distance problem. React refuses to solve it, and makes two assumptions about UIs instead (section 4).

The price is that React sometimes misses the smallest possible diff. "Good and linear" beats "perfect and cubic", and the `key` prop is a direct result of that trade.

### Two myths about the Virtual DOM

```js
// Not how React works: it never reads the page to find changes.
const changed = diff(document.body, newDescription);

// How React works: it compares its own two trees, and the DOM is only output.
apply(diff(previousTree, nextTree), document.body);
```

The "Virtual DOM" is just React's own trees. You pretend to rebuild the whole UI every render. React's **reconciler**, the part that compares trees (section 3), turns that pretense into a few real mutations.

It is also <Mark kind="circle">not inherently fast</Mark>. For one small change, a hand-written DOM update wins, because React does diffing work an expert would skip. React's modern speed wins come from scheduling work it can pause.

### Try it

In a React app in the browser, render a static `<p>Hello</p>` beside a counter button. Edit the paragraph's text by hand in the Elements panel, then click the counter. Your edit survives, because React compared its own trees and never read the live DOM.

## 2. Elements, components and instances

People say "component" for three different things: the function you wrote, the thing it returns, and the live piece of UI with state.

### The short version

A **component** is the function you write, a recipe. When React calls it, it returns **elements**: small, immutable, plain objects that describe the screen, not DOM nodes.

An **instance** is one live occurrence of a component, with its own state. For function components that state lives on a fiber, React's internal record for one element at one position across renders.

An element's `type` decides what React does with it. A string such as `'div'` is a host element, which the renderer turns into a real node. A function is a composite element, which React must call. Every render makes new elements, and comparing them with the previous ones is reconciliation.

### The element object

```js
console.log(element);
console.log(Object.isFrozen(element));
console.log(JSON.stringify(element));
```

| Field | What it holds |
|---|---|
| `$$typeof` | `Symbol.for('react.transitional.element')`, the proof that this is an element |
| `type` | A string for host elements, or your function or class |

The development build freezes each element to catch mutation. Production skips the freeze and the `_owner` and `_store` fields, and keeps a legacy `ref` field. In React 19, `ref` is a normal prop, so function components receive it without `forwardRef`. `element.ref` is deprecated.

### Recipe, description, live occurrence

```jsx
function Toolbar() {
    return <button className="primary">Save</button>; // returns an element
}

function Page() {
    return (
        <>
            <Toolbar /> {/* instance 1, with its own state */}
            <Toolbar /> {/* instance 2, a separate fiber */}

```

Class components have a real instance object, `this`. Function components keep their state on the fiber instead.

"The component re-rendered" therefore means three things. React called your function again, got fresh elements, and reconciled them against fibers that already exist. Your function never touched the DOM.

## 3. The reconciler and the renderer

`useState` and Suspense behave the same in React DOM and React Native, yet one makes HTML elements and the other makes native views. How can one set of hooks serve both?

### The short version

React is split into two layers. The reconciler, the `react-reconciler` package, owns the diff, fibers, hooks, scheduling and Suspense, and knows nothing about the DOM. The **renderer**, such as `react-dom`, knows how to create and change nodes on one platform.

The two talk through a fixed set of functions called the **host config**, such as `createInstance` and `appendChild`. Because the cleverness sits above that line, every hook works on every renderer. In React 19 you enter React DOM through `createRoot`.

### The host config

```js
// Simplified teaching version of a host config, shaped like React DOM's.
const hostConfig = {
    createInstance(type, props) {
        return document.createElement(type); // 'div' becomes a real <div>
    },
    createTextInstance(text) {
        return document.createTextNode(text);
    },
    appendChild(parent, child) {
        parent.appendChild(child);
    },
    insertBefore(parent, child, before) {
        parent.insertBefore(child, before);
    },
    removeChild(parent, child) {
        parent.removeChild(child);
    },
    commitUpdate(node, type, oldProps, newProps) {
        // diff oldProps against newProps and apply the difference
    },
};
```

The reconciler decides what changes and calls these functions. React DOM's real config, `ReactFiberConfigDOM.js`, adds functions such as `hideInstance`. Suspense and `<Activity>`, which hides UI without unmounting it (section 14), use it. In React 19, `commitUpdate` receives old and new props and diffs them itself.

<GuideFigure figure="react-host-config" />

Renderers exist for the DOM, React Native, the terminal, 3D scenes, PDFs and tests.

### Where the hand-off shows

```js
// Work tags from ReactWorkTags.js: what kind of thing a fiber is.
const FunctionComponent = 0;
const ClassComponent = 1;
const HostRoot = 3; // the root of a host tree
const HostComponent = 5; // a host element such as 'div'
const HostText = 6; // a text node
```

Names that start with `Host` mark the line where the reconciler hands work to the platform. A `HostComponent` fiber ends up as a real node.

```jsx

createRoot(document.getElementById("root")).render(<App />);
```

React 19 removed `ReactDOM.render`. So `createRoot` is the only way in, or `hydrateRoot`, which attaches React to HTML the server already sent. The old synchronous legacy mode is gone.

You never wrote a hook, yet a reconciler on top of these functions could run any hook. `ink` and `@react-three/fiber` are real renderers built this way.

## 4. The diff: type and position

An input loses its text when a parent re-renders. A panel resets when you toggle a flag. Both come from the two rules React uses to compare trees.

### The short version

React walks the new element tree against the old fiber tree, position by position, comparing `type`. Same type: React keeps the fiber and DOM node and updates the changed props. Different type: React tears down the old subtree and builds a new one, so <Mark kind="underline" wraps>all state below that spot is lost</Mark>.

That is assumption one: different types produce different trees. Assumption two covers lists: a `key` tells React which child is which across renders, matched only among siblings. These two rules also explain the opening bug, because a component defined inside another is a new type on every render.

### Same type keeps state, a new type rebuilds

```jsx
function Panel({ editing }) {
    // Different types at one position: each toggle unmounts one and mounts the other.
    return editing ? <Editor /> : <Viewer />;
}

function Field({ editing }) {
    // Same type at one position: the input and its text survive the toggle.
    return <input className={editing ? "edit" : "view"} />;
}
```

| At one position | What React does | State below |
|---|---|---|
| Same `type` | Keeps the fiber and DOM node, updates changed props, recurses into children | Kept |
| Different `type` | Unmounts the old subtree, runs its cleanups, destroys its nodes, mounts the new one | Lost |

React makes no attempt to find similar parts under a type change, which is the price of linear time. State belongs to the position in the tree, not to the line of JSX.

### The opening bug

```jsx
function SearchBox({ query, setQuery }) {
    return <input value={query} onChange={(e) => setQuery(e.target.value)} />;
}

function SearchPage() {
    const [query, setQuery] = useState("");
    return <SearchBox query={query} setQuery={setQuery} />;
}
```

In the opening code, each render of `SearchPage` created a new `SearchBox` function. React compares types with `===`, so the old and new types differed, and React remounted the input every time. Defined at module scope, as here, the type is the same function on every render, so React keeps the input.

### Keys: identity among siblings

```jsx
<ul>
    {todos.map((todo) => (
        <TodoRow key={todo.id} todo={todo} />
    ))}
</ul>
```

A key promises that this element is the same item as last render's element with that key, even if it moved. React matches keys only among children of one parent, never across the whole tree.

### Try it

In a React app in the browser, build the opening `SearchPage` and add `useEffect(() => console.log("mounted"), [])` inside `SearchBox`. Type a word and see it log on every keystroke. Move `SearchBox` to module scope and the log stops.

## 5. Keys and the list algorithm

You add sorting to a list, and suddenly checkboxes are ticked on the wrong rows. The data is right, but the UI is scrambled. The cause is the key you chose.

### The short version

React walks old and new lists together while keys match by position, the fast path for appends and edits. When keys stop matching, it maps the remaining old fibers by key. Each new element looks up its key: a hit reuses that fiber, a miss creates one, and leftovers are deleted.

With the array index as key, position 0 always matches position 0, whatever item now sits there. So instance state, such as typed text, a checkbox or focus, sticks to the slot instead of following the item. <Mark kind="marker" wraps>Use a stable id from your data</Mark> for any list that can change order.

### The algorithm, simplified

This runs in Node as it is.

```js
// Simplified teaching version of reconcileChildrenArray (ReactChildFiber.js).
// Old children are fibers with a key and an index. New children are keys.
function reconcileList(oldKeys, newKeys) {
    const ops = [];
    let i = 0;
    // Pass 1: walk both lists while the keys match by position.
    while (i < oldKeys.length && i < newKeys.length && oldKeys[i] === newKeys[i]) {
        ops.push(`keep ${newKeys[i]}`);
        i++;
    }
    if (i === newKeys.length) {
        // New list used up: delete what is left of the old one.
        for (const key of oldKeys.slice(i)) ops.push(`delete ${key}`);
        return ops;
    }
    if (i === oldKeys.length) {
        // Old list used up: everything left is new (the append fast path).
        for (const key of newKeys.slice(i)) ops.push(`insert ${key}`);
        return ops;
    }
    // Pass 2: put the remaining old fibers in a Map from key to old index.
    const map = new Map(oldKeys.slice(i).map((key, offset) => [key, i + offset]));
    let lastPlacedIndex = 0;
    for (; i < newKeys.length; i++) {
        const key = newKeys[i];
        if (!map.has(key)) {
            ops.push(`insert ${key}`);
            continue;
        }
        const oldIndex = map.get(key);
        map.delete(key);
        if (oldIndex < lastPlacedIndex) {
            ops.push(`move ${key}`); // it sat left of an item already placed
        } else {
            ops.push(`keep ${key}`);
            lastPlacedIndex = oldIndex;
        }
    }
    for (const key of map.keys()) ops.push(`delete ${key}`);
    return ops;
}

console.log(reconcileList(["a", "b", "c"], ["a", "b", "c", "d"]).join(", "));
console.log(reconcileList(["a", "b", "c"], ["c", "a", "b"]).join(", "));
console.log(reconcileList(["a", "b", "c"], ["b", "c", "a"]).join(", "));
```

```text role="output"
keep a, keep b, keep c, insert d
keep c, move a, move b
keep b, keep c, move a
```

| Step | What React does | Covers |
|---|---|---|
| Pass 1 | Walks both lists while keys match by position | Edits, the common case |
| New list ends first | Deletes the old fibers that are left | Removing items from the end |
| Old list ends first | Creates the new elements that are left | First render, appending |
| Pass 2 | Maps the remaining old fibers by key, then reuses, moves or creates | Reorders, inserts, filters |
| Leftovers | Deletes every old fiber nobody claimed | Removed items |

A fiber with no key goes into the map under its index. A matching key with a different type still gets a new fiber, by the rule from section 4.

### How React decides what moved

React tracks `lastPlacedIndex`, the highest old index among items it kept in place. A reused item with a lower old index sat left of something already placed, so its node must move. Otherwise it stays, and `lastPlacedIndex` rises.

So moving `c` to the front moves both `a` and `b`, two DOM moves for a one-item change. Moving `a` to the end moves only `a`. The heuristic is cheap and linear, not minimal.

<GuideFigure figure="rr-keys" />

### Why the index is a trap

```jsx
// Fine only if the list never reorders, inserts or filters, and rows hold no state.
items.map((item, index) => <Row key={index} item={item} />);

// Correct for any list that can change order.
items.map((item) => <Row key={item.id} item={item} />);
```

With index keys, React reuses the fiber at index 0 for whatever item is now first, and only updates its props. Anything that belongs to the instance rather than the data sticks to the slot. Uncontrolled input text, checkbox state, focus and a running CSS transition all land on the wrong row.

That is a correctness bug, and also a performance bug, since every row gets new props.

### Changing a key on purpose

```jsx
<EditForm key={recordId} record={record} />
```

A new key means a new item, so React unmounts the old `EditForm` and mounts a fresh one with clean state. This is usually cleaner than copying a prop into state and resetting it in an effect.

### Try it

In a React app, render five rows, each with its own `useState` checkbox, plus a shuffle button. Tick two boxes and shuffle, once with `key={index}` and once with `key={item.id}`. Predict which rows stay ticked first. Then run `reconcileList(["a", "b", "c", "d"], ["d", "a", "b", "c"])` and count the moves.

## 6. Fiber: work you can pause

Old React froze the page during a big update. Modern React can keep typing smooth while it renders something heavy. What changed underneath?

### The short version

Before React 16, rendering was plain recursion. Its progress lived on the JavaScript call stack, and nothing can pause a call stack halfway. **Fiber** made each unit of work a plain object on the heap, linked to its parent, first child and next sibling.

Because React now owns the progress, it can stop between any two fibers, give the browser the thread, and resume later. It can drop unfinished work by dropping a reference. A fiber is both a stack frame React controls and the record of one component at one position. Two summary fields let React skip a quiet subtree with one check.

### A walk you can stop

```js
// Simplified teaching version: a tree walk that can stop and resume.
function fiber(name, ...children) {
    const node = { name, child: null, sibling: null, return: null };
    children.forEach((kid, i) => {
        kid.return = node;
        if (i === 0) node.child = kid;
        else children[i - 1].sibling = kid;
    });
    return node;
}

const root = fiber("App", fiber("Header"), fiber("Main", fiber("List", fiber("Item"))));

let next = root; // the only state: where to go next
function work(budget) {
    while (next !== null && budget-- > 0) {
        console.log("begin", next.name);
        if (next.child) {
            next = next.child;
            continue;
        }
        while (next !== null && next.sibling === null) next = next.return; // climb up
        next = next === null ? null : next.sibling;
    }
}

work(3);
console.log("-- paused, the browser could run here --");
work(Infinity);
```

```text role="output"
begin App
begin Header
begin Main
-- paused, the browser could run here --
begin List
begin Item
```

This walk needs one pointer, `next`. A recursive walk keeps its place in nested calls, and no code can leave them and come back. The old **stack reconciler** worked that way, so a big render had to finish while input and paint waited.

### The fields that matter

Each pending update carries a **lane**, one bit that stands for its priority. `renderLanes` is the set of lanes the current render is working on. Section 10 covers lanes properly.

```js
// The fields of a fiber, grouped by job (ReactInternalTypes.js, React 19).
const fiber = {
    // What this fiber is
    tag, // FunctionComponent, HostComponent, SuspenseComponent… the loop switches on it
    key, // the reconciliation key
    type, // the function, class or string it came from
    stateNode, // the DOM node, the class instance, or the root

    // The tree, as linked pointers
    return, // the parent: where the loop goes after this subtree
    child, // the first child only
    sibling, // the next sibling
    index, // position among siblings

    // Input and output of rendering
    pendingProps, // props for the render in progress
    memoizedProps, // props from the last render
    memoizedState, // for a function component, the head of its hook list (section 11)
    updateQueue, // queued updates and effects
    dependencies, // the contexts this fiber read
    ref, // the ref prop, with refCleanup holding a ref's cleanup function

    // Work and effects
    lanes, // pending update priorities on this fiber (section 10)
    childLanes, // the union of lanes anywhere below
    flags, // what commit must do here: Placement, Update, Ref, Passive…
    subtreeFlags, // the union of flags anywhere below
    deletions, // children to remove, marked on the parent with ChildDeletion

    // Double buffering
    alternate, // this fiber's twin in the other tree (section 7)
};
```

`return` is named after a return address: after a fiber's subtree, the loop goes back to it, as a function returns to its caller. Older source called `flags` by the name `effectTag`.

<GuideFigure figure="rr-fiber-fields" />

### Two summaries make skipping cheap

```js
const SyncLane = 0b10;
const header = { lanes: 0, childLanes: 0 }; // nothing pending here or below
const main = { lanes: 0, childLanes: SyncLane }; // an update waits somewhere below

const renderLanes = SyncLane;
console.log((header.childLanes & renderLanes) === 0); // true: skip Header's subtree
console.log((main.childLanes & renderLanes) === 0); // false: go down into Main
```

```text role="output"
true
false
```

`childLanes` asks whether any work waits below, and `subtreeFlags` asks whether anything below needs committing. Each is one bitwise AND, so React proves a subtree is quiet without walking into it.

### Try it

Replace the two `work` calls in the walk with five calls to `work(1)`. Each call handles one fiber and stops, yet the walk never loses its place. Then give `Header` a child and confirm the walk visits it with no change to `work`.

## 7. Two trees: double buffering

If React can stop halfway through a render, why do you never see half an update on screen?

### The short version

React keeps two fiber trees. The **current** tree matches the screen and is always complete. The **work-in-progress** tree is being built and may be unfinished, because nothing displays it. Each fiber points to its twin in the other tree through `alternate`, and React only edits the work-in-progress tree.

If React abandons a render, it drops that tree, and the screen never saw it. At commit, React applies the DOM changes in one synchronous pass, then points the root at the finished tree. The old tree becomes the spare for the next update. Graphics calls this double buffering.

### Reusing the spare tree

```js
// Simplified teaching version of createWorkInProgress (ReactFiber.js).
function createWorkInProgress(current, pendingProps) {
    let wip = current.alternate;
    if (wip === null) {
        wip = { props: null, alternate: current }; // first update: allocate a twin
        current.alternate = wip;
    }
    wip.props = pendingProps; // later updates: reuse the spare twin
    return wip;
}

const first = { props: { n: 0 }, alternate: null };
const root = { current: first };

for (const n of [1, 2]) {
    const wip = createWorkInProgress(root.current, { n });
    // ...render into wip while root.current stays on screen...
    root.current = wip; // the swap at commit
    console.log(`commit ${n}: is the first object current?`, root.current === first);
}
```

```text role="output"
commit 1: is the first object current? false
commit 2: is the first object current? true
```

The first update allocates a twin. Later updates reuse the spare instead of allocating a new tree, which keeps memory churn down. The real function does this per fiber, and the list algorithm calls it for every child it reuses.

Whenever you read that a render can be interrupted, ask which tree React was building. The answer is always the disposable one, and that is why interruption is safe.

</MarginNote>

### Where the swap happens

```js
// From flushMutationEffects in ReactFiberWorkLoop.js (simplified).
commitMutationEffects(root, finishedWork, lanes); // the DOM changes
root.current = finishedWork; // the work-in-progress tree is now current
// ...then the layout phase runs
```

The swap is not the whole commit. React applies every DOM change, then moves the pointer, then runs layout effects. So `componentWillUnmount` still sees the old tree, and `componentDidMount` sees the new one. You never see half a commit because the mutation phase runs synchronously, so the browser cannot paint in the middle.

### Try it

Run the snippet with a third commit and predict whether `first` is current after it. Then, in a React app, update a slow filtered list inside `startTransition` (section 8), and type fast. You see the old full list or the new one, never half of each.

## 8. The work loop and bailouts

"React renders" is not something you can debug. What does React do, step by step, during a render? And how does it skip parts of the tree?

### The short version

React processes one fiber at a time. Going down, `beginWork` calls your component, runs its hooks and reconciles its children. Going up, `completeWork` builds DOM nodes off screen and folds each child's lanes and flags into its parent. A concurrent render asks between fibers whether to yield.

Before rendering a fiber, `beginWork` checks for a **bailout**. If the props object is the same and nothing is pending, React skips the fiber. If `childLanes` shows no work below either, it skips the whole subtree. So a parent's render renders its children, and `React.memo` is a bailout you ask for.

### The loop

```js
// The two render loops in ReactFiberWorkLoop.js, React 19.2 and 19.3.
function workLoopSync() {
    while (workInProgress !== null) {
        performUnitOfWork(workInProgress);
    }
}

function workLoopConcurrentByScheduler() {
    while (workInProgress !== null && !shouldYield()) {
        performUnitOfWork(workInProgress);
    }
}
```

Urgent renders use the first loop and run to the end. A **transition**, an update marked non-urgent with `startTransition`, uses the second, which checks `shouldYield()` between fibers.

```js
// Simplified teaching version of performUnitOfWork.
function performUnitOfWork(fiber) {
    const next = beginWork(fiber.alternate, fiber, renderLanes); // down: returns the first child
    fiber.memoizedProps = fiber.pendingProps;
    if (next !== null) {
        workInProgress = next;
    } else {
        completeUnitOfWork(fiber); // up: complete, then a sibling or the parent
    }
}
```

`completeUnitOfWork` completes the fiber, then moves to its sibling. With no sibling, it climbs to the parent and completes that too. The result is a depth-first walk: down, across, back up.

<GuideFigure figure="rr-work-loop" />

### Going down: beginWork and the bailout

```js
// Simplified teaching version of the checks at the top of beginWork.
function beginWork(current, fiber, renderLanes) {
    if (current !== null && current.memoizedProps === fiber.pendingProps) {
        const hasWork = (fiber.lanes & renderLanes) !== 0 || contextChanged(fiber);
        if (!hasWork) {
            if ((fiber.childLanes & renderLanes) === 0) return null; // skip the whole subtree
            return cloneChildren(fiber); // skip this fiber, keep walking below
        }
    }
    return renderComponent(current, fiber, renderLanes); // call it, reconcile its children
}
```

Without a bailout, `beginWork` calls your function, runs its hooks, and reconciles the returned elements by the rules of sections 4 and 5. New and moved children get `flags` such as `Placement`. The real bailout path runs through `bailoutOnAlreadyFinishedWork` in `ReactFiberBeginWork.js`.

The first check compares the props object by reference. When a parent renders, JSX creates a new props object for every child, even with identical values. So <Mark kind="marker" wraps>a parent's render renders every child below it</Mark>, unless something restores the same props.

`React.memo` does that. It compares old and new props shallowly and, if they match, takes the bailout path. A memoized child still renders when you pass a new object, array or function each time. A second, later bailout exists too. If a component renders but its state, props object and context did not change, React keeps its old children.

### Going up: completeWork

```js
// Simplified teaching version of bubbleProperties in ReactFiberCompleteWork.js.
function bubbleProperties(fiber) {
    let childLanes = 0;
    let subtreeFlags = 0;
    for (let child = fiber.child; child !== null; child = child.sibling) {
        childLanes |= child.lanes | child.childLanes;
        subtreeFlags |= child.flags | child.subtreeFlags;
    }
    fiber.childLanes = childLanes;
    fiber.subtreeFlags = subtreeFlags;
}
```

For a new host fiber, `completeWork` calls `createInstance`, appends the finished children, and sets initial props, all off screen. For an existing node with new props, React 19 only marks the fiber with `Update`. The prop diff waits for `commitUpdate` in the commit phase.

Then `bubbleProperties` folds each child's work into the parent. `setState` also writes its lane into every ancestor's `childLanes`, so the summary is ready before the render starts.

### Try it

In a React app, record an interaction in the React DevTools Profiler. Grey bars are components that did not render in that commit. Wrap a child in `memo`, pass it an inline object prop, and watch it stay coloured. Move the object to module scope and watch it turn grey.

## 9. The render phase and the commit phase

Why must render code be pure? Why does `useLayoutEffect` run before paint and `useEffect` usually after? And why does a `fetch` in a component body fire twice?

### The short version

The render phase calls your components and builds the work-in-progress tree. It must be pure, because React may run it several times, pause it, or throw it away. The commit phase applies the result in one synchronous burst: before mutation, mutation, where the DOM changes, and layout, before paint.

Passive effects, your `useEffect` calls, run after commit. Usually that is after paint, but a click's render flushes them before paint. In development, StrictMode tests both contracts by rendering twice and running each effect's setup and cleanup an extra time.

### Render may run many times

```jsx
function Profile({ id }) {
    fetch(`/api/users/${id}`); // BUG: runs on every render attempt, kept or not
    const [user, setUser] = useState(null);

    useEffect(() => {
        let ignore = false;
        fetch(`/api/users/${id}`)
            .then((response) => response.json())
            .then((data) => {
                if (!ignore) setUser(data);
            });
        return () => {
            ignore = true;
        };
    }, [id]);

    return <p>{user?.name}</p>;
}
```

<MarginNote note="render is a plan, commit is the change">

Render only works out what should change. Commit is the only step that touches the DOM.

</MarginNote>

Render must be pure: no DOM changes, subscriptions, network calls, or ref writes that change the output. A side effect in render leaks out of every discarded attempt as a duplicate request or corrupted state. Side effects belong in effects or event handlers, which run only for work that commits.

### The commit sub-phases

```js
// Simplified teaching version of commitRoot in ReactFiberWorkLoop.js.
function commitRoot(root, finishedWork) {
    schedulePassiveEffects(); // useEffect work, for later
    commitBeforeMutationEffects(finishedWork); // read the DOM before it changes
    commitMutationEffects(finishedWork); // change the DOM
    root.current = finishedWork; // the swap from section 7
    commitLayoutEffects(finishedWork); // the DOM is updated, not yet painted
}
```

| Sub-phase | What runs | When |
|---|---|---|
| Before mutation | `getSnapshotBeforeUpdate`, for example to read a scroll position | Before any DOM change |
| Mutation | Inserts, moves, removals, `commitUpdate`, old ref detach, `useInsertionEffect`, `useLayoutEffect` cleanups, `componentWillUnmount` | The DOM changes |
| Layout | `useLayoutEffect` setup, `componentDidMount`, `componentDidUpdate`, ref attach | After the DOM changes, before paint |
| Passive | All previous `useEffect` cleanups, then every new setup | Usually after paint |

In the layout phase the DOM is correct but not yet painted. That is the moment to measure an element and adjust it with no flicker, at the cost of delaying paint. In React 19 a ref callback can also return a cleanup function, which React calls when it detaches the ref.

<GuideFigure figure="rr-commit-phases" />

### When useEffect really runs

```js
// From the end of the commit in ReactFiberWorkLoop.js (simplified).
if (includesSyncLane(pendingEffectsLanes)) {
    flushPendingEffects(); // a click's render: run passive effects now, before paint
}
```

After a click or key press, React flushes passive effects at once, so the result is "immediately observable".

| Hook | Cleanup runs | Setup runs | Blocks paint? |
|---|---|---|---|
| `useLayoutEffect` | Mutation sub-phase | Layout sub-phase | Yes |
| `useEffect` | Before the new setups | After paint, or before it after a click | Only after a click or key press |

To measure or position something before the user sees it, such as a tooltip, use `useLayoutEffect`. Do not default to it, because it blocks paint on every update. For fetching, subscriptions and logging, use `useEffect`. To run work after paint even after a click, as with an `alert()`, wrap it in `setTimeout`.

### StrictMode rehearses both contracts

```jsx
createRoot(document.getElementById("root")).render(
    <StrictMode>
        <App />
    </StrictMode>,
);
```

| In development, inside StrictMode | Extra work | What it catches |
|---|---|---|
| Component bodies | Called twice | Side effects in render |
| Initializers, reducers and updaters of `useState`, `useReducer`, `useMemo` | Called twice | Impure state logic |
| Effects on mount, since React 18 | Setup, cleanup, setup | Effects that do not clean up |
| Ref callbacks on mount | Setup, cleanup, setup | Refs that do not clean up |

React 19 reuses the first render's `useMemo` and `useCallback` results during the second render, and React DevTools dims the second call's logs. Production builds do none of this.

<MarginNote note="the double run is a rehearsal, not a bug">

If code only works with StrictMode off, it has a real bug. Concurrent rendering can repeat renders, and `<Activity>` unmounts and remounts effects. StrictMode makes those events happen early, where you can see them.

</MarginNote>

### Try it

In a React app under StrictMode, log "render" in a component body. Add an effect that logs "effect" and returns a cleanup that logs "cleanup".

```text role="output"

```

## 10. Scheduling, briefly

A search box filters a large list. With plain state it stutters as you type. With a transition, the input stays smooth while the list catches up.

### The short version

Concurrent rendering is not multiple threads. It is cooperative time slicing on one thread: render for about 5ms, yield so the browser can handle input, resume. Only non-urgent renders are sliced: transitions, and Suspense retries after suspended data arrives (section 13). A click, a scroll or a timer update renders in one blocking pass.

Each update's lane is one bit in a 31-bit number, and `childLanes` collects the lanes below a fiber. React renders the most urgent lanes first. If a click or key press arrives mid-transition, React drops the half-built tree and starts the urgent one, safely, because of section 7. The [scheduler and lanes guide](/articles/react-scheduler-and-lanes-internals) is the full story.

### How React yields

```js
// Simplified teaching version of how the scheduler comes back after a yield.
const channel = new MessageChannel();
channel.port1.onmessage = () => workLoopConcurrentByScheduler(); // the next slice
function yieldToBrowser() {
    channel.port2.postMessage(null); // a new task: the browser can handle input first
}
```

The `scheduler` package yields this way. The message comes back as a new task, without the 4ms clamp that nested `setTimeout` calls suffer.

"Concurrent" means several renders can be in progress and React switches between them. "Parallel" would mean running at the same moment, which main-thread JavaScript cannot do.

### Lanes in one snippet

```js
const SyncLane = 0b0000000010; // a click
const TransitionLane1 = 0b0100000000; // startTransition

let pendingLanes = 0;
pendingLanes |= TransitionLane1;
pendingLanes |= SyncLane;

console.log((pendingLanes & SyncLane) !== 0); // is a click pending?
console.log((pendingLanes & -pendingLanes) === SyncLane); // the lowest bit is the most urgent
console.log((pendingLanes & ~SyncLane) === TransitionLane1); // remove the click
```

```text role="output"
true
true
true
```

A lower bit means a higher priority, and every question is one instruction.

| Update comes from | Lane | How it renders |
|---|---|---|
| A click or a key press | `SyncLane` | Blocking, at the end of a microtask |
| `mousemove`, scroll, drag | `InputContinuousLane` | Blocking |
| `setTimeout`, a promise, a network response | `DefaultLane` | Blocking |
| `startTransition`, `useDeferredValue` | A transition lane | Time-sliced and interruptible |
| A Suspense retry | A retry lane | Time-sliced |
| Idle work | `IdleLane` | Time-sliced, only when nothing else is pending |
| Hidden `<Activity>` content | `OffscreenLane` | Time-sliced, last of all |

### Batching and flushSync

```jsx
function handleClick() {
    setCount((c) => c + 1);
    setFlag((f) => !f);
    setText("saved"); // three updates, one render
}
```

`setState` does not render. It queues the update and asks React to schedule the root, which React does in a microtask. So every `setState` in one event, promise callback or timeout piles up before the render starts.

This automatic batching arrived with React 18's `createRoot`. Before it, only updates inside React event handlers batched.

```jsx
flushSync(() => setCount((c) => c + 1)); // render and commit now
const height = listRef.current.scrollHeight; // the DOM is already updated
```

`flushSync`, from `react-dom`, renders and commits its updates before it returns. It defeats batching and slicing, so use it only when you must read the updated DOM at once.

| API | What it does |
|---|---|
| `startTransition`, `useTransition` | Marks updates as non-urgent, and `isPending` shows a quiet working state |
| `useDeferredValue` | Gives a slow subtree a lagging copy of a value |

### Try it

In a React app, build an input that filters 3,000 rows, each doing a little busy-work in render, and type fast. Then pass the query through `useDeferredValue`. The input stays smooth while the list lags behind.

## 11. Hooks live on the fiber

"Don't call hooks in conditions or loops." Why not? Once you see where hook state lives, the rule becomes the only design that could work.

### The short version

A function component has no `this` to hold state. So React stores its hooks as a linked list on the fiber's `memoizedState`, one node per hook call. It matches nodes to calls <Mark kind="circle">purely by order</Mark>. Nothing in the list records names.

If a hook runs only sometimes, every later call reads the wrong node, and nothing warns you at runtime. On mount, React allocates the nodes. On update, it walks the existing list. A different internal **dispatcher** handles each case, which is also how React throws when you call a hook outside a component.

### A hook list in 30 lines

```js
// Simplified teaching version of the hook list in ReactFiberHooks.js.
const fiber = { memoizedState: null }; // head of the hook list
let cursor = null;
let mounting = true;

function nextHook(initial) {
    if (mounting) {
        const hook = { memoizedState: initial, next: null };
        if (cursor === null) fiber.memoizedState = hook;
        else cursor.next = hook;
        cursor = hook;
        return hook;
    }
    cursor = cursor === null ? fiber.memoizedState : cursor.next;
    return cursor;
}

const useState = (initial) => nextHook(initial).memoizedState;

function render(showName) {
    cursor = null;
    const name = showName ? useState("Ada") : "(hidden)";
    const age = useState(36);
    console.log(name, age);
}

render(true); // mount: two hooks
mounting = false;
render(true); // update: same order, same slots
render(false); // update: one hook skipped
```

```text role="output"
Ada 36
Ada 36
(hidden) Ada
```

On the third render the first `useState` is skipped, so the `age` call takes the first node, which holds `"Ada"`. One skipped call shifts every call after it.

```js
// The real hook object (ReactFiberHooks.js).
const hook = {
    memoizedState, // the state value, an effect object, or a useMemo cache
    baseState, // the state before updates skipped at a lower priority
    baseQueue, // those skipped updates
    queue, // the update queue for useState and useReducer
    next, // the next hook, or null
};
```

<GuideFigure figure="react-hook-list" />

### The two rules, from the storage

| Rule | Why the storage needs it |
|---|---|
| Same order every render | The cursor must meet the same node for the same call, so no conditions, loops or early returns before a hook |
| Only at the top level of a component or custom hook | Only there has React set up the fiber, the cursor and the dispatcher |

`eslint-plugin-react-hooks` enforces both, and now also reports problems found by the React Compiler, a build tool covered in section 14. `use()` is the one exception. It reads a promise or a context without taking a node, so it may sit inside a condition.

### Mount, update and the dispatcher

```js
// Simplified teaching version of the dispatcher swap in renderWithHooks.
ReactSharedInternals.H = current === null ? HooksDispatcherOnMount : HooksDispatcherOnUpdate;
const children = Component(props); // every useState call goes through H
ReactSharedInternals.H = ContextOnlyDispatcher; // outside render, every hook throws
```

On mount, `useState` allocates a node and runs your initializer. On update, the same line reads the node from the current fiber, through `alternate`, and applies queued updates. Outside rendering, `ContextOnlyDispatcher` makes every hook throw "Invalid hook call". The [hooks guide](/articles/react-hooks-and-effects-internals) follows each hook through this machinery.

### Try it

Swap the two `useState` lines in `render` and predict all three output lines before you run it. In a real component, write `if (cond) useState(0)` and read the lint error. It protects the cursor.

## 12. Updates, equal values and tearing

Call `setCount(count + 1)` three times and the count rises by one. Call `setCount((c) => c + 1)` three times and it rises by three. And state libraries warn about something called tearing.

### The short version

`setState` does not change state at once. It adds an update to the hook's queue, marks the fiber's lanes, and asks React to schedule a render. React applies the queue during that render. Three `setCount(count + 1)` calls read the same `count`, so they queue the same number. Updater functions each receive the previous result.

If the new state is equal by `Object.is`, React can skip the render. **Tearing** is a different hazard. A sliced render can pause, an external store can change in the gap, and two components then show two versions. `useSyncExternalStore` prevents that.

### The queue drains at render time

```js
// Simplified teaching version of a state hook's update queue.
function makeHook(value) {
    return { memoizedState: value, queue: [] };
}

function setState(hook, action) {
    hook.queue.push(action); // queue it, do not compute yet
}

function processQueue(hook) {
    let state = hook.memoizedState;
    for (const action of hook.queue) {
        state = typeof action === "function" ? action(state) : action;
    }
    hook.queue = [];
    hook.memoizedState = state;
    return state;
}

const a = makeHook(0);
const count = a.memoizedState; // the value this render saw
setState(a, count + 1);
setState(a, count + 1);
setState(a, count + 1);
console.log("value form:", processQueue(a));

const b = makeHook(0);
setState(b, (c) => c + 1);
setState(b, (c) => c + 1);
setState(b, (c) => c + 1);
console.log("updater form:", processQueue(b));
```

```text role="output"
value form: 1
updater form: 3
```

The real queue is a circular linked list on `hook.queue.pending`. Internally, `useState` is `useReducer` with a built-in reducer, which is why the two behave alike.

### Equal values skip work

```jsx
const [count, setCount] = useState(0);
setCount(0); // Object.is(0, 0) is true, so React can skip this render
```

The **eager bailout** applies when the fiber has no other pending updates. React computes the new state inside the `setState` call and, if it is equal, never schedules a render.

Otherwise React computes it during render, and an equal result lets it skip the children. React may still call your component once, so rely on the principle, not on a render count.

### Tearing and useSyncExternalStore

```js
// A store outside React: one mutable value and a set of listeners.
let value = 0;
const listeners = new Set();
const store = {
    get: () => value,
    set(next) {
        value = next;
        listeners.forEach((listener) => listener());
    },
    subscribe(listener) {
        listeners.add(listener);
        return () => listeners.delete(listener);
    },
};
```

React state is a snapshot, fixed for one render, so it cannot tear. An external store can. A sliced render may read `store.get()` in component A, yield, and let a click change the store. Then component B reads the new value, and one screen shows two versions.

```jsx
function Counter() {
    const current = useSyncExternalStore(store.subscribe, store.get);
    return <p>{current}</p>;
}
```

After a concurrent render, React compares each store's snapshot with the value it rendered. If the store changed mid-render, React renders again synchronously, so every component shows one value. React-Redux and Zustand use this hook. A hand-rolled subscription with `useEffect` and `useState` is the pattern that tears.

### Try it

In the queue snippet, queue `count + 5` and then `(c) => c * 2`, and predict the result before you run it.

## 13. Suspense in the render loop

A component "waits" for data, and a fallback appears in its place. What happens inside the render loop when a component is not ready?

### The short version

When a component needs data that is not ready, its render cannot finish. In React 19 it calls `use(promise)`, and `use` throws an internal signal that React catches. React unwinds to the nearest `<Suspense>` boundary and renders its `fallback` instead.

React also listens to the promise, and when it resolves, renders the subtree again on a retry lane. Pings, retries and pre-warming are covered in depth in the [Suspense guide](/articles/react-suspense-internals).

### What suspending looks like

```jsx
import { Suspense, use } from "react";

const commentsPromise = fetchComments(); // created once, outside render

function Comments() {
    const comments = use(commentsPromise); // suspends while pending
    return comments.map((c) => <p key={c.id}>{c.text}</p>);
}

function Post() {
    return (
        <Suspense fallback={<p>Loading…</p>}>
            <Comments />
        </Suspense>
    );
}
```

`use` throws a special `SuspenseException` and keeps the promise aside. The work loop catches it and walks up the `return` pointers to the nearest boundary. Older libraries threw the promise itself, and React still accepts that, but your code should use `use` or a Suspense-ready library.

| Situation | What React does |
|---|---|
| The data resolves while the render is in progress | Pings the render's lane and tries again |
| The fallback has already committed | Schedules a retry on a retry lane |
| A transition would hide visible content | Keeps the old UI and waits |
| The suspended component has siblings | Commits the fallback first, then pre-renders the siblings |

On the server, Suspense lets React stream HTML. Ready parts go first, with each waiting boundary's fallback as a placeholder, then its content as data arrives. The client hydrates each piece as it lands. Since 19.2, React briefly holds these reveals so several appear together.

### Try it

In a React app, wrap a `lazy(() => import("./Chart"))` component in a Suspense boundary and throttle the network in DevTools. Watch the fallback, then the chart. Then switch between two lazy tabs inside `startTransition`, and the old tab stays visible instead.

## 14. The layer on top: Compiler, Activity, View Transitions

People say you no longer need `useMemo` and `useCallback`. And what do `<Activity>` and `<ViewTransition>` add?

### The short version

The React Compiler, stable since 1.0 in October 2025, inserts memoization at build time. It only optimizes code that follows the Rules of React.

`<Activity mode="hidden">`, stable in React 19.2, hides UI while keeping its state and DOM, and renders it at the lowest priority. `<ViewTransition>`, stable in React 19.3, animates transition updates with the browser's View Transitions API. All three depend on the purity and cleanup contracts from section 9.

### The React Compiler

```jsx
// What you write.
function TodoList({ todos, filter }) {
    const visible = todos.filter((t) => t.status === filter);
    return <List items={visible} />;
}

// Roughly what the compiler emits (simplified).
import { c as _c } from "react/compiler-runtime";

function TodoList({ todos, filter }) {
    const $ = _c(3); // a cache array kept on the fiber
    let visible;
    if ($[0] !== todos || $[1] !== filter) {
        visible = todos.filter((t) => t.status === filter);
        $[0] = todos;
        $[1] = filter;
        $[2] = visible;
    } else {
        visible = $[2];
    }
    return <List items={visible} />;
}
```

The compiler does not change the reconciler. It is a Babel plugin that tracks how data flows through each component. It caches values and JSX in an array React keeps on the fiber. Because the cached `visible` keeps its identity, a memoized `List` can take the bailout from section 8.

| Point | What it means for you |
|---|---|
| Hand memoization | Becomes an escape hatch, mainly when a value's identity feeds an effect's dependencies. Elsewhere it adds noise, and forgotten `useCallback` dependencies stop being a bug class. |
| Code that breaks the rules | Skipped, and reported through `eslint-plugin-react-hooks` |
| Adoption | On by default in Expo SDK 54, offered in Vite and Next.js templates. Enable it behind a flag, pin the version, and test effects whose dependencies are memoized values. |

### Activity

```jsx
function Tabs({ tab }) {
    return (
        <Activity mode={tab === "profile" ? "visible" : "hidden"}>
            <ProfilePanel />
        </Activity>
    );
}
```

Hidden content stays mounted. React hides its DOM with `display: none`, runs its effect cleanups, keeps its state, and renders its updates on `OffscreenLane`. It can pre-render a hidden tab so showing it is instant. This is the public face of React's internal Offscreen machinery. Unmounting a tab instead loses its state and pays the mount cost again.

### View Transitions and smaller changes

```jsx
function Gallery({ photo }) {
    return (
        <ViewTransition>
            <Photo key={photo.id} photo={photo} />
        </ViewTransition>
    );
}

startTransition(() => setPhoto(next)); // React animates this update
```

`<ViewTransition>` animates elements that enter, exit or change during a transition, and `addTransitionType` tags the kind of change. Both were experimental in 19.2 and are stable in 19.3.

React 19.2 also changed the default `useId` prefix to `_r_`, so generated IDs are valid `view-transition-name` values. It added Performance Tracks to Chrome DevTools too. The Scheduler ⚛ track shows work by priority, including when React waits for paint. The Components ⚛ track shows render times.

### Try it

In a React app, build two tabs, one with a text input. Implement them once by rendering only the active tab, and once with `<Activity>`. Type in the input, switch tabs and switch back. Only Activity keeps your text.

## 15. Debugging with the model

Something re-renders too often, or an interaction feels slow. You want a procedure, not a guess followed by `useMemo` everywhere.

### The short version

Ask four questions in order. What scheduled this render: its own state, a context, a parent's render, or an external store? Could it have bailed out, or did a parent pass new objects? Is the cost in the render phase or the commit phase? Is urgent work blocking a transition?

The React DevTools Profiler and React's Performance Tracks answer each question directly, so you see the cause instead of guessing. Most bugs then map to one mechanism from this guide.

### The four questions

```js
// Label your own work, and it appears beside the Scheduler ⚛ track in a trace.
performance.mark("filter-start");
const rows = filterRows(allRows, query);
performance.measure("filter rows", "filter-start");
```

| Question | Where to look | Typical fix |
|---|---|---|
| What scheduled the render? | The Profiler's "Why did this render?", once you turn on recording why components render | Move state down, or split a context |
| Could it have bailed out? | The Profiler flame chart | `memo`, stable props including `children`, or the Compiler |
| Render cost or commit cost? | The Render and Commit blocks on the Scheduler ⚛ track | Transitions, `useDeferredValue`, `<Activity>`, smaller components, fewer DOM changes, lighter layout effects |
| Is urgent work blocking a transition? | The Scheduler ⚛ track | Make the urgent work cheaper, or move heavy work out of it |

## The whole thing in one list

1. React turns `UI = f(state)` into DOM changes by comparing its own two trees, never by reading the DOM.
2. Elements are immutable plain objects, and `type` decides between a host node and a component to call.
3. The reconciler owns the algorithm and hooks, and renderers plug in through the host config.
4. The O(n) diff rests on two rules: a new type rebuilds the subtree, and keys identify siblings.
5. The list algorithm walks in order, then maps by key, and index keys glue state to positions.
6. Fibers are heap objects linked by `child`, `sibling` and `return`, so rendering can pause and resume.
7. React builds a work-in-progress tree beside the current one and swaps the pointer after the DOM changes.
8. `beginWork` renders or bails out, and `completeWork` builds nodes and bubbles `childLanes` and `subtreeFlags`.
9. Render must be pure, and commit runs before mutation, mutation and layout, then passive effects.
10. Hooks are a linked list matched by call order, and updates wait in a queue until the next render.

## Further reading

### React's own docs

[Render and Commit](https://react.dev/learn/render-and-commit) and [Preserving and Resetting State](https://react.dev/learn/preserving-and-resetting-state) cover sections 1 to 5 from the user's side. The [`useEffect` reference](https://react.dev/reference/react/useEffect) states the rule about effects after a click.

### React Fiber Architecture

Andrew Clark's unfinished 2016 note, [React Fiber Architecture](https://github.com/acdlite/react-fiber-architecture), explains why Fiber exists. Since then its priority number became lanes, and its `requestIdleCallback` plan became a `MessageChannel` scheduler. Its `output` field and coroutines gave way to `flags` and `completeWork`.

### The legacy reconciliation page

The old React docs page on [Reconciliation](https://legacy.reactjs.org/docs/reconciliation.html) states the O(n³) cost and the two assumptions.

### Suspense

The [`<Suspense>` reference](https://react.dev/reference/react/Suspense), the [`use` reference](https://react.dev/reference/react/use) and Dan Abramov's [New Suspense SSR Architecture in React 18](https://github.com/reactwg/react-18/discussions/37) cover the API, streaming and selective hydration.

### Release posts

The [React 19 upgrade guide](https://react.dev/blog/2024/04/25/react-19-upgrade-guide), the [React 19.2](https://react.dev/blog/2025/10/01/react-19-2) and [React 19.3](https://react.dev/blog/2026/09/09/react-19-3) posts, and the [React Compiler 1.0](https://react.dev/blog/2025/10/07/react-compiler-1) post date each change. The [React Compiler docs](https://react.dev/learn/react-compiler) and the [Rules of React](https://react.dev/reference/rules) list what the compiler relies on.

[ReactChildFiber.js](https://github.com/facebook/react/blob/main/packages/react-reconciler/src/ReactChildFiber.js) and [ReactFiberWorkLoop.js](https://github.com/facebook/react/blob/main/packages/react-reconciler/src/ReactFiberWorkLoop.js) are the two files this guide reads most.
