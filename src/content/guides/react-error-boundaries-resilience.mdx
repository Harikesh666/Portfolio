A dashboard shows ten widgets. One of them reads a field from a user record that has not loaded yet, and the whole page turns white.

```jsx
function ProfileCard({ user }) {
    return <h2>{user.profile.name}</h2>; // TypeError: user.profile is undefined
}

export default function Dashboard({ user }) {
    return (
        <main>
            <Revenue />
            <Signups />
            <ProfileCard user={user} />
        </main>
    );
}
```

One bad read in one widget removed nine healthy ones. The console shows the error, but the user sees a blank screen. Nothing in this code asked React to do that.

This guide shows why React does it, and how an **error boundary** stops it. You will follow a thrown error up the tree to the boundary that catches it, and into the reports React sends. You will also see which errors never reach a boundary, and why.

> Current as of React 19.2 and 19.3. Error boundaries have been stable since React 16. React 19 added the `onCaughtError` and `onUncaughtError` root options and changed how React reports errors.

## 1. Why one render error blanks the whole app

Why not just skip the broken widget and render the other nine? Because React cannot know what else the error broke.

### The short version

When a component throws while React renders it, React's half-built tree is incomplete. React can no longer promise that the screen matches your state. If no error boundary catches the error, React unmounts the whole tree and leaves the container empty.

React chose this on purpose in React 16. Before that, a render error could corrupt React's internal state and leave a wrong UI on screen. A wrong amount or a wrong message recipient is worse than a blank page, because users act on it.

An error boundary is a component that catches errors below it and shows a fallback for that part only. It turns a blank app into one broken widget.

### What React does with an uncaught error

Drop this into any React 19 app.

```jsx
function Boom() {
    throw new Error("boom");
}

export default function App() {
    return (
        <>
            <h1>Healthy heading</h1>
            <Boom />
        </>
    );
}
```

The heading never appears, and the root container ends up empty. In development, the console shows the error once, then a warning like this one.

```text role="output"
Uncaught Error: boom
    at Boom (App.jsx:2)
An error occurred in the <Boom> component.
Consider adding an error boundary to your tree to customize error handling behavior.
```

React 19 empties the container by rendering `null` at the root.

```js
// From createRootErrorUpdate in ReactFiberThrow.js (simplified).
update.payload = { element: null }; // "Unmount the root by rendering null."
update.callback = () => logUncaughtError(root, errorInfo); // calls onUncaughtError
```

So "one component throws, the whole app goes blank" is not a bug. <Mark kind="marker" wraps>React refuses to show a UI it can no longer trust</Mark>.

### Why a blank screen beats a wrong one

React's job is to keep the DOM in sync with your render output. That works only if rendering behaves like a pure function of props and state. A throw breaks that assumption halfway through a render.

React has two choices at that point.

| Choice | Who did it | What the user sees | Risk |
|---|---|---|---|
| Keep the partial UI | React 15 and earlier | Some parts new, some stale | A wrong value the user trusts |
| Unmount everything | React 16 and later | A blank screen | Obvious failure, nothing misleading |

The React 16 announcement gave two examples. In Messenger, a broken UI could send a message to the wrong person. In a payments app, a wrong amount is worse than no amount.

<MarginNote note="a blank screen beats a wrong one">

A blank screen is bad, but it is honestly bad. The user can see that something broke, and nothing on screen invites them to act on stale data.

</MarginNote>

This is the same instinct as a program that stops on a failed assertion instead of running on in an undefined state.

### A boundary is a try/catch for part of the tree

```jsx
class ErrorBoundary extends React.Component {
    state = { error: null };

    static getDerivedStateFromError(error) {
        return { error }; // show the fallback on this render
    }

    componentDidCatch(error, errorInfo) {
        logToService(error, errorInfo.componentStack); // report it
    }

    render() {
        if (this.state.error) return <p>This widget is unavailable.</p>;
        return this.props.children;
    }
}
```

Wrap the risky widget, and only that spot changes.

```jsx
<main>
    <Revenue />
    <Signups />
    <ErrorBoundary>
        <ProfileCard user={user} />
    </ErrorBoundary>
</main>
```

The "try" is rendering the children, and the "catch" is the fallback. A boundary defines a **blast radius**: failures inside it stay inside it, and everything outside keeps working. The fallback is safe to show because you wrote it to be simple and consistent.

So the drastic default protects you wherever you have not thought about failure. A boundary is how you say that you have, and what React should show instead.

### Try it

Render `<Boom />` from above with no boundary and watch the heading vanish. Then wrap `<Boom />` in `ErrorBoundary` and confirm that the heading stays and the fallback appears in its place. This is a browser exercise.

## 2. The two methods: getDerivedStateFromError and componentDidCatch

A boundary needs two methods with long names. Why two, and which one runs when?

React works in two phases. The **render phase** calls your components to compute the new tree, and the **commit phase** applies that tree to the DOM and runs effects. [The rendering guide](/articles/react-rendering-reconciliation-internals) covers both.

### The short version

Catching an error needs two kinds of work, and they belong to two different phases. `static getDerivedStateFromError(error)` runs in the render phase, while React renders the boundary again. It returns the state that switches the boundary to its fallback, so it must be pure.

`componentDidCatch(error, errorInfo)` runs in the commit phase, after the fallback is in the DOM. That is the place for side effects such as logging. Its `errorInfo.componentStack` names the component that threw and every component above it. In practice you define both: one so the user sees a fallback, one so your team hears about it.

### The render-phase half

```jsx
static getDerivedStateFromError(error) {
    return { error }; // merged into state, then render() shows the fallback
}
```

React calls this while it renders the boundary again in the same render pass. The render phase must be pure, because React may run it more than once or throw its result away. In development under Strict Mode, React calls it twice on purpose to expose side effects.

It is `static`, like `getDerivedStateFromProps`. A static method has no `this`, which makes side effects awkward. That keeps the method on one question: given this error, what state shows the fallback?

### The commit-phase half

```jsx
componentDidCatch(error, errorInfo) {
    sendToService({
        message: error.message,
        stack: error.stack,
        componentStack: errorInfo.componentStack,
    }); // a side effect, allowed here in the commit phase
}
```

React calls `componentDidCatch` during the commit, at the same point as `componentDidMount`. The `error` is whatever was thrown. It is usually an `Error`, but JavaScript lets you throw any value, even a string.

### Two stacks, two questions

```text
error.stack                      errorInfo.componentStack
TypeError: Cannot read ...       at ProfileCard (Dashboard.jsx:2)
    at ProfileCard (...)         at ErrorBoundary (ErrorBoundary.jsx:1)
    at renderWithHooks (...)     at main
    at beginWork (...)           at Dashboard (Dashboard.jsx:6)
```

The JavaScript **call stack** tells you which functions ran, including React's own. The **component stack** tells you where in your tree the error happened. For a render error, the component stack is usually the faster clue. Report both. In production, component names are minified, so decode them with source maps like any stack.

<GuideFigure figure="eb-two-methods" />

### One method alone

| Methods defined | What happens on an error |
|---|---|
| Both | Fallback renders at once, `componentDidCatch` logs |
| Only `getDerivedStateFromError` | Fallback renders, nothing is logged by you |
| Only `componentDidCatch` | The boundary renders nothing, then must call `setState` itself |

The last row is the old React 16.0 style.

```jsx
// Deprecated: the boundary shows nothing until componentDidCatch sets state.
componentDidCatch(error) {
    this.setState({ error });
}
```

React renders `null` children first, then a second synchronous render shows the fallback, so users rarely see the empty frame. If `componentDidCatch` does not call `setState`, the boundary swallows the error and shows nothing. In development React then warns: "Error boundaries should implement getDerivedStateFromError()". `getDerivedStateFromError` arrived in React 16.6 to fix all this.

The root options in section 9 receive the same `error` and an `errorInfo` with the same `componentStack`. So the report has one shape at a boundary and at the root.

### Try it

Give the section 1 boundary a `console.log` in each method, then render `<Boom />` inside it. You should see `getDerivedStateFromError` log before `componentDidCatch`. Then print `errorInfo.componentStack` and check that its first line names `Boom`. This is a browser exercise.

## 3. Why boundaries are still classes

Everything else in modern React is a function and a hook. Why does this one feature still need a class?

### The short version

As of React 19.3, React has <Mark kind="circle">no built-in hook</Mark> that catches a child's render error. The only way to define a boundary is a class with `getDerivedStateFromError` or `componentDidCatch`. Boundaries shipped in React 16, before hooks existed in 16.8, and react.dev still says there is no function equivalent "yet".

The usual explanation is that a hook runs inside its own component's render, while a boundary reacts to a different component's failed render. In practice this costs little. You write one small class and reuse it everywhere, or you use the `react-error-boundary` package, whose `<ErrorBoundary>` is a class inside.

### One class, reused

```jsx
// ErrorBoundary.jsx: the one class in the codebase
export class ErrorBoundary extends React.Component {
    state = { error: null };
    static getDerivedStateFromError(error) {
        return { error };
    }
    render() {
        return this.state.error ? this.props.fallback : this.props.children;
    }
}
```

```jsx
<ErrorBoundary fallback={<p>Chart unavailable.</p>}>
    <RevenueChart />
</ErrorBoundary>
```

The class is about ten lines. Every function component in the app can now use it as an ordinary element.

### Why a hook is awkward here

```jsx
// Hypothetical. React has no such hook.
function Panel() {
    const error = useCatchChildError(); // runs while Panel renders
    return error ? <p>Chart unavailable.</p> : <RevenueChart />;
}
```

`RevenueChart` renders only after `Panel` has returned its JSX. By then `Panel`'s hook calls are over, so there is no hook call left to receive the error.

A **fiber** is React's record for one component instance in the tree, with a `return` pointer to its parent. React needs a fiber it can come back to and render again with new state, and a class boundary is that fiber. This is the usual explanation, not an official design note.

### The react-error-boundary package

```jsx
import { ErrorBoundary } from "react-error-boundary";

<ErrorBoundary
    fallbackRender={({ error, resetErrorBoundary }) => (
        <div role="alert">
            <p>{error.message}</p>
            <button onClick={resetErrorBoundary}>Try again</button>
        </div>
    )}
    onError={(error, info) => sendToService(error, info.componentStack)}
>
    <RevenueChart />
</ErrorBoundary>;
```

| Prop or hook | What it does |
|---|---|
| `fallback`, `fallbackRender`, `FallbackComponent` | Three ways to give the fallback UI |
| `onError(error, info)` | Called from its `componentDidCatch`, for logging |
| `resetKeys` | Reset when any listed value changes (section 8) |
| `onReset` | Called when the boundary resets |
| `useErrorBoundary()` | Returns `showBoundary`, `resetBoundary` and `error` (section 7) |

Its source declares `class ErrorBoundary extends Component`. Its README recommends version 5 for runtimes without ES modules.

### Try it

Install `react-error-boundary`, swap your class for its `<ErrorBoundary FallbackComponent={Fallback}>`, and confirm that the behavior matches. Then open `node_modules/react-error-boundary` and find `getDerivedStateFromError` in its built code.

## 4. Throw and unwind: finding the nearest boundary

A component deep in the tree throws, and the right boundary catches it. How does React find that boundary?

### The short version

React renders one fiber at a time inside a loop that catches anything a component throws. When a throw lands, `throwException` in `ReactFiberThrow.js` starts at the thrower's parent and follows `return` pointers up the fiber tree. It stops at the first class fiber that defines `getDerivedStateFromError` or `componentDidCatch`, or at the root as a last resort.

React marks that fiber and queues a capture update on it. Then it unwinds: it walks the same path upward, discards the failed work, and starts rendering again at the boundary in the same render pass. Like `try`/`catch`, the nearest enclosing handler wins, and a boundary never catches its own throw.

### A teaching model of the search

This runs in Node.

```js
// Simplified teaching version of the error path in throwException (ReactFiberThrow.js).
function fiber(name, parent, extra = {}) {
    return { name, return: parent, didCapture: false, ...extra };
}

const root = fiber("HostRoot", null, { isRoot: true });
const app = fiber("App", root);
const boundary = fiber("ErrorBoundary", app, { isBoundary: true });
const card = fiber("ProfileCard", boundary);
const avatar = fiber("Avatar", card);

function findHandler(thrower) {
    let node = thrower.return; // start at the parent, never the thrower
    while (node !== null) {
        if (node.isRoot) return node; // last resort: unmount everything
        if (node.isBoundary && !node.didCapture) return node;
        node = node.return;
    }
}

console.log(findHandler(avatar).name);
console.log(findHandler(boundary).name);
boundary.didCapture = true; // it is already showing its fallback
console.log(findHandler(card).name);
```

```text role="output"
ErrorBoundary
HostRoot
HostRoot
```

Each fiber's `return` pointer leads to its parent, so the walk mirrors an exception bubbling up the call stack. The real loop tests `fiber.tag === ClassComponent` and looks up both methods on the class and its instance.

<GuideFigure figure="react-unwind" />

### The three rules the model shows

| Thrower | Who catches | Why |
|---|---|---|
| `Avatar`, below the boundary | `ErrorBoundary` | The nearest qualifying ancestor |
| The boundary itself | The next boundary up, or the root | The search starts at the thrower's parent |
| The boundary's own fallback | The next boundary up | A boundary already showing its fallback in this render is skipped |

A sibling boundary never catches, because it is not on the upward path. This is why a top-level boundary above your other boundaries matters.

### Mark first, then unwind

The real code makes two passes. The first pass, `throwException`, only marks the boundary. It uses a **lane**, React's label for an update's priority. Each render works on a set of lanes, as [the scheduler guide](/articles/react-scheduler-and-lanes-internals) explains.

```js
// From throwException in ReactFiberThrow.js (simplified).
workInProgress.flags |= ShouldCapture;
const lane = pickArbitraryLane(rootRenderLanes); // a lane from this render
const update = createClassErrorUpdate(lane);
initializeClassErrorUpdate(update, root, workInProgress, errorInfo);
enqueueCapturedUpdate(workInProgress, update);
```

The capture update carries two things. Its payload calls `getDerivedStateFromError(error)`, and its callback calls `componentDidCatch`. Because the lane comes from the current render, no new render is scheduled. `ShouldCapture` is a flag bit on the fiber that means "catch here". Its partner `DidCapture` means "this boundary is already showing its fallback in this render".

The second pass, `unwindUnitOfWork` in `ReactFiberWorkLoop.js`, walks up from the thrower. It calls `unwindWork` on each fiber, which pops anything the fiber pushed, such as context values.

```js
// From unwindWork in ReactFiberUnwindWork.js (simplified).
case ClassComponent: {
    if (workInProgress.flags & ShouldCapture) {
        workInProgress.flags = (workInProgress.flags & ~ShouldCapture) | DidCapture;
        return workInProgress; // begin work again here
    }
    return null; // keep unwinding
}
```

At the marked boundary the walk stops, and React runs the boundary's begin phase again. It processes the capture update, calls `getDerivedStateFromError`, and renders the fallback.

### The failed children are thrown away

When a boundary renders after a capture, React does not reuse its old children.

```js
// From finishClassComponent in ReactFiberBeginWork.js (simplified).
if (current !== null && didCaptureError) {
    forceUnmountCurrentAndReconcile(current, workInProgress, nextChildren, renderLanes);
}
```

The source explains that the normal children and the fallback are two different sets. The half-built subtree never commits. React commits a tree in which the fallback replaces the failed region. The unwind also skips the thrower's remaining siblings, since the fallback replaces them anyway.

## 5. After the catch: one synchronous retry, then commit

The boundary has its fallback. Does React commit it right away?

### The short version

Not quite. Before React looks for a boundary, it records that this render errored. When the render finishes, React 19 renders the whole root once more, synchronously. It includes every pending lane except offscreen work, the hidden content React prerenders in the background.

This retry exists because a concurrent render can read data that changes while it yields, and a clean blocking render may succeed.

If the retry succeeds, React commits the real UI and reports the first error to `onRecoverableError`. If it throws again, React commits the boundary's fallback. So a throwing component renders at least twice, <Mark kind="circle">even in production</Mark>. Errors in effects take a different route: a new synchronous render after the commit.

### A teaching model of the retry

This runs in Node.

```js
// Simplified teaching version of recoverFromConcurrentError (ReactFiberWorkLoop.js).
let calls = 0;
function Flaky() {
    calls += 1;
    if (calls === 1) throw new Error("stale read");
    return "<p>ok</p>";
}

function renderRoot() {
    try {
        return { status: "completed", html: Flaky() };
    } catch (error) {
        return { status: "errored", error };
    }
}

function performWorkOnRoot() {
    let result = renderRoot();
    if (result.status === "errored") {
        const first = result.error;
        result = renderRoot(); // one more try, synchronously, before committing
        if (result.status === "completed") {
            console.log("onRecoverableError:", first.message);
        }
    }
    console.log("commit:", result.html ?? "the boundary fallback");
}

performWorkOnRoot();
```

```text role="output"
onRecoverableError: stale read
commit: <p>ok</p>
```

### What the real code checks

```js
// From performWorkOnRoot in ReactFiberWorkLoop.js, React 19.2 and 19.3 (simplified).
if (exitStatus === RootErrored) {
    const errorRetryLanes = getLanesToRetrySynchronouslyOnError(root, lanes);
    if (errorRetryLanes !== NoLanes) {
        lanes = errorRetryLanes; // every pending lane except OffscreenLane
        exitStatus = recoverFromConcurrentError(root, lanes, errorRetryLanes); // renderRootSync
    }
}
```

React calls `renderDidError` for every ordinary error before the boundary search, so the retry happens even when a boundary caught. It also happens for urgent `SyncLane` renders, not only for time-sliced transitions.

| Retry result | What commits | What React reports |
|---|---|---|
| Succeeds | The real UI | The first error, wrapped, to `onRecoverableError` |
| Throws again | The boundary's fallback | The final error, to `onCaughtError` or `onUncaughtError` |

The wrapped error's message begins "There was an error during concurrent rendering but React was able to recover". The original error sits in `error.cause`.

One guard keeps the retry honest. The source comment gives this case.

```js
use(Promise.resolve("uncached")); // a new promise on every render
throw new Error("Oops!");
```

In the retry, the fresh promise can make the component **suspend**, pausing on data that is not ready, before it reaches the throw. The retry then looks like a success, though the error is only hidden.

React spots this because the retry attached new ping listeners. A **ping** listener is a callback React attaches to a promise so it can render again when the promise settles. React switches the retry off for those lanes until they finish cleanly.

### Errors during the commit

Effects run after the DOM changes, so there is no render to unwind. React catches these errors in the commit code and sends them to `captureCommitPhaseError`.

```js
// Simplified teaching version of captureCommitPhaseError (ReactFiberWorkLoop.js).
function captureCommitPhaseError(sourceFiber, nearestMountedAncestor, error) {
    let node = nearestMountedAncestor;
    while (node !== null) {
        if (node.tag === HostRoot || isErrorBoundary(node)) {
            enqueueUpdate(node, createErrorUpdate(error), SyncLane);
            ensureRootIsScheduled(rootOf(node)); // a new, urgent render shows the fallback
            return;
        }
        node = node.return;
    }
}
```

| Where it threw | How React reaches the boundary |
|---|---|
| Render, constructor, `getDerivedStateFromProps` | The unwind, inside the same render, then one retry |
| `useLayoutEffect`, `useEffect`, a ref callback | A `SyncLane` capture update and a new render |
| `componentDidMount`, `componentDidUpdate`, `componentWillUnmount` | A `SyncLane` capture update and a new render |

React flushes `SyncLane` work without going through the scheduler, as the scheduler guide explains, so the fallback follows the failed commit almost at once.

### Try it

Make a component throw only on its first call, as `Flaky` does, and give the root an `onRecoverableError` that logs. You should see the real content and one recoverable error.

Then make it throw every time. The `getDerivedStateFromError` log should appear twice, once per attempt, or four times under Strict Mode in development. `componentDidCatch` should log once. Don't count the component's own calls, because React also calls it to build stack frames. This is a browser exercise.

## 6. What boundaries catch, and what they miss

You wrapped a component in a boundary, yet an error in its `onClick` sailed straight past. Why?

### The short version

An error boundary catches <Mark kind="marker" wraps>only what React hits while it renders or commits your components</Mark>: render functions, class constructors, lifecycle methods, effects and ref callbacks. Boundaries miss errors in event handlers, timers, promise callbacks and code after an `await`, because those run when React is not building UI.

They also miss errors on the server, and errors in the boundary itself, which go to the next boundary up. React 19 sends an event handler's error to `window.reportError`, so it shows as a global error, not a crash.

Actions, functions you run through `useTransition`, `useActionState` or `<form action>`, are the exception: their errors reach the nearest boundary.

### The table

| Where the error is thrown | Caught by a boundary? | Where it goes instead |
|---|---|---|
| A component's render | Yes | The nearest boundary |
| A class constructor | Yes | The nearest boundary |
| An effect, a ref callback, a class lifecycle | Yes | The nearest boundary, through a new render |
| A React event handler such as `onClick` | No | `window.reportError` |
| `setTimeout`, a `.then` callback, code after `await` | No | An uncaught exception or an unhandled rejection |
| A `useTransition` `startTransition` callback | Yes | The nearest boundary around that component |
| The boundary's own render or fallback | Not by itself | The next boundary up |
| Server rendering | No | The server's `onError` (section 11) |

### Effects are covered

```jsx
function Chart() {
    useEffect(() => {
        throw new Error("chart init failed"); // caught, after the commit
    }, []);
    return <canvas />;
}
```

Many older articles list only "lifecycle methods". Hook effects, layout effects and ref callbacks also take the commit-phase path from section 5. The boundary around `Chart` shows its fallback one synchronous render later.

### Why event handlers are missed

```jsx
function SaveButton() {
    return (
        <button
            onClick={() => {
                throw new Error("save failed"); // no boundary sees this
            }}
        >
            Save
        </button>
    );
}
```

By the time you click, React has already rendered and committed the button. The handler runs during event dispatch, not during a render, so there is nothing to unwind.

<MarginNote note="no render running, so nothing to unwind">

The screen was consistent before the handler ran, and it is still consistent after. The handler may leave your own state half updated, but React has no broken tree to replace.

</MarginNote>

React 19 still catches the error. Its dispatcher wraps each listener.

```js
// From executeDispatch in DOMPluginEventSystem.js, React 19.
try {
    listener(event);
} catch (error) {
    reportGlobalError(error); // window.reportError, then the next listener runs
}
```

So the error fires a global `error` event on `window`. It never reaches a boundary and never calls `onUncaughtError`. A plain `addEventListener` handler you attach yourself behaves like any JavaScript listener.

### Why async code is missed

```jsx
useEffect(() => {
    fetchUser(id).then((user) => {
        setUser(user.profile.name); // throws later, outside any render
    });
}, [id]);
```

The effect body ran inside React's commit, but the `.then` callback runs on a later microtask. React is not involved in running it, so a throw there becomes an **unhandled rejection**, a rejected promise with no handler. Only a global listener sees it.

```js
window.addEventListener("unhandledrejection", (event) => {
    report("async", event.reason); // errors from promise callbacks land here
});
```

### Try it

Wrap `SaveButton` in a boundary and add `window.addEventListener("error", (e) => console.log("global:", e.error.message))`. Click the button. You should see "global: save failed" and no fallback. Now move the `throw` into the component body, and the fallback should appear. This is a browser exercise.

## 7. Errors outside render: handle locally or forward

Handler and async errors need your help. When should you show an inline message, and when should a boundary take over?

### The short version

Most handler and async errors are local and recoverable: a failed save, a network blip, a bad input. Catch them with `try`/`catch`, store a message in state, and offer a retry. The user keeps their context.

Some failures are fatal for a region, and should look like a render crash. Forward those into a boundary by storing the error in state and throwing it during the next render. `showBoundary` from `react-error-boundary` does exactly that.

React 19 Actions forward for you. An **Action** is a function, often async, that you pass to a transition or a form. Errors from a `useTransition` callback, a `useActionState` action or a `<form action>` reach the nearest boundary with no extra code.

### Local handling

```jsx
async function handleSave() {
    try {
        await saveToServer(draft);
    } catch (err) {
        setSaveError(err.message); // inline "Save failed. Retry?"
    }
}
```

This is the right default. A whole-region fallback would throw away the user's draft for a failure that one retry may fix.

### Forwarding by throwing during render

```jsx
function ReportPanel() {
    const [error, setError] = useState(null);
    if (error) throw error; // this render throws, so the unwind finds a boundary

    async function handleLoad() {
        try {
            await loadCriticalReport();
        } catch (e) {
            setError(e); // schedules the render that throws
        }
    }

    return <button onClick={handleLoad}>Load report</button>;
}
```

Setting state schedules a render. That render throws, and a render error is exactly what boundaries catch. You have turned an async error into a render error.

<GuideFigure figure="eb-forwarding" />

### showBoundary does the same dance

```jsx
import { useErrorBoundary } from "react-error-boundary";

function ReportPanel() {
    const { showBoundary } = useErrorBoundary();

    async function handleLoad() {
        try {
            await loadCriticalReport();
        } catch (e) {
            showBoundary(e); // the nearest react-error-boundary shows its fallback
        }
    }

    return <button onClick={handleLoad}>Load report</button>;
}
```

The hook's source calls `setState({ error, hasError: true })`, then throws `state.error` during render. It must sit inside a `react-error-boundary` `<ErrorBoundary>`.

### Actions forward for you

```jsx
function AddComment() {
    const [isPending, startTransition] = useTransition();
    return (
        <button
            disabled={isPending}
            onClick={() =>
                startTransition(async () => {
                    await postComment(); // a rejection here reaches the boundary
                })
            }
        >
            Post
        </button>
    );
}
```

React catches the throw or the rejection inside its `startTransition`. It stores a rejected thenable in the hook's pending state, so the next render of `AddComment` rethrows the error. A boundary around `AddComment` then shows its fallback.

| API | On a throw or rejection |
|---|---|
| `startTransition` from `useTransition` | The nearest boundary around the component |
| A `useActionState` action | The nearest boundary, and React cancels the queued actions |
| A `<form action={fn}>` function | The nearest boundary around the form |
| `startTransition` imported from `react` | `window.reportError` only, because no hook can rethrow it |
| `useOptimistic` | The optimistic value reverts when the transition ends |

A form works the same way, because React runs its `action` in a transition.

```jsx
<ErrorBoundary fallback={<p>Could not send your message.</p>}>
    <form action={async (formData) => await sendMessage(formData)}>
        <input name="text" />
        <button>Send</button>
    </form>
</ErrorBoundary>
```

So an action should throw only for failures it cannot handle. Return expected ones, such as a validation error, as state.

```jsx
const [state, submit, isPending] = useActionState(async (previous, formData) => {
    const qty = Number(formData.get("qty"));
    if (!Number.isInteger(qty)) return { error: "Enter a whole number." }; // expected: show inline
    await updateCart(qty); // unexpected failure: throws, and the boundary takes over
    return { error: null };
}, { error: null });
```

When an action throws, React rejects every action still waiting in the queue and stops running new ones. The error boundary's reset is how the user starts again.

## 8. Resetting a boundary

Once a boundary shows its fallback, it stays there. How do you get the real content back without reloading the page?

### The short version

A boundary renders its fallback until you clear its error state. There are three ways. A "try again" button can call `setState` to clear the error. `react-error-boundary` can reset itself when a value in its `resetKeys` array changes. Or you can change the boundary's `key`, which remounts it and its whole subtree with fresh state.

The danger is resetting into the same conditions. The child throws again, the boundary catches again, and the screen flickers forever. That is <Mark kind="underline">an infinite error-reset loop</Mark>. So tie every reset to a change, such as a new input, a new route, or data that has arrived.

### A manual reset

```jsx
class ErrorBoundary extends React.Component {
    state = { error: null };
    static getDerivedStateFromError(error) {
        return { error };
    }
    reset = () => this.setState({ error: null }); // render the children again
    render() {
        if (this.state.error) return <Fallback onRetry={this.reset} />;
        return this.props.children;
    }
}
```

The next render returns the children, and React tries them again. `react-error-boundary` passes the same function to your fallback as `resetErrorBoundary`.

### resetKeys

```jsx
<ErrorBoundary FallbackComponent={Fallback} resetKeys={[userId]}>
    <UserProfile userId={userId} />
</ErrorBoundary>
```

If the profile for one `userId` throws and the user picks another, the boundary resets and renders the new profile. The library compares the keys after each update, and this runs in Node.

```js
// The comparison react-error-boundary runs on resetKeys after each update.
function hasArrayChanged(a = [], b = []) {
    return a.length !== b.length || a.some((item, index) => !Object.is(item, b[index]));
}

console.log(hasArrayChanged([42], [42])); // same userId
console.log(hasArrayChanged([42], [43])); // a new userId
console.log(hasArrayChanged([{ id: 42 }], [{ id: 42 }])); // a new object every render
console.log(hasArrayChanged([NaN], [NaN])); // Object.is treats NaN as equal
```

```text role="output"
false
true
true
false
```

The third line is a trap. An object literal in `resetKeys` is new on every render, so any re-render resets the boundary and can start the loop. Pass primitive values.

The library also skips the check on the first update after an error. So a key that changed in the same update as the error does not reset the boundary at once.

### A key remount

```jsx
<ErrorBoundary key={location.pathname} fallback={<RouteError />}>
    <Outlet />
</ErrorBoundary>
```

A new `key` tells React this is a different element, so it unmounts the old boundary and mounts a fresh one. All state in the subtree resets, not just the error. It is heavier, but it guarantees a clean start.

<GuideFigure figure="eb-reset" />

### Choosing a reset

| Kind of error | Good reset | Why |
|---|---|---|
| Transient, such as a network blip | A "try again" button | The outside world may have changed |
| Tied to an input, such as a bad `userId` | `resetKeys` on that input | The next render has different inputs |
| A whole route failed | A `key` on the route path | Navigation is the change |
| Deterministic, such as a null read on every render | None. Fix the code | Any reset just throws again |

A blind loop also floods your error service with the same report many times a second. Designing recovery means deciding which change makes a retry worth trying, then resetting on that change.

### Try it

Make a child throw when a `mode` prop is `"bad"`. Click "try again" with the prop unchanged, and the fallback returns at once. Add `resetKeys={[mode]}`, switch the prop to `"good"`, and the boundary should recover by itself.

Then simulate a transient error. Make a child throw while a global `window.failing` flag is true, and set the flag to false from the console. "Try again" should now recover, because the outside world changed. This is a browser exercise.

## 9. The React 19 root options and console reporting

Boundaries decide what the user sees. Where do you put the code that tells your team?

### The short version

React 19 gives `createRoot` and `hydrateRoot` three callbacks, each called with the `error` and an `errorInfo` holding `componentStack`. `onCaughtError` runs when a boundary caught the error. `onUncaughtError` runs when none did and React unmounted the tree. `onRecoverableError` runs when React fixed the problem itself.

Recoverable cases include a successful retry and a hydration mismatch, where server HTML differs from the client's first render (section 11).

Each callback replaces a default. By default, caught errors go to `console.error`, while uncaught and recoverable errors go to `window.reportError`. React 19 also stopped re-throwing render errors, so one caught error now logs once, where React 18 printed three errors in development.

### Wiring the three callbacks

```jsx
import { createRoot } from "react-dom/client";

const root = createRoot(document.getElementById("root"), {
    onCaughtError(error, errorInfo) {
        report("caught", error, errorInfo.componentStack); // a boundary showed a fallback
    },
    onUncaughtError(error, errorInfo) {
        report("uncaught", error, errorInfo.componentStack); // the app went blank: alert
    },
    onRecoverableError(error, errorInfo) {
        report("recoverable", error.cause ?? error, errorInfo.componentStack);
    },
});
root.render(<App />);
```

<MarginNote note="report at the root, recover in the tree">

The root options never show a fallback. Boundaries still decide the UI for each region, and the root gives you one place to report every error.

</MarginNote>

### When each one fires

| Callback | Fires when | Default without it |
|---|---|---|
| `onCaughtError` | A boundary caught a render or commit error | `console.error` |
| `onUncaughtError` | No boundary caught it, and the root rendered `null` | `window.reportError`, plus a development `console.warn` |
| `onRecoverableError` | React recovered without your help | `window.reportError` |

`onCaughtError` runs just before the boundary's `componentDidCatch`, from the same commit callback. Its `errorInfo` also carries `errorBoundary`, the boundary instance, which tells you which region failed.

```js
onCaughtError(error, { componentStack, errorBoundary }) {
    report("caught", error, componentStack, errorBoundary?.constructor.name); // minified in production builds
},
```

Recoverable errors often wrap the original in `error.cause`. The same options work on `hydrateRoot`, where `onRecoverableError` matters most.

```js
hydrateRoot(document, <App />, { onRecoverableError, onCaughtError, onUncaughtError });
```

### What changed in React 19

```text
React 18, one caught error:
  Uncaught Error: hit                      (thrown)
  Uncaught Error: hit                      (thrown again after recovery failed)
  The above error occurred in the Throws component ...

React 19, one caught error:
  Error: hit
  The above error occurred in the Throws component ...
  React will try to recreate this component tree from scratch using the error boundary you provided, ErrorBoundary.
```

React 18 re-threw render errors so they reached global handlers. React 19 reports instead. **`window.reportError`** is a browser API that fires a global `error` event as if the error were uncaught, without unwinding any stack.

```js
// Paste into a browser console.
window.addEventListener("error", (event) => console.log("saw:", event.error.message));
reportError(new Error("hello"));
```

You should see "saw: hello", followed by the browser's own uncaught-error line. If your production reporting relied on re-thrown errors, move it to these callbacks. React 19 also removed a development-only replay that made caught errors reach `window` error listeners.

### Overriding a default

Providing a callback replaces React's logging for that category. Without care, caught errors can vanish from the console during development.

```jsx
onCaughtError(error, errorInfo) {
    if (import.meta.env.DEV) console.error(error, errorInfo.componentStack); // keep it visible
    report("caught", error, errorInfo.componentStack);
},
```

A monitoring SDK may provide a helper for these options. If you use one, check that it keeps the development logging you rely on. Inside `act` in tests, React rethrows uncaught errors into the test instead.

### Try it

Then adapt `Flaky` from section 5 to return `<p>ok</p>` as JSX, and `onRecoverableError` should fire while the content renders. This is a browser exercise.

## 10. Errors and Suspense: one unwind, two thrown values

A loading spinner and an error fallback look like different features. Why do they behave so alike?

### The short version

Both are the same mechanism. A component throws, React catches the throw in its work loop, and `throwException` walks up to the nearest boundary that handles that kind of value. The first check is whether the value has a `then` method.

A **thenable** (a promise-like object) means "not ready", so React finds the nearest `<Suspense>` boundary and shows its fallback temporarily. React retries when the promise settles, on a retry lane.

Anything else means "broken", so React finds the nearest error boundary and keeps its fallback until a reset. A rejected promise read with `use()` throws its reason, which takes the error path.

### The first branch

This runs in Node.

```js
// Simplified teaching version of the first check in throwException.
function route(value) {
    if (value !== null && typeof value === "object" && typeof value.then === "function") {
        return "Suspense path: show the nearest fallback, retry when it settles";
    }
    return "error path: find the nearest error boundary";
}

console.log(route(new Promise(() => {})));
console.log(route(new Error("boom")));
console.log(route("a thrown string"));
```

```text role="output"
Suspense path: show the nearest fallback, retry when it settles
error path: find the nearest error boundary
error path: find the nearest error boundary
```

In React 19, `use()` does not throw your promise directly. It throws an internal `SuspenseException`, and the work loop swaps in the tracked thenable before calling `throwException`. Throwing a raw promise still works, but React treats it as the deprecated pattern.

`use()` is not the only way in. A `React.lazy` component whose code has not loaded reaches the same branch, because React unwraps it as if it had called `use()`. Suspense-enabled data libraries, such as TanStack Query's `useSuspenseQuery`, get there too. A lazy import that fails throws its error, which takes the error path.

```jsx
const Chart = lazy(() => import("./Chart.jsx")); // loading: suspends. failed import: error boundary
```

### Side by side

| | Error boundary | Suspense boundary |
|---|---|---|
| Thrown value | Anything without `then` | A thenable |
| Boundary searched for | A class with `getDerivedStateFromError` or `componentDidCatch` | The nearest `<Suspense>` |
| Fallback lasts | Until you reset it | Until the promise settles |
| Follow-up | One synchronous retry, then commit | A ping or a retry-lane render |
| Siblings of the thrower | Skipped | Skipped now, prerendered later |

<Mark kind="marker" wraps>Same unwind, different thrown value, different follow-up</Mark>. An error will not fix itself, so React does not retry after it commits the fallback.

A promise will settle, so React stores it on the Suspense boundary and attaches a ping listener. Retry lanes are never forced to finish synchronously, and React renders them in small slices that yield to the browser, as the scheduler guide explains.

### Pairing the two boundaries

```jsx
<ErrorBoundary fallback={<p>Could not load comments.</p>}>
    <Suspense fallback={<Spinner />}>
        <Comments postId={id} />
    </Suspense>
</ErrorBoundary>
```

`Comments` can throw two kinds of value, and each boundary catches its own kind. Put the error boundary outside, so a failed fetch replaces the spinner too. The data-fetching guide's `useSuspenseQuery` example uses this pair.

```jsx
function Comments({ postId }) {
    const comments = use(fetchComments(postId)); // pending: suspends. rejected: throws the reason
    return comments.map((c) => <p key={c.id}>{c.text}</p>);
}
```

Cache the promise from `fetchComments`. A promise created during render is new on every attempt, so React can never reuse the one it waited for.

`<Activity mode="hidden">` keeps a subtree mounted but hidden, and React prerenders it in the background. In React 19.3, an error inside a hidden `<Activity>` aborts that prerender instead of escaping into the visible UI. The error surfaces at the nearest boundary when the Activity becomes visible. React 19.2 has no such guard.

The promise side goes much deeper: pings, retries, fallback throttling, transitions that avoid fallbacks, and reveal order. [The Suspense guide](/articles/react-suspense-internals) covers it.

### Try it

Make `fetchComments` reject after one second, and wrap `Comments` as above. You should see the spinner, then the error fallback. Make it resolve instead, and the comments replace the spinner. This is a browser exercise.

## 11. Server rendering, hydration and recoverable errors

Your app renders on the server first. What happens to a throw there, and what are those hydration warnings?

### The short version

Error boundaries do not run on the server. If a component throws inside a `<Suspense>` boundary, the server sends that boundary's fallback HTML, calls your `onError`, and leaves the client to retry. If the client render succeeds, the user never knows, and `onRecoverableError` fires. A throw in the shell, outside every Suspense boundary, fires `onShellError` as well as `onError`.

On the client, **hydration** attaches React to the server's HTML instead of rebuilding it. If the client's first render differs, the mismatch is recoverable. React throws away the server HTML up to the nearest Suspense boundary, renders that part on the client, and reports it.

### Errors on the server

```js
import { renderToPipeableStream } from "react-dom/server";

let didError = false;
const { pipe } = renderToPipeableStream(<App />, {
    onShellReady() {
        res.statusCode = didError ? 500 : 200;
        pipe(res);
    },
    onShellError() {
        res.statusCode = 500;
        res.send("<h1>Something went wrong</h1>"); // nothing streamed yet
    },
    onError(error) {
        didError = true;
        console.error(error); // keep logging if you override it
    },
});
```

| Where the server render throws | What the server sends | What the client does |
|---|---|---|
| In the shell | Your `onShellError` document | Nothing to hydrate |
| Inside a `<Suspense>` boundary | That boundary's fallback HTML | Renders it on the client, then reports a recoverable error |

Streaming SSR works in Suspense-boundary units. The server sends each boundary's fallback first and streams the real content in as it finishes. That is why a server error inside a boundary costs only that boundary.

```jsx
<Layout> {/* the shell: a throw here fires onShellError */}
    <Suspense fallback={<PostsSkeleton />}>
        <Posts /> {/* a throw here: skeleton HTML, then the client retries */}
    </Suspense>
</Layout>
```

In production, React hides the server's message from the browser. The client's recoverable error says only "The server could not finish this Suspense boundary", with no details. In development it carries the server's real message.

An optional `digest` string returned from `onError` links the two logs. In React 19, read it as `error.digest`, because `errorInfo.digest` was removed.

### Hydration mismatches

```jsx
function Clock() {
    return <p>{new Date().toLocaleTimeString()}</p>; // differs between server and client
}
```

The server and the browser read the clock at different moments, so the text differs. React 19 reports "Hydration failed because the server rendered text didn't match the client".

| Cause | Fix |
|---|---|
| `Date.now()`, `Math.random()` | Compute once on the server and pass it down |
| `typeof window !== "undefined"` branches | Render the same first, then update in an effect |
| Locale date formatting | Format with a fixed locale and time zone |
| Invalid HTML nesting, such as a `<div>` in a `<p>` | Fix the markup |
| A browser extension edits the page | Often ignorable. React 19 skips unexpected tags in `<head>` and `<body>` |

Since React 18, React no longer patches single nodes. It client-renders from the nearest `<Suspense>` boundary, or the whole root if there is none. So a mismatch costs you the server HTML for that region, and placing Suspense boundaries limits the damage.

### Errors thrown while hydrating

Any error during hydration takes the same route first. React marks the nearest Suspense boundary for client rendering and queues a recoverable error. Its message begins "There was an error while hydrating but React was able to recover", and the original error is its `cause`. An error boundary steps in only if the client render throws too.

For one unavoidable difference, such as a timestamp, mark that element.

```jsx
<time dateTime={iso} suppressHydrationWarning>
    {new Date(iso).toLocaleTimeString()}
</time>
```

`suppressHydrationWarning` silences the warning for that element's own text and attributes, one level deep. React does not patch the mismatched text, so use it only where the difference does not matter.

### Try it

In a server-rendered app, render `Math.random()` in a component and load the page. The console should show the hydration error, and an `onRecoverableError` callback on `hydrateRoot` should fire while the page keeps working. Move the value into an effect, and both should disappear. This needs a real server-rendered app.

## 12. Where to put boundaries

You know how boundaries work. Where should they go in a real app?

### The short version

Place boundaries by blast radius. Ask for each region: if this breaks, what is the smallest sensible thing to take down, and what must keep working?

A good layout has three layers. A top-level boundary means no failure ever leaves a white screen. Route and section boundaries keep one broken feature from taking down its neighbors. Tight boundaries guard the parts you trust least.

The trade-off is granularity. Too few boundaries and one failure removes too much. Too many and one bad response fills the page with tiny "something went wrong" boxes, which confuses users more than one clear message.

### The layers

```jsx
<ErrorBoundary fallback={<CrashPage />}>                 {/* 1. the net */}
    <Shell>
        <ErrorBoundary key={pathname} fallback={<RouteError />}>   {/* 2. the route */}
            <Dashboard>
                {widgets.map((w) => (
                    <ErrorBoundary key={w.id} fallback={<WidgetDown name={w.name} />}>  {/* 3. a widget */}
                        <Widget config={w} />
                    </ErrorBoundary>
                ))}
            </Dashboard>
        </ErrorBoundary>
    </Shell>
</ErrorBoundary>
```

| Layer | Where | What it buys | Pair it with |
|---|---|---|---|
| Top-level net | Around the whole app | A designed error page, never a blank screen | `onCaughtError`, since the net turns crashes into caught errors |
| Route or section | Each route, panel or dashboard widget | One broken feature, the rest still works | A `key` or `resetKeys` for recovery |
| Risky component | Third-party widgets, user-supplied data, experiments, past crash sites | A tight, specific fallback | Logging, since these fail more |

With a net in place, `onUncaughtError` fires only when the net itself, or something above it, fails. Treat it as an alarm.

Every app needs the net. The route and section layer gives most apps the biggest win. The React 16 announcement describes Messenger wrapping its sidebar, info panel, conversation log and message input in separate boundaries.

For the third layer, a small wrapper keeps risky parts uniform.

```jsx
function Guarded({ name, children }) {
    return (
        <ErrorBoundary fallback={<p>{name} is unavailable right now.</p>}>
            {children}
        </ErrorBoundary>
    );
}

<Guarded name="Map">
    <ThirdPartyMap center={office} />
</Guarded>;
```

<MarginNote note="ask what should still work when this breaks">

If the answer is "everything else on the page", the region deserves its own boundary. If the answer is "nothing useful", let the error reach the boundary above it.

</MarginNote>

### Granularity

Below the level of a separable region, boundaries hurt more than they help. A list where each item has its own boundary turns one bad API response into fifty broken rows. Put the boundary around the list, and show one clear message.

Match boundaries to data. Regions that load from separate sources fail independently, so they make natural boundary units. Suspense boundaries often sit at the same seams, which is why the pair from section 10 is so common.

Give every fallback a way forward, such as a retry button or a link home, wired to a reset from section 8. Keep reporting at the root, so adding or moving a boundary never changes what your team sees.

### Frameworks

```jsx
// app/dashboard/error.js in the Next.js App Router
"use client"; // error boundaries must be Client Components

export default function Error({ error }) {
    const message = error instanceof Error ? error.message : String(error);
    return <p>Dashboard failed: {message}</p>;
}
```

Next.js wraps each route segment in a boundary built from your `error.js`. Its docs type `error` as `unknown`, so narrow it first. In production, Server Component errors arrive with a generic message and a `digest`.

Frameworks also implement `redirect()` and `notFound()` by throwing special errors. A hand-written boundary can catch those by mistake, so prefer the framework's own boundary inside its routes.

### Try it

Take a screen with several independent regions. Add a top-level boundary, then one per region. Make one region throw and confirm that only it shows a fallback. Remove the region boundaries, and the whole screen should drop to the top-level fallback. This is a browser exercise.

## 13. Debugging errors, and reading the source

Something went wrong in production. How do you go from the symptom to the mechanism, fast?

### The short version

First find what threw and where it ran: a render, an effect, an event handler, async code, or hydration. That tells you whether a boundary could ever catch it. Then check that a boundary sat above the thrower, and that the boundary's own render could not throw.

Read `errorInfo.componentStack` from `componentDidCatch` or a root callback to locate the component. In development, React 19.1 added owner stacks, which name the components that rendered the failing one. Then fix the cause, or tie the reset to a real change. Most symptoms map to one row of the table below.

### Symptoms and mechanisms

| Symptom | Likely mechanism | Fix |
|---|---|---|
| The whole app goes white | No boundary above the throw, or the boundary threw | Add a top-level net, and keep fallbacks simple |
| A boundary ignored an error | It came from a handler or async code | Handle it locally, or forward it (section 7) |
| A boundary ignored an error from a child | The boundary is a sibling, not an ancestor | Move it above the thrower |
| The fallback flickers | A reset into the same conditions | Reset only on a change (section 8) |
| A render ran twice in production | The synchronous retry after an error | Expected. Look for the real error |
| A recoverable error you never threw | A hydration mismatch or a successful retry | Read `error.cause`, fix the difference |
| Caught errors no longer reach `window.onerror` in development | React 19 removed the development replay that re-threw them | Report from `onCaughtError` |

### Two stacks in development

```jsx
import * as React from "react"; // a namespace import, so production builds do not break

function ProfileCard({ user }) {
    if (!user.profile && process.env.NODE_ENV !== "production") {
        console.log(React.captureOwnerStack()); // development only. Not exported in production builds
    }
    return <h2>{user.profile?.name}</h2>;
}
```

The component stack lists parents in the tree. React builds it by walking `return` pointers from the failing fiber, which is why it mirrors your tree rather than the call stack. The owner stack lists the components that created this element and passed its props, which is often where bad data came from.

Owner stacks exist only in development. Production builds do not export `captureOwnerStack` at all, so a named import would be `undefined` and calling it would throw. Guard the call and use a namespace import, as above.

React DevTools helps too. Its Components panel has a button that forces the selected component into an errored state. That tests a boundary's fallback and reset without editing any code.

### Reading the source

Paths are relative to `packages/` in the React repository.

| File | What to look for |
|---|---|

## The whole thing in one list

1. With no boundary, a render error makes React render `null` at the root, because a wrong UI is worse than a blank one.
2. A boundary is a class: `getDerivedStateFromError` picks the fallback in the render phase, and `componentDidCatch` logs in the commit phase.
3. `throwException` searches up from the thrower's parent for the nearest boundary, marks it, and the unwind re-renders it in the same pass.
4. A boundary never catches its own throw or its own fallback's throw, so keep a top-level boundary above the others.
5. After any render error, React 19 renders the whole root once more, synchronously, and commits the fallback only if that also fails.
6. Boundaries catch errors in render, constructors, lifecycles, effects and refs, but not handlers, async code or the server.
7. React 19 sends event handler errors to `window.reportError`, while errors from `useTransition`, `useActionState` and `<form action>` Actions reach the nearest boundary.
8. Reset with state, `resetKeys` or a `key`, and always tie the reset to a change.
9. `onCaughtError`, `onUncaughtError` and `onRecoverableError` centralize reporting, and React 19 no longer re-throws render errors.
10. Suspense uses the same unwind: a thenable gets a temporary fallback and a retry, while anything else gets an error boundary.

## Further reading

### Error boundaries in the React docs

The [`Component` reference](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary) documents `getDerivedStateFromError`, `componentDidCatch` and the list of errors boundaries miss.

### The root options

The [`createRoot` reference](https://react.dev/reference/react-dom/client/createRoot) and the [`hydrateRoot` reference](https://react.dev/reference/react-dom/client/hydrateRoot) document `onCaughtError`, `onUncaughtError` and `onRecoverableError`, and the hydration rules.

### What React 19 changed

The [React 19 release post](https://react.dev/blog/2024/12/05/react-19) shows the new console output, and the [React 19 upgrade guide](https://react.dev/blog/2024/04/25/react-19-upgrade-guide) explains why errors are no longer re-thrown.

### Why React unmounts on an error

[Error Handling in React 16](https://legacy.reactjs.org/blog/2017/07/26/error-handling-in-react-16.html) is the original announcement, with the Messenger and payments reasoning.

### Actions and server errors

The [`useTransition` reference](https://react.dev/reference/react/useTransition) covers errors in transitions, and [`renderToPipeableStream`](https://react.dev/reference/react-dom/server/renderToPipeableStream) covers errors inside and outside the shell.

### The library and the source

[`react-error-boundary`](https://github.com/bvaughn/react-error-boundary) is the de facto boundary library. [ReactFiberThrow.js](https://github.com/facebook/react/blob/main/packages/react-reconciler/src/ReactFiberThrow.js) and [ReactFiberErrorLogger.js](https://github.com/facebook/react/blob/main/packages/react-reconciler/src/ReactFiberErrorLogger.js) are the two files this guide reads most.

### reportError on MDN

MDN's [`reportError`](https://developer.mozilla.org/en-US/docs/Web/API/Window/reportError) page explains the global error event that React 19 uses for uncaught errors.
