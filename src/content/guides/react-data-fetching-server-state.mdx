A profile page shows the user's name in the header and again in the main panel. Each component fetches it the way most of us first learned.

```jsx
function HeaderName({ id }) {
    const [user, setUser] = useState(null);

    useEffect(() => {
        fetchUser(id).then(setUser);
    }, [id]);

    return user ? <span>{user.name}</span> : <Spinner />;
}
```

The page fires two identical requests. Navigate away and back, and both spinners return. Save a new name in the panel, and the header keeps the old one until a reload. Nothing here is a typo. The code stores a copy of server data in component state, and component state cannot do what that copy needs.

This guide shows why fetched data is a **cache**, and what a cache needs that component state lacks. TanStack Query v5 is the working example, and the guide reads its source where the behavior matters.

> Current as of React 19.2 and 19.3, and TanStack Query v5 (5.108). The React adapter, `@tanstack/react-query`, is still v5. Only the Svelte packages and the Vue Devtools have moved to v6.

## 1. Server state is a cache, not state

The opening code works hard to keep a copy in step with a server it does not control. It writes cache logic without calling it that.

### The short version

Start from one blunt claim: <Mark kind="marker" wraps>the data you fetch from a server is not your application's state</Mark>. It is a cache, a local copy of data whose real home is the server. That one fact explains everything a server-state tool does.

A cache can go stale, because the real data changes. It is shared by many components, owned elsewhere so you do not control when it changes, and loaded asynchronously. A server-state library is a cache manager. It handles freshness, sharing and synchronization, so you stop building them on top of `useState`.

### Two kinds of state

| | Client state | Server state |
|---|---|---|
| Examples | A modal is open, a form draft, a selected tab | A user, a list of todos, search results |
| Who owns it | Your app | The server |
| How you get it | Synchronously, you set it | Asynchronously, over the network |
| Can it go stale? | No, your copy is the truth | Yes, the server can change it at any time |
| Who else needs it | Usually one part of the tree | Often many distant components |

Client state is a single source of truth. Server state is a copy of someone else's truth.

### Every cache needs a policy

```js
let serverName = "Ada"; // the real home of the data
const fetchUser = async (id) => ({ id, name: serverName });

const cache = new Map();
async function getUser(id) {
    if (!cache.has(id)) cache.set(id, await fetchUser(id));
    return cache.get(id); // fast, but how old is it?
}

console.log((await getUser(5)).name);
serverName = "Grace"; // someone renames the user on the server
console.log((await getUser(5)).name);
```

```text role="output"
Ada
Ada
```

Your browser's HTTP cache copies files from a server, and a CPU cache copies main memory. Each copy is fast to read but can drift from the source. So every cache needs a policy for when to trust the copy.

The toy has no policy, so it serves "Ada" forever. "When do I trust the cached copy?" is the question `staleTime` answers in section 5. The `useState` approach has no answer at all.

### What a cache manager must do

Once fetched data is a cache, the list of jobs writes itself. The second column shows what goes wrong when component state plays the cache, as in the opening code.

| The cache needs | Without it, in component state | TanStack Query's answer | Section |
|---|---|---|---|
| An address | Nothing to share or invalidate by | The query key | 3 |
| A status model | `isLoading` and `error` flags that can contradict each other | `status` and `fetchStatus` | 4 |
| A freshness policy | No rule for when to trust the copy | `staleTime` | 5 |
| A retention policy | Navigate away and back, and the spinner returns, because the state died with the component | `gcTime` | 6 |
| Sharing | Three components needing user 5 fire three requests | One entry per key | 7 |
| Background sync | Tab away for ten minutes and the copy is silently old, unless you hand-wire focus listeners and polling | Refetch triggers | 8 |
| A write story | After a save, every holder of the old data is wrong, so you thread refetch callbacks or lift state | Mutations and invalidation | 11 |

Lifting state, Context and global client stores are not on the list, because a cache is not client state. Moving server state out also shrinks your real client state, often to a few small UI flags.

TanStack Query, formerly React Query, is the reference here. SWR and RTK Query follow the same model: a keyed cache, stale-while-revalidate (section 5), deduplication, background sync and invalidation.

### Try it

Save the toy cache as `cache.mjs` and give it a policy: store `fetchedAt` with each entry and refetch when the copy is older than 1,000ms.

```js
const staleTime = 1000;
async function getUser(id) {
    const entry = cache.get(id);
    if (!entry || Date.now() - entry.fetchedAt >= staleTime) {
        cache.set(id, { data: await fetchUser(id), fetchedAt: Date.now() });
    }
    return cache.get(id).data;
}
```

Read the user, rename it on the "server", read again, wait one second, and read once more. You should see `Ada`, `Ada`, `Grace`. You just wrote a freshness policy.

## 2. Why useEffect and useState is the wrong tool

An effect that stores its result in state works for one screen, then collapses under races and repetition.

### The short version

Fetching in `useEffect` is not wrong because effects cannot fetch. It is wrong because the result lands in component-local state, and local state is not a shared cache. That one limit forces you to rebuild what a cache provides: status flags, race handling, deduplication, caching across mounts and background refetching.

You rebuild it in every component that fetches. A race shows the cost: type "a" then "ab", and if the slower "a" response lands last, it overwrites the right answer. A server-state library replaces all of this with one shared cache.

### The manual fetch

```jsx
function User({ id }) {
    const [data, setData] = useState(null);
    const [isLoading, setIsLoading] = useState(true);
    const [error, setError] = useState(null);

    useEffect(() => {
        let ignore = false; // the race guard
        setIsLoading(true);
        setError(null);
        fetchUser(id)
            .then((d) => {
                if (!ignore) {
                    setData(d);
                    setIsLoading(false);
                }
            })
            .catch((e) => {
                if (!ignore) {
                    setError(e);
                    setIsLoading(false);
                }
            });
        return () => {
            ignore = true; // cleanup drops the stale response
        };
    }, [id]);
    // ...
}
```

This is correct manual code, and it already carries a lot. Three pieces of state form a "boolean soup", where nothing stops `isLoading` and `error` from contradicting each other. The `ignore` flag guards against a race.

### The race the ignore flag stops

Run this in Node. Two requests start, and the first one is slower.

```js
const delays = { a: 300, ab: 100 };

function fakeSearch(q) {
    return new Promise((resolve) => setTimeout(() => resolve(`results for "${q}"`), delays[q]));
}

// The user types "a", then "ab". Each keystroke starts a request.
for (const q of ["a", "ab"]) {
    fakeSearch(q).then((r) => console.log("showing", r));
}
```

```text role="output"
showing results for "ab"
showing results for "a"
```

The screen ends on the results for "a", which is wrong. React runs an effect's cleanup before the next effect, so a flag set in cleanup marks the old request as stale. Add this below the race snippet, replacing its loop.

```js
let cleanupPrevious = () => {};

function runEffect(q) {
    cleanupPrevious(); // React runs the old effect's cleanup first
    let ignore = false;
    fakeSearch(q).then((r) => {
        if (!ignore) console.log("showing", r);
    });
    cleanupPrevious = () => {
        ignore = true;
    };
}

runEffect("a");
runEffect("ab");
```

```text role="output"
showing results for "ab"
```

An `AbortController` goes further and cancels the request itself.

```js
useEffect(() => {
    const controller = new AbortController();
    fetch(`/api/users/${id}`, { signal: controller.signal })
        .then((r) => r.json())
        .then(setData)
        .catch(() => {}); // an aborted fetch rejects
    return () => controller.abort();
}, [id]);
```

Even with the race fixed, the data lives in one component's state, so every gap in the section 1 table remains. Lifting state up shares it, but re-renders a large subtree and still gives no caching. When the same guard, flags and refetch code wrap every fetch, you are hand-rolling a cache.

### Strict Mode shows the problem early

```jsx
<StrictMode>
    <User id={5} />
</StrictMode>
```

In development, Strict Mode mounts each component, unmounts it, and mounts it again, to surface effects that cannot survive a remount. So the Network tab shows two requests for one user. Production runs the effect once.

### The effect is fine, the storage is not

```jsx
function User({ id }) {
    const { data, isLoading, error } = useQuery({
        queryKey: ["user", id],
        queryFn: () => fetchUser(id),
    });
    // ...
}
```

<MarginNote note="the problem is the storage, not the effect">

An effect synchronizes a component with an external system, and the network is one. So an effect can fetch. But keeping your UI in step with a remote source is a caching problem, and effects come with no cache.

</MarginNote>

A library does not abolish the effect. It owns the synchronization centrally, in a cache every component subscribes to. That is why `useQuery` feels like relief. The win is not nicer syntax but a shared cache where there was none.

### Try it

In Node, swap the delays in the race snippet so "ab" is slower, and predict both runs. In a browser app, render two copies of the manual `User` and watch two requests fire.

Then swap in the `useQuery` version inside a `QueryClientProvider`, the component that hands the cache to your tree (section 15). One request should serve both.

## 3. Query keys: the cache is a key-value store

Query keys like `['user', id]` look like a naming habit, until a filter change does not refetch.

### The short version

The cache is a key-value store, a map from a hashed **query key** to an entry. The entry holds the data, its status, timestamps and the components watching it. The key is the data's address.

The same key means the same entry, which gives you sharing, deduplication and instant hits. A different key means a different entry, which is how new parameters fetch new data. Keys are hashed by value, so `{ a: 1, b: 2 }` and `{ b: 2, a: 1 }` hit one entry.

One rule follows. A key must include every input the fetch uses, or the cache cannot tell two requests apart.

### The cache is a Map

```js
// Simplified teaching version of QueryCache in query-core/src/queryCache.ts.
const queries = new Map(); // queryHash -> Query

const entry = {
    queryKey: ["user", 5],
    state: { data: { name: "Ada" }, status: "success", dataUpdatedAt: 1716200000000 },
    observers: [], // the mounted components using this entry
};
queries.set('["user",5]', entry);
```

The real `QueryCache` keeps a `Map` from a string `queryHash` to a `Query` object. Each `Query` is one cache entry.

### Hashing by value

```js
// Simplified teaching version of hashKey in query-core/src/utils.ts.
const isPlainObject = (v) => Object.prototype.toString.call(v) === "[object Object]";

function hashKey(queryKey) {
    return JSON.stringify(queryKey, (_, val) =>
        isPlainObject(val)
            ? Object.keys(val)
                  .sort()
                  .reduce((out, key) => {
                      out[key] = val[key];
                      return out;
                  }, {})
            : val,
    );
}

console.log(hashKey(["todos", { status: "done", page: 2 }]));
console.log(hashKey(["todos", { page: 2, status: "done" }]));
console.log(hashKey(["user", 5]) === hashKey(["user", "5"]));
```

```text role="output"
["todos",{"page":2,"status":"done"}]
["todos",{"page":2,"status":"done"}]
false
```

`hashKey` is `JSON.stringify` with object keys sorted. The contents of a key, not its identity, choose the entry. So two `useQuery` calls anywhere in the app with `['user', 5]` read the same entry. But the number `5` and the string `"5"` are different addresses.

### Every input belongs in the key

```js
// WRONG: filter changes the data but not the key
useQuery({ queryKey: ["todos"], queryFn: () => fetchTodos(filter) });

// RIGHT: every input the fetch depends on is in the key
useQuery({ queryKey: ["todos", { filter }], queryFn: () => fetchTodos(filter) });
```

In the wrong version, `filter: 'active'` and `filter: 'archived'` share one address. The cache hands back whichever was fetched first, and changing the filter does not refetch. From the cache's point of view, nothing about the address changed.

This is the dependency-array bug in another form. An effect that reads a value missing from its dependency array does not rerun. A query whose key lacks an input does not refetch. People describe query keys as "dependency arrays for your fetch" for this reason.

### Changing the key is how you refetch

```jsx
function User({ id }) {
    // id 5 -> 6 changes the key, so useQuery reads another entry
    const { data } = useQuery({ queryKey: ["user", id], queryFn: () => fetchUser(id) });
    return <h1>{data?.name}</h1>;
}
```

When `id` changes, you do not call "refetch". `useQuery` points at a different entry. If that entry is empty, it fetches. If it is cached, the data shows at once.

### Hierarchy and prefix matching

```js
// Simplified teaching version of partialMatchKey in query-core/src/utils.ts.
function partialMatchKey(a, b) {
    if (a === b) return true;
    if (typeof a !== typeof b || !a || !b || typeof a !== "object") return false;
    if (Array.isArray(b)) {
        return Array.isArray(a) && b.length <= a.length && b.every((item, i) => partialMatchKey(a[i], item));
    }
    return Object.keys(b).every((key) => partialMatchKey(a[key], b[key]));
}

const cached = [["todos"], ["todos", { status: "done" }], ["todos", 5], ["user", 5]];
console.log(cached.filter((key) => partialMatchKey(key, ["todos"])).length);
console.log(cached.filter((key) => partialMatchKey(key, ["todos", { status: "done" }])).length);
```

```text role="output"
3
1
```

Filters such as `invalidateQueries({ queryKey: ['todos'] })` match keys by prefix. Arrays match element by element, and objects match when every listed property agrees. Pass `exact: true` to match one key only. So build keys from general to specific: `['todos']`, then `['todos', { filter }]`, then `['todos', id]`. One broad key can then refresh a whole family.

### Key factories and serializable keys

```js
// A query key factory: build keys in one place so they cannot drift.
export const todoKeys = {
    all: ["todos"],
    lists: () => [...todoKeys.all, "list"],
    list: (filter) => [...todoKeys.lists(), { filter }],
    detail: (id) => [...todoKeys.all, "detail", id],
};
```

Many teams keep keys in small factories like this one, so a typo cannot split one entry into two. Keys must also survive `JSON.stringify`, so use ids, strings, numbers and plain objects, never functions or class instances.

A wrong key causes collisions, stale hits and refetches that never fire. All three are one bug: a key that does not faithfully address its data.

### Try it

Add these lines to the `hashKey` snippet and predict the output before you run it.

```js

console.log(hashKey(["todos", () => 1]));
```

```text role="output"

```

The functions vanish from the hash, so two different sort functions would share one entry. Then add `console.log(hashKey(["user", Number("5")]) === hashKey(["user", 5]))`. An id read from a URL is a string, and converting it should print `true`.

## 4. The status model: two axes, not one boolean

You want a spinner on first load and a small hint during background updates, but `isLoading`, `isPending` and `isFetching` blur together.

### The short version

A query's state lives on <Mark kind="circle">two axes</Mark>, because "do I have data?" and "is a request running?" are separate questions. `status` answers the first with `pending`, `success` or `error`. `fetchStatus` answers the second with `fetching`, `paused` or `idle`.

You need both, because "I have data and I am refetching it" is common and one boolean cannot say it. The derived flags are shorthands. `isLoading` means no data and a request running, so a full-screen spinner uses it.

`isFetching` means any request is running, background refreshes included, so a small hint uses it. Mixing them up causes the classic spinner bugs.

### Two questions, two fields

```jsx
const { status, fetchStatus, data } = useQuery({ queryKey: ["todos"], queryFn: fetchTodos });
```

This is "make illegal states unrepresentable" applied to async data. Splitting the axes lets every real combination exist and no impossible one.

| `status` | `fetchStatus` | What is happening |
|---|---|---|
| `pending` | `fetching` | The first load. Nothing to show yet |
| `pending` | `idle` | No data and no request, for example a disabled query |
| `pending` | `paused` | It wants to fetch but is offline (section 9) |
| `success` | `idle` | Cached data, nothing running |
| `success` | `fetching` | Showing cached data while revalidating in the background |
| `error` | `idle` | The last fetch failed, after its retries |
| `error` | `fetching` | Refetching after a failed refresh, with the old data still shown |

v5 renamed the status `loading` to `pending`.

### The derived flags

| Flag | Defined as | Use it for | Before v5 |
|---|---|---|---|
| `isPending` | `status === 'pending'` | "There is no data yet" | `isLoading` |
| `isLoading` | `isPending && isFetching` | A spinner instead of content | `isInitialLoading` |
| `isFetching` | `fetchStatus === 'fetching'` | A small "updating" hint beside content | same |
| `isRefetching` | `isFetching && !isPending` | Background refreshes only | same |
| `isPaused` | `fetchStatus === 'paused'` | An "offline" hint | same |
| `isError`, `isSuccess` | `status` equals that value | Branching on outcome | same |

```js
// Simplified teaching version of createResult in query-core/src/queryObserver.ts.
function flags({ status, fetchStatus }) {
    const isPending = status === "pending";
    const isFetching = fetchStatus === "fetching";
    return {
        isPending,
        isLoading: isPending && isFetching, // first load: nothing to show yet
        isRefetching: isFetching && !isPending, // background refresh
    };
}

const show = (label, state) => console.log(label.padEnd(11), JSON.stringify(flags(state)));
show("first load", { status: "pending", fetchStatus: "fetching" });
show("disabled", { status: "pending", fetchStatus: "idle" });
show("refetching", { status: "success", fetchStatus: "fetching" });
```

```text role="output"
first load  {"isPending":true,"isLoading":true,"isRefetching":false}
disabled    {"isPending":true,"isLoading":false,"isRefetching":false}
refetching  {"isPending":false,"isLoading":false,"isRefetching":true}
```

### The spinner rule

```jsx
function Todos() {
    const { data, isLoading, isFetching } = useQuery({ queryKey: ["todos"], queryFn: fetchTodos });

    if (isLoading) return <Spinner />; // first load only
    return (
        <>
            {isFetching && <small>Updating…</small>}
            <TodoList todos={data} />
        </>
    );
}
```

Binding the spinner to `isFetching` instead makes it flash on every background refetch. Section 10 shows the opposite bug, a spinner that never stops.

### Errors keep the data

```js
// From createResult: a failed refresh keeps its data.
const isRefetchError = status === "error" && data !== undefined;
const isLoadingError = status === "error" && data === undefined;
```

`status: 'error'` does not mean "no data". If a background refetch fails, the old data stays and `status` becomes `error`, which `isRefetchError` reports.

While a query retries, `status` does not change. `failureCount` and `failureReason` grow instead (section 9). Only when retries run out does `status` become `error`.

### Try it

Add this row to the `flags` snippet and predict it first: a query that wants to fetch while offline.

```js

```

`isLoading` should be `false`, because nothing is fetching. A paused first load needs its own `isPaused` hint.

## 5. Stale-while-revalidate, and what staleTime controls

You set `staleTime` because a tutorial did. Now the app either refetches constantly or never updates, and you cannot connect the knob to the behavior.

### The short version

The core behavior is **stale-while-revalidate**. When a component asks for data, the cache serves what it has at once, with no spinner if a copy exists. If that copy is stale, the cache also refetches in the background and swaps in fresh data when it arrives.

`staleTime` decides how long a fetched copy stays fresh. Fresh data is served with no refetch at all. Stale data is still served instantly, but the next trigger revalidates it. The default `staleTime` is 0, so data is stale the moment it arrives. That does not disable caching.

### Serve now, revalidate in the background

```jsx
const { data } = useQuery({
    queryKey: ["user", 5],
    queryFn: () => fetchUser(5),
    staleTime: 60_000, // trust this copy for one minute
});
```

The name comes from HTTP caching, and it is the algorithm: serve the stale copy, and revalidate it. The user sees data at once and watches it quietly update. That "instant, then fresh" feel is the defining experience of a good server-state setup.

<GuideFigure figure="react-stale-while-revalidate" />

### The fresh-or-stale test

```js
// Simplified teaching version of Query.isStaleByTime in query-core/src/query.ts.
let now = 0; // a fake clock in milliseconds

function isStaleByTime(entry, staleTime = 0) {
    if (entry.data === undefined) return true; // no data is always stale
    if (staleTime === "static") return false; // never stale, even when invalidated
    if (entry.isInvalidated) return true; // invalidateQueries marks it stale
    return now >= entry.dataUpdatedAt + staleTime;
}

const entry = { data: { name: "Ada" }, dataUpdatedAt: 0, isInvalidated: false };

now = 0;
console.log(isStaleByTime(entry)); // default staleTime 0
console.log(isStaleByTime(entry, 60_000));
now = 60_000;
console.log(isStaleByTime(entry, 60_000));
```

```text role="output"
true
false
true
```

Missing data and invalidated data are always stale, and `'static'` data never is. With the default of 0, the cache is still fully active: between triggers, components share the cached copy, and deduplication merges simultaneous requests (section 7). It never fetches on every render, and the default favors correctness over network traffic.

### Choosing a staleTime

| Data | Example | `staleTime` |
|---|---|---|
| Changes often and must be current | A live dashboard, a feed, shared documents | `0` or a few seconds |
| Changes sometimes, slight lag is fine | A profile, a product page | Minutes |
| Changes only when you change it | Settings you edit through mutations | `Infinity`, still invalidatable |
| Never changes while the app runs | Feature flags fetched at boot, a country list | `'static'` |

`Infinity` and `'static'` both stop time-based refetches. `'static'` is stricter: `invalidateQueries` cannot make it stale, and a trigger set to `'always'` skips it.

Set a default for the whole app on the `QueryClient`, and override it per query.

```js
const queryClient = new QueryClient({
    defaultOptions: { queries: { staleTime: 30_000 } },
});
```

"It refetches too much" usually means `staleTime: 0` on data that barely changes. "It never updates" usually means a huge `staleTime` on data that changes often. Both fixes match `staleTime` to how often the data really changes, and neither involves `gcTime`.

### Try it

Add two lines to the `isStaleByTime` snippet and predict them first.

```js
entry.isInvalidated = true;
console.log(isStaleByTime(entry, Infinity), isStaleByTime(entry, "static"));
```

```text role="output"
true false
```

Invalidation beats `Infinity` but not `'static'`.

## 6. Garbage collection: gcTime and how the cache is pruned

You set `gcTime`, once called `cacheTime`, to control freshness, and nothing you expect happens. It governs what happens after nobody uses the data.

### The short version

`gcTime` is how long an inactive entry stays in memory before the cache deletes it. An entry is inactive when no mounted component observes it. The default is 5 minutes. It lets a user leave a screen and come back within that window to see the old data at once, while it revalidates.

This is a retention policy, not a freshness policy. `staleTime` decides when data in use is checked again. `gcTime` decides how long data out of use is remembered. v5 renamed it from `cacheTime` because people read "cache time" as "how long data stays fresh", which is `staleTime`'s job.

### Observers decide active or inactive

```jsx
function UserPage({ id }) {
    useQuery({ queryKey: ["user", id], queryFn: () => fetchUser(id) }); // an observer
    // ...
}
// Navigate away: UserPage unmounts, its observer leaves, and the gcTime clock starts.
```

Every entry tracks its **observers**, the mounted components using its key. Their count decides the entry's fate.

| Event | What the cache does |
|---|---|
| At least one observer is mounted | The entry is in use and never collected |
| The last observer unmounts | A garbage-collection timer of `gcTime` starts |
| A new observer arrives before the timer fires | The timer is cancelled, and the old data shows at once |
| The timer fires | The entry is deleted, and the next request starts cold |

This is reference-counted garbage collection. The cache keeps data while something refers to it and reclaims it a set time after the last reference goes.

```js
// Simplified teaching version of Removable and Query observers in query-core.
class Entry {
    observers = 0;
    timer = null;
    constructor(cache, key, gcTime) {
        Object.assign(this, { cache, key, gcTime });
    }
    subscribe() {
        this.observers += 1;
        clearTimeout(this.timer); // someone came back: cancel the removal
    }
    unsubscribe() {
        this.observers -= 1;
        if (this.observers === 0) {
            this.timer = setTimeout(() => this.cache.delete(this.key), this.gcTime);
        }
    }
}

const cache = new Map();
const entry = new Entry(cache, "user-5", 50); // gcTime: 50ms for the demo
cache.set("user-5", entry);

entry.subscribe();
entry.unsubscribe(); // last observer leaves: the 50ms timer starts
setTimeout(() => entry.subscribe(), 20); // back within gcTime
setTimeout(() => console.log("after 80ms:", cache.has("user-5")), 80);
setTimeout(() => entry.unsubscribe(), 90); // leaves again
setTimeout(() => console.log("after 160ms:", cache.has("user-5")), 160);
```

```text role="output"
after 80ms: true
after 160ms: false
```

The real code adds two guards. When the timer fires, `optionalRemove` deletes the entry only if it still has no observers and no fetch is running. And an entry keeps the longest `gcTime` any observer asked for.

Why wait at all? A longer `gcTime` makes more returns instant and holds more memory. A shorter one frees memory sooner and causes more cold loads. On the server the default is `Infinity`, because a server-side cache lives only for one request.

### Two clocks, two questions

| | `staleTime` | `gcTime` |
|---|---|---|
| Governs an entry | While it is in use | After it falls out of use |
| Question | How long do I trust this copy? | How long do I keep unused data? |
| Default | `0` | 5 minutes (client), `Infinity` (server) |
| When it runs out | The next trigger revalidates | The entry is deleted |

<MarginNote note="how long to keep, not how long to trust">

The two barely interact, because they describe different moments. A query can be stale yet cached: in use, past its `staleTime`, served while it revalidates. A query can be fresh when last fetched yet collected, once it sits unused past `gcTime`.

</MarginNote>

## 7. Deduplication and sharing: one request, many consumers

Three components that need the same data used to fire three requests. With a keyed cache, this simply stops.

### The short version

Every component that calls `useQuery` with the same key subscribes to the same entry. So N components asking for `['user', 5]` share one entry and trigger one fetch, not N. Requests in flight are deduplicated too.

A second fetch for a key that is already fetching joins the running promise instead of starting another. Freshness still applies. Fresh data needs no request, and stale data gets one request, which every later subscriber joins. All subscribers re-render when the entry updates. No common ancestor holds the data, because it lives outside the component tree.

### One entry, many subscribers

```jsx
function useUser(id) {
    return useQuery({ queryKey: ["user", id], queryFn: () => fetchUser(id) });
}

function HeaderName({ id }) {
    const { data } = useUser(id);
    return <span>{data?.name}</span>;
}

function ProfilePanel({ id }) {
    const { data } = useUser(id); // same key, same entry
    return <h1>{data?.name}</h1>;
}
```

A component that calls `useQuery` owns no data. It subscribes to the entry at that address, through `useSyncExternalStore` (section 15). Context cannot share data this well, because it re-renders every consumer when its value changes. A store outside the tree, keyed by the data's natural identity, can.

### One request

```js
// Simplified teaching version of in-flight deduplication in Query.fetch.
let requests = 0;
const inFlight = new Map();

function fetchUser(id) {
    requests += 1;
    return new Promise((resolve) => setTimeout(() => resolve({ id, name: "Ada" }), 50));
}

function fetchQuery(key, queryFn) {
    if (inFlight.has(key)) return inFlight.get(key); // join the running request
    const promise = queryFn().finally(() => inFlight.delete(key));
    inFlight.set(key, promise);
    return promise;
}

const three = [1, 2, 3].map(() => fetchQuery('["user",5]', () => fetchUser(5)));
const results = await Promise.all(three);
console.log("requests:", requests);
console.log("same object:", results[0] === results[2]);
```

```text role="output"
requests: 1
same object: true
```

<Mark kind="marker" wraps>This sharing and deduplication is automatic, and it is the thing component-local state could never do.</Mark> In the real code, `Query.fetch` checks whether a fetch is running and returns its promise. A screen with a dozen widgets reading one query fires one request.

One exception is deliberate. `refetchQueries`, `invalidateQueries` and a query's `refetch` function cancel a running fetch when the entry has data, because the caller asked for newer data.

## 8. Background refetching: how the cache stays fresh

You tab away, come back, and the data is already current. Or the app seems to refetch "for no reason". Either way, you want to know what triggers a refetch.

### The short version

The cache does not poll the server constantly. It revalidates stale entries at moments when fresh data is likely to matter. A component mounts with that key. The tab becomes visible again. The network reconnects. Each of these triggers is on by default and gated by `staleTime`, so fresh data is left alone.

An optional `refetchInterval` turns a query into a poller, and it ignores `staleTime`. The usual fix for "it refetches too much" is a higher `staleTime`, not switching triggers off. Disabling the focus refetch removes the main mechanism that keeps a tabbed-away app current.

### The triggers

| Option | Default | Fires when | Gated by `staleTime`? |
|---|---|---|---|
| `refetchOnMount` | `true` | A component mounts and subscribes to the key | Yes |
| `refetchOnWindowFocus` | `true` | The tab becomes visible again | Yes |
| `refetchOnReconnect` | `true` | The browser fires its `online` event, since data from before the outage is likely old | Yes |
| `refetchInterval` | `false` | Every N milliseconds while mounted | No |

Each `refetchOn…` option also accepts `'always'`, which refetches even fresh data, and `false`. A disabled query, or one with `staleTime: 'static'`, ignores all three `refetchOn…` options.

```js
// Simplified teaching version of shouldFetchOn in query-core/src/queryObserver.ts.
function shouldFetchOn(option, { enabled = true, stale, staleTime = 0 }) {
    if (!enabled || staleTime === "static") return false;
    return option === "always" || (option !== false && stale);
}

console.log(shouldFetchOn(true, { stale: true })); // default, data is stale
console.log(shouldFetchOn(true, { stale: false })); // default, data is fresh
console.log(shouldFetchOn("always", { stale: false })); // refetch even when fresh
console.log(shouldFetchOn(true, { stale: true, enabled: false })); // disabled query
```

```text role="output"
true
false
true
false
```

### How the cache notices focus and the network

```js
// Simplified teaching version of focusManager and onlineManager.
window.addEventListener("visibilitychange", () => {
    if (document.visibilityState !== "hidden") queryCache.onFocus();
});
window.addEventListener("online", () => queryCache.onOnline());
```

The `QueryClient` listens once, globally, and fans the event out to queries with observers. In v5 the focus refetch listens only to `visibilitychange`, not the window `focus` event. The online manager starts by assuming you are online and then follows `online` and `offline` events, because `navigator.onLine` gave false negatives in Chromium.

### Polling

```jsx
useQuery({
    queryKey: ["build", id],
    queryFn: () => fetchBuild(id),
    refetchInterval: 3000, // poll every 3s while mounted
    refetchIntervalInBackground: false, // the default: pause while the tab is hidden
});
```

An interval refetches on schedule whether or not the data is stale. That makes live data, like a dashboard or a build status, possible without sockets.

### Control it with staleTime

Turn a trigger off only when it is wrong for one query, like a one-time fetch that should never refetch on focus. Two more paths are deliberate. The `refetch` function a query returns forces a revalidation, for a refresh button. And mutations invalidate queries after a write (section 11).

### Try it

In a browser app with the Devtools open, set `staleTime: 0`, switch tabs and back, and watch the entry flip to fetching. With `staleTime: Infinity`, nothing happens.

## 9. Retries, offline and cancellation

A failed request shows no error for seconds, an offline laptop leaves queries in a strange state, and a user leaves mid-request. Each case has a defined behavior.

### The short version

A failed query retries 3 times before it reports an error, waiting 1s, 2s and then 4s. The delay doubles each time and is capped at 30s. While it retries, `status` stays as it was and `failureCount` grows. Retries also pause while the tab is hidden or the device is offline.

With the default `networkMode: 'online'`, a query that wants to fetch while offline does not start. It waits with `fetchStatus: 'paused'`. Every `queryFn` receives an `AbortSignal`. If your code passes it to `fetch`, a cancelled query aborts its request. Mutations do not retry by default, and neither do queries on the server.

### Retry with backoff

```js
// defaultRetryDelay from query-core/src/retryer.ts.
const defaultRetryDelay = (failureCount) => Math.min(1000 * 2 ** failureCount, 30000);

console.log([0, 1, 2, 3, 4, 5, 6].map(defaultRetryDelay).join(" "));
```

```text role="output"
1000 2000 4000 8000 16000 30000 30000
```

The default `retry` is 3, so a failing query makes four attempts in about 7 seconds before `status` becomes `error`. Change it per query or on the `QueryClient`.

```js
useQuery({
    queryKey: ["user", id],
    queryFn: () => fetchUser(id),
    retry: (failureCount, error) => error.status !== 404 && failureCount < 2,
});
```

| Where | Default `retry` |
|---|---|
| Queries in the browser | 3, with the backoff above |
| Queries on the server | 0 |
| Mutations | 0 |
| `queryClient.query()` and other imperative calls | `false` unless you set it |

### Network mode

| `networkMode` | Offline behavior |
|---|---|
| `'online'` (default) | Does not start. `fetchStatus` is `'paused'` until the network returns |
| `'always'` | Ignores the network status completely, as for a local database |
| `'offlineFirst'` | Runs the `queryFn` once, so a service worker cache can answer, then pauses retries |

A paused query resumes when the `online` event fires. In every mode, even `'always'`, retries also wait while the tab is hidden.

### Cancellation with AbortSignal

```js
useQuery({
    queryKey: ["todos"],
    queryFn: async ({ signal }) => {
        const res = await fetch("/api/todos", { signal }); // abortable
        return res.json();
    },
});
```

TanStack Query creates an `AbortController` for each fetch and passes its `signal` to your `queryFn`. Run this in Node to see what an abort does.

```js
// What TanStack Query does with the signal it hands your queryFn (simplified).
function queryFn({ signal }) {
    return new Promise((resolve, reject) => {
        const timer = setTimeout(() => resolve("data"), 1000);
        signal.addEventListener("abort", () => {
            clearTimeout(timer); // fetch(url, { signal }) does this for you
            reject(new Error("aborted"));
        });
    });
}

const controller = new AbortController();
queryFn({ signal: controller.signal }).then(console.log, (e) => console.log(e.message));
setTimeout(() => controller.abort(), 100); // the query was cancelled
```

```text role="output"
aborted
```

A query is cancelled by `queryClient.cancelQueries`, or when its last observer unmounts. In the unmount case, a `queryFn` that never read `signal` keeps running so its result can be cached, unless it was a paused first load. One that read it is aborted. Either way, a cancel reverts the entry to its state before the fetch.

### Try it

In the abort snippet, change the abort delay from 100 to 2000 and predict the output. It should print `data`, because the request finished before anyone cancelled it.

## 10. The enabled flag and dependent queries

You need a user's posts, but only after another query gives you the user's id. You cannot wrap `useQuery` in an `if`, because that breaks the rules of hooks.

### The short version

`enabled` is an option that says whether a query may run. While it is `false`, the query does not fetch and ignores every trigger. When it becomes `true`, the query behaves normally. It exists because hooks must be called unconditionally, in the same order on every render.

So you always call `useQuery` and pass the condition as an option. The classic use is a **dependent query**: `enabled: !!userId` keeps the posts query waiting until the user query supplies an id. One trap follows: a disabled query with no data has `isPending` true, so a spinner must use `isLoading`.

### Why not an if

```jsx
// WRONG: a conditional hook changes the hook order between renders
if (userId) {
    useQuery({ queryKey: ["posts", userId], queryFn: () => fetchPosts(userId) });
}

// RIGHT: always call the hook, and gate the fetch with an option
useQuery({ queryKey: ["posts", userId], queryFn: () => fetchPosts(userId), enabled: !!userId });
```

React stores hooks in order on the component's fiber, its internal record of the component instance. An `if` around a hook shifts that order and mixes up the slots. `enabled` moves the condition from "whether to call the hook" into an option, as a dependency array does for an effect.

### Dependent queries

```jsx
const { data: user } = useQuery({
    queryKey: ["user", email],
    queryFn: () => fetchUser(email),
});
const userId = user?.id;

const { data: posts } = useQuery({
    queryKey: ["posts", userId],
    queryFn: () => fetchPosts(userId),
    enabled: !!userId, // wait until we actually have an id
});
```

The posts query exists from the first render but is disabled, so it never requests `['posts', undefined]`. When the user query resolves, `enabled` flips to `true` and the posts query runs. That is sequential fetching with no effect and no `if`. Other gates look the same: `enabled: searchTerm.length > 0`, or `enabled: isLoggedIn`.

### The permanent spinner

```jsx
const { isPending, isLoading } = useQuery({ queryKey: ["posts", userId], queryFn, enabled: !!userId });

if (isPending) return <Spinner />; // WRONG: spins while merely disabled
if (isLoading) return <Spinner />; // RIGHT: spins only while actually fetching
```

A disabled query with no cached data has `status: 'pending'` and `fetchStatus: 'idle'`. So `isPending` is `true` while nothing loads. `isLoading` also needs `isFetching`, which is false while disabled. This is really the status model from section 4, showing up through `enabled`.

### Keep the key complete

Key the query fully, even with inputs it is gated on. `['posts', undefined]` is harmless while the query is disabled, and once enabled the key already addresses the right entry. Do not "fix" a dependent query by leaving the dependency out of the key.

Derive `enabled` from real values. A condition built from an unstable or wrong value gives queries that never run, or run at the wrong time. And if the key is incomplete, `enabled` will not fix it.

### skipToken

```js
import { skipToken, useQuery } from "@tanstack/react-query";

useQuery({
    queryKey: ["posts", userId],
    queryFn: userId ? () => fetchPosts(userId) : skipToken, // TypeScript knows userId is defined here
});
```

`skipToken` disables a query the same way, but TypeScript can narrow `userId` inside the function. `useSuspenseQuery` accepts neither `enabled` nor `skipToken` (section 14).

### Try it

This one runs in a browser app. Build the user-then-posts pair and watch the Network tab. No `posts` request should appear until the `user` request resolves.

## 11. Mutations and cache invalidation

The user creates a todo, and the list shows old data until a reload. Nothing tells the cached reads they are out of date.

### The short version

A **mutation** is a write: create, update or delete. You run it with `useMutation`, which gives you a `mutate` function and its own status. Their real job is to make the cache honest again, because after a successful write your cached reads describe a server that has changed.

You reconcile in one of two ways. Invalidating marks the affected queries stale and refetches the active ones, the safe default. Writing with `setQueryData` puts a known new value straight into the cache. A mutation is finished when the cache reflects the new reality, not when the write succeeds.

### useMutation

```jsx
function AddTodo() {
    const queryClient = useQueryClient();
    const mutation = useMutation({
        mutationFn: (newTodo) => createTodo(newTodo),
        onSuccess: () => {
            // the server changed, so the cached list is stale: refetch it
            return queryClient.invalidateQueries({ queryKey: ["todos"] });
        },
    });

    return (
        <button disabled={mutation.isPending} onClick={() => mutation.mutate({ title: "Buy milk" })}>
            Add
        </button>
    );
}
```

A read is idempotent, cacheable and shared. A write is a one-shot action with side effects, so it gets its own hook. `useMutation` returns `mutate`, the `variables` you passed, and flags. `isPending`, renamed from `isLoading` in v5, disables the button, and `isError` shows the failure.

| Callback | Runs | Typical job |
|---|---|---|
| `onMutate` | Before `mutationFn`, and is awaited | Optimistic updates (section 12) |
| `onSuccess` | After a successful write | Invalidate, or write the result into the cache |
| `onError` | After a failed write | Roll back an optimistic update |
| `onSettled` | After either outcome | Invalidate to reconcile with the server |

When `onSuccess` or `onSettled` returns a promise, the mutation stays pending until it resolves. Returning `invalidateQueries` keeps the button disabled until the list has refetched.

### Strategy one: invalidate

<Mark kind="marker" wraps>Invalidation is how a write tells every relevant read "you are out of date now."</Mark>

```js
// Simplified teaching version of invalidateQueries (query-core/src/queryClient.ts).
// Paste this whole block after the partialMatchKey function from section 3 (skip that snippet's demo lines).
const cache = [
    { key: ["todos"], active: true, isInvalidated: false },
    { key: ["todos", { status: "done" }], active: false, isInvalidated: false },
    { key: ["user", 5], active: true, isInvalidated: false },
];

function invalidateQueries({ queryKey }) {
    for (const entry of cache.filter((e) => partialMatchKey(e.key, queryKey))) {
        entry.isInvalidated = true; // stale from now on
        if (entry.active) console.log("refetch", JSON.stringify(entry.key)); // refetchType 'active'
    }
}

invalidateQueries({ queryKey: ["todos"] });
console.log(cache.map((e) => e.isInvalidated).join(" "));
```

```text role="output"
refetch ["todos"]
true true false
```

`invalidateQueries` marks every entry the filter matches as invalidated, which makes it stale. Then it refetches the active ones in the background. Inactive matches refetch the next time a component uses them. Pass `refetchType: 'none'` to only mark, or `'all'` to refetch inactive entries too.

You are telling the cache "the truth changed, go ask the server again", with no guess about the answer. The cost is one round trip, a fair price for consistency.

### Strategy two: write the cache directly

```js
onSuccess: (createdTodo) => {
    queryClient.setQueryData(["todos"], (old = []) => [...old, createdTodo]); // a new array, never a push
},
```

When you already know the new state, write it into the cache and skip the refetch. The entry counts as freshly fetched. Return a new value instead of mutating the old one, or structural sharing (section 15) cannot see the change. `setQueryData` is also the mechanism underneath optimistic updates (section 12).

| Strategy | Network | You must know | Risk |
|---|---|---|---|
| `invalidateQueries` | One refetch per active match | Which keys changed | A brief moment of old data |
| `setQueryData` | None | The exact new data | The cache drifts from the server if you guess wrong |
| Both | One refetch | Roughly the new data | Low: instant feedback, then reconciled |

When a write succeeds but the screen shows old data, ask one question: did I invalidate or update the right keys? The stale-after-write bug is almost always a missing or mis-keyed invalidation. The source changed, and nobody told the copy.

### Try it

In the `invalidateQueries` snippet, call `invalidateQueries({ queryKey: ["todos", { status: "done" }] })` instead and predict the output. It should print no refetch line, because the matching entry is inactive, and then `false true false`.

## 12. Optimistic updates

The user toggles a checkbox, and the UI waits for the server before it moves. You want the change to appear at once and undo itself only if the server refuses.

### The short version

An **optimistic update** shows the expected result before the server confirms, and rolls it back if the write fails. TanStack Query offers two ways. The simple way renders the pending mutation's `variables` in the component, so the cache is never touched.

The cache way writes the guess into the cache so every reader sees it. `onMutate` cancels running refetches, snapshots the data, writes the guess and returns the snapshot. `onError` restores it, and `onSettled` invalidates. React 19's `useOptimistic` does the same for Actions, async functions React tracks as pending, with no query cache. The rollback is the part to get right.

### Via the UI: render the variables

```jsx
const addTodo = useMutation({
    mutationFn: (text) => postTodo(text),
    onSettled: () => queryClient.invalidateQueries({ queryKey: ["todos"] }),
});

<ul>
    {todos.map((todo) => (
        <li key={todo.id}>{todo.text}</li>
    ))}
    {addTodo.isPending && <li style={{ opacity: 0.5 }}>{addTodo.variables}</li>}
</ul>;
```

While the mutation is pending, a faded item shows what the user sent, and the refetched list later brings the real one. If the write fails, the item disappears, but `variables` survive the error, so you can offer a retry button.

If another component needs the pending item, give the mutation a `mutationKey`, a label like a query key, and `useMutationState` finds it from anywhere.

### Via the cache: the four steps

```js
useMutation({
    mutationFn: toggleTodo,
    onMutate: async (toggled, context) => {
        await context.client.cancelQueries({ queryKey: ["todos"] }); // 1. stop refetches
        const previous = context.client.getQueryData(["todos"]); // 2. snapshot
        context.client.setQueryData(["todos"], (old) => applyToggle(old, toggled)); // 3. guess
        return { previous }; // passed on as onMutateResult
    },
    onError: (error, toggled, onMutateResult, context) => {
        context.client.setQueryData(["todos"], onMutateResult.previous); // 4a. roll back
    },
    onSettled: (data, error, toggled, onMutateResult, context) =>
        context.client.invalidateQueries({ queryKey: ["todos"] }), // 4b. reconcile
});
```

In current v5, the value `onMutate` returns arrives as `onMutateResult`. The last argument, `context`, carries the `QueryClient` as `context.client`. Older code calls the third argument `context`, and it works the same by position.

| Step | Call | Why it exists |
|---|---|---|
| 1. Cancel | `cancelQueries` | A refetch already in flight could land after your guess and overwrite it with old server data |
| 2. Snapshot | `getQueryData` | The rollback point, returned from `onMutate` |
| 3. Guess | `setQueryData` | Every reader of `['todos']` re-renders with the expected value at once |
| 4a. Roll back | `setQueryData` in `onError` | A failed write must not leave the UI showing it |
| 4b. Reconcile | `invalidateQueries` in `onSettled` | The server may add a timestamp, assign an id or apply a rule you did not copy |

Step 1 is the same race as the effect fetch in section 2: two async results compete, and you make the right one win.

```js
// The cache recipe in miniature: snapshot, write, roll back.
const cache = new Map([["todos", [{ id: 1, done: false }]]]);

async function toggleTodo(id) {
    const previous = cache.get("todos"); // snapshot
    cache.set("todos", previous.map((t) => (t.id === id ? { ...t, done: !t.done } : t)));
    console.log("optimistic:", cache.get("todos")[0].done);
    try {
        await Promise.reject(new Error("500")); // the server says no
    } catch {
        cache.set("todos", previous); // roll back to the snapshot
        console.log("rolled back:", cache.get("todos")[0].done);
    }
}

await toggleTodo(1);
```

```text role="output"
optimistic: true
rolled back: false
```

The rollback is what people get wrong. Skipping it is worse than no optimism, because the user believes a failed write worked. The snapshot-and-restore is not polish, because <Mark kind="underline" wraps>an optimistic update that cannot undo itself leaves the UI lying after a failure</Mark>.

<GuideFigure figure="df-optimistic" />

### Choosing a layer

An **Action** is an async function you pass to a form's `action` prop or to `startTransition`, and React tracks it as pending until it settles. The [scheduler and lanes guide](/articles/react-scheduler-and-lanes-internals) covers transitions and Actions.

```jsx
function LikeButton({ likes, likeAction }) {
    const [optimisticLikes, addOptimisticLike] = useOptimistic(likes, (current) => current + 1);

    return (
        <form action={async () => {
            addOptimisticLike();
            await likeAction();
        }}>
            <button>{optimisticLikes} likes</button>
        </form>
    );
}
```

React 19's `useOptimistic` shows an optimistic value while an Action is pending, then reverts to the real value when it settles. It applies one model at the framework level: show the expected result now, reconcile when the truth arrives.

| Need | Reach for |
|---|---|
| The optimistic item appears only in the component that fires the mutation | The mutation's `variables` |
| Every reader of a cached query must see the change | The `onMutate` cache recipe |
| A form Action's local UI, with no query cache | `useOptimistic` |

### Try it

In the miniature snippet, delete the `cache.set("todos", previous)` line and run it again. The second line should print `rolled back: true`. The failed toggle sticks, which is exactly the lie the snapshot prevents.

## 13. Pagination, infinite queries and prefetching

Paginated lists blank on every page change, infinite scroll is fiddly by hand, and a detail page always shows a spinner. Each has a built-in answer.

### The short version

All three are the same cache read in different ways. For pagination, each page is its own entry keyed by page number. `placeholderData: keepPreviousData` keeps showing the previous page while the next one loads, so the list never blanks.

For infinite scroll, `useInfiniteQuery` stores every loaded page in one entry, and `fetchNextPage` appends the next page using a cursor from `getNextPageParam`. Because it is one entry, scrolling back up does not refetch. For instant navigation, you prefetch on hover with `queryClient.query()`. The destination's `useQuery` then finds the data waiting, so it renders with no spinner.

### Pagination without the flicker

```jsx
import { keepPreviousData, useQuery } from "@tanstack/react-query";

const { data, isPlaceholderData } = useQuery({
    queryKey: ["todos", { page }],
    queryFn: () => fetchTodos(page),
    placeholderData: keepPreviousData, // while page 2 loads, keep showing page 1
});
```

Each page in its own entry is correct, since pages hold different data. But a new page means a new, empty entry, so without a placeholder the list drops to `pending` and flickers through a spinner.

While the new page loads, `placeholderData` returns the previous page with `status: 'success'` and `isPlaceholderData: true`. Use the flag to dim the list or disable "next". The placeholder is never written to the cache, so each page stays correctly keyed.

```js
// keepPreviousData from query-core/src/utils.ts is the identity function.
const keepPreviousData = (previousData) => previousData;
console.log(keepPreviousData(["page 1 rows"]));
```

```text role="output"
[ 'page 1 rows' ]
```

v5 removed the old `keepPreviousData: true` option. You now pass this identity function to `placeholderData`.

### Infinite queries

```jsx
const { data, fetchNextPage, hasNextPage, isFetchingNextPage } = useInfiniteQuery({
    queryKey: ["feed"],
    queryFn: ({ pageParam }) => fetchFeed(pageParam),
    initialPageParam: 0, // required in v5
    getNextPageParam: (lastPage) => lastPage.nextCursor ?? null, // null: no more pages
    getPreviousPageParam: (firstPage) => firstPage.prevCursor ?? null, // optional: scrolling up
    maxPages: 5, // optional: keep at most five pages in memory
});

const items = data?.pages.flatMap((page) => page.items) ?? [];
```

Infinite scroll accumulates pages into one growing list. The entry holds `pages`, the fetched results, and `pageParams`, the cursor used for each. `getNextPageParam` turns the last page into the next cursor. `hasNextPage` is `true` unless it returns `null` or `undefined`. Call `fetchNextPage` when the user nears the bottom, and render `data.pages` flattened.

`getPreviousPageParam` does the same for scrolling up. The whole list is one entry, shared and cached like any query, so scrolling back up does not refetch. When it goes stale, TanStack Query refetches every page in order, starting from the first, so cursors never point at shifted data.

`maxPages` caps how many pages that refetch has to load. Pages it dropped are fetched again through `getPreviousPageParam` when the user scrolls back to them.

### Prefetching

```jsx
import { noop } from "@tanstack/react-query";

function PostLink({ id }) {
    const queryClient = useQueryClient();
    const prefetch = () =>
        queryClient.query({ queryKey: ["post", id], queryFn: () => fetchPost(id), staleTime: 60_000 }).catch(noop);

    return (
        <Link to={`/posts/${id}`} onMouseEnter={prefetch} onFocus={prefetch}>
            Read post
        </Link>
    );
}
```

Prefetching fetches data into the cache before the component that needs it mounts. Matching keys is the only wiring needed. `queryClient.query()` fetches unless the cached data is still fresh, and returns the data. Unlike the old `prefetchQuery`, it rejects when the fetch fails, so a prefetch that `useQuery` can retry later ends in `.catch(noop)`.

Since 5.102, `query()` replaces `prefetchQuery` and `fetchQuery`, and `query({ ...options, staleTime: 'static' })` replaces `ensureQueryData`. The old methods still work but are deprecated. `queryClient.infiniteQuery({ ..., pages: 3 })` prefetches several pages of an infinite query at once.

A prefetched entry with no observer is collected after `gcTime`. Routers often prefetch on link hover, and that removes many navigation spinners for little code.

## 14. Suspense for data, and React 19's use()

Every data component checks `isLoading`, then `isError`, and only then renders the data. Suspense moves those branches out of the component.

### The short version

With **Suspense**, a component tells React "I am not ready" while its data loads. React shows the nearest `<Suspense>` fallback, and an error boundary catches failures. Loading and errors become structure instead of branches. `useSuspenseQuery` suspends instead of returning `pending`, so `data` is always defined inside the component.

React 19's `use(promise)` is the raw form: it suspends on a pending, cached promise. `useSuspenseQuery` adds the whole cache on top. The costs are real. Boundary placement decides what blanks out, nested suspending components can create a waterfall, and a key change shows the fallback again unless it is non-urgent.

### useSuspenseQuery

```jsx
function Profile({ id }) {
    // No isLoading, no isError: if this line returns, data is defined.
    const { data } = useSuspenseQuery({
        queryKey: ["user", id],
        queryFn: () => fetchUser(id),
    });
    return <h1>{data.name}</h1>;
}

function Page({ id }) {
    return (
        <ErrorBoundary fallback={<ErrorMessage />}>
            <Suspense fallback={<Spinner />}>
                <Profile id={id} />
            </Suspense>
        </ErrorBoundary>
    );
}
```

The types encode the guarantee: `data` is `T`, not `T | undefined`. The three-way branch from section 4 becomes two boundaries placed once. `ErrorBoundary` is not built into React: write one as a class component, or use the `react-error-boundary` package.

v5 made these hooks stable: `useSuspenseQuery`, `useSuspenseInfiniteQuery` and `useSuspenseQueries`. The old `suspense: true` option on `useQuery` is gone.

### What useSuspenseQuery changes

| Behavior | `useQuery` | `useSuspenseQuery` |
|---|---|---|
| First load | Returns `isPending: true` | Suspends to the nearest `<Suspense>` |
| `data` type | `T \| undefined` | `T` |
| `enabled`, `skipToken`, `placeholderData` | Available | Not available |
| Error with no data | Returned as `error` | Thrown to the error boundary |
| Error while cached data exists | Returned as `error` | Not thrown, the old data keeps rendering |
| Background refetch | `isFetching` is true | Same, with no suspending |
| Minimum `staleTime` | None | 1,000ms, so a remount after suspending does not refetch at once |

Only a missing entry suspends, so a background refetch never brings the fallback back.

### use(): suspend on a promise

```jsx
function Comments({ commentsPromise }) {
    const comments = use(commentsPromise); // suspends while pending
    return comments.map((c) => <p key={c.id}>{c.text}</p>);
}
```

`use(promise)` returns the value once the promise resolves, suspends while it is pending, and throws to the error boundary if it rejects. Unlike other hooks, you can call it inside an `if`. Here is the mechanism, simplified from `trackUsedThenable` in `ReactFiberThenable.js`.

```js
// Simplified teaching version of how use() reads a promise (ReactFiberThenable.js).
const SuspenseException = new Error("suspended");

function use(promise) {
    if (promise.status === "fulfilled") return promise.value;
    if (promise.status === "rejected") throw promise.reason;
    if (promise.status !== "pending") {
        promise.status = "pending";
        promise.then(
            (value) => Object.assign(promise, { status: "fulfilled", value }),
            (reason) => Object.assign(promise, { status: "rejected", reason }),
        );
    }
    throw SuspenseException; // React catches this and shows the fallback
}

const userPromise = Promise.resolve({ name: "Ada" }); // created once, outside render

function render() {
    try {
        console.log("rendered", use(userPromise).name);
    } catch (e) {
        if (e !== SuspenseException) throw e;
        console.log("suspended, showing fallback");
        userPromise.then(render); // React retries when the promise settles
    }
}

render();
```

```text role="output"
suspended, showing fallback
rendered Ada
```

React writes `status` and `value` onto the promise itself, and on the retry it reads the value synchronously. That only works when the same promise object comes back on every render. So a promise passed to `use` in a Client Component must come from a cache, a framework or a Server Component.

`useSuspenseQuery` does not call `use()`, but throws its own fetch promise, which React also accepts. Use `use()` for one-off promises, such as one a Server Component passes down, and `useSuspenseQuery` for cached server data.

### How React 19 shows the fallback

When a component suspends, React 19 commits the nearest fallback at once instead of first rendering every sibling. Then it renders the suspended siblings in the background to "pre-warm" their requests. React also reveals finished content at most once every 300ms, so boundaries that resolve close together appear together.

<MarginNote note="the component stops owning its spinner">

The trade is that loading and error states move from inside the component to the boundaries around it. The code gets cleaner, but you must place those boundaries on purpose.

</MarginNote>

### Boundaries, waterfalls and transitions

The fallback belongs to the nearest `<Suspense>` ancestor. Place it too high, and one small loading piece blanks a large region. Place one per section, and each loads on its own.

```jsx
// WATERFALL: Comments only starts fetching after Post resolves
function Post({ id }) {
    const { data: post } = useSuspenseQuery({ queryKey: ["post", id], queryFn: () => fetchPost(id) });
    return (
        <article>
            <h1>{post.title}</h1>
            <Comments postId={id} />
        </article>
    );
}

// PARALLEL: both start in the same render
const [{ data: post }, { data: comments }] = useSuspenseQueries({
    queries: [
        { queryKey: ["post", id], queryFn: () => fetchPost(id) },
        { queryKey: ["comments", id], queryFn: () => fetchComments(id) },
    ],
});
```

Nested suspending components serialize requests that could run together. Start fetches as early as possible: hoist them with `useSuspenseQueries`, or prefetch above the boundary with `usePrefetchQuery` or `queryClient.query()`.

A **transition** marks an update as non-urgent, so React may keep the old screen while it renders the new one. `startTransition` and `useDeferredValue` both create one.

```jsx
const [id, setId] = useState(1);
const [, startTransition] = useTransition();

// A key change re-suspends. In a transition, React keeps showing the old content instead.
<button onClick={() => startTransition(() => setId(id + 1))}>Next</button>;
```

If a boundary already shows content and suspends again, React shows the fallback again, unless the update was a transition. `useSuspenseQuery` has no `placeholderData`, so a transition is how you keep the old page on screen.

### Try it

Run the `use()` snippet, then move the `Promise.resolve` line inside `render` and stop after three retries with a counter. Every attempt should print `suspended, showing fallback`, because each render makes a new promise React has never seen. That is why `use()` needs a cached promise.

## 15. How the cache plugs into React, and Server Components

Under the black box sit a few plain classes, one React hook, and a hydration step for server rendering.

### The short version

The cache is an **external store**, state that lives outside React's tree. A `QueryClient` holds a `QueryCache` of `Query` entries. Each `useQuery` call creates a `QueryObserver` and subscribes to it through `useSyncExternalStore`. That hook is why v5 requires React 18, and it keeps every component reading one consistent snapshot.

Structural sharing keeps unchanged data at the same reference. Tracked properties re-render a component only for fields it reads. `select` narrows a subscription to a slice. With Server Components, you prefetch on the server, dehydrate the cache, and hydrate it on the client, so the client starts warm.

### The pieces

```text
QueryClient                  one per app, given to QueryClientProvider
└── QueryCache               Map<queryHash, Query>
    └── Query                one entry: state, retryer, gc timer, observers
        └── QueryObserver    one per useQuery call: options, timers, result
```

| Class | File in `query-core/src` | Job |
|---|---|---|
| `QueryClient` | `queryClient.ts` | Public API: `invalidateQueries`, `setQueryData`, `query`, focus and online wiring |
| `QueryCache` | `queryCache.ts` | The keyed store, `build` and `find` by hash |
| `Query` | `query.ts` | State, the fetch with dedup and retries, garbage collection |
| `QueryObserver` | `queryObserver.ts` | Per-component options, staleness timers, derived flags |
| `focusManager`, `onlineManager` | `focusManager.ts`, `onlineManager.ts` | The triggers from section 8 |
| `notifyManager` | `notifyManager.ts` | Batches notifications and flushes them in a `setTimeout(0)` |

Create the `QueryClient` once on the client, for example in `useState(() => new QueryClient())`. A new client on every render would throw the cache away.

### The useSyncExternalStore bridge

```js
// Simplified teaching version of useBaseQuery (react-query/src/useBaseQuery.ts).
function useBaseQuery(options) {
    const client = useQueryClient();
    const [observer] = useState(() => new QueryObserver(client, options));
    const result = observer.getOptimisticResult(options);

    useSyncExternalStore(
        useCallback((onStoreChange) => observer.subscribe(notifyManager.batchCalls(onStoreChange)), [observer]),
        () => observer.getCurrentResult(),
        () => observer.getCurrentResult(),
    );

    useEffect(() => observer.setOptions(options), [options, observer]);
    // suspense is set internally by useSuspenseQuery
    if (options.suspense && result.isPending) throw observer.fetchOptimistic(options);
    return options.notifyOnChangeProps ? result : observer.trackResult(result); // tracked properties
}
```

<Mark kind="marker" wraps>The cache is the external-store pattern, realized for server state</Mark>. `useSyncExternalStore` is React 18's primitive for subscribing to a store outside React. The v5 migration guide names it as the reason v5 needs React 18 or later.

It also prevents **tearing**. Under concurrent rendering, React can pause a render partway. If a store changes during the pause, components rendered before and after it would show different values, two versions of one screen. `useSyncExternalStore` detects the change and re-renders consistently. The cost: a store change during a transition is redone as a blocking render.

### Fewer re-renders: structural sharing, tracked properties, select

```js
// Simplified teaching version of replaceEqualDeep in query-core/src/utils.ts.
const isObject = (v) => v !== null && typeof v === "object";

function replaceEqualDeep(prev, next) {
    if (prev === next) return prev;
    if (!isObject(prev) || !isObject(next) || Array.isArray(prev) !== Array.isArray(next)) return next;
    const copy = Array.isArray(next) ? [] : {};
    let same = Object.keys(prev).length === Object.keys(next).length;
    for (const key of Object.keys(next)) {
        copy[key] = replaceEqualDeep(prev[key], next[key]);
        if (copy[key] !== prev[key]) same = false;
    }
    return same ? prev : copy; // nothing changed: keep the old reference
}

const before = { user: { name: "Ada" }, posts: [{ id: 1, likes: 3 }] };
const after = JSON.parse('{"user":{"name":"Ada"},"posts":[{"id":1,"likes":4}]}');

const shared = replaceEqualDeep(before, after);
console.log(shared === before); // something changed
console.log(shared.user === before.user); // but user did not
console.log(shared.posts === before.posts); // posts did
```

```text role="output"
false
true
false
```

Every refetch parses fresh JSON, so every object is new. **Structural sharing** keeps the old reference wherever nothing changed. A component wrapped in `memo`, which React skips when its props are unchanged, then sees the same `data.user` and skips work.

```jsx
function TodoCount() {
    const { data: count } = useQuery({
        queryKey: ["todos"],
        queryFn: fetchTodos,
        select: (todos) => todos.length, // subscribe to a slice
    });
    return <span>{count}</span>;
}
```

`select` transforms the data for one component, and its result is memoized and structurally shared too. With **tracked properties**, the result is a Proxy that records which fields you read. `TodoCount` reads only `data`, so neither an `isFetching` change nor a todo edit that keeps the count re-renders it.

| Mechanism | What it keeps stable | Turn it off | What defeats it |
|---|---|---|---|
| Structural sharing | Unchanged parts of `data` keep their references | `structuralSharing: false`, or pass your own function | Data that is not JSON-compatible |
| Tracked properties | A re-render happens only for fields you read | `notifyOnChangeProps: 'all'` | Rest destructuring, as in `const { data, ...rest } = useQuery(...)` |
| `select` | The component sees only its slice | Leave it out | Nothing, but an inline function re-runs on every render |

### Server Components and hydration

```tsx
// app/posts/page.tsx, a Server Component
import { dehydrate, HydrationBoundary, noop, QueryClient } from "@tanstack/react-query";

export default async function PostsPage() {
    const queryClient = new QueryClient(); // a new client per request
    await queryClient.query({ queryKey: ["posts"], queryFn: getPosts }).catch(noop); // the client can retry

    return (
        <HydrationBoundary state={dehydrate(queryClient)}>
            <Posts /> {/* a Client Component calling useQuery({ queryKey: ["posts"] }) */}
        </HydrationBoundary>
    );
}
```

A Server Component can `await` data and send the result as HTML plus the RSC payload. That payload is a serialized description of the rendered tree ([Server Components guide](/articles/react-server-components-internals)). So render-only data may need no client cache. Once you want refetching, mutations or background sync over it, you want it in the client cache.

The pattern: fetch on the server, **dehydrate** the cache into plain data, send it with the page, and **hydrate** it into the client `QueryClient`. The client's `useQuery` finds the data and skips its first fetch. From there it behaves like any client cache.

| Rule | Why |
|---|---|
| Create a server `QueryClient` per request | A module-level client would share one user's data with the next |
| Set a client `staleTime` above 0 | Otherwise the client refetches the moment it hydrates |
| Do not render query data in a Server Component too | The server-rendered copy will not update when the client refetches |
| Pending queries can be dehydrated (since 5.40) | Opt in with `shouldDehydrateQuery`, then start a prefetch without awaiting it and stream the result |

For Next.js, the experimental `@tanstack/react-query-next-experimental` package goes further. A `useSuspenseQuery` starts fetching on the server during server-side rendering (SSR) and streams the result into the client cache. The [Server Components guide](/articles/react-server-components-internals) covers the framework side.

### Try it

In the structural sharing snippet, change `likes` in `after` back to `3` and predict the three lines. They should print `true`, `true`, `true`. Identical JSON keeps the old reference at every level, so nothing re-renders.

## 16. Pitfalls and debugging

Each data-fetching symptom points at one mechanism from the earlier sections, and fixing the mechanism beats patching the symptom.

### The short version

Most data-fetching bugs come from a short list. Server data sits in client-state tools, or an effect copies query data into local state. A key misses an input, or `staleTime` and `gcTime` get confused. A spinner watches the wrong flag, `enabled` comes from a wrong value, or Suspense creates a waterfall.

Each one breaks a single mechanism, and naming it is the fix. To debug, open the TanStack Query Devtools before you touch code. Read the query's key, `status`, `fetchStatus`, freshness and observer count. Then fix the problem at its level: key, freshness, status, invalidation or gating.

### The anti-patterns

Most anti-patterns show up as a symptom in the table further down. These four do not, so catch them in review.

| Anti-pattern | Mechanism it breaks | Fix |
|---|---|---|
| Server data in `useState`, Redux or Context | Server state is a cache (section 1) | Keep it in the query cache. A server response in Redux is the smell |
| Copying `data` into state with an effect | One source of truth | Use `data`, `select` to transform, or seed a form draft once |
| Functions or class instances in keys | Keys are hashed with `JSON.stringify` (section 3) | Key by ids, primitives and plain objects |
| Nested suspending queries | Suspense waterfalls (section 14) | Hoist with `useSuspenseQueries`, or prefetch |

### The effect copy

```jsx
// WRONG: a second source of truth, kept in sync by an effect
const { data } = useQuery({ queryKey: ["user", id], queryFn: () => fetchUser(id) });
const [user, setUser] = useState(null);
useEffect(() => setUser(data), [data]);

// RIGHT: read the cache, and keep only the draft as local state
const { data: user } = useQuery({ queryKey: ["user", id], queryFn: () => fetchUser(id) });
const [draftName, setDraftName] = useState(null); // null means "not edited yet"
const name = draftName ?? user?.name ?? "";
```

The wrong version combines derived state with an effect whose only job is to copy, and the copy drifts as soon as a refetch lands. To edit, let a form own a draft and submit through a mutation. The cache is already the store.

v5 removed `onSuccess`, `onError` and `onSettled` from `useQuery`, because they invited this copy. Mutation callbacks remain.

### Symptoms and mechanisms

| Symptom | Likely mechanism | What to check in the Devtools | Fix |
|---|---|---|---|
| Old data after a save | Missing or mis-keyed invalidation | The query should flip to fetching after the mutation | Invalidate a key that prefix-matches the query |
| Spinner never goes away | `isPending` on a disabled query | `pending` with `idle`, and `enabled: false` | Bind the spinner to `isLoading` |
| Spinner flashes on every refetch | Spinner bound to `isFetching` | `success` with `fetching` | Bind it to `isLoading` |
| List flickers on page change | A new key means a new empty entry | A fresh `pending` entry per page | `placeholderData: keepPreviousData` |
| Changing an input does not refetch | Input missing from the key, the most common "it does not update" bug | The key does not change when the input does | Add the input to the key |
| A query never runs | `enabled` is false or built from a wrong value, or the component is not mounted | `idle` and `pending`, or no observers | Gate on a clear boolean, or fix the mount |
| Refetches too often | `staleTime` left at 0, or `gcTime` tuned by mistake | The entry turns stale at once | Raise `staleTime`, not `gcTime` |
| Memory grows, or too many cold loads | `gcTime` too high or too low | Inactive entries piling up or vanishing | Tune `gcTime` to how users navigate |
| Same request twice | Keys that differ subtly, or Strict Mode | Two entries that look almost identical | Make the keys identical |

### The same request twice

Identical keys always share one request, so a double request usually means two keys that only look alike. An extra field is enough, or the number and string ids from the section 3 hash snippet.

Strict Mode is the other cause, and only in development. `useQuery` usually fetches once, because the remount joins the request already running. But if your `queryFn` reads `signal`, the unmount aborts the first request, so the Network tab shows one cancelled request and a second one.

### Set up the Devtools

```jsx
import { ReactQueryDevtools } from "@tanstack/react-query-devtools";

<QueryClientProvider client={queryClient}>
    <App />
    <ReactQueryDevtools initialIsOpen={false} />
</QueryClientProvider>;
```

The panel lists every query with its key, status, freshness and observer count. It makes the cache visible, so it is your first instrument. Production builds leave it out by default.

Take a real data bug from your own app and read the query in the Devtools before you change any code. Name the section whose mechanism it implicates, and fix it there.

## The whole thing in one list

1. Fetched data is a cache of server state, and a server-state library is a manager for that cache.
2. A query key is the entry's address, hashed by value, and it must contain every input the fetch uses.
3. `status` says whether you have data and `fetchStatus` says whether a request runs, so spinners use `isLoading`.
4. Stale-while-revalidate serves the cached copy at once and refetches in the background only when it is stale.
5. `staleTime` (default 0) decides freshness while data is in use, and `gcTime` (default 5 minutes) decides retention after.
6. One entry per key means many components share one copy and one in-flight request.
7. Mount, focus and reconnect refetch only stale data, while `refetchInterval` polls regardless.
8. Queries retry 3 times with backoff, pause offline, and abort through the `signal` your `queryFn` receives.
9. Mutations make the cache honest by invalidating keys or writing data, and optimistic updates must roll back.
10. `useSuspenseQuery` and `use()` move loading to boundaries, and the cache reaches React through `useSyncExternalStore`.
