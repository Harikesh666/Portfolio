A dashboard feels slow. Every keystroke in its search box makes the whole page stutter. The React DevTools Profiler, which records what rendered and why, shows 200 components rendering per letter.

```jsx
const AppContext = createContext(null);

function App() {
    const [user, setUser] = useState(null);
    const [search, setSearch] = useState(""); // typed into one small input

    return (
        <AppContext value={{ user, setUser, search, setSearch }}>
            <Header />
            <Dashboard />
        </AppContext>
    );
}
```

No library caused it, and a library is not the first fix. The search text lives at the top, inside a context every component reads. So each keystroke changes a value that 200 components depend on.

This guide shows how to decide where each piece of state lives and who owns it. The ladder runs from local state up to Context, stores and server caches. It also opens the two React 19 mechanisms behind the upper rungs: context propagation and `useSyncExternalStore`.

## 1. Where state lives decides what re-renders

Most "which state library should we use" debates start in the wrong place. The question that decides whether an app stays maintainable comes first: where does each piece of state live, and who owns it?

### The short version

State management is mostly not about tools. For each piece of state you decide two things. Its **location** is the component that holds it. Its **ownership** is the component responsible for changing it.

Location matters because a state change re-renders the owner and, by default, its whole subtree. State at the root re-renders the app. So keep state in the lowest component that uses it. Climb to lifting, Context or a store only when forced, because each rung costs more. Server data and URL state sit on their own axes.

### State is not one thing

Look at the state of a typical page.

```js
const pageState = {
    inputText: "react", // one input reads it, changes every keystroke
    isModalOpen: false, // one modal
    theme: "dark", // read everywhere, changes rarely
    currentUser: { id: 7 }, // read everywhere, owned by the server
    products: [], // a copy of server data
    selectedRowId: 3, // shared by a table and a detail panel
};
```

These values have different lifetimes, owners and sharing needs. Treating them as one pile is the root cause of most state-management pain. So ask of each piece: who needs this, and who changes it?

### Location is blast radius

`React.memo` wraps a component so it skips re-rendering when its props did not change. With no such boundaries in the way, a state change re-renders the owner and every component below it. Here is a simplified teaching model you can run in Node.

```js
const tree = {
    App: ["Header", "Page"],
    Header: [],
    Page: ["Sidebar", "Search"],
    Sidebar: [],
    Search: ["Input", "Results"],
    Input: [],
    Results: [],
};

function rerendered(owner) {
    return [owner, ...tree[owner].flatMap(rerendered)];
}

console.log(rerendered("Input").join(" "));
console.log(rerendered("App").join(" "));
```

```text role="output"
Input
App Header Page Sidebar Search Input Results
```

Only the owner moved between the two lines. That is why <Mark kind="marker" wraps>the location of state decides the blast radius</Mark> of every change to it. Location is a performance and correctness decision, not a matter of style.

### Ownership is traceability

```jsx
function Table() {
    const [selectedId, setSelectedId] = useState(null); // Table owns it
    return <Rows selectedId={selectedId} onSelect={setSelectedId} />; // Rows can only ask
}
```

In React's one-way data flow, the component that calls `useState` or `useReducer` owns that state and alone calls the setter. Every other component receives the value as a prop, to read it, or a callback, to ask for a change.

Clear ownership makes data flow traceable. When a value is wrong, you look at its owner, not at fifteen components that might have touched it. Diffuse ownership, where many components mutate one shared blob, makes large apps hard to reason about.

### The ladder

| Rung | Owner | Use it when | What it costs |
|---|---|---|---|
| Local state | The component that uses it | One component needs it | Nothing extra |
| Lifted state | The nearest common ancestor | A few nearby components share it | A bigger re-render, props to thread |
| Context | A provider component high up | Many distant components read an ambient value | Implicit links, every consumer re-renders |
| External store | A module outside React | Wide sharing, frequent changes, each reader using a different part | A dependency and its concepts |
| Server cache | The server, cached by a query library | The data lives on a server | A separate axis, not a higher rung |
| URL | The address bar | View state worth sharing in a link | A separate axis, not a higher rung |

Each rung up widens the blast radius, spreads ownership or adds a dependency. Most state belongs on the first rung, and most "we need Redux" conversations turn out to be "we put state on the wrong rung."

## 2. Colocation: keep state as low as it will go

A form sits deep in the tree, but its state lives far above it, where it seemed easy to find. Every keystroke re-renders half the app. So you start wrapping components in `React.memo` to hold the re-renders back.

### The short version

Keeping each piece of state as close as possible to where it is used is called **colocation**. Ideally the state sits inside the one component that uses it. A state change re-renders its owner and that owner's subtree, so the lower the owner, the smaller the re-render.

Lifting state higher than needed is the most common self-inflicted React performance problem, and only the Profiler shows it. Colocation also ties the state's lifetime to its owner, so it disappears on unmount. And it keeps a component's whole story readable in one place.

### The propagation rule

```jsx
function Page() {
    const [query, setQuery] = useState(""); // held three levels too high
    return (
        <>
            <SearchBox query={query} onChange={setQuery} />
            <Chart />
            <ActivityFeed />
        </>
    );
}
```

When a component's state changes, React re-renders it, then its children, and theirs. It stops only at a bailout. One kind is a `React.memo` boundary whose props are unchanged. The other is an element that is the very same object as last render, such as one passed in as `children`.

Here every keystroke re-renders `Chart` and `ActivityFeed`, though neither reads `query`. `Page` creates fresh `<Chart />` and `<ActivityFeed />` elements on each render.

### Move the state down

```jsx
function Page() {
    return (
        <>
            <SearchBox />
            <Chart />
            <ActivityFeed />
        </>
    );
}

function SearchBox() {
    const [query, setQuery] = useState(""); // now it re-renders only SearchBox
    return <input value={query} onChange={(event) => setQuery(event.target.value)} />;
}
```

Wrapping `Chart` in `React.memo` would have treated the symptom, spending memoization to contain a re-render that need not exist. Moving the state down removes the re-render at its source.

### State lives and dies with its owner

```jsx
{isEditing && <EditForm />} // close the form and its draft state is gone
```

React keeps state by a component's position in the tree, which the React docs call **preserving and resetting state**. Local state is created when its owner mounts and discarded when it unmounts, so it cleans up after itself.

Lifted state outlives the components that use it. A wizard that must remember earlier steps wants that. More often it is a stale-data bug, such as a parent still holding a child's form draft after the child is gone.

Day to day, colocation helps readability even more than speed. A reader sees the whole story in one component, instead of tracing a prop back through every layer.

### The rule, and its limit

Start every piece of state local, and lift it only when a second component genuinely needs it, as section 3 shows. Do not pre-lift "in case," or to a convenient central place.

Colocation does not mean keeping two copies of one value so each stays local. Two local copies drift apart, which is the bug section 4 removes.

### Try it

In a React app, render this `Parent` and type into the input.

```jsx
function Child({ name }) {
    console.log("render", name);
    return <p>{name}</p>;
}

function Parent() {
    const [text, setText] = useState("");
    return (
        <>
            <input value={text} onChange={(event) => setText(event.target.value)} />
            <Child name="chart" />
            <Child name="feed" />
        </>
    );
}
```

Both children log on every keystroke. Move the input and its state into its own `SearchBox` component, and the children go silent, with no `React.memo` anywhere. Strict Mode, React's development-only checking mode, may print each line twice.

## 3. Lifting state up, and what it costs

A list and a detail panel both need to know which item is selected. You know the answer is "lift state up," but you are not sure how high is too high.

### The short version

Siblings cannot share state directly, because data flows only down and neither is the other's ancestor. So you move the state to their nearest common ancestor, which is called **lifting state up**. The ancestor passes the value down as a prop, and passes callbacks down so children can request changes.

This is React's own answer to sharing. Lift to the nearest common ancestor and no higher, because the owner roots every re-render the state triggers. Lifting has two costs. The owner's subtree re-renders on every change, and the value must pass through any components in between, which is called prop drilling.

### One owner, controlled children

```jsx
function Panel() {
    const [selectedId, setSelectedId] = useState(null); // the single source of truth
    return (
        <>
            <List selectedId={selectedId} onSelect={setSelectedId} />
            <Detail selectedId={selectedId} />
        </>
    );
}
```

`Panel` is the single owner. `List` and `Detail` are now **controlled**: they reflect the value and request changes to it. A controlled `<input>` works the same way, which is why it takes both `value` and `onChange`. The value flows down and change requests flow up.

<GuideFigure figure="sm-lift" />

Lift higher "to be safe," and the same change re-renders components that have nothing to do with the state. The rule is "as high as necessary, no higher," which is colocation applied in the other direction.

### Cost one: the owner's subtree re-renders

A selected-row value that changes on a click re-renders one panel, which is cheap. Lifting hurts only when the value changes very often, such as every keystroke, and the subtree is large.

| Situation | Fix |
|---|---|
| Only one child really needs the fast value | Push the state back down (section 2) |
| A large sibling does not read the value | Put a `React.memo` boundary around it |
| Many distant components read a fast value | Step outside the tree into a store (section 12) |

### Cost two: prop drilling, and narrow props

When the readers sit far below the owner, the value and its callbacks must pass through every component in between. Section 7 decides when that is fine. Whatever the depth, pass narrow props.

```jsx
// Narrow: each child's contract says exactly what it uses
<List selectedId={selectedId} onSelect={setSelectedId} />

// Wide: every child is coupled to the whole state shape
<List state={state} setState={setState} />
```

Narrow props keep each child's dependencies clear. The whole state object and the raw setter couple every child to the full shape and spread ownership back out.

### Try it

In a React app with React DevTools, render two siblings that share a value through their parent.

```jsx
function Control({ value, onChange }) {
    return <input value={value} onChange={(event) => onChange(event.target.value)} />;
}

function Display({ value }) {
    return <p>You typed: {value}</p>;
}

function Parent() {
    const [value, setValue] = useState(""); // the nearest common ancestor owns it
    return (
        <>
            <Control value={value} onChange={setValue} />
            <Display value={value} />
        </>
    );
}
```

Then move the `useState` two levels higher and record a keystroke in the Profiler. It shows the extra components that now re-render for no reason.

## 4. Do not store what you can derive

You keep a `filteredItems` state next to `items` and `filter`, and an effect recomputes it. Sometimes the screen shows stale results. The bug is that `filteredItems` should never have been state.

### The short version

A value you can compute from existing state or props is a **derivation**, not state. Compute it during render instead of storing it. A stored copy makes two sources of truth for one fact. They drift apart, which produces the whole family of "these two things disagree" bugs.

A derived value is correct by construction, because every render recomputes it from the only real source. Syncing a copy with an effect also costs an extra render. Wrap the computation in `useMemo` only when profiling shows it is expensive. By the same rule, store `selectedId` and derive the selected item.

### Two sources of truth drift

Run this in Node.

```js
let items = ["apple", "avocado", "banana"];
let filter = "a";
let filteredItems = items.filter((item) => item.startsWith(filter)); // a stored copy

items = [...items, "apricot"]; // one code path forgets to update the copy

console.log("stored:", filteredItems.length);
console.log("derived:", items.filter((item) => item.startsWith(filter)).length);
```

```text role="output"
stored: 2
derived: 3
```

<MarginNote note="keep each fact in one place">

The stored copy went stale because nothing forced it to follow its inputs. The derived value cannot go stale, because it has no existence apart from its inputs.

</MarginNote>

### The effect version, and the fix

```jsx
// Anti-pattern: a derived value stored as state and synced with an effect
const [items, setItems] = useState([]);
const [filter, setFilter] = useState("");
const [filteredItems, setFilteredItems] = useState([]);
useEffect(() => {
    setFilteredItems(items.filter((item) => item.name.includes(filter)));
}, [items, filter]);
```

The effect version is slower as well as buggier. The component renders with the old `filteredItems`. Then the effect runs after the **commit**, the step where React applies a render to the DOM, and its setter causes a second render.

```jsx
// Derive during render: one source of truth, one render
const [items, setItems] = useState([]);
const [filter, setFilter] = useState("");
const filteredItems = items.filter((item) => item.name.includes(filter));
```

The React docs say that when no external system is involved, you should not need an effect. If an effect only calls `setX` from other state or props, `X` should be a derivation.

### When the derivation is expensive

```jsx
const sorted = useMemo(
    () => [...items].sort(compareByPrice), // runs again only when items changes
    [items],
);
```

Sorting a large list on every render wastes work when most renders did not change the inputs. `useMemo` caches the result and recomputes only when an input changes. The value stays a derivation, so it still cannot desync. The React Compiler, a build-time tool that adds memoization automatically, inserts much of this for you.

### Store the id, derive the item

```jsx
const [items, setItems] = useState(initialItems);
const [selectedId, setSelectedId] = useState(null);
const selectedItem = items.find((item) => item.id === selectedId); // derived, never stale
```

A `selectedItem` object stored beside `items` goes stale when the item is edited. A `count` stored beside an array is the same mistake. The general rule is to <Mark kind="underline" wraps>store the minimal set of independent facts</Mark> and derive everything else. Every redundant piece of state is a future desync.

### Try it

In a React app, render `<FilteredList items={["apple", "avocado", "banana"]} />` and type `p` into the input.

```jsx
function FilteredList({ items }) {
    const [filter, setFilter] = useState("");
    const [filteredItems, setFilteredItems] = useState(items);
    useEffect(() => {
        setFilteredItems(items.filter((item) => item.includes(filter)));
    }, [items, filter]);
    console.log("render", JSON.stringify(filter), filteredItems.length);
    return <input value={filter} onChange={(event) => setFilter(event.target.value)} />;
}
```

```text role="output"
render "p" 3
render "p" 1
```

The first render pairs the new filter with the old list, which is the stale moment. React then runs the effect and renders a second time. Strict Mode may double each line. Replace the state and effect with `const filteredItems = items.filter(…)`, and each keystroke logs one correct line.

## 5. Shaping state so it cannot contradict itself

A component keeps `isLoading`, `isError`, `error` and `data` as four separate values. It keeps reaching states that should be impossible, such as an error flag with no error. Each bug is a different illegal combination of the flags.

### The short version

The shape of your state decides which bugs are possible. Two principles do most of the work. Never keep two pieces of state that encode one fact or can disagree. And when several flags describe one situation, model it as one value with named states.

Three independent booleans form 8 combinations, but only 4 are legal. A single `status` value can form only the legal ones, so the others cannot be written down. Flat, normalized shapes keep immutable updates local. Good structure makes whole categories of bugs impossible instead of merely unlikely.

### Count the states

Run this in Node.

```js
const combos = [];
for (const isLoading of [false, true]) {
    for (const isError of [false, true]) {
        for (const hasData of [false, true]) {
            combos.push({ isLoading, isError, hasData });
        }
    }
}

const legal = combos.filter(
    ({ isLoading, isError, hasData }) => Number(isLoading) + Number(isError) + Number(hasData) <= 1,
);
console.log(combos.length, "representable,", legal.length, "legal");
```

```text role="output"
8 representable, 4 legal
```

The legal states are idle, loading, success with data and error with an error. The other four, such as loading and error at once, are bugs waiting to be reached.

### One status value

```js
// Only the legal states can be constructed.
// { status: "idle" }
// { status: "loading" }
// { status: "success", data }
// { status: "error", error }
const [request, setRequest] = useState({ status: "idle" });
```

Now "loading and error at once" is not a bug to prevent but a state that cannot be written down. The principle is called **making illegal states unrepresentable**. Rendering collapses into a switch over the legal states.

```jsx
switch (request.status) {
    case "idle":
        return <SearchPrompt />;
    case "loading":
        return <Spinner />;
    case "success":
        return <Results data={request.data} />; // data always exists here
    case "error":
        return <ErrorMessage error={request.error} />;
}
```

### Keep state flat, and normalize collections

```js
// Normalized: items in a lookup by id, plus an array of ids for order
const state = {
    ids: [1, 2],
    entities: {
        1: { id: 1, title: "Buy milk", done: false },
        2: { id: 2, title: "Write guide", done: true },
    },
};

const next = {
    ...state,
    entities: { ...state.entities, 2: { ...state.entities[2], done: false } }, // one entry changes
};
```

React detects changes by identity, so an immutable update must create a new object at every level it changes. The deeper the nesting, the more places an update can go wrong. A normalized shape keeps items in a lookup by id, so updating one item touches one entry. Redux Toolkit ships `createEntityAdapter` for this `ids` plus `entities` shape.

### What does not belong in state

```jsx
const timerId = useRef(null); // changing it never re-renders
```

Class instances and functions generally do not belong in state, because they complicate updates and equality. A mutable value that rendering never reads, such as a timer id, belongs in a ref.

A well-shaped state removes a whole layer of validation and "this should never happen" comments, because the bad situations can no longer be expressed.

### Try it

Every independent flag doubles the representable states. Run this in Node, then add a fifth flag and predict the count.

```js
const flags = ["isLoading", "isError", "hasData", "isRefreshing"];
console.log(2 ** flags.length, "representable with", flags.length, "flags");
```

```text role="output"
16 representable with 4 flags
```

With a `status` value, adding "refreshing" adds one state, not eight. In TypeScript, type `request` as a union of the legal shapes, and an illegal combination fails to compile.

## 6. Reducers and state machines

Your update logic has spread across a dozen handlers, each calling several setters, and one update fires while a related one does not. "Use a reducer" sounds like ceremony. It is how the structure from section 5 stays enforced as the code changes.

### The short version

A **reducer** gathers every way a piece of state can change into one pure function, `(state, action) => newState`. The state changes live in one readable place that you can test without React. The reducer is the only code that writes the state, so it enforces the shape from section 5.

A **state machine** goes further. It names the states and lists, for each one, which events do anything, and it ignores the rest. So a second submit while submitting is not a bug you guard against. It is a move between states that does not exist, enforced every day, not only on the day you refactored.

### useState is a reducer with a built-in function

```js
// From ReactFiberHooks.js, React 19 (types removed).
function basicStateReducer(state, action) {
    return typeof action === "function" ? action(state) : action;
}
```

When `useState` updates, React runs the same reducer machinery as `useReducer`, with this function as the reducer. So choosing between them is about where update logic lives, not performance. Several `setState` or `dispatch` calls in one event still render once, which the [scheduler and lanes guide](/articles/react-scheduler-and-lanes-internals) explains as batching.

### A reducer shaped as a machine

Run this in Node.

```js
function reducer(state, action) {
    switch (state.status) {
        case "idle":
            if (action.type === "FETCH") return { status: "loading" };
            return state; // anything else from idle does nothing
        case "loading":
            if (action.type === "SUCCESS") return { status: "success", data: action.data };
            if (action.type === "ERROR") return { status: "error", error: action.error };
            return state; // a second FETCH while loading does nothing
        case "success":
        case "error":
            if (action.type === "FETCH") return { status: "loading" };
            return state;
    }
}

let state = { status: "idle" };
const actions = [
    { type: "FETCH" },
    { type: "FETCH" },
    { type: "SUCCESS", data: ["a", "b"] },
    { type: "ERROR", error: "too late" },
];
for (const action of actions) {
    state = reducer(state, action);
    console.log(action.type.padEnd(7), "->", state.status);
}
```

```text role="output"
FETCH   -> loading
FETCH   -> loading
SUCCESS -> success
ERROR   -> success
```

The duplicate `FETCH` and the late `ERROR` changed nothing, and `success` always carries `data`. You added no defensive checks. You described the legal moves and let everything else fall through.

### Two perks that matter for architecture

```jsx
const [state, dispatch] = useReducer(reducer, { status: "idle" });
```

First, `dispatch` keeps the same identity for the life of the component. Passing it deep or through Context never causes a re-render by itself, which section 10 relies on. Second, a reducer is pure. Strict Mode calls it twice in development, so a reducer that mutates state shows its bug early.

### When to use a machine library

| Need | Tool |
|---|---|
| A few states and moves in one component | A reducer shaped as a machine |
| Nested or parallel states, guards, visual charts | A state machine library such as XState |
| Side effects orchestrated by the machine itself | A state machine library |

The point is the modeling discipline, named states and explicit moves between them. A plain reducer carries it, and a library is an upgrade for when it outgrows a `switch`.

### Try it

Add these lines to the Node example and predict each status first. After the earlier output, the new lines print this.

```js
console.log(reducer({ status: "idle" }, { type: "ERROR", error: "boom" }).status);
console.log(reducer({ status: "error", error: "boom" }, { type: "FETCH" }).status);
```

```text role="output"
idle
loading
```

An error cannot arrive before a fetch starts, and a retry from the error state works. In a React app, wire `dispatch({ type: "FETCH" })` to a button and click it twice quickly. The second click is a no-op you never special-cased.

## 7. Prop drilling: when it is fine and when it is a smell

You lifted some state, and now `value` and `onChange` pass through five components that only hand them along. It feels wrong, but you have also heard that Context is overused.

### The short version

Passing a prop through components that do not use it, only to reach a deep one that does, is called **prop drilling**. Passing a prop one or two levels to a child that uses it is not drilling. That is props doing their job.

Drilling costs clarity, not speed. A little of it is often clearer than Context, because explicit props show where a value comes from. It becomes a smell when one value threads through many layers and clutters their signatures. Before reaching for Context, try composition: pass the deep child down from where the data lives.

### What drilling looks like

```jsx
function Page({ user }) {
    return <Layout user={user} />; // Layout ignores user
}

function Layout({ user }) {
    return <Sidebar user={user} />; // so does Sidebar
}

function Sidebar({ user }) {
    return <Avatar user={user} />; // only Avatar reads it
}
```

Every middle signature now advertises a prop it ignores, and a reader tracing `user` must follow it through each layer. Speed is not the issue. Passing a prop is nearly free, and a well-placed `React.memo` stops unrelated re-renders.

<MarginNote note="explicit flow is a feature">

Still, explicit props make the data flow visible in the code. Context makes the link implicit, so a consumer just knows a value and you must go and find the matching provider.

</MarginNote>

### When it becomes a smell

| Signal | Verdict |
|---|---|
| One or two levels, and the child uses the prop | Not drilling. Keep it. |
| A few pass-through levels on one path | Fine. Explicit flow is worth it. |
| The same value threads through many layers or branches | A smell |
| The value is ambient, like a theme, user or locale | A real case for Context (section 8) |

Context has costs of its own: the re-renders in sections 9 to 11, and every reader depends on a provider above it. Trading two levels of explicit props for that is usually a bad trade. The React docs agree: first ask whether passing props is fine, and whether the deep component needs to be that deep.

### Composition before Context

```jsx
function Page({ user }) {
    return (
        <Layout>
            <Sidebar>
                <Avatar user={user} /> {/* rendered where the data already lives */}
            </Sidebar>
        </Layout>
    );
}

function Layout({ children }) {
    return <div className="layout">{children}</div>; // no user prop anymore
}
```

If a layout only drills props to render one child, let the parent with the data render that child and pass it as `children`. This often dissolves drilling without Context's implicit link.

### Try it

In a React app, build both versions of `Page` above, and add this line as the first line of `Layout` in each.

```jsx
console.log("Layout props:", Object.keys(props)); // write Layout(props) to see them all
```

The drilled version logs `["user"]`, a prop `Layout` never uses. The composed version logs `["children"]`, and `Avatar` still receives `user` from the component that owns it.

## 8. Context is a transport, not a state manager

You reach for Context expecting it to manage shared state. It cannot subscribe a reader to part of a value, prevents no re-renders, and needs a `useState` beside it to hold anything. The confusion is a category error.

### The short version

React's **Context** makes a value available to a whole subtree without passing it through props at every level. That is its only job, a form of **dependency injection**: a component receives what it needs from outside.

It does not store state, manage updates or reduce re-renders. You hold the state with `useState` or `useReducer` above, and Context delivers it to deep readers.

So "Context versus Redux" is a confused comparison. The real pair is "Context plus `useState`" against "an external store." In React 19 you render the context itself as the provider, `<ThemeContext value={theme}>`. Context fits ambient values that change rarely, such as a theme, the current user or a locale.

### Create, provide, read

```jsx
import { createContext, useContext, useMemo, useState } from "react";

const ThemeContext = createContext(null); // null: the value with no provider above

function ThemeProvider({ children }) {
    const [theme, setTheme] = useState("light"); // the state lives here
    const value = useMemo(() => ({ theme, setTheme }), [theme]); // section 10 explains why
    return <ThemeContext value={value}>{children}</ThemeContext>; // Context carries it
}

function useTheme() {
    const context = useContext(ThemeContext);
    if (context === null) throw new Error("useTheme must be used inside ThemeProvider");
    return context;
}
```

`createContext` makes a channel, and its argument is the default value, used only when no provider sits above a reader. A provider puts a value on the channel for its subtree. A reader gets the nearest provider above it, never one rendered by the same component.

Notice the division of labor. `useState` manages the theme and Context delivers it. The `useTheme` hook gives readers one clean way in, with a helpful error if the provider is missing.

### The React 19 provider syntax

```jsx
<ThemeContext value={value}>{children}</ThemeContext> // React 19
<ThemeContext.Provider value={value}>{children}</ThemeContext.Provider> // still works
```

Since React 19, `createContext` sets `context.Provider = context`. Save this as an `.mjs` file in any project with React 19 installed, and run it with Node.

```js
import { createContext } from "react";

const ThemeContext = createContext("light");
console.log(ThemeContext.Provider === ThemeContext);
```

```text role="output"
true
```

Both lines above render the same object. The React docs call `.Provider` the legacy spelling, and the React 19 release post says a future version will deprecate it.

### useContext and use(Context)

```jsx
function Banner({ show }) {
    if (!show) return null;
    const { theme } = use(ThemeContext); // allowed: use() may run inside a condition
    return <div className={theme}>Welcome back</div>;
}
```

`useContext` is a Hook, so it must run at the top level of a component, never inside an `if` or a loop. React 19's `use(ThemeContext)` reads the same value but may run inside conditions and loops. Both subscribe the component to changes in the same way.

### Context does not hold anything

Context is <Mark kind="circle">a transport</Mark> with no memory. A new value always comes from the state that feeds the provider. And Context optimizes nothing: every reader re-renders when the value changes, with no way to subscribe to part of it.

| Value | Good fit for Context? | Why |
|---|---|---|
| Theme, locale, current user | Yes | Read in many places, changes rarely |
| Feature flags | Yes | Ambient, almost never changes |
| Search text typed every keystroke | No | Re-renders every reader per key |
| A large object, each reader using one part | No | Every reader re-renders for any field |

For values that change often, or that each reader uses a different part of, delivering the whole value to everyone is the wrong model. Using Context more carefully does not fix it, and sections 11 and 12 explain why.

### Try it

In a React app, wrap a few layers of components in the `ThemeProvider` above, and put this button at the bottom.

```jsx
function ThemeToggle() {
    const { theme, setTheme } = useTheme();
    return <button onClick={() => setTheme(theme === "light" ? "dark" : "light")}>{theme}</button>;
}
```

The layers in between carry no theme prop. Then replace the provider's `useState` with a constant `"light"` and a no-op setter. The button still reads the value but can no longer change it, because Context transports state and does not hold it.

## 9. How a context change reaches its readers

You put a value in Context, and now every reader re-renders constantly, even behind `React.memo` and even when the part it reads did not change. You suspect Context is slow. The real cause is almost always how you built the provider's value.

### The short version

When a provider renders, React compares its new `value` with the old one using `Object.is`, an identity check. If they differ, every component that reads that context re-renders. <Mark kind="marker" wraps>The unit of change is the whole value</Mark>, never one field. `React.memo` cannot stop it, because React checks context reads before memo may skip a component.

The common trap is an inline object such as `value={{ user, setUser }}`. It is a new object on every render, so every reader re-renders on every render. React 19 finds readers lazily, when it is about to skip a subtree, but the result is the same.

### Object.is compares identity

Run this in Node.

```js
const value = { theme: "dark" };
console.log(Object.is(value, value)); // the same object
console.log(Object.is(value, { theme: "dark" })); // equal contents, new object
console.log(Object.is(NaN, NaN), NaN === NaN); // where Object.is differs from ===
```

```text role="output"
true
false
true false
```

Equal contents do not make equal values, and React never looks inside a context value.

### How React 19 finds the readers

```js
// Simplified teaching version of lazy propagation (ReactFiberNewContext.js).
function propagate(fiber, context, marked = []) {
    for (const child of fiber.children) {
        if (child.reads.includes(context)) {
            marked.push(child.name); // React visits its children during render
            continue;
        }
        propagate(child, context, marked);
    }
    return marked;
}

const leaf = (name, reads = []) => ({ name, reads, children: [] });
const provider = {
    name: "AppContext",
    reads: [],
    children: [
        {
            name: "Layout (memo)",
            reads: [],
            children: [leaf("ThemeButton", ["AppContext"]), leaf("UserMenu", ["AppContext"]), leaf("Footer")],
        },
    ],
};

// Only user changed, but React tracks the context, not the field.
console.log(propagate(provider, "AppContext"));
```

```text role="output"
[ 'ThemeButton', 'UserMenu' ]
```

Each fiber, React's object for one component instance, keeps a list of the contexts it read in its last render. A provider only pushes its new value while React renders it. Before React skips a subtree with no pending work, it calls `lazilyPropagateParentContextChanges`.

That function looks up the tree for providers whose value changed by `Object.is`. A **lane** is React's priority bit for an update, and `childLanes` records the lanes pending below a fiber. The function walks down, marking each matching reader with the render's lanes and each ancestor's `childLanes`. The [scheduler and lanes guide](/articles/react-scheduler-and-lanes-internals) covers both.

### Why React.memo does not help

```jsx
const ThemeButton = memo(function ThemeButton() {
    const { theme } = useContext(AppContext); // a context dependency, not a prop
    return <button className={theme}>Toggle</button>;
});
```

`React.memo` lets a component skip rendering when its props are unchanged. But even when the props match, React first runs `checkScheduledUpdateOrContext`, which also compares the component's context reads. A changed context counts as work, so memo never gets to skip.

This is by design, because a reader exists to respond to its context. So memo on the readers cannot fix a context re-render problem.

### The inline-object trap

```jsx
function AppProvider({ children }) {
    const [user, setUser] = useState(null);
    const [theme, setTheme] = useState("light");
    // Bug: a brand-new object literal on every render
    return <AppContext value={{ user, setUser, theme, setTheme }}>{children}</AppContext>;
}
```

`AppProvider` re-renders whenever its parent re-renders or either state changes, and each time `value={{ ... }}` builds a new object. So React re-renders every reader, even one that reads only `theme` when only `user` changed. Context is not slow. It was handed a new value every render and faithfully reported a change.

An inline array or function as the value has the same problem. This one mistake is the most common cause of "Context made my app re-render everywhere."

<GuideFigure figure="react-context-value" />

### The one big context

A stable value has a second trap. Put many unrelated pieces in one value, such as `{ user, theme, notifications, cart }`, and any change creates a new value. A reader of `theme` re-renders when `cart` changes. The size and mix of a context's value is a re-render hazard of its own.

### Before React 19

React 18 propagated eagerly: when a provider's value changed, `propagateContextChange` walked its whole subtree at once. React 19.0 switched on lazy propagation behind the `enableLazyContextPropagation` flag, and 19.1 removed the flag. Which components re-render did not change.

### Try it

In a React app, render the `AppProvider` above around these two memoized readers, plus a button that calls `setUser`.

```jsx
const ThemeReader = memo(function ThemeReader() {
    const { theme } = useContext(AppContext);
    console.log("ThemeReader render");
    return <p>{theme}</p>;
});

const UserReader = memo(function UserReader() {
    const { user } = useContext(AppContext);
    console.log("UserReader render");
    return <p>{user ?? "nobody"}</p>;
});
```

Change `user` and both readers log, past their memo. Re-render the provider's parent without changing any state, and both log again.

## 10. Taming context: stabilize, split, separate

You now know why Context over-renders. For ambient state it is still the right tool, so you want moves that stop the waste.

### The short version

Three fixes each target a cause from section 9. First, stabilize the provider's value with `useMemo`, so its identity changes only when its contents do. Second, split one big context into several, grouped by how often each part changes and who reads it. Third, put state and its `dispatch` in two separate contexts.

The third fix is the strongest. `dispatch` never changes identity, so a component that only dispatches never re-renders when the state changes. Together the fixes make Context perform well for ambient and moderately changing state. They cannot let a reader subscribe to part of one context's value, which is its hard ceiling.

### Fix one: stabilize the value

```jsx
const value = useMemo(() => ({ user, setUser }), [user]); // setUser is already stable
return <AppContext value={value}>{children}</AppContext>;
```

Here is what `useMemo` keeps between renders, as a simplified teaching version you can run in Node.

```js
let previous = null;
function memoValue(user, setUser) {
    if (previous !== null && Object.is(previous.user, user)) return previous.value;
    previous = { user, value: { user, setUser } };
    return previous.value;
}

const setUser = () => {};
const first = memoValue("Ada", setUser);
const second = memoValue("Ada", setUser); // the provider re-rendered, user did not change
const third = memoValue("Grace", setUser);
console.log(Object.is(first, second), Object.is(second, third));
```

```text role="output"
true false
```

When the provider re-renders for an unrelated reason, `value` keeps its identity, so readers stay quiet. The React Compiler often inserts this memoization for you. Either way, a provider value must keep its identity across renders where its contents did not change.

### Fix two: split by change rate and reader

```jsx
<UserContext value={userValue}>
    <ThemeContext value={themeValue}>
        <NotificationsContext value={notificationsValue}>{children}</NotificationsContext>
    </ThemeContext>
</UserContext>
```

A component that reads only the theme now ignores new notifications. Draw the lines by asking what changes together and who reads what. Keep a fast value out of any context that quiet readers depend on.

Pushed too far, splitting becomes provider sprawl, a deep stack of providers holding one field each. When you split purely for performance rather than logical grouping, you have outgrown Context.

### Fix three: separate state from dispatch

```jsx
const StateContext = createContext(null);
const DispatchContext = createContext(null);

function TodosProvider({ children }) {
    const [state, dispatch] = useReducer(reducer, initialState);
    return (
        <StateContext value={state}>
            <DispatchContext value={dispatch}>{children}</DispatchContext>
        </StateContext>
    );
}

function AddTodoButton() {
    const dispatch = useContext(DispatchContext); // never re-renders when todos change
    return <button onClick={() => dispatch({ type: "added" })}>Add</button>;
}
```

`dispatch` keeps its identity forever, so `DispatchContext` never reports a change, and only readers of `StateContext` re-render. The React docs present this reducer-plus-two-contexts pattern as the way to scale Context.

### Try it

In a React app, wrap the value of the over-rendering `AppProvider` from section 9 in `useMemo`. The readers stop logging when only the provider's parent re-renders. Then build `TodosProvider` from fix three, and add one line to `AddTodoButton`.

```jsx
console.log("AddTodoButton render"); // logs at mount, then never again
```

Render the button and a list that reads `StateContext` as `children` of `TodosProvider`, passed in from the component above it. Click a few times. The list logs on every click, and the button stays silent after mount, where Strict Mode may log it twice.

## 11. The selectivity gap: why Context does not scale

You stabilized and split your contexts, and it is still not enough. One context's value legitimately changes often, many readers each need a different part of it, and every change re-renders all of them.

### The short version

Context has no built-in way to subscribe to a **slice**, one part of a larger value. A reader re-renders when the value changes, full stop, and cannot say "only when `value.theme` changes." This is the **selectivity gap**. Splitting contexts works around it one whole context at a time, but within one context there is no selection.

A **selector** is a function that picks one slice out of a value. Context selectors have been an open React proposal since 2019, and React 19.3 has none. So when many readers take different slices of fast-changing shared state, move it into an external store, where each component subscribes to its slice.

### Whole value versus a selected slice

Run this in Node.

```js
const before = { count: 1, name: "Ada" };
const after = { ...before, count: 2 };

console.log("context sees a change:", !Object.is(before, after));

const selectName = (value) => value.name;
console.log("name selector sees a change:", !Object.is(selectName(before), selectName(after)));
```

```text role="output"
context sees a change: true
name selector sees a change: false
```

Context only runs the first comparison. A store runs the second, once per component selector.

<MarginNote note="all or nothing for every consumer">

A reader that uses only `name` still re-renders when `count` changes. It subscribed to the context, not to `name`, and no `memo` or `useMemo` on the reader side changes that.

</MarginNote>

### Selectors React does not have

```jsx
// Not a React API. The open RFC proposes something like this:
const name = useContextSelector(AppContext, (value) => value.name);
```

An RFC, or Request for Comments, is React's public design-proposal process. The "Context selectors" RFC, reactjs/rfcs pull request 119, opened in July 2019 and is still unmerged.

Userland libraries fill the gap. The best known, `use-context-selector` by Daishi Kato, only accepts contexts made with its own `createContext`. It builds selector subscriptions on top of React context rather than making native context selective.

### Why concurrency raises the price

A **transition** is an update marked non-urgent with `startTransition`. React renders it in short pausable chunks, and a more urgent update can restart it from scratch, as the [scheduler and lanes guide](/articles/react-scheduler-and-lanes-internals) shows. A context change that reaches 200 readers makes each such pass 200 components wide. The wider the broadcast, the more work every restarted pass repeats.

### When to step outside

| Shared state is… | Tool |
|---|---|
| Read by many, changes rarely | Context, stabilized and split |
| Read by many, changes often, read whole | Context can work, so measure first |
| Read by many, changes often, sliced differently | An external store with selectors |

No tuning closes the gap, because it is a missing feature. The fix is to keep that state outside React's tree, where updating one slice re-renders only its readers. React's bridge for that is `useSyncExternalStore`.

### Try it

Add a `count` selector to the Node example and predict the result. After the earlier output, the new line prints this.

```js
const selectCount = (value) => value.count;
console.log("count selector sees a change:", !Object.is(selectCount(before), selectCount(after)));
```

```text role="output"
count selector sees a change: true
```

Only the `count` reader would re-render in a store. In a React app, put `{ count, name }` in one context with a memoized reader for each field, and update `count`. Both readers log, which is the gap.

## 12. External stores and useSyncExternalStore

You are about to pick a store library, and they look nothing alike on the surface. You want the one idea they share, so the choice is about ergonomics.

### The short version

Every **external store** works the same way underneath. The state lives in a plain object or closure outside React's tree. Components subscribe through a selector that picks out the slice they read. When the state changes, the store calls its subscribers, and only components whose slice changed re-render.

React's bridge is `useSyncExternalStore(subscribe, getSnapshot)`. It prevents **tearing**, where one screen shows two versions of the same store. `getSnapshot` must return the same value while the store is unchanged. A store change re-renders synchronously, never as a transition. Once you see this shape, <Mark kind="underline" wraps>the libraries differ in how you declare state, not in what they do</Mark>.

### A store in 20 lines

Run this in Node.

```js
function createStore(initialState) {
    let state = initialState;
    const listeners = new Set();
    return {
        getState: () => state,
        setState(partial) {
            state = { ...state, ...partial }; // a new object, so changes are visible by identity
            listeners.forEach((listener) => listener());
        },
        subscribe(listener) {
            listeners.add(listener);
            return () => listeners.delete(listener); // the unsubscribe function
        },
    };
}

const store = createStore({ user: { name: "Ada" }, cart: [] });

function connect(label, selector) {
    let last = selector(store.getState());
    store.subscribe(() => {
        const next = selector(store.getState());
        if (!Object.is(last, next)) {
            last = next;
            console.log(label, "re-renders");
        }
    });
}

connect("UserName", (state) => state.user.name);
connect("CartBadge", (state) => state.cart.length);
store.setState({ cart: ["book"] });
```

```text role="output"
CartBadge re-renders
```

Changing the store skips React's top-down propagation entirely. The store calls each subscriber, which runs its selector and compares the result with the last one. `UserName` stayed quiet, because its selector still returned `"Ada"`.

This inverts Context's model. Context pushes the whole value down to every reader. A store lets each component pull exactly its slice, which closes the selectivity gap.

<GuideFigure figure="sm-store" />

Every subscriber's selector still runs on every store change. But only components whose slice changed re-render, and a selector call is far cheaper than a render.

### Binding it to React

```jsx
import { useSyncExternalStore } from "react";

function useStore(selector) {
    return useSyncExternalStore(store.subscribe, () => selector(store.getState()));
}

function CartBadge() {
    const count = useStore((state) => state.cart.length);
    return <span>{count}</span>;
}
```

`subscribe` takes a callback and returns an unsubscribe function. `getSnapshot` returns the current slice, and React compares its results with `Object.is`. Declare `subscribe` outside the component, because a new `subscribe` on each render makes React re-subscribe. You will rarely write this hook yourself, because store libraries call it for you.

### getSnapshot must be cached

```js
const selectSummary = (state) => ({ name: state.user.name, items: state.cart.length });
console.log(Object.is(selectSummary(store.getState()), selectSummary(store.getState())));
```

```text role="output"
false
```

This selector builds a new object on every call, so two calls with no change between them still differ. React would treat every check as a store change and render forever. In development React calls `getSnapshot` twice and logs "The result of getSnapshot should be cached to avoid an infinite loop."

Select primitives or existing objects, or cache the derived object until the store changes. Continue the Node example.

```js
let lastState;
let lastSummary;
function selectSummaryCached(state) {
    if (state !== lastState) {
        lastState = state; // the store made a new state object, so rebuild
        lastSummary = { name: state.user.name, items: state.cart.length };
    }
    return lastSummary;
}
console.log(Object.is(selectSummaryCached(store.getState()), selectSummaryCached(store.getState())));
```

```text role="output"
true
```

Zustand 5 passes your selector straight into `getSnapshot`, which is why it offers `useShallow` for selectors that return new objects.

### How React prevents tearing

```js
// Simplified teaching version of the check in ReactFiberWorkLoop.js, React 19.
const exitStatus = renderRootConcurrent(root, lanes); // may pause between components
if (!isRenderConsistentWithExternalStores(finishedWork)) {
    renderRootSync(root, lanes); // a store changed mid-render: redo it without pausing
}
```

A transition render can pause between components to let the browser work. If the store changes during a pause, components before it saw the old value and components after it see the new one. That split screen is tearing.

React prevents it in two ways. First, a store notification schedules the re-render at `SyncLane`, the most urgent lane, which renders without pausing. So store-driven updates are never transitions.

Second, a component that reads a store during a non-blocking render records its snapshot. After the render, React calls every `getSnapshot` again. If any value changed, React redoes the render as a blocking one, which cannot pause.

| Situation | What React does |
|---|---|
| The store calls its subscribers | Re-renders affected components at `SyncLane` |
| A transition render read the store, then the store changed | Redoes the render synchronously before commit |
| Server rendering or hydration | Calls `getServerSnapshot`, which is required there |

Hydration is React attaching to HTML the server already rendered, so the server and the first client render must agree. `getServerSnapshot` supplies the store value both sides use.

So a store mutation can never be a non-blocking transition. That is also why the React docs advise against suspending on a store value. A Suspense boundary shows a fallback, such as a spinner, while its content waits for data. A store change would swap visible content for that fallback.

### The mental model

| Part | Job |
|---|---|
| State outside the tree | A change skips top-down propagation |
| Selector subscription | Each component re-renders only when its slice changes |
| A safe React binding | No tearing under concurrent rendering |

Zustand, Valtio and React Redux call `useSyncExternalStore` for the third part. Jotai is an exception, because its default hooks subscribe with their own `useReducer` and `useEffect` pair.

### Try it

Add a third subscriber to the Node store, then change the user's name. Predict which labels print. After the earlier output, the new lines print this.

```js
connect("Greeting", (state) => `Hello, ${state.user.name}`);
store.setState({ user: { name: "Grace" } });
```

```text role="output"
UserName re-renders
Greeting re-renders
```

`CartBadge` stays quiet, because the cart length is still 1. In a React app, connect two components through `useStore` and confirm the same split. Then pass `selectSummary` as the selector. Expect the console warning, then a "Maximum update depth exceeded" crash.

## 13. Store libraries as archetypes

The field is crowded: Redux Toolkit, Zustand, Jotai, Valtio, MobX, and the ghost of Recoil in old tutorials. You need to know which shape each one is, not a feature bake-off.

### The short version

The libraries cluster into four archetypes, all built on the store model from section 12. A single store, such as Redux Toolkit, changes one object through dispatched actions and pure reducers. A minimal store, such as Zustand, keeps one store with selectors but cuts the ceremony to a hook and setters, with no provider.

Atomic libraries, such as Jotai, build state bottom-up from tiny atoms, and reading an atom is the subscription. Proxy libraries, such as Valtio and MobX, let you mutate a plain-looking object while they track reads. Pick by your state's shape and your team's taste. A "wrong" pick costs mostly ergonomics, not architecture.

### The four archetypes

| Archetype | Example | You write | Strength | Trade |
|---|---|---|---|---|
| Single store | Redux Toolkit | Slices, actions, selectors | Predictable, time-travel devtools, middleware | The most ceremony |
| Minimal store | Zustand | A hook with setters | Very little code, no provider | Less imposed structure |
| Atomic | Jotai | Small atoms and derived atoms | Fine-grained by construction | Many small pieces to name |
| Proxy | Valtio, MobX | Plain mutation, `state.count++` | The most natural-feeling code | Re-renders are less explicit |

### Single store: Redux Toolkit

```js
import { configureStore, createSlice } from "@reduxjs/toolkit";

const cartSlice = createSlice({
    name: "cart",
    initialState: { items: [] },
    reducers: {
        added(state, action) {
            state.items.push(action.payload); // Immer turns this into an immutable update
        },
    },
});

export const { added } = cartSlice.actions; // action creators, generated for you
export const store = configureStore({ reducer: { cart: cartSlice.reducer } });
```

Redux Toolkit is the official modern way to write Redux. It generates action creators, and Immer turns reducer code that looks like mutation into immutable updates. Every change is an explicit action, so changes are logged and replayable. Time-travel devtools use that log to step the app back and forth through its past states.

Middleware gives side effects and async flows one clear place to live. Redux Toolkit earns its keep in large apps with complex, widely shared client state. For a small app, or for mostly server or local state, it is overkill.

### Minimal store: Zustand

```js
import { create } from "zustand";

const useCart = create((set) => ({
    items: [],
    add: (item) => set((state) => ({ items: [...state.items, item] })),
}));

function CartBadge() {
    const count = useCart((state) => state.items.length); // a selector subscription
    return <span>{count}</span>;
}
```

Zustand has Redux's shape, one store read through selectors, stripped to the bone. `create` returns a hook, setters update the state, and no provider wraps your tree. Its hook calls `useSyncExternalStore` with your selector. It imposes less structure and bundles lighter tooling, and it is a good default for global client state.

### Atomic: Jotai

```js
import { atom, useAtomValue } from "jotai";

const priceAtom = atom(20);
const quantityAtom = atom(3);
const totalAtom = atom((get) => get(priceAtom) * get(quantityAtom)); // a derived atom

function Total() {
    return <span>{useAtomValue(totalAtom)}</span>; // re-renders only when total changes
}
```

Instead of one store defined from the top, you build state from many small **atoms**. A derived atom recomputes when the atoms it reads change, and components subscribe to exactly the atoms they read. This fits many small interdependent pieces, such as form fields or filters.

Recoil pioneered the atom model at Meta. Meta archived its repository at the start of 2025, and its last release shipped in April 2023, so do not start new projects on it. Jotai is the actively maintained library in the same style.

### Proxy: Valtio and MobX

```js
import { proxy, useSnapshot } from "valtio";

const state = proxy({ count: 0 });

function Counter() {
    const snap = useSnapshot(state); // tracks which properties this component reads
    return <button onClick={() => state.count++}>{snap.count}</button>;
}
```

You read and write state like a plain mutable object. A JavaScript Proxy is an object wrapper that can intercept every property read and write. MobX uses observables, values that record who reads them. Either way, the library re-renders exactly the components that read a changed property.

The code feels the most natural, but the magic is the least explicit, and mutation is a different mental model from React's. MobX is the long-established option and Valtio a lighter one.

### Do not start here

Most state is local, lifted or server data, and none of that needs a global store. Reach for one only for client state that many components share and slice differently, or that changes often enough for the selectivity gap to bite.

### Try it

In a React app with `zustand` and `jotai` installed, define the same UI state both ways.

```js
import { create } from "zustand";
import { atom } from "jotai";

const useUi = create((set) => ({
    theme: "light",
    sidebarOpen: false,
    toggleSidebar: () => set((state) => ({ sidebarOpen: !state.sidebarOpen })),
}));

const sidebarOpenAtom = atom(false);
```

Build a theme reader and a sidebar button on each, with a `console.log` per render. Toggle the sidebar in both versions. Only the sidebar components log, so the behavior is identical, and only the shape of the code differs.

## 14. Server state and URL state

You fetch data into `useState`, or into Redux beside your UI state. Then you write loading flags, error handling, refetch-on-focus, caching and deduplication by hand, and the data still goes stale.

### The short version

Mixing up two kinds of state is the biggest state-management mistake. **Client state** belongs to your app and is always current: toggles, form inputs, selections. **Server state** is a local cache of data a server owns. It is asynchronous and shared, and it can be stale the moment it arrives.

Server state needs caching, deduplication, background refetching and staleness rules that `useState`, Context and client stores lack. Query libraries such as TanStack Query and RTK Query provide them. Moving server data there shrinks your client state to something small and local. The URL is a third owner, for view state people should share or bookmark.

### Client state and server state side by side

| Property | Client state | Server state |
|---|---|---|
| Owner | Your app | A server or third-party API |
| Timing | Synchronous: set it and it is the new value | Asynchronous: fetching takes time and can fail |
| Freshness | Always exactly what you last set | Can go stale without your app doing anything |
| Sharing | One source of truth in the browser | Many components, tabs and users see the same data |
| Needs | A place to live | Caching, deduplication, refetching, a `status` |

Fetching gives every piece of server state loading and error conditions, the `status` value from section 5. Others can change the real data, so "when should I refetch?" becomes a real question. For client state, it does not exist.

<MarginNote note="server data is a cache you borrowed">

When you store server data in `useState` or Redux, you use a tool with none of those abilities. So you rebuild them by hand: a loading flag, an error state, a manual cache, refetch logic, deduplication and focus listeners.

</MarginNote>

### What a query cache does for you

Here is one of those jobs, deduplication, as a simplified teaching version. Save it as an `.mjs` file, because it uses top-level `await`, and run it with Node.

```js
const inFlight = new Map();
function fetchOnce(key, fetcher) {
    if (!inFlight.has(key)) {
        inFlight.set(key, fetcher().finally(() => inFlight.delete(key)));
    }
    return inFlight.get(key);
}

let requests = 0;
const getUser = () => new Promise((resolve) => setTimeout(() => resolve({ id: 1, request: ++requests }), 10));

const [a, b] = await Promise.all([fetchOnce("user", getUser), fetchOnce("user", getUser)]);
console.log(a === b, "requests:", requests);
```

```text role="output"
true requests: 1
```

Two components asked for the same data at once, and one request went out. A query library builds this in, and much more.

```jsx
import { useQuery } from "@tanstack/react-query";

function Profile({ userId }) {
    const { status, data, error } = useQuery({
        queryKey: ["user", userId], // the cache key
        queryFn: () => fetchUser(userId),
    });
    if (status === "pending") return <Spinner />;
    if (status === "error") return <ErrorMessage error={error} />;
    return <h1>{data.name}</h1>;
}
```

| TanStack Query v5 default | Value | Effect |
|---|---|---|
| `staleTime` | 0 | Cached data counts as stale at once, so it refetches on the next trigger |
| `gcTime` | 5 minutes in the browser | Unused cache entries are removed after 5 minutes |
| `refetchOnWindowFocus` | `true` | Returning to the tab refetches stale queries |
| `refetchOnReconnect` | `true` | Coming back online refetches stale queries |
| A second fetch while one runs | Shares the first promise | One request, many readers |

A background refetch keeps showing the cached data while it runs, so the user sees something at once and the screen updates quietly.

React Query was renamed TanStack Query at version 4, and RTK Query is the same idea inside Redux Toolkit. The [data fetching guide](/articles/react-data-fetching-server-state) covers query keys, stale-while-revalidate and optimistic updates in depth.

### Most "global state" is server state

Much of what people put in Redux, Context or atoms is really server state that belongs in a query cache. Once it moves, the remaining client state is small, local and simple. "Do we need Redux?" often becomes "No, most of that was server state."

### The URL owns shareable state

```js
const url = new URL("https://shop.example/products?category=shoes&page=2");

const page = Number(url.searchParams.get("page") ?? "1");
url.searchParams.set("page", String(page + 1));

console.log(url.searchParams.get("category"), page);
console.log(url.search);
```

```text role="output"
shoes 2
?category=shoes&page=3
```

Some view state should survive a reload or travel in a link, such as a filter, a page number or an open tab. The URL owns that state, and components derive their view from it.

A copy in `useState` is a second source of truth that drifts from the address bar. Your router's search-param API, or `URLSearchParams`, reads and writes it.

### Try it

Add these lines to the end of the `fetchOnce` file, and predict `requests` before you run it. After the earlier output, the new line prints this.

```js
await fetchOnce("user", getUser); // the first request has already settled
console.log("requests:", requests);
```

```text role="output"
requests: 2
```

Deduplication only shares a request that is still in flight. Keeping the answer for later, and deciding when it is stale, is the cache's other job, which `staleTime` and `gcTime` control. Then count the bookkeeping lines around one `useState` fetch in your own code. That count is roughly what a query library handles for you.

## 15. Choosing a rung, and debugging the wrong one

You have the pieces. Now you want a repeatable way to place any piece of state, and to map a symptom back to the rung that caused it.

### The short version

Ask an ordered list of questions about each piece of state, and stop at the first yes. Is it server data? Can it be derived? Does it belong in the URL?

Does one component, or the children it renders, use it? Do a few nearby components share it? Is it widely shared but rarely changing?

Only shared state that changes often and is read in slices reaches an external store. The order runs from cheap to expensive, so most state lands low. Debugging runs the same map backward: find the symptom, name the rung, and apply that section's fix. Use the Profiler for re-renders, and ask "which copy is the real one?" for disagreements.

### The questions, in order

Run this in Node.

```js
function whereDoesItLive(piece) {
    if (piece.ownedByServer) return "a server cache (a query library)";
    if (piece.derivable) return "nowhere: compute it during render";
    if (piece.inUrl) return "the URL";
    if (piece.readers === 1) return "local state"; // one component, plus the children it renders
    if (piece.nearby) return "lifted to the nearest common ancestor";
    if (!piece.changesOften) return "Context over useState or useReducer";
    return "an external store with selectors";
}

const pieces = [
    { name: "product list", ownedByServer: true },
    { name: "filtered list", derivable: true },
    { name: "search page number", inUrl: true },
    { name: "input text", readers: 1 },
    { name: "selected row", readers: 2, nearby: true },
    { name: "theme", readers: 40, changesOften: false },
    { name: "cursor positions", readers: 40, changesOften: true },
];
for (const piece of pieces) console.log(piece.name.padEnd(18), "->", whereDoesItLive(piece));
```

```text role="output"
product list       -> a server cache (a query library)
filtered list      -> nowhere: compute it during render
search page number -> the URL
input text         -> local state
selected row       -> lifted to the nearest common ancestor
theme              -> Context over useState or useReducer
cursor positions   -> an external store with selectors
```

<Mark kind="circle">The order matters</Mark>. Server data comes first because it removes the largest share of state from every later question. Derivation comes second because it deletes state instead of placing it. Local state is the default for what remains. Lifted state moves to Context only when drilling becomes the smell from section 7.

The order follows cost. Deriving costs nothing, local state is cheapest, lifting widens the blast radius, Context adds implicit links and broad re-renders, and a store adds a dependency. One question sits outside the order: complex state changes with illegal combinations get a reducer or state machine, wherever the state lives.

### Symptoms and mechanisms

| Symptom | Likely mechanism | Fix |
|---|---|---|
| A subtree re-renders on every keystroke or drag | State lifted too high, or in a context that changes per key | Colocate it, or move it to a store with selectors (2, 12) |
| Every reader of a context re-renders, even behind memo | An inline value, or one big context | `useMemo`, split contexts, separate dispatch (10) |
| Readers of different slices of one fast value all re-render | The selectivity gap | An external store (11, 12) |
| Two values disagree | Derivable state stored as a second copy | Store the minimal facts, derive, delete the syncing effect (4) |
| An "impossible" state appears | A shape that allows it, or unconstrained state changes | One `status` value, a reducer machine (5, 6) |
| Stale data, hand-written caching and loading flags | Server state treated as client state | A query library (14) |
| Nobody can tell where a value comes from | Diffuse ownership | One owner with narrow props, or one reducer (1, 3, 6) |
| A store feels like a lot of ceremony | Escalated past the needed rung | Re-run the questions (15) |

For re-render problems, record the interaction in the React DevTools Profiler and read which components rendered and why. For disagreements, a second copy of a fact is almost always the bug.

```

```

Few pieces get past the one-component question. Then take one real re-render or desync bug from your app and name its row in the symptom table. Apply the fix, and confirm it in the Profiler.

## The whole thing in one list

1. Where state lives sets the blast radius of its changes, and one clear owner makes data flow traceable.
2. Keep state as low as it will go, and lift it only to the nearest common ancestor that needs it.
3. Never store what you can derive, because a value computed during render cannot go stale.
4. Shape state so illegal combinations cannot be written, and gather complex state changes in a reducer.
5. Context is a transport for state you manage with `useState` or `useReducer`, provided as `<Context value>` in React 19.
6. Context compares the whole value with `Object.is` and re-renders every reader, even behind `React.memo`.
7. Stabilize, split and separate dispatch to tame Context, but no React version gives it slice subscriptions.
8. An external store keeps state outside React and lets each component subscribe to its slice.
9. `useSyncExternalStore` needs a cached `getSnapshot`, and it re-renders synchronously so the screen never tears.
10. Server data belongs in a query cache, shareable view state in the URL, and both stay out of client-state tools.
