A menu should close when you click anywhere else on the page. The usual fix pairs a `document` listener with a React handler that stops the click.

```jsx
function Menu() {
    const [open, setOpen] = useState(false);

    useEffect(() => {
        const close = () => setOpen(false);
        document.addEventListener("click", close);
        return () => document.removeEventListener("click", close);
    }, []);

    return (
        <button
            onClick={(event) => {
                event.stopPropagation(); // keep the document from closing it
                setOpen((o) => !o);
            }}
        >
            {open ? "Close" : "Open"} menu
        </button>
    );
}
```

It works in React 19. But open DevTools and select the button: its only `click` entry is an empty function, and your handler is nowhere on it. And `stopPropagation` is a React method, yet it stopped a listener React never touched. In React 16 the same code failed.

This guide explains both puzzles. React catches events at one place, finds your handlers by walking its own component tree, and decides how urgent each resulting update is. By the end you can predict which handler fires, in what order, and why.

> Current as of React 19.2 and 19.3. The shape of the event system dates from React 17, which moved its listeners to the root container and removed event pooling.

## 1. Why React has its own event system

You write `<button onClick={handleClick}>`, and clicking works. So where is the listener, if not on the button?

### The short version

React <Mark kind="circle">does not attach</Mark> your handlers to your DOM nodes. It places a fixed set of listeners on the root container, the node you pass to `createRoot`. When a native event reaches them, React finds your handlers by walking its internal tree of fibers.

React does this for four reasons. It normalizes events across browsers. It needs about one listener per event type, not one per handler. It gives each event a priority that becomes the lane of your update. And events follow the component tree you wrote, even for portals, whose DOM sits elsewhere.

So `onClick` is a description React fulfils, not a DOM listener.

### Your handler is not on your button

Chrome's console has a helper, `getEventListeners`, that lists the listeners on a node. Select your button in the Elements panel, where `$0` refers to it.

```js
// Chrome DevTools console only.
$0.onclick; // an empty function from React, not your handler
getEventListeners(document.getElementById("root")).click.length; // 2
```

React sets that empty `onclick` on every element with an `onClick` prop. It works around old Mobile Safari, which did not bubble clicks from plain elements to a delegated listener. It does nothing, and your function is never attached. The root container has two real `click` listeners, one for each phase of the event, as section 7 shows.

### Where your handler lives instead

When React creates a DOM node, it stores your props on the node under a private key. It never calls `addEventListener` with your function.

```js
// Simplified teaching version of what onClick={handleClick} becomes.
buttonNode["__reactProps$x7k2"] = { onClick: handleClick, children: "Save" };
// No buttonNode.addEventListener("click", handleClick) anywhere.
```

The real key ends in random characters. React reads this object when an event arrives, as section 6 shows.

### Four jobs for one layer

| Job | What it gives you | Where |
|---|---|---|
| Normalize events | One `SyntheticEvent` interface in every browser | Section 2 |
| Delegate | About one listener per event type, however many handlers you write | Sections 3 to 5 |
| Prioritize | A click's update is urgent, a `mousemove`'s less so | Sections 9 and 10 |
| Follow the component tree | Events from a portal reach the component that rendered it | Sections 7 and 11 |

Normalization mattered most in React's early years, when browsers disagreed on property names and behavior. Modern browsers agree far more, but the wrapper still smooths a few sharp edges.

Prioritizing is the job people overlook, and today it is arguably the most important. A native `addEventListener` call has no link to React's update machinery. React's event system is the front door to that machinery: it turns a user's gesture into a prioritized, batched update.

### Try it

In a scratch app, render a button with an `onClick`. Open the Elements panel, select the button, and open the Event Listeners tab. With "Ancestors" unchecked, the button shows only the empty `onclick`, never your function. Select the root container and you find React's listeners there. Then run the two console lines above.

## 2. The synthetic event object

Your handler receives `e`, with `e.preventDefault()`, `e.target` and `e.stopPropagation()`. It looks like a native event. What is it really?

### The short version

`e` is a `SyntheticEvent`, an object React builds around the native browser event for each dispatch. It copies the standard fields, such as `type`, `target`, `clientX` and `key`, and fixes a few browser differences. Its `preventDefault` and `stopPropagation` call the native methods too. `e.nativeEvent` gives you the raw event.

React 16 reused these objects from a pool and wiped them after each dispatch, so reading `e` later returned blanks unless you called `e.persist()`. React 17 removed pooling, so you can read `e` asynchronously. `e.persist()` now does nothing. One field still clears: `e.currentTarget` reads `null` once your handler returns.

### A wrapper with a native core

```jsx
function handleClick(e) {
    console.log(e instanceof MouseEvent); // false: a React object
    console.log(e.nativeEvent instanceof MouseEvent); // true: the browser's event
    console.log(e.type, e.target.tagName); // "click" "BUTTON"
}
```

Reach for `e.nativeEvent` when you need a non-standard property or must pass the event to a browser API.

React builds one constructor per event family, from an interface that lists the fields to copy.

```js
// Simplified teaching version of createSyntheticEvent (SyntheticEvent.js).
function SyntheticEvent(type, nativeEvent, target, Interface) {
    this.type = type;
    this.nativeEvent = nativeEvent;
    this.target = target;
    this.currentTarget = null; // set per handler during dispatch
    for (const name in Interface) {
        const normalize = Interface[name];
        this[name] = normalize ? normalize(nativeEvent) : nativeEvent[name];
    }
}

SyntheticEvent.prototype.stopPropagation = function () {
    this.nativeEvent.stopPropagation(); // the browser's event stops too
    this.isPropagationStopped = () => true;
};
```

`preventDefault` follows the same pattern and calls the native `preventDefault`. A normalizer such as `getEventKey` turns old browser key codes into standard `key` names.

A synthetic event is a logical event. It usually matches one native event, but not always. In `onMouseLeave`, `e.nativeEvent` is a `mouseout`, and `onChange` on a text field comes from `input`. Section 12 explains why.

### Event pooling, and why it is gone

React 16 and earlier kept a pool of event objects. React took one, filled it in and called the handlers. Once dispatch finished, it reset every field to `null` and put it back. The goal was less garbage collection. The cost was a notorious bug: any asynchronous read saw a blank event, unless you first called `e.persist()`.

The React team found that pooling gave no speed-up in modern browsers and confused developers. React 17 removed it. Every dispatch now builds a fresh object that React never reuses.

```jsx
function handleClick(e) {
    setTimeout(() => {
        console.log(e.type); // "click": the object was never recycled
        console.log(e.currentTarget); // null: React clears it after each handler
    }, 1000);
}
```

React sets `currentTarget` to the element whose handler is running, then clears it. Copy it first if you need it later.

```jsx
async function handleClick(e) {
    const button = e.currentTarget; // read it now
    await save();
    button.focus();
}
```

React's `currentTarget` is the element in the React tree, so it can differ from `e.nativeEvent.currentTarget`, which is usually the root container. If an event comes back blank asynchronously in a modern app, the cause is something else, not pooling.

### Try it

In a click handler, log `e.type` and `e.currentTarget` inside `setTimeout(..., 1000)`. The type survives and `currentTarget` is `null`. Log `e.nativeEvent` to see the raw event underneath. Then copy `e.currentTarget` into a variable before the timeout and log that instead. It now prints the button. Section 12 has an experiment where the native type differs from React's.

## 3. Delegation: one listener for a thousand handlers

A table with a thousand rows, each with an `onClick`, still adds no click listeners to its rows. How does one listener serve them all?

### The short version

In **event delegation**, one listener on an ancestor handles events from many descendants. It works because most events bubble: after firing on the target, they travel up through every ancestor. The listener reads `event.target` to learn where the event began.

React applies this to the whole app, with about one listener per event type and phase on the root container. Adding `onClick` only records a prop, so it costs no DOM listener. A row rendered later needs no new listener either. However many handlers you write, <Mark kind="marker" wraps>the listeners are all at the root</Mark>.

### Delegation in plain JavaScript

```js
const list = document.querySelector("[data-list]");

list.addEventListener("click", (event) => {
    const item = event.target.closest("[data-item]");
    if (!item || !list.contains(item)) return;
    console.log(item.dataset.item);
});
```

A click on any item bubbles up to the list, where one listener runs. `closest` finds which item the click came from. Items added later work at once, because nobody has to wire them up.

### React's version

React automates the same idea. Here is a first draft that walks DOM nodes and reads the stored props.

```js
// Simplified teaching version, first draft: React-style delegation for clicks.
container.addEventListener("click", (nativeEvent) => {
    let node = nativeEvent.target;
    while (node !== null && node !== container) {
        const props = node["__reactProps$x7k2"];
        props?.onClick?.(nativeEvent);
        node = node.parentNode;
    }
});
```

The real version walks fibers instead of DOM nodes, which section 6 explains. It also wraps the event and supports both phases. But the economics are the same.

| | One listener per element | Delegation at the root |
|---|---|---|
| Real listeners for 1,000 clickable rows | 1,000 | 2 (capture and bubble) |
| A row added later | Needs a new listener | Works with no change |
| Cost of writing `onClick` | A DOM call per element | Storing a prop |

The real listener count is small and fixed. The number of `onClick` props can be enormous. React bridges the gap by working out "which element was this, and which handlers care" itself.

Delegation has been part of React since its first release. What changed over time is where the listeners sit, which is the next section.

### Try it

Render a list whose items each have an `onClick`, and a button that appends an item.

```jsx
function List() {
    const [items, setItems] = useState(["a", "b"]);
    return (
        <>
            <button onClick={() => setItems([...items, String(items.length)])}>Add</button>
            <ul>
                {items.map((item) => (
                    <li key={item} onClick={() => console.log(item)}>{item}</li>
                ))}
            </ul>
        </>
    );
}
```

Add a few items and click them. Each logs its name. In DevTools, no `<li>` holds your handler, and the root's listener count never changes.

## 4. The root container

"At the root" sounds clear, but older articles say React listens on `document`. Which is it, and why does the answer matter?

### The short version

Since React 17, every root attaches its own listeners to its own **root container**, the node you pass to `createRoot` or `hydrateRoot`. They do it at once, before your first render, so React is ready for any event type. One exception goes on `document`: `selectionchange`, which the browser fires only there.

Before React 17, React listened on `document` instead. Two React copies on one page then shared one node and broke each other's events. An embedded widget also collided with the host page's handlers. React 17 moved the listeners down to fix both. So a native `document` listener now sits above React, which section 8 builds on.

### What createRoot attaches

```js
// Simplified teaching version of listenToAllSupportedEvents (DOMPluginEventSystem.js).
function listenToAllSupportedEvents(container) {
    if (container[listeningMarker]) return; // only once per container
    container[listeningMarker] = true;
    for (const name of allNativeEvents) {
        if (name === "selectionchange") continue; // goes on the document
        if (!nonDelegatedEvents.has(name)) {
            listen(container, name, { capture: false }); // bubble phase
        }
        listen(container, name, { capture: true }); // capture phase
    }
    listen(container.ownerDocument, "selectionchange", { capture: false });
}
```

`allNativeEvents` holds every event type some React prop needs. React registers them all up front, well over a hundred listeners, and never adds more as you render. The React 17 changelog calls this "Attach all known event listeners when the root mounts".

| Event kind | Capture listener | Bubble listener |
|---|---|---|
| Ordinary events, such as `click` or `keydown` | Root container | Root container |
| Events that do not bubble, such as `scroll` or media events | Root container | The element itself (section 5) |
| `selectionchange` | None | `document` |
| Any event inside a portal | The portal's container too (section 11) | The portal's container too |

### Before React 17: everything on document

React 16 attached its listeners to `document`. Every event on the page bubbled to `document`, where React caught it. That worked for one app per page. It failed on pages with more.

| Problem | With listeners on `document` | With listeners on each root container |
|---|---|---|
| Two React versions nested on one page, during a gradual migration | Both trees listened on `document`. A nested tree's `stopPropagation` came too late, so the outer tree still received the event | Each tree handles events in its own container, and a nested stop holds |
| React as one widget on a larger non-React page | React's handlers reached the whole page and met the host's own `document` handlers | React's handling stays inside React's part of the page |
| Teardown | One global pile on `document` | Listeners scoped to the root's node and lifetime |

The changelog states it plainly: "Delegate events to roots instead of document." React 17 shipped almost no new features. This change was its main purpose, because it made safe, incremental upgrades possible.

### A root inside a root

In a gradual migration, the old app often renders an empty `div`, and the new app mounts inside it once that `div` exists.

```jsx
function OldApp() {
    const slot = useRef(null);
    useEffect(() => {
        const inner = createRoot(slot.current); // the new app mounts inside the old one
        inner.render(<NewApp />);
        return () => setTimeout(() => inner.unmount());
    }, []);
    return (
        <div onClickCapture={() => console.log("OldApp capture")} onClick={() => console.log("OldApp onClick")}>
            <div ref={slot} />
        </div>
    );
}

createRoot(document.getElementById("old-app")).render(<OldApp />);
```

```text role="output"
OldApp capture
NewApp onClick, stop
```

That output comes from a click on a `NewApp` button whose `onClick` calls `e.stopPropagation()`. Each container holds its own listeners, so the stop happens at the inner container. `OldApp`'s bubble handlers sit higher up, on `old-app`, and never see the click. Its capture handlers already ran on the way down. With both trees on `document`, the stop came too late.

### Try it

Make two sibling containers and render a root into each. In the console, run `getEventListeners(document.getElementById("old-app")).click` and the same for `new-app`. Each has its own pair. Then check `getEventListeners(document)`, where you find only `selectionchange` from React.

## 5. Events that skip delegation

Delegation needs events that bubble. What happens with `scroll`, which does not, and with touch and wheel events, where one listener can slow down scrolling?

### The short version

Some events do not bubble consistently in the DOM. Examples are `scroll`, `load`, `error`, `invalid`, `toggle`, `close` and two dozen media events such as `ended`. A bubble listener on the root would never hear them.

So React adds the bubble listener to the element itself. It always does so for elements such as `<img>`, `<video>` or `<dialog>`, and for `scroll` once you pass `onScroll`.

Since React 17, `onScroll` fires only on the element that scrolled, as in the browser. An ancestor can still watch with `onScrollCapture`. Separately, React makes its `touchstart`, `touchmove` and `wheel` listeners **passive**, a promise never to cancel the default action. So `preventDefault()` in `onWheel` or `onTouchMove` is ignored.

### Non-delegated events go on the element

```jsx
<div style={{ overflow: "auto", height: 200 }} onScroll={() => console.log("scrolled")}>
    {rows}
</div>
```

When React sets the `onScroll` prop, it calls `listenToNonDelegatedEvent("scroll", node)`. Select this `div` and run `getEventListeners($0).scroll` in the console: React's listener is right there.

| Group | Examples | Where React listens in the bubble phase |
|---|---|---|
| Scrolling | `scroll`, `scrollend` | On the element with the prop |
| Media | `play`, `pause`, `ended`, `timeupdate`, `error` | On every `<audio>` and `<video>` |
| Resources | `load`, `error` | On `<img>`, `<link>`, `<iframe>` and similar elements |
| Forms and dialogs | `invalid`, `toggle`, `cancel`, `close` | On every `<input>`, `<select>`, `<textarea>`, `<details>` or `<dialog>` |

The source gives the reason in a comment: "these events do not consistently bubble in the DOM". Apart from scrolling, React attaches these by element type, whether or not you pass a handler.

```jsx
// React listens for "ended" on this <video> element, not on the root.
<video src={clip} onEnded={() => setFinished(true)} />
```

### onScroll does not bubble

```jsx
<div onScrollCapture={() => console.log("ancestor capture")} onScroll={() => console.log("ancestor onScroll")}>
    <div style={{ overflow: "auto", height: 100 }} onScroll={() => console.log("child onScroll")}>
        {longContent}
    </div>
</div>
```

```text role="output"
ancestor capture
child onScroll
```

Scrolling the inner box never runs the ancestor's `onScroll`. React 16 emulated bubbling for `onScroll`, which fired handlers on distant ancestors for unrelated nested scrolls. The React 17 changelog reads "Don't emulate bubbling of the onScroll event". So put `onScroll` on the element that scrolls. The root's capture listener still sees every scroll, which is why `onScrollCapture` works.

### Passive listeners ignore preventDefault

A passive listener promises the browser it will never call `preventDefault()`. The browser can then scroll at once instead of waiting for your code. Browsers make `touchstart`, `touchmove` and `wheel` listeners on `document` passive by default. React 17 kept that behavior after moving to the root, so its own listeners for those three are passive too.

```jsx
// Ignored: React's wheel listener is passive. Chrome logs a warning.
<div onWheel={(e) => e.preventDefault()}>{map}</div>
```

To block scrolling, attach your own non-passive listener with a ref.

```jsx
function ZoomableMap() {
    const ref = useRef(null);
    useEffect(() => {
        const node = ref.current;
        const zoom = (e) => {
            e.preventDefault(); // works: this listener is not passive
            console.log("zoom by", e.deltaY);
        };
        node.addEventListener("wheel", zoom, { passive: false });
        return () => node.removeEventListener("wheel", zoom);
    }, []);
    return <div ref={ref}>{map}</div>;
}
```

### Try it

Build the nested scroll boxes above and scroll the inner one. You should see "ancestor capture" and "child onScroll", but never "ancestor onScroll". Then add `onWheel={(e) => e.preventDefault()}` to a scrollable box. The box still scrolls, and Chrome's console warns about a passive listener. Swap in `ZoomableMap` and the page stops scrolling over it.

## 6. The dispatch path

A click lands on a deep button, and the listener is far away at the root. What happens between the browser's event and your `handleClick`?

### The short version

The root's listener first sets the **update priority**, the urgency any `setState` in your handlers will get (section 9). Then React reads the native event's `target` and follows a private key on that DOM node to its **fiber**, React's object for that element. From there React knows where in its own tree the event began.

Next, **event plugins** turn the native event into React events. Each plugin walks up the fiber tree from the target and collects the matching handlers. It pushes them, with a synthetic event, onto a **dispatch queue**. Finally React runs the queue in order. One listener at the root thus behaves as if every element had its own.

### From DOM node to fiber

Every DOM node React creates carries two private keys. Select one in the Elements panel and run this in the console.

```js
// Chrome DevTools console.
Object.keys($0).filter((key) => key.startsWith("__react"));
// ["__reactFiber$x7k2", "__reactProps$x7k2"]
```

`__reactFiber$` points to the node's fiber, and `__reactProps$` holds its current props, your handlers included. A fiber links to its parent through `fiber.return`, so React can walk from any fiber up to the root. `getClosestInstanceFromNode` starts at the target and climbs the DOM until it finds a node with a fiber key.

### The path, step by step

```js
// Simplified teaching version of ReactDOMEventListener.js and DOMPluginEventSystem.js.
function dispatchDiscreteEvent(domEventName, flags, container, nativeEvent) {
    const previous = getCurrentUpdatePriority();
    setCurrentUpdatePriority(DiscreteEventPriority); // section 9
    try {
        dispatchEvent(domEventName, flags, container, nativeEvent);
    } finally {
        setCurrentUpdatePriority(previous);
    }
}

function dispatchEvent(domEventName, flags, container, nativeEvent) {
    const targetFiber = getClosestInstanceFromNode(nativeEvent.target);
    const dispatchQueue = [];
    extractEvents(dispatchQueue, domEventName, targetFiber, nativeEvent, flags);
    processDispatchQueue(dispatchQueue, flags);
}
```

| Step | Function | What happens |
|---|---|---|
| 1 | The browser | The native event fires at the target and travels to the root container |
| 2 | `dispatchDiscreteEvent` and friends | React's listener sets the update priority for this event type |
| 3 | `getClosestInstanceFromNode` | React goes from the target node to its fiber |
| 4 | `extractEvents` | Plugins collect handlers along the fiber path and build synthetic events |
| 5 | `processDispatchQueue` | React calls each handler with the synthetic event |
| 6 | Your `setState` calls | Updates get the event's lane and render together (sections 9 and 10) |

<GuideFigure figure="react-delegation" />

### Plugins fill the dispatch queue

`SimpleEventPlugin` handles events that map one to one, such as `click` and `keydown`. Other plugins build React's own meanings, such as `onChange`, from other native events (section 12).

```js
// Simplified teaching version of SimpleEventPlugin.extractEvents.
function extractEvents(dispatchQueue, domEventName, targetFiber, nativeEvent, flags) {
    const reactName = topLevelEventsToReactNames.get(domEventName); // "click" to "onClick"
    const inCapturePhase = (flags & IS_CAPTURE_PHASE) !== 0;
    const listeners = accumulateSinglePhaseListeners(targetFiber, reactName, inCapturePhase);
    if (listeners.length > 0) {
        const event = new SyntheticMouseEvent(reactName, domEventName, nativeEvent);
        dispatchQueue.push({ event, listeners }); // created only when someone listens
    }
}
```

`accumulateSinglePhaseListeners` is the walk up the fiber tree, and section 7 runs a version of it. It reads each handler from the fiber's current props. It skips mouse handlers such as `onClick` on a disabled `button`, `input`, `select` or `textarea`.

<MarginNote note="one walk explains order, stopPropagation and portals">

Every later behavior comes from this walk. Handler order is the order of the walk. `stopPropagation` ends the walk early. Portals are the walk following fibers where the DOM goes elsewhere.

</MarginNote>

### Running the queue

```js
// Simplified teaching version of executeDispatch (DOMPluginEventSystem.js).
function executeDispatch(event, listener, currentTarget) {
    event.currentTarget = currentTarget;
    try {
        listener(event);
    } catch (error) {
        reportError(error); // reported as uncaught, and the next handler still runs
    }
    event.currentTarget = null;
}
```

A throwing handler does not stop the others. Error boundaries do not catch event handler errors, because the error never happens during rendering.

One more check happens first. If the target sits in server-rendered HTML that React has not **hydrated** yet, meaning connected to its components, React cannot find a fiber. For a discrete event such as a click or a key press, React hydrates that part at once and then dispatches.

For hover and focus, it remembers only the latest `mouseover`, `pointerover`, `focusin` or `dragenter` and replays it after hydration. Other events on unhydrated HTML, such as `mousemove`, reach no handler.

### Try it

Nest three elements, each with an `onClick` that logs its name, around a button. Click the button: the names print from the button outward. Then select the button node and run the `Object.keys` line above. Read the props object with the second key.

```js
// Chrome DevTools console.
const key = Object.keys($0).find((k) => k.startsWith("__reactProps$"));
$0[key]; // { onClick: ƒ, children: … }
```

Your `onClick` sits on the node as a prop, while the listener sits on the root.

## 7. Capture and bubble on the fiber tree

React offers `onClickCapture` as well as `onClick`. If your handlers never reach your elements, how does React reproduce the DOM's two phases?

### The short version

A DOM event travels in two phases. **Capture** runs from the top of the page down to the target. **Bubble** runs from the target back up. React puts two listeners per event type on the root container, one per phase. Each does its own walk from the target fiber to the root and collects only its phase's handlers.

The capture walk runs `onClickCapture` handlers top-down. The bubble walk runs `onClick` handlers bottom-up. Because <Mark kind="underline">the path comes from the fiber tree, not the DOM</Mark>, React's order follows the JSX you wrote. The two trees usually match. Portals are where they differ.

### Two phases in one component

```jsx
function PropagationDemo() {
    const log = (label) => () => console.log(label);
    return (
        <div onClickCapture={log("div capture")} onClick={log("div bubble")}>
            <section onClickCapture={log("section capture")} onClick={log("section bubble")}>
                <button onClickCapture={log("button capture")} onClick={log("button bubble")}>
                    Click me
                </button>
            </section>
        </div>
    );
}
```

```text role="output"
div capture
section capture
button capture
button bubble
section bubble
div bubble
```

### A toy you can run

This Node script builds three fake fibers and runs both walks. Save it as `toy.mjs` and run `node toy.mjs`.

```js
// A tiny fake fiber tree: each fiber has props and a return pointer.
const log = (text) => () => console.log(text);
const div = { props: { onClickCapture: log("div capture"), onClick: log("div bubble") }, return: null };
const section = { props: { onClickCapture: log("section capture"), onClick: log("section bubble") }, return: div };
const button = { props: { onClickCapture: log("button capture"), onClick: log("button bubble") }, return: section };

// Simplified teaching version of accumulateSinglePhaseListeners.
function collect(targetFiber, reactName, inCapturePhase) {
    const propName = inCapturePhase ? reactName + "Capture" : reactName;
    const listeners = [];
    for (let fiber = targetFiber; fiber !== null; fiber = fiber.return) {
        const listener = fiber.props[propName];
        if (listener) listeners.push(listener);
    }
    return listeners; // target first, root last
}

// Simplified teaching version of processDispatchQueueItemsInOrder.
function run(event, listeners, inCapturePhase) {
    const ordered = inCapturePhase ? [...listeners].reverse() : listeners;
    for (const listener of ordered) {
        if (event.stopped) return;
        listener(event);
    }
}

const event = { stopped: false, stopPropagation() { this.stopped = true; } };
run(event, collect(button, "onClick", true), true); // the root's capture listener
run(event, collect(button, "onClick", false), false); // the root's bubble listener
```

```text role="output"
div capture
section capture
button capture
button bubble
section bubble
div bubble
```

Both walks build the same target-first list. The capture run reads it backward, root to target. The bubble run reads it forward, target to root. Neither walk looks at the DOM.

### Where React's phases sit in the browser's

In plain DOM code, the third argument of `addEventListener` picks the phase, and bubble is the default.

```js
node.addEventListener("click", onBubble); // bubble phase, the default
node.addEventListener("click", onCapture, { capture: true }); // capture phase
```

React 17 made capture handlers use the browser's real capture phase. The changelog reads "Make all Capture events use the browser capture phase". So React's capture listener fires as the native event passes the root container on its way down, before any native listener on the target.

The bubble listener fires on the way back up, after native listeners below the root.

Most React events have a `Capture` form, but not all. `onMouseEnter`, `onMouseLeave`, `onPointerEnter` and `onPointerLeave` have no capture phase. Plugins that build React's own meanings, such as `onChange`, run only in the bubble listener and replay both phases there.

In everyday code you use the bubble phase. Capture is for an ancestor that must see an event before its children do, such as a router or an analytics logger.

## 8. Native listeners: order and stopPropagation

Sooner or later you add a native `addEventListener` next to React's handlers. In what order do they run, and what does each `stopPropagation` really stop?

### The short version

Two propagation systems handle one click: the browser's, over the DOM, and React's, over fibers. React runs both of its phases from the root container. So a native listener on an element fires as the event passes that element, which can be before React's handlers. A native bubble listener on a child runs before React's `onClick`.

`e.stopPropagation()` in a React handler stops React's walk. It also calls the native method while the event sits at the root, so bubble listeners on `document` and `window` never fire. That is why the opening menu works. A native `stopPropagation` below the root is harsher: the event never reaches React's bubble listener, so no `onClick` runs.

### When you still need native listeners

- A non-passive `wheel` or `touchmove` listener that must call `preventDefault()`
- Listeners on `window` or `document`, such as global shortcuts or outside-click detection
- DOM that React does not manage, such as a third-party widget
- Interop with a library that dispatches its own events

The usual shape is an effect with a ref and a cleanup.

```jsx
useEffect(() => {
    const node = ref.current;
    const onNativeClick = () => console.log("native listener on the node");
    node.addEventListener("click", onNativeClick);
    return () => node.removeEventListener("click", onNativeClick);
}, []);
```

### The order of one click

Put a listener at every level, native and React, and click a button inside `#outer`. Both elements are rendered by React inside the root container.

| Order | Listener | Phase |
|---|---|---|
| 1 | Native on `window` | Capture |
| 2 | Native on `document` | Capture |
| 3 | React `onClickCapture` on `#outer`, then on the button | Capture, at the root |
| 4 | Native on `#outer` | Capture |
| 5 | Native on the button | Target |
| 6 | Native on `#outer` | Bubble |
| 7 | React `onClick` on the button, then on `#outer` | Bubble, at the root |
| 8 | Native on `document` | Bubble |
| 9 | Native on `window` | Bubble |

<MarginNote note="the native listener on the node gets there first">

Reason from position, not from the order you wrote the code. React sits at the root container. A native listener sits on its own node, and the event passes that node first.

</MarginNote>

If you need a native listener to run after React's logic, this geometry makes that awkward. It is usually a sign to move the work into the React handler. Prefer React's event system for anything React manages, and keep native listeners for the cases listed above.

### React's stopPropagation

```jsx
document.addEventListener("click", () => console.log("document listener"));

<div onClick={() => console.log("div onClick")}>
    <button onClick={(e) => { console.log("button onClick"); e.stopPropagation(); }}>Go</button>
</div>;
```

```text role="output"
button onClick
```

React stops its walk, so `div onClick` never runs. And because the synthetic `stopPropagation` calls the native one at the root, <Mark kind="marker" wraps>the document listener never hears the click either</Mark>.

This changed in React 17. When React listened on `document`, the native event had already reached `document`, so a React `stopPropagation` came too late. Older articles still say a `document` listener always fires. In React 17 and later it does not.

A `document` listener that must see every click, even stopped ones, should listen in the capture phase. Rows 1 and 2 of the table run before React does anything.

```js
document.addEventListener("click", onAnyClick, { capture: true });
```

### A native stopPropagation starves React

```jsx
useEffect(() => {
    const node = buttonRef.current;
    const stop = (e) => e.stopPropagation();
    node.addEventListener("click", stop);
    return () => node.removeEventListener("click", stop);
}, []);

return <button ref={buttonRef} onClick={() => console.log("never runs")}>Go</button>;
```

The native event stops at the button and never bubbles up to the root container. React's bubble listener never fires, so no React `onClick` runs, on the button or on any ancestor. React's capture handlers did run, at row 3.

A library that stops propagation inside your tree can silently swallow React events this way.

### preventDefault

`e.preventDefault()` on a synthetic event calls the native `preventDefault`. It cancels the browser's default action, such as submitting a form, following a link or scrolling for some keys.

```jsx
<form
    onSubmit={(e) => {
        e.preventDefault(); // no page reload
        save(new FormData(e.currentTarget));
    }}
>
```

It behaves like the native method, except in passive listeners (section 5). It is unrelated to `stopPropagation`: one cancels the browser's action, the other stops the event's travel.

### Try it

Render the `div` and button above, but give the button `ref={buttonRef}` and remove its `e.stopPropagation()` for now. Then add these four native listeners in an effect.

```js

document.addEventListener("click", () => console.log("document capture"), true);
document.addEventListener("click", () => console.log("document bubble"));
buttonRef.current.addEventListener("click", () => console.log("native button"));
```

Click the button and check the order against the table. Put `e.stopPropagation()` back in the button's `onClick`, and "document bubble" disappears. Move the stop into the native button listener, and every React `onClick` disappears too.

## 9. Event priority

A click should update the screen before the next frame. A stream of `mousemove` events should not starve everything else. Where does React learn which is which?

### The short version

React gives every event type an **event priority**, and in React 19 each priority is a lane value. Discrete events such as `click`, `keydown` and `input` are deliberate, one-off actions, so they get `SyncLane`. Continuous events such as `mousemove`, `scroll` and `wheel` arrive in streams, so they get `InputContinuousLane`. Everything else gets `DefaultLane`.

The root's listener sets this priority while it dispatches, and each `setState` in your handler takes it as the update's lane. A click's update renders in a microtask, right after the event.

A `mousemove` update waits for a scheduler task, a later browser task run by React's scheduler, so the browser gets a turn first. Inside `startTransition`, an update gets a low-priority transition lane instead.

### Three tiers

A **time-sliced** render works in small chunks and checks for more urgent work between them. None of these three tiers is time-sliced. React's scheduler has five levels, and user-blocking is the second most urgent.

| Event priority | Lane in React 19 | Example events | How the update renders |
|---|---|---|---|
| `DiscreteEventPriority` | `SyncLane` | `click`, `keydown`, `keyup`, `input`, `change`, `submit`, `pointerdown`, `touchstart`, `focusin` | In a microtask after the event, never time-sliced |
| `ContinuousEventPriority` | `InputContinuousLane` | `mousemove`, `mouseover`, `pointermove`, `drag`, `dragover`, `scroll`, `wheel`, `touchmove` | In a scheduler task at user-blocking priority, never time-sliced |
| `DefaultEventPriority` | `DefaultLane` | `load`, `error`, `animationend`, `transitionend`, media progress events | In a scheduler task at normal priority, never time-sliced |

The lists shift a little between versions. React 19.3 moved `resize` from discrete to continuous. The `message` event takes its priority from whatever scheduler task is running.

### The classifier

`getEventPriority` in `ReactDOMEventListener.js` is a long `switch` over event names. Here is a runnable slice of it.

```js
// Lane values from ReactFiberLane.js, React 19.
const SyncLane = 0b10;
const InputContinuousLane = 0b1000;
const DefaultLane = 0b100000;

// Event priorities are lanes (ReactEventPriorities.js).
const DiscreteEventPriority = SyncLane;
const ContinuousEventPriority = InputContinuousLane;
const DefaultEventPriority = DefaultLane;

// Simplified teaching version of getEventPriority: a few cases of many.
function getEventPriority(domEventName) {
    switch (domEventName) {
        case "click":
        case "keydown":
        case "input":
        case "submit":
            return DiscreteEventPriority;
        case "mousemove":
        case "pointermove":
        case "scroll":
        case "wheel":
            return ContinuousEventPriority;
        default:
            return DefaultEventPriority;
    }
}

for (const name of ["click", "mousemove", "load"]) {
    console.log(name, getEventPriority(name).toString(2));
}
```

```text role="output"
click 10
mousemove 1000
load 100000
```

React runs this once per listener, when `createRoot` registers it. It picks `dispatchDiscreteEvent`, `dispatchContinuousEvent` or plain `dispatchEvent` as the listener. The first two also clear any surrounding transition for the length of the dispatch.

### From the event to the update's lane

When your handler calls `setState`, React picks the lane in a fixed order.

```js
// Simplified teaching version of requestUpdateLane and resolveUpdatePriority.
function laneForNewUpdate() {
    if (currentTransition !== null) return claimTransitionLane(); // startTransition wins
    if (currentUpdatePriority !== NoLane) return currentUpdatePriority; // set by React's listener
    if (window.event !== undefined) return getEventPriority(window.event.type); // a native listener
    return DefaultLane; // a timer, a promise, a network response
}
```

So urgency is inferred from the event, and you never declare it. A `setState` inside a native `addEventListener("click")` callback still gets `SyncLane`, through `window.event`.

<MarginNote note="the lane belongs to the moment, not to the setter">

The same setter gets a different lane from a click, a mouse move, a timer or a transition. The event that is running decides.

</MarginNote>

`useTransition` and `startTransition` lower priority on purpose.

```jsx
function handleClick(id) {
    setSelected(id); // SyncLane: renders right after the event
    startTransition(() => setFilter(id)); // a transition lane: sliced and interruptible
}
```

The expensive update gets a transition lane, so React can render it in slices and interrupt it. The event sets the default, and transitions override it downward. The [scheduler and lanes guide](/articles/react-scheduler-and-lanes-internals) follows the lane from here.

### What the tier changes

Discrete and continuous updates both render in one blocking pass. Neither is time-sliced, so a click cannot interrupt a `mousemove` render that has started. The difference is timing. `SyncLane` work renders in a microtask before the browser gets a turn. `InputContinuousLane` work becomes a scheduler task, so the browser can paint or deliver more input first.

Continuous updates also interrupt a transition in progress, which default updates never do. And React marks sync and continuous lanes expired after 250ms, against 5 seconds for default and transition lanes.

### Try it

Drop this into a React 19 app. Focus the button with Tab and press Enter, which clicks it without moving the mouse. Then move the mouse over it and read the first new lines.

```jsx

    const [n, setN] = useState(0);
    console.log("render", n);
    const handler = (label) => () => {
        setN((v) => v + 1);
        queueMicrotask(() => console.log("my microtask"));
        console.log(label, "handler done");
    };
    return <button onClick={handler("click")} onMouseMove={handler("mousemove")}>{n}</button>;
}
```

```text role="output"

render 1
my microtask
mousemove handler done
my microtask
render 2
```

The click's render comes before your microtask, because React queued its microtask first. The `mousemove` render comes after it, in a scheduler task. StrictMode in development may print each render twice.

## 10. Batching: from handler to one render

You call `setState` three times in one click handler, and the component renders once. Where does that batch come from?

### The short version

`setState` never renders. It queues an update on the fiber, marks the lane as pending, and asks React to schedule the root. Scheduling queues at most one microtask, however many updates arrive. Once your handlers return, that microtask renders every pending `SyncLane` update in one pass. So three `setState` calls in a click give one render with all three applied.

React 19 has no "batching mode" around event handlers. Batching is a side effect of deferring the render, so it also works in timeouts, promises and native listeners. That is React 18's **automatic batching**.

Two exceptions flush early. A form field's change event renders at once, so a **controlled input**, whose value comes from state, stays in sync. And `flushSync` renders at once when you must read the updated DOM.

### Three updates, one render

```jsx
function BatchedCounter() {
    const [count, setCount] = useState(0);
    console.count("render");

    function handleClick() {
        setCount((value) => value + 1);
        setCount((value) => value + 1);
        setCount((value) => value + 1);
    }

    return <button onClick={handleClick}>{count}</button>;
}
```

One click adds one line to the render count, and the button shows 3. The updater form, `value => value + 1`, makes the three updates compose inside that one render.

### Where the batch comes from

This runnable toy shows the whole trick. Save it as `batch.mjs` and run it with Node.

```js
// Simplified teaching version: why three setState calls give one render.
let state = 0;
const queue = [];
let renderQueued = false;

function setState(update) {
    queue.push(update); // remember the update, do not render
    if (!renderQueued) {
        renderQueued = true;
        queueMicrotask(render); // one render, after the handler returns
    }
}

function render() {
    renderQueued = false;
    for (const update of queue.splice(0)) state = update(state);
    console.log("render", state);
}

function handleClick() {
    setState((c) => c + 1);
    setState((c) => c + 1);
    setState((c) => c + 1);
    console.log("handler done");
}

handleClick();
```

```text role="output"
handler done
render 3
```

React's version of `renderQueued` is `ensureRootIsScheduled`, and its microtask renders the `SyncLane` work. An update with another lane, such as a `mousemove` update, gets a scheduler task instead. Either way the render waits until your code has finished.

The event system is what connects your handler to this pipeline. The event sets the lane, your handler queues updates, and React renders and commits once at that lane.

<GuideFigure figure="ev-batching" />

### Change events flush early

```jsx
function Name() {
    const [name, setName] = useState("");
    return <input value={name} onChange={(e) => setName(e.target.value)} />;
}
```

This input is controlled: its value comes from state. The browser has already changed the field, so React must make the DOM match state again. When any form field fires a change event, React renders the pending sync work before its listener returns, without waiting for the microtask.

For a controlled field, it then sets the DOM value to the `value` prop. An input with `value="fixed"` and an empty `onChange` therefore never changes, however you type.

Keep the `setName` call synchronous inside `onChange`. If it runs after an `await`, the restore puts the old value back first, and the cursor can jump.

### flushSync, the escape hatch

```jsx
import { flushSync } from "react-dom";

function openDialog() {
    flushSync(() => setOpen(true)); // renders and commits before it returns
    dialogRef.current.focus(); // the dialog is already in the DOM
}
```

`flushSync` renders pending sync updates before it returns, including ones queued earlier in the handler. Use it only when the next line must read the committed DOM.

### Before React 18

Older React batched only inside React event handlers. Updates in a `setTimeout`, a promise callback or a native listener each rendered on their own.

```jsx
setTimeout(() => {
    setCount((c) => c + 1);
    setFlag((f) => !f); // React 17: two renders. React 18 and 19: one.
}, 0);
```

React 18's `createRoot` deferred every render to a microtask or a task, so batching now happens everywhere. The React handler is still the clearest example, and still where an interaction gets its priority.

### Try it

Put `BatchedCounter` on screen and click: one render per click. Move the three `setCount` calls into a `setTimeout` inside the handler, and it is still one render per click. Then wrap the first call in `flushSync`.

```jsx
function handleClick() {
    flushSync(() => setCount((value) => value + 1));
    setCount((value) => value + 1);
    setCount((value) => value + 1);
}
```

The render count now rises by two per click: one forced render, then one batched render. Under StrictMode in development, every count doubles, because React renders each component twice there.

## 11. Portals: events follow the React tree

You render a modal with `createPortal`, so its DOM lands in `document.body`, clear of a parent's `overflow: hidden`. A click inside it then fires an `onClick` on the component that rendered it. Did the event teleport?

### The short version

A **portal** renders a component's DOM into another DOM node, while the component stays where you wrote it in the React tree. React attaches its full set of listeners to the portal's container too, such as `document.body`. When you click inside the portal, that listener catches the event and walks up the fiber tree.

The walk passes through the component that rendered the portal, because that is its parent fiber. So React handlers on the portal's React ancestors fire, even though the DOM is elsewhere. Native listeners follow the DOM path, which does not include those ancestors. Here <Mark kind="marker" wraps>the DOM and React trees diverge, and events follow React's</Mark>.

### A portal splits the two trees

```jsx
function Sidebar() {
    return (
        <aside onClick={() => console.log("Sidebar onClick")}>
            {createPortal(<button>Inside the modal</button>, document.body)}
        </aside>
    );
}
```

```text role="output"
Sidebar onClick
```

In the DOM, the button is a child of `body`, far from the `<aside>`. In the fiber tree, its parent is the portal, and the portal's parent is `Sidebar`. Clicking the button logs "Sidebar onClick".

### Each portal container gets listeners

The root container is inside `body`, so a click on a direct child of `body` never bubbles through it. React handles this by calling `listenToAllSupportedEvents` on every portal container as well.

```js
// Chrome DevTools console, once a portal has rendered into body.
getEventListeners(document.body).click.length; // 2: React's capture and bubble pair
```

A click inside the modal reaches the listener on `body`. React finds the button's fiber and walks `fiber.return` upward: the button, the portal, `Sidebar`'s `<aside>`, and on to the root. It collects every `onClick` on the way.

If a portal's container sits inside the root container instead, the root's listener ignores the event. The portal's own listener already handled it.

### Three consequences

| Listener | Sees a click inside the portal? | Why |
|---|---|---|
| React `onClick` on a React ancestor of the portal | Yes | React walks fibers, and the ancestor is on the fiber path |
| Native listener on that ancestor's DOM node | No | The modal's DOM is not inside that node |
| Native bubble listener on the portal container, here `body` | Yes, even after a React `onClick` stops it | React's listener sits on the same node, and `stopPropagation` never blocks other listeners on the node where it runs |
| Native listener on `document` or `window` | Yes, unless a React handler stopped it | They sit above the portal container on the DOM path |

The first row is often what you want. A container that owns a modal logically also hears its events. If not, call `e.stopPropagation()` inside the portal, or render the portal higher in the tree. The react.dev `createPortal` page suggests both.

### Fixing outside-click detection

The classic bug lives in the second row. A native outside-click check on a wrapper treats a click in its own portaled menu as outside.

```js
// Broken: the portaled menu is not inside wrapperRef in the DOM.
const isInside = wrapperRef.current.contains(event.target);

// Fixed: also check the portal's own DOM.
const isInsideFixed = wrapperRef.current.contains(event.target) || menuRef.current?.contains(event.target);
```

The other fix is to handle it in React, which already counts the portal as inside. For example, set a flag in the menu's `onClick` and read it in the `document` listener.

<GuideFigure figure="ev-portal" />

### Try it

Render `Sidebar` above and click the modal button: "Sidebar onClick" prints. Then add a native listener to the `<aside>` with a ref, and click the modal button again.

```jsx

    const log = () => console.log("native aside listener");
```

The native listener stays silent, because the DOM path from the button never passes the `<aside>`. The React handler fires, because the fiber path does. Portals are not a special case of the event system. They are the case where its rule becomes visible.

## 12. React's own event meanings

Some React events seem arbitrary. `onChange` fires on every keystroke, `onFocus` bubbles, and `onMouseEnter` does not. What are they built from?

### The short version

Several React events are logical events that plugins assemble from other native events. `onChange` on a text field comes from `input`, so it fires on every keystroke, unlike native `change`, which waits for blur. `onFocus` and `onBlur` come from `focusin` and `focusout`, which bubble, so a parent can watch focus anywhere inside it.

`onMouseEnter` and `onMouseLeave` come from the bubbling `mouseover` and `mouseout`, but behave like the browser's non-bubbling enter and leave events. Each difference is React choosing the more useful meaning. Read `e.nativeEvent.type` to see which native event lies underneath. React's docs say the exact mapping is not public API.

### The plugins

| Plugin | React events | Built from |
|---|---|---|
| `SimpleEventPlugin` | `onClick`, `onKeyDown`, `onFocus`, `onBlur` and most others | One native event each |
| `ChangeEventPlugin` | `onChange` | `input`, `change` or `click`, by element |
| `EnterLeaveEventPlugin` | `onMouseEnter`, `onMouseLeave`, `onPointerEnter`, `onPointerLeave` | `mouseout`, `mouseover` and the pointer forms |
| `SelectEventPlugin` | `onSelect` | Focus, mouse, key and `selectionchange` events |
| `BeforeInputEventPlugin` | `onBeforeInput`, composition events | `textInput`, key and composition events |
| `FormActionEventPlugin` | Functions passed to `<form action>` | `submit` |

A source comment calls `SimpleEventPlugin` the basic functionality and the rest "essentially polyfills". A **polyfill** is code that fills in a behavior the platform lacks, here an event meaning no browser event provides directly.

### onChange is not native change

```jsx
<input value={text} onChange={(e) => setText(e.target.value)} />
```

Native `change` on a text field fires only when the field loses focus after an edit. Controlled inputs need every keystroke, so React's `onChange` listens to `input` instead. It also checks that the value really changed.

| Element | Native event behind `onChange` |
|---|---|
| Text `<input>`, `<textarea>` | `input` |
| `<select>`, `<input type="file">` | `change` |
| Checkbox, radio | `click` |

If you need the blur-time behavior, attach a native `change` listener yourself.

### onFocus and onBlur bubble

```jsx
<form onFocus={(e) => console.log("focused", e.target.name, "via", e.nativeEvent.type)}>
    <input name="email" />
    <input name="password" />
</form>
```

```text role="output"
focused email via focusin
```

Native `focus` and `blur` do not bubble, which makes focus hard to watch on a container. React 17 rebuilt `onFocus` and `onBlur` on `focusin` and `focusout`, which do bubble. In the changelog: "Use browser focusin and focusout for onFocus and onBlur".

### onMouseEnter and onMouseLeave do not bubble

```jsx
<ul onMouseEnter={() => console.log("entered the list")}>
    <li>One</li>
    <li>Two</li>
</ul>
```

Moving between the two items prints nothing more. Native `mouseover` and `mouseout` bubble and fire again on every child, which is noisy for hover effects. React synthesizes enter and leave from them, once per element and its subtree. The events travel from the element being left to the one being entered, with no capture phase.

<MarginNote note="these differences are on purpose">

React renames a more useful event, switches to a bubbling twin, stops fake bubbling or synthesizes cleaner behavior. Each time it picks the meaning you usually want.

</MarginNote>

### Try it

Add `onChange` to a text input that logs `e.nativeEvent.type`, and type: `input` prints on every key. Put the `onFocus` form above on screen and tab through it. Add `onMouseLeave={(e) => console.log(e.nativeEvent.type)}` to a box and leave it: `mouseout` prints.

## 13. Debugging and reading the source

A handler will not fire, fires in the wrong order, or reaches a surprising component. How do you find the cause without guessing?

### The short version

Most event bugs fall into four groups. Some are about which handler fires: delegation, the fiber walk and portals. Some are about order: React at the root versus native listeners on their nodes. Some are about stopping, since the two systems each have a `stopPropagation`. The rest are about meaning, such as `onChange` and `onScroll`.

Classify the bug first, then confirm the geometry in DevTools. Your nodes hold none of your handlers, and the root container and portal containers hold React's listeners. Then think in two trees. The DOM tree carries native listeners. The fiber tree carries React's propagation, <Mark kind="circle">not the DOM</Mark>. Ask which tree the behavior follows.

### Symptoms and causes

| Symptom | Likely cause | Fix |
|---|---|---|
| An ancestor's handler never fires | The event does not bubble in React, such as `onScroll` | Put the handler on the element, or use `onScrollCapture` |
| No React `onClick` fires, though capture handlers did | A native listener below the root called `stopPropagation` | Remove it, or handle the event in React |
| `onClick` ignores a disabled button | React skips mouse handlers on disabled form controls | Expected, so use `aria-disabled` if clicks must arrive |
| A native listener runs before React's handler | It sits on a node the event passes first | Reason from position, or move the work into React |
| A `document` listener misses some clicks | A React handler called `stopPropagation` | Listen with `{ capture: true }` |
| A portal click reaches a far-away component | Events follow the fiber tree | Stop propagation in the portal, or move the portal |
| Outside-click treats the portal as outside | The native check follows the DOM | Also check the portal's node, or decide in React |
| `preventDefault` does nothing on wheel or touch | React's listener for it is passive | Add a native listener with `{ passive: false }` |
| `e.currentTarget` is `null` in a callback | React clears it after each handler | Copy it before the `await` or timeout |
| An error in a handler skips the error boundary | Handlers run outside rendering | Catch it in the handler |

When no handler fires, check first whether the event reaches the root at all. Two console listeners on the root container tell you.

```js
// Chrome DevTools console.
const root = document.getElementById("root");
root.addEventListener("click", () => console.log("reached the root going down"), true);
root.addEventListener("click", () => console.log("came back up to the root"));
```

If only the first line prints, a native listener below the root stopped the event. If both print and your handler still stays silent, look at the fiber side: the prop, a disabled control or a portal.

Two old symptoms belong to React 16. An event that comes back blank asynchronously meant pooling. One React copy breaking another's events meant listeners on `document`. In React 17 and later, neither should happen. If one does, check for an old React copy still on the page, or for code that still listens on `document`.

### Try it

Rebuild one bug from this guide: a native listener that stops clicks below a React `onClick`.

```jsx
function Swallowed() {
    const ref = useRef(null);
    useEffect(() => {
        const stop = (e) => e.stopPropagation();
        ref.current.addEventListener("click", stop);
        return () => ref.current?.removeEventListener("click", stop);
    }, []);
    return (
        <div onClickCapture={() => console.log("capture ran")} onClick={() => console.log("bubble ran")}>
            <button ref={ref}>Click</button>
        </div>
    );
}
```

Before changing anything, name its group: which handler, order, stopping or meaning. Then add the two root listeners from "Symptoms and causes" and click. Only "capture ran" and "reached the root going down" print, which points at stopping. Finally, open `DOMPluginEventSystem.js` and find `accumulateSinglePhaseListeners`, the walk from section 7.

## The whole thing in one list

1. React never attaches your handlers to your nodes, and stores them as props instead.
2. React gives each root container a capture and a bubble listener per event at `createRoot`, and each portal container when the portal mounts.
3. Events that do not bubble, such as `scroll` and media events, get a listener on the element itself, and `onScroll` does not bubble.
4. React registers `touchstart`, `touchmove` and `wheel` as passive, so `preventDefault` there needs a native listener.
5. Dispatch goes from the target node to its fiber, walks up the fiber tree, and runs the collected handlers with a fresh `SyntheticEvent`.
6. Capture handlers run top-down from the root's capture listener, and bubble handlers run bottom-up from its bubble listener.
7. A React `stopPropagation` stops React's walk and native `document` listeners, while a native one below the root stops React's bubble handlers.
8. Discrete, continuous and default events give `SyncLane`, `InputContinuousLane` and `DefaultLane`, unless a transition is running.
9. Updates batch because React renders later, in a microtask or a scheduler task, not because of an event-only mode.
10. Portal events follow the fiber tree, and `onChange`, `onFocus` and `onMouseEnter` are logical events built from other native events.
