Type one letter into this product page's filter box, and the input stutters. The page has 10,000 products, and every keystroke makes React do far more than show one letter.

```jsx
function ProductPage({ products }) {
    const [query, setQuery] = useState("");
    const visible = products
        .filter((p) => p.name.includes(query))
        .sort((a, b) => a.price - b.price);

    return (
        <>
            <input value={query} onChange={(e) => setQuery(e.target.value)} />
            <Header cart={{ count: 3 }} onOpenCart={() => openCart()} />
            <ProductList items={visible} />
        </>
    );
}
```

Each keystroke re-renders `Header`, filters and sorts 10,000 products again, and renders every row. The usual first move is to wrap everything in `memo`. Here, most of those wrappers would change nothing, and the code does not show why.

This guide shows where React spends time and how to fix each cause at its source. You will learn why components re-render, how React skips work, what the React Compiler automates, and when to render less or ship less.

## 1. Two kinds of slow: rendering or shipping

"My app is slow" is at least two problems, and the fix for one does nothing for the other. You can wrap components in `memo` when the real problem is a three-megabyte bundle. Or you can split the bundle when the real problem is a thousand rows that re-render on every keystroke.

### The short version

React performance splits into two mostly separate problems. **Load performance** is everything before the app responds. The browser downloads, parses and runs your JavaScript, so the cost is bytes. **Runtime performance** is everything after. Each interaction re-renders components and changes the DOM, so the cost is work per interaction.

The symptoms differ. A load problem shows a blank or frozen page that later works fine. A runtime problem loads fine, then lags as you type or scroll. The fixes do not transfer: splitting and smaller bundles fix loads, while fewer, cheaper and lower-priority renders fix runtime work. So decide the axis first, then measure on that axis.

### Two phases of an app's life

| | Load | Runtime |
|---|---|---|
| Main cost | Bytes to download, parse and execute | Renders and DOM changes per interaction |
| Symptoms | Slow first paint, clicks ignored at first | Laggy typing, janky scrolling, freezes |
| Measured with | Bundle analyzer, Network tab, load metrics | React Profiler, Performance panel |
| Fixed by | Splitting, lighter dependencies, Server Components (sections 15 and 16) | Cheaper, fewer and lower-priority renders, virtualization (sections 3 to 14) |

```jsx
// A load fix: this code downloads only when the user opens settings.
const Settings = lazy(() => import("./Settings"));

// A runtime fix: this list skips re-rendering when its props are unchanged.
const ProductList = memo(function ProductList({ items }) {
    return <ul>{items.map((p) => <li key={p.id}>{p.name}</li>)}</ul>;
});
```

Optimizing on the wrong axis is the most common way performance work fails.

### One rule over both

Both axes are full of things that feel slow but are not. So one rule sits over the whole guide: <Mark kind="marker">measure before you optimize</Mark>.

### Try it

Hard-reload a page you think is slow, so nothing comes from the cache, then paste this into the console.

```js
const [nav] = performance.getEntriesByType("navigation");
const scripts = performance.getEntriesByType("resource").filter((r) => r.initiatorType === "script");
const bytes = scripts.reduce((sum, r) => sum + r.transferSize, 0);
console.log("DOM ready after", Math.round(nav.domContentLoadedEventEnd), "ms");
console.log("JavaScript transferred:", Math.round(bytes / 1024), "KB");
```

Cross-origin scripts without a `Timing-Allow-Origin` header report 0 bytes. Then type into a field and scroll a list. If the page was slow before it answered, you have a load problem. If it lags only while you use it, you have a runtime problem.

## 2. What causes a re-render

Most developers believe a component re-renders "when its props change". So when a child re-renders with identical props, it looks like a bug. It is not a bug. The belief is wrong, and it makes every later optimization confusing.

### The short version

A component re-renders for four reasons: its own state changed, its parent re-rendered, a context it reads changed, or a key change remounted it. The surprise is the second one. When a parent renders, React renders all of its children by default, whether their props changed or not.

Props changing is not the trigger. The parent rendering is. A child with no props at all still re-renders every time its parent does. That default is why `memo` exists: it opts a child out, so the child re-renders only when its props actually differ. If React only rendered on prop changes, `memo` would be pointless.

### Rendering walks down

This Node script is a simplified teaching version of how a render spreads.

```js
// Simplified teaching version: a render walks down from whoever rendered.
const tree = {
    name: "App",
    children: [
        { name: "Header", children: [] },
        { name: "List", children: [{ name: "Row", children: [] }, { name: "Row", children: [] }] },
    ],
};

function render(node, depth = 0) {
    console.log(`${"  ".repeat(depth)}render ${node.name}`);
    for (const child of node.children) render(child, depth + 1);
}

render(tree.children[1]); // List's state changed
```

```text role="output"
render List
  render Row
  render Row
```

A **render** means React calls your component function and compares its output with last time. React starts at the component whose state changed and walks down, rendering every component below it. `Header` did not render, because it is not below `List`.

### The four causes

React compares values with `Object.is`, which works like `===` except that `NaN` equals itself.

| Cause | What happens | What stops it |
|---|---|---|
| Its own state changed | `setState` or `dispatch` queues an update, and the component renders | Nothing, that is the point. Setting an `Object.is`-equal value skips re-rendering it and its children |
| Its parent re-rendered | React renders every child below the parent | `memo` or composition (sections 5 and 9) |
| A context it reads changed | Every component that reads that context renders | Splitting the context, or a store (section 11) |
| Its key changed | React unmounts the old instance and mounts a new one | A stable key (section 10) |

A key change is not really a re-render. It is a remount, which costs more and throws away the component's state.

### A child with no props

```jsx
function Clock() {
    console.log("Clock rendered");
    return <p>{new Date().toLocaleTimeString()}</p>;
}

function Counter() {
    const [count, setCount] = useState(0);
    return (
        <>
            <button onClick={() => setCount(count + 1)}>{count}</button>
            <Clock />
        </>
    );
}
```

`Clock` takes no props, yet it logs on every click. It re-renders because `Counter` rendered, not because anything about `Clock` changed.

### Why memo exists

```jsx
const Clock = memo(function Clock() {
    console.log("Clock rendered");
    return <p>{new Date().toLocaleTimeString()}</p>;
});
```

With `memo`, React checks `Clock`'s props first and skips it when none changed, so it logs once. So when a component re-renders with the same props, ask first whether its parent rendered.

### Try it

Build `Counter` with the plain `Clock`, click three times, and count the logs.

```text role="output"
Clock rendered
Clock rendered
Clock rendered
Clock rendered
```

That is one log for the mount and one per click. Strict Mode, a development check that renders components twice to expose impure code, may double each line. Now switch to the `memo` version and click again: only the mount logs.

## 3. Cheap renders, costly work

You found a component that re-renders "too often" and wrapped it in `memo`. The app felt exactly the same. That re-render was never the cost, and the real cost was somewhere else.

### The short version

A plain re-render is usually cheap. React calls a function, gets back a few objects, and compares them with the last ones. For a simple component that takes microseconds, so blanket memoization often saves nothing you can measure.

Real cost comes from three places. One is expensive work in the render body, like sorting 10,000 items. Another is a render that cascades through thousands of descendants. The third is a **commit**, React's step of writing changes to the real DOM, that touches many nodes.

Kent C. Dodds sums up the rule: <Mark kind="underline" wraps>fix the slow render before you fix the re-render</Mark>. Make one render cheap first. Reduce how often it runs only when the count itself costs time.

### Measuring one render's cost

Run this in Node.

```js
const products = Array.from({ length: 100_000 }, (_, id) => ({ id, price: Math.random() }));

console.time("sort 100,000 products");
const sorted = [...products].sort((a, b) => a.price - b.price);
console.timeEnd("sort 100,000 products");

console.time("create one element");
const element = { type: "li", props: { children: sorted[0].id } };
console.timeEnd("create one element");
```

The sort takes tens of milliseconds and the element a hundredth of one. A frame lasts about 16ms at 60fps, so that sort in a render body drops frames on every keystroke. The opening's 10,000 products cost a few milliseconds per keystroke, before React renders a single row.

### Three real costs

| Cost | Example | Fix |
|---|---|---|
| Expensive work in render | Filtering and sorting 10,000 products on every render | Cache it with `useMemo`, or compute it elsewhere (section 7) |
| A cascade into a huge subtree | One state change re-renders 5,000 rows | Move state down, a `memo` boundary, or virtualization (sections 5, 9 and 14) |
| Many DOM mutations | A render that changes thousands of nodes | Fewer nodes and stable keys (sections 10 and 14) |

### Expensive work: cache the computation

```jsx
function ProductList({ products, query }) {
    const visible = useMemo(
        () => products.filter((p) => p.name.includes(query)).sort((a, b) => a.price - b.price),
        [products, query],
    );
    return <ul>{visible.map((p) => <li key={p.id}>{p.name}</li>)}</ul>;
}
```

The component still renders as often as before. Each render is now cheap, because the filter and sort rerun only when `products` or `query` changes. This `useMemo` caches a computation. That is a different job from `memo` skipping a component, and mixing the two up leads to memoizing the wrong thing.

### Cascades and commits

One render of a component with thousands of descendants means thousands of function calls and comparisons. Here, cutting re-renders genuinely helps, because the re-render is large.

DOM operations in the commit, and the layout and paint they trigger, are far slower than JavaScript. A render that changes thousands of nodes is slow in the commit, however fast the render was.

```js
// In the console: how many DOM nodes does this page hold?
console.log(document.getElementsByTagName("*").length);
```

A few thousand nodes is normal. Tens of thousands usually means a long list that section 14 can shrink.

### Slow render or frequent render?

If one render is expensive, make it cheaper first. If it is cheap but frequent, leave it alone. You decide which case you are in by measuring, because render cost is exactly what intuition gets wrong.

### Try it

Put the sort into a component body beside a counter button, and record a click in the React DevTools Profiler. Wrap the sort in `useMemo` and record again. The component renders just as often, but each render drops to almost nothing.

## 4. Measure first: the Profiler and Performance Tracks

You optimized for an afternoon, and the app feels the same, because you were guessing. A re-render you can see in the console might be free. A layout cost you cannot see might be the whole problem. And changes interact: memoizing one thing can shift the cost elsewhere.

### The short version

Never optimize without a measurement. The React DevTools Profiler records an interaction and shows, for each commit, which components rendered and how long each took. With its "why" setting on, it also shows why each one rendered. React 19.2 adds Performance Tracks to Chrome's Performance panel, so React's renders sit beside layout, paint and long tasks.

The `<Profiler>` component measures a subtree from code. The method is a loop. Reproduce the slow interaction, find the real bottleneck, change one thing, and measure again. If the change did not help, revert it.

### The React DevTools Profiler

Install React DevTools, open the Profiler tab, record an interaction, then stop.

| View | What it shows | What it tells you |
|---|---|---|
| Flamegraph | Each component as a bar whose width is its render time | Where the time went |
| Ranked chart | Components sorted by render time | The most expensive renders |
| Why did this render? | Reasons such as "the parent component rendered", "props changed", "hooks changed" or "context changed" | Which cause from section 2, and so which fix. "Hooks changed" points at the component's own state |

The "why" reasons need a Profiler setting, often labelled "Record why each component rendered while profiling". "This list rendered 40 times during one keystroke, 8ms each, because its parent rendered" is a diagnosis you can act on.

### Measuring from code with `<Profiler>`

```jsx
import { Profiler } from "react";

function onRender(id, phase, actualDuration, baseDuration) {
    console.log(`${id} ${phase}: ${actualDuration.toFixed(1)}ms, ${baseDuration.toFixed(1)}ms without memo`);
}

export function Page({ visible }) {
    return (
        <Profiler id="ProductList" onRender={onRender}>
            <ProductList items={visible} />
        </Profiler>
    );
}
```

React calls `onRender` after each commit inside the subtree. `phase` is `"mount"`, `"update"` or `"nested-update"`. `actualDuration` is the time this commit spent rendering the subtree. `baseDuration` estimates the cost with no memoization, so working memoization keeps `actualDuration` far below it.

`<Profiler>` adds a little overhead, so production builds turn it off. To measure in production, use React's profiling build.

```js
// vite.config.js: swap in React's profiling build for a production test.
export default {
    resolve: {
        alias: { "react-dom/client": "react-dom/profiling" },
    },
};
```

### React Performance Tracks

React 19.2 writes its own tracks into traces you record in Chrome's Performance panel.

| Track | What it shows |
|---|---|
| Scheduler ⚛ | Each render on a Blocking, Transition, Suspense or Idle subtrack, split into update, render, commit and effects |
| Components ⚛ | A flamegraph of render and effect time per component, with changed props in development |

Tracks appear automatically in development builds. Profiling builds show the Scheduler track. Their Components track lists only components inside a `<Profiler>`, unless the DevTools extension is installed. [The scheduler guide](/articles/react-scheduler-and-lanes-internals) explains the subtracks.

You can label your own work so it lines up with React's tracks.

```js
performance.mark("filter-start");
const visible = filterProducts(products, query);
performance.measure("filter products", "filter-start");
```

### The browser's Performance panel

The Performance panel shows the whole main thread: scripting, layout, paint, long tasks over 50ms and dropped frames. For loads it shows the bundle's download and parse. When jank comes from layout and paint, the React Profiler looks fine, and only this panel shows the cost.

Record with **CPU throttling** at 4x. This DevTools setting slows the CPU on purpose, because your users' phones are slower than your machine.

### The loop

1. Reproduce and record the specific slow interaction, not the app in general.
2. Read the recording for the real bottleneck: which component, which phase, which cause.
3. Make one change aimed at that bottleneck.
4. Record again, and compare. If it did not help, revert it.

<MarginNote note="both of those steps are measuring">

Most failed performance work skips the first and last steps. An optimization you cannot show helped should not stay, because it adds memo boundaries, split points or indirection for a benefit nobody measured.

</MarginNote>

### Try it

Wrap one slow part of your app in `<Profiler>` with the `onRender` above, and perform the slow interaction. Then record it in the Profiler tab, find the widest bar, and read why it rendered. Change one thing and compare.

## 5. Bailouts: how React skips a subtree

You know `memo` "prevents re-renders", but not where it acts or what it checks. Without that, you sprinkle it and hope, and you cannot predict when it will help.

### The short version

A **bailout** is React skipping a component because nothing it depends on changed. At each **fiber**, React's object for one component instance, React asks three questions. Is the props object the same one as last time? Is an update pending in this render? Did a context it reads change? If all say no, React reuses the old result.

A parent re-render creates a new props object for every child, so the first check fails. `memo` adds a second chance. It compares each prop with `Object.is`, and if all match, it bails out. That makes `memo` <Mark kind="circle">a boundary</Mark> that stops a parent's re-render from flowing down.

### What React checks at every fiber

Each fiber stores the props of its last render and the lanes of its pending updates. A **lane** is React's priority label for an update, and `renderLanes` is the set of lanes the current render is working on.

```js
// Simplified teaching version of the bailout check in beginWork (ReactFiberBeginWork.js).
function beginWork(current, workInProgress, renderLanes) {
    const sameProps = current.memoizedProps === workInProgress.pendingProps;
    const hasUpdate = (current.lanes & renderLanes) !== 0;
    const contextChanged = checkIfContextChanged(current.dependencies);
    if (sameProps && !hasUpdate && !contextChanged) {
        return bailoutOnAlreadyFinishedWork(current, workInProgress, renderLanes);
    }
    return renderComponent(current, workInProgress, renderLanes);
}
```

The props check uses `===` on the whole props object, not on each prop. JSX builds a new props object every time the parent runs.

```jsx
// Two evaluations of the same JSX build two different props objects.
const first = <Row id={1} />;
const second = <Row id={1} />;
console.log(first.props === second.props); // false
```

So after a parent re-renders, this check fails for every child, even when every prop is equal.

### The subtree check

```js
// Simplified teaching version of bailoutOnAlreadyFinishedWork.
function bailoutOnAlreadyFinishedWork(current, workInProgress, renderLanes) {
    if ((workInProgress.childLanes & renderLanes) === 0) {
        return null; // nothing below has work: skip the whole subtree
    }
    cloneChildFibers(current, workInProgress);
    return workInProgress.child; // a descendant has its own update: keep walking
}
```

Each fiber keeps `childLanes`, the set of lanes pending somewhere below it. So a bailout skips the work the parent caused. A descendant with its own state update, or one that reads a changed context, still renders.

### memo adds a props comparison

Run this simplified version of React's `shallowEqual` in Node.

```js
// Simplified teaching version of shared/shallowEqual.js.
function shallowEqual(prev, next) {
    if (Object.is(prev, next)) return true;
    const keys = Object.keys(prev);
    if (keys.length !== Object.keys(next).length) return false;
    return keys.every((key) => Object.hasOwn(next, key) && Object.is(prev[key], next[key]));
}

console.log(shallowEqual({ id: 7, label: "Ada" }, { id: 7, label: "Ada" }));
console.log(shallowEqual({ style: { padding: 8 } }, { style: { padding: 8 } }));
console.log(Object.is(NaN, NaN), NaN === NaN);
```

```text role="output"
true
false
true false
```

When a parent re-renders, React runs this comparison on the `memo` component's old and new props, and also checks that its `ref` did not change. If every prop is `Object.is`-equal, React bails out without calling the component.

Shallow means one level deep. Equal primitives pass. Objects, arrays and functions pass only when they are the same object, which is where `memo` so often fails.

<GuideFigure figure="react-memo-bailout" />

### A boundary, not a speed-up

When `memo` bails out, React produces no new children for it, so the branch below stays as it was. Place a boundary where a parent's re-render should stop cascading into a subtree that does not need it.

```jsx
const Panel = memo(function Panel({ title }) {
    const [open, setOpen] = useState(false); // changing this still re-renders Panel
    const theme = use(ThemeContext); // a new theme still re-renders Panel
    return <section className={theme}>{/* ... */}</section>;
});
```

`memo` gates only the parent-render path, one of the four causes from section 2. Own state and context still re-render the component. react.dev calls `memo` a performance optimization, not a guarantee.

### Try it

Give `Counter` from section 2 a `memo` child that receives a number prop that never changes. Confirm in the Profiler that the child does not render when you click. Then pass `count` as the prop, and watch the child render on every click.

## 6. Why memo so often does nothing

You wrapped a component in `memo`, profiled it, and it re-renders exactly as much as before. `memo` is doing precisely what it was told, and the problem is the props you feed it.

### The short version

The most common reason `memo` does nothing is a prop with a new identity on every render. An inline object like `style={{ padding: 8 }}`, an inline array or an arrow function is a brand-new value each time the parent runs. `Object.is` compares objects by identity, so it reports a change, and the bailout never fires.

The boundary works, but the props are unstable. Fix it by passing primitives, moving constants to module scope, or using `useMemo` and `useCallback`. JSX passed as `children` breaks `memo` the same way. The second reason is context, which `memo` cannot stop.

### New values on every render

Run this in Node.

```js
function render() {
    return { style: { padding: 8 }, items: [1, 2, 3], onSelect: () => {} };
}

const before = render();
const after = render();
console.log(before.style === after.style, before.items === after.items, before.onSelect === after.onSelect);
```

```text role="output"
false false false
```

A component function creates fresh objects, arrays and functions every time it runs. Here is that fact meeting `memo`.

```jsx
const MemoChild = memo(function MemoChild({ style, items, onSelect }) {
    /* ... */
});

function Parent() {
    const [count, setCount] = useState(0);
    return (
        <>
            <button onClick={() => setCount((c) => c + 1)}>{count}</button>
            <MemoChild style={{ padding: 8 }} items={[1, 2, 3]} onSelect={() => handle()} />
        </>
    );
}
```

<MarginNote note="new identity means changed, even with equal contents">

`MemoChild` re-renders on every click, because all three props are new values each time.

</MarginNote>

### Stabilize the props

```jsx
function Parent() {
    const [count, setCount] = useState(0);
    const style = useMemo(() => ({ padding: 8 }), []);
    const items = useMemo(() => [1, 2, 3], []);
    const onSelect = useCallback(() => handle(), []);
    return (
        <>
            <button onClick={() => setCount((c) => c + 1)}>{count}</button>
            <MemoChild style={style} items={items} onSelect={onSelect} />
        </>
    );
}
```

Now the three props keep their identity across renders, every comparison passes, and `MemoChild` stays quiet. So `memo` and stable props are a package deal. A boundary with unstable props is pure overhead, because it compares every time and never bails out.

That is also why `memo(Header)` in the opening would change nothing: `cart` and `onOpenCart` are new on every render.

### Better: props that are stable by nature

```jsx
const CARD_STYLE = { padding: 8 }; // one identity for the whole program

function UserRow({ user }) {
    return <MemoCard style={CARD_STYLE} userId={user.id} />; // a number compares by value
}
```

Often you can avoid unstable props altogether. Pass `userId` instead of a `{ userId }` object. Move true constants to module scope, where they have one identity forever. Use composition so the value never crosses the boundary (section 9).

### children breaks memo too

```jsx
const Card = memo(function Card({ children }) {
    return <div className="card">{children}</div>;
});

function Profile({ user }) {
    return (
        <Card>
            <Avatar user={user} />
        </Card>
    );
}
```

`children` is a prop. Each `Profile` render creates a new `<Avatar />` element, so `Card` always sees a changed `children` prop and renders.

### A custom comparison

```jsx
const Chart = memo(ChartView, (prev, next) => {
    return prev.data.version === next.data.version && prev.onHover === next.onHover;
});
```

The second argument replaces `shallowEqual`, and returning `true` means "skip". It must compare every prop, including functions, or the component keeps calling stale handlers. Avoid deep equality checks, which can freeze the page as the data grows.

### When the render comes from context

If the Profiler says a `memo` component rendered because context changed, stabilizing its props will not help (section 11). The React Compiler (section 8) stabilizes props like these automatically.

### Try it

Build `Parent` with the inline props and record three clicks in the Profiler. `MemoChild` renders each time. Switch to the stabilized `Parent`, and it renders only on mount. Then pass `MemoChild` a `<span>` as `children`, and watch the bailout break again.

## 7. useMemo and useCallback

When should you write `useMemo` or `useCallback`? Both look like free speed. They are not free, and in many codebases most of them save nothing.

### The short version

`useMemo` caches the result of a calculation between renders, and `useCallback` caches a function. Each keeps its cached value until a dependency changes, compared with `Object.is`. They have two jobs. The main one is **referential stability**, which means keeping an object or function the same across renders. A `memo` boundary or a dependency array then sees no change.

The second job is skipping an expensive calculation. react.dev suggests it when the calculation takes 1ms or more. Memoization has its own cost, so caching trivial work loses time. The cache is a hint, not a promise. With the Compiler on, you rarely write either hook.

### A teaching version of useMemo

Run this simplified version in Node.

```js
// Simplified teaching version of useMemo: one cache slot for one call site.
let slot = null;

function useMemo(compute, deps) {
    if (slot !== null && deps.every((dep, i) => Object.is(dep, slot.deps[i]))) {
        return slot.value; // same deps: reuse
    }
    slot = { value: compute(), deps };
    return slot.value;
}

function render(products, query) {
    return useMemo(() => {
        console.log("filtering");
        return products.filter((name) => name.includes(query));
    }, [products, query]);
}

const products = ["apple", "apricot", "banana"];
console.log(render(products, "ap"));
console.log(render(products, "ap"));
console.log(render(products, "ban"));
```

```text role="output"
filtering
[ 'apple', 'apricot' ]
[ 'apple', 'apricot' ]
filtering
[ 'banana' ]
```

The second call reuses the cached array, and the third computes again. React keeps one slot per hook call on the fiber, which is why hooks must run in the same order every render.

`useCallback(fn, deps)` is the same idea for a function.

```js
const onSelect = useCallback((id) => select(id), [select]);
const sameThing = useMemo(() => (id) => select(id), [select]);
```

### The two jobs

| Job | Example | Worth it when |
|---|---|---|
| Stable identity | `style` or `onSelect` passed to a `memo` child, or used in an effect's dependencies | A boundary or an effect depends on it |
| Skip expensive work | Filtering 10,000 products | `console.time` shows 1ms or more, with CPU throttling on |

To check a calculation, time it during the real interaction.

```js
console.time("filter products");
const visible = products.filter((p) => p.name.includes(query));
console.timeEnd("filter products");
```

If the logged time is well under 1ms, a `useMemo` around it costs more than it saves. Storing the value and comparing dependencies happen on every render.

### What it does not promise

React keeps the cache unless it has a reason to drop it. It drops it in development when you edit the component's file, and whenever a component suspends during its first mount. A component **suspends** when it pauses because data or code is not ready yet.

In Strict Mode, development also calls your calculation twice to reveal impure code. So use `useMemo` only for speed, never for correctness.

```jsx
// options is a new object every render, so this cache never hits.
const options = { caseSensitive: false };
const visible = useMemo(() => filter(products, options), [products, options]);
```

A memo with an unstable dependency recomputes every time and adds its own cost on top.

### Try it

Paste the teaching `useMemo` into Node and add a fourth call, `render([...products], "ban")`. Predict whether it filters, then run it. A copied array is a new dependency, so it filters again, even though its contents are equal.

## 8. The React Compiler

Stabilizing every prop that feeds every boundary by hand is tedious, and one inline arrow function breaks it. The React Compiler, stable as 1.0 since October 2025, does that work at build time.

### The short version

The **React Compiler** is a build-time plugin, `babel-plugin-react-compiler`, that adds memoization to your components and hooks. It works out which values each expression depends on and caches them in slots. Values and child elements then keep their identity until their inputs change. A reused child element passes React's same-props check, so the child bails out as if wrapped in `memo`.

The **Rules of React** say components must be pure during render. When the Compiler detects a break, it skips that component with no error by default, but it cannot detect every break. It is opt-in: installing React 19 does not turn it on. With it on, write plain code, and keep `useMemo` for rare cases, such as an effect dependency.

### What compiled code looks like

For `<Greeting name="Ada" />` inside a parent, the Compiler emits code shaped like this.

```jsx
import { c as _c } from "react/compiler-runtime";

function Parent() {
    const $ = _c(1); // one cache slot for this component
    let t0;
    if ($[0] === Symbol.for("react.memo_cache_sentinel")) {
        t0 = <Greeting name="Ada" />;
        $[0] = t0;
    } else {
        t0 = $[0];
    }
    return t0;
}
```

`_c` is React's `useMemoCache` hook, which gives the component an array of slots that survive renders. Run this simplified version in Node to see the effect.

```js
// Simplified teaching version of what the Compiler emits for one child element.
const EMPTY = Symbol.for("react.memo_cache_sentinel");
const $ = [EMPTY, EMPTY]; // the component's cache slots

function Parent(name) {
    let child;
    if ($[0] !== name) {
        child = { type: "Greeting", props: { name } }; // inputs changed: build it
        $[0] = name;
        $[1] = child;
    } else {
        child = $[1]; // inputs unchanged: reuse the same object
    }
    return child;
}

const first = Parent("Ada");
const second = Parent("Ada");
const third = Parent("Grace");
console.log(first === second, second === third);
```

```text role="output"
true false
```

The same element means the same props object, which passes the `===` check from section 5. So React skips `Greeting` with no `memo` in sight. The Compiler can also cache values after an early return or inside a condition, where hooks are not allowed.

### What it covers

| Case | Compiled? |
|---|---|
| Objects, arrays, functions and JSX built in a component or hook | Yes, cached per expression |
| A child re-render caused by its parent | Yes, through reused elements |
| An expensive call inside a component | Yes, cached per component instance |
| The same calculation used by many components | Each component keeps its own copy |
| Plain functions outside components and hooks | No, memoize those yourself if they are slow |
| Code where it detects a Rules of React violation | Skipped, with no error by default |

React DevTools marks compiled components with a "Memo ✨" badge, the quickest way to check that a component was compiled. Meta reports that on its Quest Store, initial loads and navigations improved by up to 12%. Some interactions became more than 2.5 times faster, with memory unchanged.

### Turning it on

```js
// babel.config.js: the Compiler must run first among your Babel plugins.
module.exports = {
    plugins: ["babel-plugin-react-compiler"],
};
```

```js
// next.config.js: stable in Next.js 16, off unless you set it.
// Also install babel-plugin-react-compiler as a dev dependency.
module.exports = {
    reactCompiler: true,
};
```

Vite and Rsbuild run it through their Babel integration, and new Expo apps (SDK 54 and later) start with it on. It also supports React 17 and 18, through a `target` option and the `react-compiler-runtime` package.

### The Rules of React, and opting out

The Compiler memoizes only code it can analyze as safe. Components and hooks must not mutate props or state during render, and must call hooks unconditionally. When it detects a violation, it leaves that component uncompiled.

```jsx
function Profile({ user }) {
    user.name = user.name.trim(); // mutates a prop: the Compiler skips this component
    return <p>{user.name}</p>;
}
```

It cannot catch everything: sorting a prop in place with `items.sort()` compiles without complaint. The `recommended` preset of current `eslint-plugin-react-hooks` versions runs the same analysis as lint rules. Run them even without the Compiler, because they expose real bugs.

```jsx
function LegacyGrid(props) {
    "use no memo"; // TODO: remove after the grid stops mutating rows
    /* ... */
}
```

`"use no memo"` opts one function out. Treat it as a temporary marker for code that is not safe yet. With `compilationMode: "annotation"`, the Compiler compiles only functions marked `"use memo"`, which suits a gradual rollout.

### Existing useMemo and useCallback

For new code, react.dev recommends relying on the Compiler. Use `useMemo` or `useCallback` only where you need precise control, such as a value used as an effect dependency.

For existing code, leave current memoization in place, or test carefully before removing it, because removing it can change what the Compiler emits. Without the Compiler, sections 6 and 7 still apply in full. So the advice is to <Mark kind="marker" wraps>rely on the Compiler and stop hand-memoizing defensively</Mark>.

### Try it

In a project without the Compiler, build the unstable `Parent` from section 6 and confirm in the Profiler that `MemoChild` renders on each click. Enable the Compiler, then remove `memo` from `MemoChild`. Check for the "Memo ✨" badge, record again, and confirm that the extra renders are still gone.

## 9. Composition: fewer re-renders without memo

When a component re-renders too much, `memo` is the usual reflex. Two structural changes prevent the same re-renders with no memoization at all, and people reach for them far too late.

### The short version

Two changes to a component's structure prevent re-renders with no memoization. First, **move state down**: keep state in the smallest component that needs it. A state change re-renders only its owner and what sits below it.

Second, **lift content up**: let a parent create the expensive JSX and pass it in as `children`. When the wrapper's state changes, `children` is still the same element object the parent made, so React bails out.

Both changes remove the cause instead of guarding against it. Nothing compares props on every render, and no unstable prop can break them.

### Move state down

```jsx
// Before: every keystroke re-renders the whole page.
function SignupPage() {
    const [email, setEmail] = useState("");
    return (
        <>
            <input value={email} onChange={(e) => setEmail(e.target.value)} />
            <PlanComparison />
            <Testimonials />
        </>
    );
}
```

```jsx
// After: only EmailField re-renders per keystroke.
function EmailField() {
    const [email, setEmail] = useState("");
    return <input value={email} onChange={(e) => setEmail(e.target.value)} />;
}

function SignupPage() {
    return (
        <>
            <EmailField />
            <PlanComparison />
            <Testimonials />
        </>
    );
}
```

The size of a re-render is set by where the state lives. Moving `email` into `EmailField` shrinks it to one small component. This is colocation from [the state management guide](/articles/react-state-management-architecture), used as a performance fix.

### Lift content up as children

```jsx
function ColorPicker({ children }) {
    const [color, setColor] = useState("red");
    return (
        <div style={{ color }}>
            <input value={color} onChange={(e) => setColor(e.target.value)} />
            {children}
        </div>
    );
}

function App() {
    return (
        <ColorPicker>
            <ExpensiveTree />
        </ColorPicker>
    );
}
```

`App` creates `<ExpensiveTree />`, not `ColorPicker`. When `color` changes, React runs `ColorPicker` again, but `children` is still the element `App` made. So `ExpensiveTree`'s props object is unchanged, and React bails out.

Dan Abramov's "Before You memo()" names the idea. Before memoizing, see whether the changing state and the expensive content can become siblings passed in from a common parent. Any element prop works, not only `children`, such as `sidebar={<Sidebar />}`.

### Why prefer structure

| Question | Move state down, lift content up | `memo` |
|---|---|---|
| Does the re-render happen? | No, the cause is gone | It is blocked after a comparison |
| Cost on every render | None | A comparison of every prop |
| Can one unstable prop break it? | No | Yes |

<MarginNote note="fix the structure before reaching for memo">

The order of preference for an unwanted re-render is usually: move state down, then lift content up, then a `memo` boundary. With the Compiler on, it handles much of the third case for you.

</MarginNote>

### Try it

Build `ColorPicker` with `ExpensiveTree` written directly inside its JSX, and add a `console.log` to `ExpensiveTree`. Type in the input and watch it log on every keystroke. Then pass `ExpensiveTree` in from `App` as `children`, and watch the logging stop, with no `memo` anywhere.

## 10. Keys and list reconciliation

Your list works, but something is off. Typed text jumps to the wrong row after a sort, and reordering is slower than it should be. The cause is almost always the keys.

### The short version

React matches a list's children across renders by type and key, or by type and position when there is no key. A good key is a stable id from the data, so it travels with its item. Then a reorder moves existing DOM nodes and an insert adds one node, while every row keeps its state.

The array index is a bad key, because it names a position, not an item. Insert one row at the front, and React rewrites every row, while typed text stays with the position. A `Math.random()` key remounts every row on every render. Changing a key on purpose resets a component's state.

### Matching by position or by key

Run this simplified model in Node.

```js
// Simplified teaching version of matching children by key.
function reconcile(oldItems, newItems, keyOf) {
    const oldByKey = new Map(oldItems.map((item, i) => [keyOf(item, i), item]));
    return newItems.map((item, i) => {
        const previous = oldByKey.get(keyOf(item, i));
        if (previous === undefined) return `insert ${item}`;
        return previous === item ? `keep ${item}` : `rewrite ${previous} as ${item}`;
    });
}

const before = ["A", "B", "C"];
const after = ["X", "A", "B", "C"];
console.log(reconcile(before, after, (item, i) => i)); // key={i}
console.log(reconcile(before, after, (item) => item)); // key={item.id}
```

```text role="output"
[ 'rewrite A as X', 'rewrite B as A', 'rewrite C as B', 'insert C' ]
[ 'insert X', 'keep A', 'keep B', 'keep C' ]
```

That match decides whether React reuses an instance and its DOM, or destroys and recreates it. Reuse is cheap and keeps state. Recreating is expensive and resets state.

React also compares the element type. If the key matches but `<input>` became `<textarea>`, React destroys the old element and mounts a new one.

### The index-key trap

```jsx
{items.map((item, i) => <Row key={i} item={item} />)}
{items.map((item) => <Row key={item.id} item={item} />)}
```

With `key={i}`, key `0` meant A before the insert and means X after it. React concludes that the row with key `0` is the same row with new content. So it updates every row and appends one at the end, the most DOM work possible.

Any state tied to a row stays with the position. An uncontrolled input's text typed into A now shows on X. Index keys also defeat `memo` on rows, because every row receives a different `item` after the shift.

<GuideFigure figure="pf-keys" />

With `item.id`, the key travels with the item. React sees one new key, inserts one node, and leaves every existing row and its state alone.

### How React decides to move a node

```js
// Simplified teaching version of placeChild (ReactChildFiber.js).
function placeChild(fiber, lastPlacedIndex) {
    if (fiber.oldIndex === null) return { action: "insert", lastPlacedIndex };
    if (fiber.oldIndex < lastPlacedIndex) return { action: "move", lastPlacedIndex };
    return { action: "stay", lastPlacedIndex: fiber.oldIndex };
}
```

React walks the new list left to right and remembers the highest old position it has kept. An item whose old position is lower than that must move. So a front insert moves nothing, but moving the last item to the front moves every other item.

### Key rules

| Key | Effect |
|---|---|
| A stable id such as `item.id` | Correct, and the cheapest updates |
| The array index | Safe only for lists that never reorder, insert or delete |
| `Math.random()` or a fresh id made during render | Every row remounts on every render and loses its state |
| No key | React falls back to the index and warns in development |
| Duplicate keys among siblings | React warns, and matching becomes unreliable |

### Resetting state with a key

```jsx
<UserForm key={userId} user={user} />
```

A new key makes React unmount the old instance and mount a fresh one. When `userId` changes, every field in `UserForm` resets, with no clearing effect. A remount costs more than a re-render, so use it where the reset is the goal.

### Try it

Build a list of three items, each with an uncontrolled `<input>`, keyed by index. Type into the first row, then add an item at the front. Your text now sits on the new item. Switch to `key={item.id}` and repeat, and the text stays with its item.

## 11. The cost of context, and when to use a store

You shared some state through context, and now much of the app re-renders whenever it changes. That includes components wrapped in `memo`, so `memo` could not fix it.

### The short version

A component that reads a context with `useContext` or `use` subscribes to it directly, not through props. When the provider's value changes, compared with `Object.is`, every reader re-renders, and `memo` cannot stop it.

Three fixes cover most cases. Stabilize the value so it does not change on every provider render. Split one large context into several. Put `dispatch` in its own context, since it never changes.

The hard limit is that a reader cannot subscribe to just one field. For large, fast-changing state that many components read in slices, use an external store with selectors. Then only components whose slice changed re-render.

### Readers skip the props path

```jsx
const AuthContext = createContext(null);

function AuthProvider({ children }) {
    const [user, setUser] = useState(null);
    return <AuthContext value={{ user, setUser }}>{children}</AuthContext>;
}
```

In React 19 the context itself is the provider, and `AuthContext.Provider` is the older form. Here `value` is a new object on every `AuthProvider` render. So every reader re-renders, even inside `memo`, because a context change does not travel through props.

A `memo` component that does not read the context still bails out, and only the readers below it re-render. The Profiler reports these renders as "context changed".

### Three traps

| Trap | Why it costs | Fix |
|---|---|---|
| An inline object as the value | A new identity on every provider render | `useMemo`, or the Compiler |
| One large context | Any change re-renders readers of unrelated fields | Split it by what changes together |
| State and `dispatch` together | Readers that only dispatch re-render on every state change | Two contexts, one for each |

```jsx
const StateContext = createContext(null);
const DispatchContext = createContext(null);

function CartProvider({ children }) {
    const [cart, dispatch] = useReducer(cartReducer, []);
    return (
        <DispatchContext value={dispatch}>
            <StateContext value={cart}>{children}</StateContext>
        </DispatchContext>
    );
}
```

`dispatch` and `useState` setters never change identity. So a button that only reads `DispatchContext` never re-renders when the cart changes.

### The ceiling: no selectors

React 19.2 and 19.3 have no built-in way to read one field of a context. An external store keeps state outside React and lets each component subscribe to its own slice. Run this in Node.

```js
function createStore(initial) {
    let state = initial;
    const listeners = new Set();
    return {
        getState: () => state,
        setState(patch) {
            state = { ...state, ...patch };
            for (const listener of listeners) listener();
        },
        subscribe(listener) {
            listeners.add(listener);
            return () => listeners.delete(listener);
        },
    };
}

function connect(store, name, selector) {
    let last = selector(store.getState());
    store.subscribe(() => {
        const next = selector(store.getState());
        if (!Object.is(next, last)) console.log(`${name} re-renders`);
        last = next;
    });
}

const store = createStore({ user: "Ada", theme: "dark", cursor: 0 });
connect(store, "Avatar", (s) => s.user);
connect(store, "Shell", (s) => s.theme);
connect(store, "Cursor", (s) => s.cursor);

store.setState({ cursor: 1 });
```

```text role="output"
Cursor re-renders
```

In React, `useSyncExternalStore` connects a component to such a store. It keeps the value consistent even when React pauses a render partway (section 12).

```jsx
function useStore(store, selector) {
    return useSyncExternalStore(store.subscribe, () => selector(store.getState()));
}

const cursor = useStore(store, (s) => s.cursor);
```

The selector must return a stable value, such as a field, not a new object on each call. TanStack Query uses the same model. Its hooks subscribe through `useSyncExternalStore` and re-render only for the result fields a component reads ([the data fetching guide](/articles/react-data-fetching-server-state)).

### Choosing a home for shared state

| State | Where it belongs |
|---|---|
| Theme, locale, the signed-in user | A stabilized, split context, because it changes rarely |
| Large or fast-changing state read in slices | An external store with selectors |
| Data from the server | A server-state cache such as TanStack Query |

React can restart a low-priority render (section 12), so a broad context re-render can run more than once. Still, move to a store when measurement says so, not by default.

### Try it

Paste the store into Node, call `store.setState({ theme: "light" })`, and predict the output. Then change `connect` so it ignores the selector and logs on every change. Every component now "re-renders" on every update, which is how context readers behave.

## 12. Transitions and deferred values

The product filter from the opening is now as cheap as you can make it, yet each keystroke still needs 50ms of rendering. Some work cannot be made smaller, but it must not block typing.

### The short version

React 19 lets you mark an update as a **transition**, meaning it can wait. `startTransition` gives the update a low-priority lane. React then renders it in slices of about 5ms, and throws the half-done render away if you type again. The input's own update stays urgent and commits first.

`useDeferredValue` does the same for a value. The urgent render keeps the old value, and a background render catches up. Neither makes the work smaller, since the render still takes 50ms in total. They move it out of the keystroke's way. So reach for them after you have made the render as cheap as it can be.

### The budget problem

At 60 frames per second the browser has about 16ms per frame, so a 50ms render makes typing feel sticky.

React's **concurrent rendering** is its ability to pause a low-priority render, let the browser handle input, and resume or restart it. Without a transition, an update from a click, a key press or a timer renders in one blocking pass ([the scheduler guide](/articles/react-scheduler-and-lanes-internals)).

### useTransition: mark the update

```jsx
function Search({ products }) {
    const [text, setText] = useState("");
    const [query, setQuery] = useState("");
    const [isPending, startTransition] = useTransition();

    function handleChange(e) {
        setText(e.target.value); // urgent: the input must update now
        startTransition(() => setQuery(e.target.value)); // can wait
    }

    return (
        <>
            <input value={text} onChange={handleChange} />
            <div style={{ opacity: isPending ? 0.6 : 1 }}>
                <Results products={products} query={query} />
            </div>
        </>
    );
}

const Results = memo(function Results({ products, query }) {
    const visible = products.filter((p) => p.name.includes(query));
    return <ul>{visible.map((p) => <ProductRow key={p.id} product={p} />)}</ul>;
});

function ProductRow({ product }) {
    return <li>{product.name}</li>;
}
```

The input keeps its own urgent state, so it shows each letter at once. The `query` update runs at low priority, in slices, and React restarts it from scratch if you type again first. `isPending` is a small urgent update for dimming the old results.

`Results` is wrapped in `memo` for a reason. The urgent render re-renders `Search`, and without `memo` it would re-render `Results` with the old `query`, paying the full cost anyway.

<GuideFigure figure="pf-transition" />

### Where the expensive work must live

```jsx
// Wrong: expensiveFilter runs now, inside the event handler.
startTransition(() => {
    setResults(expensiveFilter(e.target.value));
});
```

React calls the function you pass to `startTransition` immediately and synchronously. Only the renders that its state updates cause are deferred. So the filter above still blocks the keystroke for its full 50ms. Keep expensive work in render, where the transition can defer it.

React pauses only between components, never inside one. Work spread over many components, such as thousands of `ProductRow`s, slices well. One 50ms calculation inside a single component still runs as one 50ms block, so cache it with `useMemo` or split it.

### Rules that keep transitions working

| Rule | Why |
|---|---|
| Keep the input's own state out of the transition | Transition updates cannot control a text input |
| Wrap `setState` again after an `await` | After an `await`, the code runs outside the transition |
| Expect a starved transition to finish in one pass | About 5 seconds after it became pending, it expires and renders without slicing |

```jsx
startTransition(async () => {
    const data = await fetchResults(query);
    startTransition(() => setResults(data)); // wrap again after the await
});
```

### useDeferredValue: let a value lag

```jsx
function Search({ products }) {
    const [query, setQuery] = useState("");
    const deferredQuery = useDeferredValue(query);
    const isStale = query !== deferredQuery;

    return (
        <>
            <input value={query} onChange={(e) => setQuery(e.target.value)} />
            <div style={{ opacity: isStale ? 0.6 : 1 }}>
                <Results products={products} query={deferredQuery} />
            </div>
        </>
    );
}
```

On each keystroke, React first renders with the new `query` but the old `deferredQuery`. `Results` is memoized and its props are unchanged, so that urgent render is cheap. Then React renders again in the background with the new value, and any new keystroke interrupts it.

Unlike debouncing, there is no fixed delay: a slow device just lags more. If the background render suspends, the old value stays on screen. An optional second argument, `initialValue`, lets the first render defer too.

| | `useTransition` | `useDeferredValue` |
|---|---|---|
| You control | The state update | Only the value, such as a prop |
| Pending signal | `isPending` | `value !== deferredValue` |
| The slow child needs `memo` | Yes | Yes |

### It reschedules, it does not reduce

<MarginNote note="this changes priority, not speed">

<Mark kind="marker" wraps>Concurrency reschedules the work. It does not reduce it.</Mark> The rows still render and still take 50ms in total, so transitions are tools for perceived responsiveness.

</MarginNote>

### Try it

Pass `Search` 300 products, replace `ProductRow` with this deliberately slow version, and leave out the transition.

```jsx
function ProductRow({ product }) {
    const start = performance.now();
    while (performance.now() - start < 1) {} // 1ms per row
    return <li>{product.name}</li>;
}
```

Type quickly and feel the lag. The Performance panel shows one task of about 300ms per keystroke. Add `useTransition` as above, and the input stays smooth while the list catches up. The trace now shows slices of about 5ms, because each `ProductRow` is its own component.

## 13. Activity: hidden UI that keeps its state

A page has two tabs. If you unmount the hidden tab, switching back mounts it from scratch and loses the draft the user typed. If you hide it with CSS yourself, it keeps running its effects and re-rendering at full priority.

### The short version

`<Activity>`, stable in React 19.2, hides a subtree without unmounting it. With `mode="hidden"`, React hides the children with `display: none` and keeps their state and DOM. It also destroys their effects, so hidden content stops its timers and subscriptions. Updates to hidden children still render, but at the lowest priority, after visible work.

Switching back to `"visible"` shows the old UI at once and re-creates the effects. A boundary that starts hidden pre-renders its children in the background. So code and data for a likely next screen can load early. The cost is memory, because hidden trees stay alive.

### Hide instead of unmount

```jsx
import { Activity, useState } from "react";

function Tabs() {
    const [tab, setTab] = useState("posts");
    return (
        <>
            <button onClick={() => setTab("posts")}>Posts</button>
            <button onClick={() => setTab("contact")}>Contact</button>
            <Activity mode={tab === "posts" ? "visible" : "hidden"}>
                <Posts />
            </Activity>
            <Activity mode={tab === "contact" ? "visible" : "hidden"}>
                <Contact />
            </Activity>
        </>
    );
}
```

| Approach | State kept? | Effects while hidden | Cost while hidden |
|---|---|---|---|
| `{tab === "posts" && <Posts />}` | No, it remounts | None, it is unmounted | None |
| Your own `display: none` | Yes | Keep running | Renders at full priority |
| `<Activity mode="hidden">` | Yes, state and DOM | Destroyed, then re-created on show | Low-priority renders and memory |

### Pre-rendering the next screen

```jsx
<Activity mode={step === "checkout" ? "visible" : "hidden"}>
    <Checkout />
</Activity>
```

If this boundary starts hidden, React still renders `Checkout` at the lowest priority, without its effects. Its code can load early, and so can data read through Suspense, such as with `use`. Data fetched in an effect waits. React does this work on `OffscreenLane`, which [the scheduler guide](/articles/react-scheduler-and-lanes-internals) covers.

### Try it

Give `Contact` a `<textarea>` and an effect that logs on mount and cleanup.

```jsx
function Contact() {
    useEffect(() => {
        console.log("Contact effect mounted");
        return () => console.log("Contact effect cleaned up");
    }, []);
    return <textarea placeholder="Write a message" />;
}
```

Type a draft, switch tabs, and switch back. The draft survives, and the console shows a cleanup on hide and a mount on show. Replace both `<Activity>` wrappers with `&&` conditions and repeat, and the draft is lost.

## 14. Virtualization: render only what is visible

You render a list of 10,000 rows. The page loads slowly, scrolls with jank and holds a lot of memory, though only about 20 rows fit on screen.

### The short version

A list of 10,000 rows costs 10,000 renders and 10,000 DOM nodes, plus the layout and memory to hold them. **Virtualization**, also called windowing, renders only the visible rows plus a small buffer. A spacer gives the scroll container the full height, so the scrollbar behaves.

On each scroll, the list works out which rows are in view and positions just those. Cost then depends on the viewport, not the list length, which no memoization can achieve. Use a library, and only for a list you measured as slow.

### The window math

Run this in Node.

```js
function visibleRange({ scrollTop, viewportHeight, rowHeight, count, overscan = 3 }) {
    const first = Math.floor(scrollTop / rowHeight);
    const last = Math.ceil((scrollTop + viewportHeight) / rowHeight) - 1;
    return {
        start: Math.max(0, first - overscan),
        end: Math.min(count - 1, last + overscan),
        totalHeight: count * rowHeight,
    };
}

console.log(visibleRange({ scrollTop: 4200, viewportHeight: 600, rowHeight: 35, count: 10_000 }));
```

```text role="output"
{ start: 117, end: 140, totalHeight: 350000 }
```

At 4,200 pixels down, rows 120 to 137 are in view. Three rows of **overscan** on each side hide blank gaps during fast scrolling. So React renders 24 rows instead of 10,000, inside a 350,000-pixel spacer.

### A virtual list, simplified

```jsx
// Simplified teaching version of a fixed-height virtual list.
function VirtualList({ items, rowHeight = 35, height = 600 }) {
    const [scrollTop, setScrollTop] = useState(0);
    const { start, end, totalHeight } = visibleRange({
        scrollTop, viewportHeight: height, rowHeight, count: items.length,
    });

    const rows = [];
    for (let i = start; i <= end; i++) {
        rows.push(
            <div key={items[i].id} style={{ position: "absolute", top: 0, height: rowHeight, transform: `translateY(${i * rowHeight}px)` }}>
                {items[i].name}
            </div>,
        );
    }

    return (
        <div style={{ height, overflowY: "auto", position: "relative" }} onScroll={(e) => setScrollTop(e.currentTarget.scrollTop)}>
            <div style={{ height: totalHeight }} />
            {rows}
        </div>
    );
}
```

The spacer gives the scrollbar its full size, and each rendered row sits at its real offset through `translateY`. On scroll, the window moves and React renders the new set.

### Use a library

Real lists need variable row heights, measurement and scroll anchoring, so you will not hand-write this. TanStack Virtual is headless: a hook returns the visible items and their offsets, and you render the markup.

```jsx
import { useVirtualizer } from "@tanstack/react-virtual";

function Rows({ items }) {
    const parentRef = useRef(null);
    const virtualizer = useVirtualizer({
        count: items.length,
        getScrollElement: () => parentRef.current,
        estimateSize: () => 35,
    });

    return (
        <div ref={parentRef} style={{ height: 600, overflow: "auto" }}>
            <div style={{ height: virtualizer.getTotalSize(), position: "relative" }}>
                {virtualizer.getVirtualItems().map((row) => (
                    <div key={row.key} style={{ position: "absolute", top: 0, width: "100%", height: row.size, transform: `translateY(${row.start}px)` }}>
                        {items[row.index].name}
                    </div>
                ))}
            </div>
        </div>
    );
}
```

All three common libraries use the same mechanism. Pick by how complex your list is.

| Library | Shape | Best for |
|---|---|---|
| TanStack Virtual | A headless hook | Full control of the markup |
| react-virtuoso | Ready components with automatic variable heights, grouped lists, sticky headers and an end-reached callback | Chat, feeds, grouped content |
| react-window 2.x | Small `List` and `Grid` components | Simple lists and grids |

### When not to virtualize

Rows that are not rendered are missing from find-on-page and anchor links. Screen readers miss them too, unless you add ARIA attributes such as `aria-setsize` and `aria-posinset` to each item. So virtualize only a list you measured as the bottleneck. For 50 rows it is overhead, and for 50,000 it decides between usable and frozen.

### Try it

Render 10,000 rows plainly, then run `document.getElementsByTagName("*").length` in the console. Swap in the teaching `VirtualList`, pasting `visibleRange` beside it, and run it again. The count drops by about 10,000, and scrolling stays smooth even with 4x CPU throttling.

## 15. Code splitting with lazy

Your initial load is slow. The user waits for one large bundle to download and parse, though the first screen is just a login form.

### The short version

By default a bundler packs every screen into one or a few files. So the first visit downloads code for pages the user may never open. **Code splitting** cuts the bundle into chunks that load on demand. A dynamic `import()` tells the bundler to make a separate chunk.

`lazy` wraps that import in a component. It starts the download the first time the component renders, and suspends until the code arrives, while the nearest `<Suspense>` shows a fallback. Split by route first, then heavy optional features, and preload likely chunks early. Splitting helps loading only, because a split component renders exactly as fast as before.

### import() makes a chunk

```js
import { formatReport } from "./report"; // static: bundled into the main file

const { formatReport: format } = await import("./report"); // dynamic: its own chunk, fetched now
```

A static `import` lands in the main bundle at build time. A dynamic `import()` returns a promise that loads the module at runtime. So the bundler puts that module and its private dependencies in a separate file.

### lazy and Suspense

```jsx
import { lazy, Suspense } from "react";

const SettingsPage = lazy(() => import("./SettingsPage"));

function App({ showSettings }) {
    return (
        <Suspense fallback={<Spinner />}>
            {showSettings && <SettingsPage />}
        </Suspense>
    );
}
```

The first time `SettingsPage` renders, React calls the loader and the component suspends (section 7). The nearest `<Suspense>` shows its fallback until the chunk arrives. Here is a simplified version you can run in Node.

```js
// Simplified teaching version of lazy (ReactLazy.js).
function lazy(load) {
    let status = "idle";
    let result;
    let promise;
    return function render() {
        if (status === "done") return result;
        if (promise === undefined) {
            promise = load().then((module) => {
                status = "done";
                result = module.default;
            });
        }
        throw promise; // suspend: the nearest <Suspense> shows its fallback
    };
}

const fakeImport = () => new Promise((resolve) => setTimeout(() => resolve({ default: "SettingsPage" }), 100));
const Settings = lazy(fakeImport);

try {
    Settings();
} catch (thrown) {
    console.log("suspended:", thrown instanceof Promise);
    await thrown;
    console.log("rendered:", Settings());
}
```

```text role="output"
suspended: true
rendered: SettingsPage
```

The real `lazy` calls the loader once, caches the result, renders the module's `default` export, and sends a failed load to the nearest error boundary. Declare it at module top level, because one declared inside a component resets on every render.

If a lazy component suspends during a transition under a Suspense boundary that already shows content, React keeps that content instead of the fallback. Most routers run navigations as transitions, so the old page stays visible while a route chunk loads ([the Suspense guide](/articles/react-suspense-internals)).

### Where to split

| Boundary | Example | Why |
|---|---|---|
| Route | `/settings`, `/admin`, `/reports` | Users visit one page at a time |
| Heavy optional feature | A chart, a rich text editor, a large modal | Big code that only some users need |
| Not here | A button on the first screen | It adds a loading state to the critical path |

Route splitting usually gives the largest first-load win for the least effort, and most frameworks do it by default. Do not over-split, because each chunk is another request.

### Preloading

```jsx
const loadSettings = () => import("./SettingsPage");
const SettingsPage = lazy(loadSettings);

function Nav() {
    return (
        <a href="/settings" onMouseEnter={loadSettings} onFocus={loadSettings}>
            Settings
        </a>
    );
}
```

Calling the same `import()` early, on hover, focus or idle, starts the download before the click. The module system caches it, so the render finds the code ready. It is the code version of prefetching data ([the data fetching guide](/articles/react-data-fetching-server-state)). A hidden `<Activity>` (section 13) is another way to load a likely next screen early.

### Try it

Import a large library into one page of a Vite app and build it. Convert that page to `lazy` with a `<Suspense>` fallback and build again. The library moves into its own chunk, which the Network tab shows downloading only when you open the page.

## 16. Bundle cost: shipping less JavaScript

Even after splitting, the bundle is large, and you are not sure what is in it. One date library or one careless import can add hundreds of kilobytes.

### The short version

Load time is mostly JavaScript bytes, and bytes cost twice. They take time to download on slow networks, and to parse and run on slow phones. Splitting ships code later, and three levers ship less. First, look: a bundle analyzer draws a treemap of what each dependency costs.

Second, cut. Swap heavy libraries for light ones, and import only what you use. Then check that **tree-shaking**, the bundler's removal of unused exports, really worked, because it fails silently. Third, move render-only code into Server Components. A Markdown renderer that runs only on the server never reaches the browser. Measure the bundle before and after every change.

### See what you ship

```bash
# Build with source maps, then draw a treemap of what each module costs.
npx vite build --sourcemap
npx source-map-explorer "dist/assets/*.js"
```

Most bundlers have an analyzer like this, and it almost always shows a surprise. It is the load-side version of the Profiler.

| Finding | Fix |
|---|---|
| One dependency takes a large share | Find a lighter library for the same job |
| Two versions of the same library | Align versions so only one ships |
| A large library imported for one function | Import that function's module, or write it yourself |
| Polyfills for browsers you do not support | Raise the build target |

Your own code is often a small part of the bundle, and third-party libraries are the bulk. One well-chosen swap often beats a week of micro-optimization.

```js
import _ from "lodash"; // the whole library
import debounce from "lodash/debounce"; // one function and its helpers
```

### Tree-shaking fails quietly

Tree-shaking works only when the bundler can prove that dropping a module changes nothing. CommonJS modules and modules with **side effects**, meaning code that runs on import, block that proof.

```js
// components/index.js, a "barrel" file that re-exports a folder.
export * from "./Button";
export * from "./DataGrid"; // pulls in a large grid library at the top
```

```js
import { Button } from "./components"; // may drag in DataGrid too
import { Button } from "./components/Button"; // only Button
```

If the bundler cannot prove `DataGrid` is free of side effects, importing `Button` from the barrel ships the grid too. A package can declare that it has none.

```json
{
    "name": "my-ui",
    "sideEffects": false
}
```

Set that flag only when it is true, and confirm in the analyzer that the trimming happened.

### Move render-only code to the server

```jsx
// A Server Component: marked runs on the server and never ships to the browser.
import { marked } from "marked";

export default async function Post({ slug }) {
    const source = await readPost(slug);
    return <article dangerouslySetInnerHTML={{ __html: marked.parse(source) }} />;
}
```

A Server Component renders on the server and sends its output, not its code. A heavy library used only to render, such as a Markdown parser, stays off the client. The browser still downloads React, every Client Component and the serialized output ([the Server Components guide](/articles/react-server-components-internals)).

| Lever | What it does with code |
|---|---|
| Code splitting | Ships it later |
| Lighter dependencies and tree-shaking | Ships less of it |
| Server Components | Never ships it |

### Try it

Run an analyzer on a real app and find the largest dependency. Narrow one import or replace one library, rebuild, and compare the treemap.

## 17. A method for any slow screen

You know the techniques. Now you need an order of operations, so you go from measurement to the right fix instead of the technique you read about last.

### The short version

Every fix in this guide targets one measured cause, so the method starts by measuring. First classify the axis: slow to load or slow to use. For runtime problems, record the interaction and read why components rendered.

Then take the cheapest fix that matches. Make the slow render cheap, move state down, let the Compiler memoize, and fix context, before transitions or virtualization. For load problems, analyze the bundle, split by route, trim dependencies, and move render-only code to the server. After each change, measure again, and keep the change only if the number improved.

### Runtime order

1. Is the render expensive or just frequent? Fix a slow render first (section 3).
2. Shrink the re-render at its source: move state down, lift content up (section 9).
3. Let the Compiler memoize. Without it, add `memo` with stable props where the Profiler shows a parent cascade (sections 5 to 8).
4. For "context changed" renders, stabilize and split the context, or move hot state to a store (section 11).
5. For heavy work that cannot shrink and blocks input, use a transition or a deferred value (section 12).
6. For huge lists, virtualize (section 14).

### Load order

1. Analyze the bundle before you change anything (section 16).
2. Split by route, then by heavy optional feature, and preload likely chunks (section 15).
3. Trim dependencies and confirm that tree-shaking worked (section 16).
4. Move render-only code into Server Components (section 16).

### Symptoms and causes

| Symptom | Likely cause | Fix |
|---|---|---|
| Everything re-renders, or `memo` did not help | Unstable props or `children`, or a context change | Stabilize props, use the Compiler, or split the context (sections 6, 8, 11) |
| Typing lags | One expensive render blocks input | Make it cheap or virtualize the list, then use a transition (sections 3, 12, 14) |
| A long list janks while scrolling | Too many DOM nodes | Virtualize (section 14) |
| Inputs follow the wrong row | Index keys | Stable id keys (section 10) |
| State does not reset between items | The same key for every item | `key={id}` on purpose (section 10) |
| State resets when it should not | A key made during render, such as `Math.random()` | A stable id key (section 10) |
| Slow first load, but the Profiler looks fine | Bytes, not renders | Analyze, split, trim (sections 15, 16) |
| `useMemo` everywhere, nothing faster | Trivial work, unstable deps, or redundant with the Compiler | Remove what does not help (sections 7, 8) |

When the Profiler is not open, a small development-only hook can show which props changed.

```jsx
function useWhyDidYouUpdate(name, props) {
    const previous = useRef(props);
    useEffect(() => {
        const keys = Object.keys({ ...previous.current, ...props });
        const changed = keys.filter((key) => !Object.is(previous.current[key], props[key]));
        if (changed.length > 0) console.log(name, "changed:", changed);
        previous.current = props;
    });
}
```

Call `useWhyDidYouUpdate("ProductList", props)` at the top of a component. Changed function or object props point at section 6. An empty list on a re-render points at the component's own state, its parent or a context.

### Try it

Take one real complaint about your app and write the diagnosis as a single sentence.

```text
It is slow because ___, which is the mechanism in section ___, so the fix is ___.
```

Apply that fix, record again, and stop when the measurement says it is fast enough. Doing this on two or three real problems makes the loop a habit.

## The whole thing in one list

1. React performance is two problems, rendering too much and shipping too much, so first find out which one you have.
2. A parent's render re-renders all its children by default, whatever their props.
3. Most renders are cheap, so look for expensive work in render, huge cascades or many DOM changes.
4. Measure with the Profiler, `<Profiler>` and Performance Tracks, change one thing, and measure again.
5. A bailout needs the same props object, no pending update and no context change, and `memo` adds an `Object.is` check on each prop.
6. `memo` fails when props get a new identity every render, including `children`, or when the render comes from context.
7. The React Compiler caches values and elements so children bail out, and it skips components where it detects a Rules of React violation.
8. Move state down and lift content up before reaching for `memo`, and key lists by stable ids.
9. Transitions and deferred values change when work runs, and `<Activity>` hides UI without losing its state.
10. Virtualize huge lists, split by route with `lazy`, trim dependencies, and keep render-only code on the server.
