A blog post page needs one post from a database and a Markdown parser to display it. In a client-rendered React app, it looks like this.

```jsx
import { useEffect, useState } from "react";
import { Markdown } from "./markdown"; // and its parser, shipped to every visitor

export default function Post({ id }) {
    const [post, setPost] = useState(null);
    useEffect(() => {
        fetch(`/api/posts/${id}`) // an API route you also had to write
            .then((response) => response.json())
            .then(setPost);
    }, [id]);
    if (post === null) return <p>Loading…</p>;
    return <Markdown>{post.body}</Markdown>;
}
```

The browser downloads all of it, renders a spinner, calls your API route, and renders again. With React Server Components, often shortened to RSC, the page looks like this.

```jsx
import { Markdown } from "./markdown"; // stays on the server
import { db } from "./db";

export default async function Post({ id }) {
    const post = await db.posts.find(id);
    return <Markdown>{post.body}</Markdown>;
}
```

No effect, no spinner, no API route, and neither the component nor the parser reaches the browser. But it can never hold state or answer a click. This guide shows how React splits one tree between server and browser.

> Current as of React 19.2 and 19.3. Server Components and Server Functions are stable in React 19. Framework behaviour is shown with the Next.js App Router and labelled as Next.js.

## 1. Why Server Components exist

The opening page paid twice, once to download code and once to fetch data. The react.dev docs describe a static page that ships an extra 75K of gzipped libraries for content that never changes.

### The short version

A Server Component runs only on the server, at build time or for each request, and never in the browser. Because it runs where the data lives, it can `await` a database query in its body. Its code and libraries never join the **bundle**, the JavaScript files the browser downloads. The browser receives only the rendered result.

That removes four old costs: big bundles, spinner waterfalls, API routes that only pass data along, and secrets near client code. Content-heavy pages gain the most. The price is interactivity, so interactive parts stay Client Components, the ordinary React you know.

### Rendering where the data lives

```jsx
import { readFile } from "node:fs/promises";

// No directive, so this is a Server Component.
export default async function Page({ slug }) {
    const text = await readFile(`./posts/${slug}.md`, "utf8");
    return <article>{text}</article>;
}
```

This reads a file with Node's own API, which browser code can never do.

### The trade

```jsx
export default async function Post({ id }) {
    const post = await db.posts.find(id);
    return (
        <article>
            <h1>{post.title}</h1>
            <LikeButton postId={id} /> {/* a Client Component, because it handles clicks */}
        </article>
    );
}
```

A Server Component runs, returns its output and is finished, so `LikeButton` must be a Client Component (section 4). Using RSC well means a split: structure that displays data stays on the server, and interactive bits become small Client Components.

### Try it

In a Next.js App Router project, put this in `app/page.js` with no directive.

```jsx
export default async function Page() {
    const response = await fetch("https://api.github.com/repos/facebook/react");
    const repo = await response.json();
    return <p>React has {repo.stargazers_count} stars.</p>;
}
```

Run `next build && next start` and load the page. The number should be in the first HTML. Search the page's JavaScript in the DevTools Sources panel for `stargazers_count`. It should not be there, because this component never shipped.

## 2. Two environments, one module graph

With two kinds of component, which runs where? Can they render each other? Why does one misplaced line bloat the bundle?

### The short version

One React tree now spans two environments. The server runs Server Components, and the browser runs Client Components. The line between them sits in the **module graph**, the map of which file imports which.

A file that starts with `"use client"` is a client entry point, and everything it imports becomes client code. The **bundler**, the build tool that packs browser code into bundles, reads the directive at build time. Server code can render client code, but client code cannot run server-only code.

### The boundary lives in the module graph

```jsx
// page.js: no directive, so a Server Component
import { LikeButton } from "./LikeButton";
import { formatDate } from "./format";

export default async function Page() {
    const post = await db.posts.find(1);
    return (
        <article>
            <p>{formatDate(post.date)}</p>
            <LikeButton postId={post.id} />
        </article>
    );
}
```

```jsx
// LikeButton.js: a client entry point
"use client";
import { useState } from "react";
import { formatDate } from "./format"; // pulled into the client bundle too

export function LikeButton({ postId }) {
    const [liked, setLiked] = useState(false);
    return <button onClick={() => setLiked(true)}>{liked ? "Liked" : "Like"}</button>;
}
```

The bundler walks imports from each `"use client"` file and bundles everything reachable. So the directive marks an entry point, not one component, and in a file already imported by client code it changes nothing. Server Components are the default, with no directive.

`format.js` has no directive, so it runs on the server for `page.js` and ships to the browser for `LikeButton.js`. A component with no directive works the same way. <Mark kind="marker" wraps>Wherever client code imports it, that usage is a Client Component</Mark>.

### Downward only

| Move | Allowed | Why |
|---|---|---|
| A Server Component renders a Client Component | Yes | The server leaves a hole plus the props, and the browser fills it |
| A Server Component passes JSX into a Client Component | Yes | The JSX is already rendered, so it crosses as data (section 5) |
| A client file imports a component that needs the server | No | Imported there, it becomes client code, which cannot reach a database |

```jsx
"use client";
import Comments from "./Comments"; // Comments awaits db.comments.all()

export function Sidebar() {
    return <Comments />; // now a Client Component, and it breaks
}
```

The import itself does not fail, but it turns `Comments` into client code. Bundling then fails on Node-only imports, and React warns that only Server Components can be async.

### Try it

List the client entry points in a Next.js project. The pattern matches both quote styles.

```bash
grep -rlE "^['\"]use client['\"]" --include="*.js" --include="*.jsx" --include="*.tsx" app components
```

Sketch what each file imports, since all of it ships. A shipped module with no state, effects or handlers is bundle you pay for with no benefit.

## 3. Server Components: what they can and cannot do

You add `useState` to a component, and the build tells you to add `"use client"`. Why can a Server Component not use hooks?

### The short version

A Server Component runs once per server render. It never runs in the browser, so for it there is <Mark kind="circle">no "later"</Mark>: no re-render, no user event, no committed DOM. That rules out state, effects, event handlers, browser APIs and Context.

A separate `react-server` build of `react` leaves those hooks out. Next.js turns such an import into a build error that names `"use client"`. In exchange, a Server Component can be `async`, query databases, read files, hold secrets and import heavy libraries for free.

### The server build of React

```js
// The react-server build of react (packages/react/src/ReactServer.js, React 19.2), abridged.
export {
    Children, Fragment, Suspense, StrictMode, Profiler,
    createElement, cloneElement, isValidElement, lazy, memo, forwardRef,
    use, useId, useMemo, useCallback, useDebugValue,
    cache, cacheSignal, version,
};
```

Server code picks this build through the `react-server` **export condition**. That is a `package.json` label that points one package name at different files. `use`, `useId`, `useMemo` and `useCallback` survive, because none of them needs a later. So Server Components can call `use` too.

| Not available | Why |
|---|---|
| `useState`, `useReducer` | State changes over time and triggers re-renders, and there is no later render |
| `useRef` | A ref is a mutable box kept per component instance across renders, and a server render keeps no instance |
| `useEffect`, `useLayoutEffect` | Effects run in the browser after commit, which a Server Component never reaches |
| `onClick` and other handlers | They fire on browser events, and there is no browser |
| `window`, `document`, `localStorage` | They do not exist on the server |
| Context | `useContext` is missing from the server build, and `use(Context)` throws "Cannot read a Client Context from a Server Component." |

To share a theme or a user, put the provider in a small Client Component that accepts `children`, and wrap your server tree in it.

```jsx
"use client";
import { createContext } from "react";

export const ThemeContext = createContext("light");

export function ThemeProvider({ children }) {
    return <ThemeContext value="dark">{children}</ThemeContext>;
}
```

### What it can do

```jsx
import { marked } from "marked"; // a heavy parser that never ships

export default async function Profile({ id }) {
    const user = await db.users.find(id); // the render itself is async
    return <section dangerouslySetInnerHTML={{ __html: marked(user.bio) }} />;
}
```

Because the render can be asynchronous, data fetching needs no effect. Files, internal services and environment variables are safe here, because this code never reaches the user.

"Runs once" means once per server render: at build time for a static page, per request for a dynamic one. In Next.js a navigation, `router.refresh()` or a revalidating Server Action runs them again, still on the server.

### No directive marks a Server Component

```js
"use server"; // wrong tool: every export becomes a callable Server Function

export default function Page() {
    return <p>Hello</p>;
}
```

Server Components are the default, so they need no directive. `"use server"` marks Server Functions (section 8). Advice to add it "to make a Server Component" is wrong, and react.dev calls this a common misunderstanding.

### Try it

Add state to a Server Component in a Next.js app.

```jsx
import { useState } from "react";

export default function Page() {
    const [count] = useState(0);
    return <p>{count}</p>;
}
```

The build should fail and point you to `"use client"`. Move the counter into a child file that starts with `"use client"`, render it from `Page`, and it works.

## 4. Client Components and what "use client" marks

`"use client"` sounds like "browser only", yet view-source shows your Client Component's markup in the server HTML. What does it mark?

### The short version

`"use client"` does not mean "runs only in the browser". It means "this code must exist in the browser". The bundler ships the file and its imports. On the server, each export becomes a **client reference**, a marker naming the module and export.

A Client Component then runs in two places. It renders once on the server for the first HTML, then again in the browser, where it hydrates and becomes interactive (section 7). Every module under the directive ships, so push `"use client"` down to the small interactive leaf.

### The directive

```jsx
"use client";

import { useState } from "react";

export function Counter() {
    const [count, setCount] = useState(0);
    return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

The directive goes at the very top of the file, above the imports. From there, section 2's rule applies: this module and its imports ship.

<MarginNote note="client means shipped, not browser only">

The name says where the code ships and becomes interactive. It never meant the component is absent from the server.

</MarginNote>

### What the server holds instead

A Server Component that imports `Counter` does not get the function. The bundler hands it a client reference.

```js
// Simplified teaching version of registerClientReference
// (react-server-dom-webpack, ReactFlightWebpackReferences.js).
function registerClientReference(standIn, id, exportName) {
    return Object.defineProperties(standIn, {
        $$typeof: { value: Symbol.for("react.client.reference") },
        $$id: { value: `${id}#${exportName}` }, // for example "./Counter.js#Counter"
    });
}
```

When React meets this marker as an element type, it does not call it. It writes the reference into the **payload**, the stream of data the server sends to describe the rendered tree (section 6). The browser later loads the real code.

### Keep the line low

```jsx
import { LikeButton } from "./LikeButton"; // the only "use client" file here

export default async function PostPage({ id }) {
    const post = await db.posts.find(id);
    return (
        <article>
            <PostBody markdown={post.body} /> {/* stays on the server, with its parser */}
            <LikeButton postId={id} />
        </article>
    );
}
```

Only the button ships. Adding `"use client"` to `PostPage` "just in case" would ship the page, the body and the parser. That throws away most of RSC's benefit.

### Try it

In a Next.js app, render this from a page and load it.

```jsx
"use client";

export function Hello() {
    console.log("rendering Hello");
    return <p>Hello</p>;
}
```

"rendering Hello" should print in your terminal for the server render, and in the browser console during hydration. Two runs, two environments.

## 5. What can cross the boundary

You pass `onSave={() => save(id)}` to a Client Component, and the render fails. You also heard Client Components cannot contain Server Components. Two separate rules are at work.

### The short version

Props from a Server Component to a Client Component travel inside the payload. So they must be **serializable**: React must turn them into data and back. Primitives, plain objects, arrays, `Date`, `Map`, `Set`, promises and JSX cross. A live function cannot, because its code and scope exist only in server memory. Server Functions cross as references.

Composition is a separate rule. A Client Component cannot import server-only code, but it can receive server-rendered JSX as `children`. The server renders that content first, and the client only places it.

### Rule one: props must serialize

| Crosses | Notes |
|---|---|
| string, number, bigint, boolean, null, undefined | `bigint` and `undefined` get special encodings |
| Symbols from `Symbol.for` | Only globally registered symbols |
| Plain objects and arrays | Built with literals, holding serializable values |
| `Date`, `Map`, `Set`, typed arrays, `ArrayBuffer` | Rebuilt as the same built-in type |
| Promises | The client reads them with `use()` |
| JSX from Server or Client Components | This is what makes the children slot work |
| Server Functions | A reference crosses, never the code (section 8) |

| Does not cross | Why |
|---|---|
| Other functions and closures | Their code and captured scope live in server memory |
| Class instances and null-prototype objects | Methods and prototypes are not data |
| Symbols not made with `Symbol.for` | The browser cannot find the same symbol |

That is the react.dev list. React's source also encodes `FormData`, `Blob`, `ReadableStream` and async iterables, which matter most for Server Function arguments.

### Watching a function fail

These experiments run React's real server renderer in Node. Install it in an empty folder.

```bash

```



Row `2` is what the browser gets: an error row whose message production builds hide. The `digest` is an id a framework can attach to match server logs.

Rename the prop to `format`, and React instead says functions cannot be passed directly to Client Components unless marked with `"use server"`. The fix is the rule of thumb: pass data, and define behaviour inside the Client Component.

### Rule two: composition and the children slot

```jsx
// Page.js: a Server Component
import { ClientLayout } from "./ClientLayout"; // a "use client" file
import { ServerContent } from "./ServerContent"; // awaits server data

export default function Page() {
    return (
        <ClientLayout>
            <ServerContent />
        </ClientLayout>
    );
}
```

```jsx
// ClientLayout.js
"use client";
import { useState } from "react";

export function ClientLayout({ children }) {
    const [open, setOpen] = useState(true);
    return (
        <div>
            <button onClick={() => setOpen(!open)}>Toggle</button>
            {open && children}
        </div>
    );
}
```

`Page` renders `ServerContent` on the server and passes the result into `ClientLayout` as `children`. `ClientLayout` never imports or runs `ServerContent`, and only places what it was handed. This is the slot, or donut, pattern. <Mark kind="marker" wraps>A client shell can wrap server content without ever running it</Mark>.

<GuideFigure figure="react-children-slot" />

The boundary stays one-directional. The server hands content down, and the client never reaches up.

### Promises cross too

```jsx
// A Server Component: start the query, but do not wait for it.
export default async function Page({ id }) {
    const commentsPromise = db.comments.forPost(id); // not awaited
    return <Comments commentsPromise={commentsPromise} />;
}
```

```jsx
"use client";
import { use } from "react";

export function Comments({ commentsPromise }) {
    const comments = use(commentsPromise); // suspends until the value arrives
    return <ul>{comments.map((c) => <li key={c.id}>{c.text}</li>)}</ul>;
}
```

The page streams without waiting, and the comments arrive later in the same response. Wrap `Comments` in `<Suspense>` to show a fallback meanwhile.

In `fn-prop.cjs`, rename `onClick` to `value` and try each of these. Predict first, using the tables.


## 6. The RSC payload

The browser received neither a Server Component's code nor plain HTML. So what did it receive?

### The short version

The server renders Server Components into the RSC payload, a streamed text format React calls **Flight**. It is <Mark kind="circle">not HTML</Mark> and not JavaScript. Each line is a row with a hex id, and rows refer to each other by id.

Where a Client Component appears, the payload holds a reference to its module plus its props, never its code. Rows can arrive late, so a Suspense boundary or a promise fills in when its data resolves. The format is framework-facing and can change in any release.

### Real rows from a real renderer

Save this as `flight.cjs`, next to `fn-prop.cjs`, and run it the same way.

```js
const React = require("react");
const { renderToPipeableStream, registerClientReference } = require("react-server-dom-webpack/server");
const h = React.createElement;

// What a bundler generates for a "use client" file, written by hand.
const Counter = registerClientReference(function () {}, "./Counter.js", "Counter");
const manifest = { "./Counter.js#Counter": { id: "./Counter.js", chunks: ["counter", "counter.js"], name: "Counter" } };

async function Post() {
    const title = await Promise.resolve("Hello"); // pretend this is a database query
    return h("article", null, h("h1", null, title), h(Counter, { start: 3, tags: new Set(["a"]), at: new Date(0) }));
}

renderToPipeableStream(h(Post), manifest).pipe(process.stdout);
```

```text role="output"
1:I["./Counter.js",["counter","counter.js"],"Counter"]
2:["a"]
0:["$","article",null,{"children":[["$","h1",null,{"children":"Hello"}],["$","$L1",null,{"start":3,"tags":"$W2","at":"$D1970-01-01T00:00:00.000Z"}]]}]
```

Row `0` is the root, and `Post` itself is gone. `"$L1"` stands where `Counter` was and points at row `1`, which names the module, its **chunks** (the bundle files to load) and the export. The `Set` became row `2`, and the date a `"$D"` string.

### Row tags and value encodings

A row is a hex id, a colon, an optional one-letter tag, then data. React 19's Flight client reads string tags in `processFullStringRow` and binary ones in `processFullBinaryRow`.

| Tag | The row holds |
|---|---|
| none | A JSON model: elements, props and plain values |
| `I` | A client reference: module id, chunks, export name |
| `H` | A hint, such as a stylesheet or font to preload |
| `E` | An error thrown while rendering that part |

Other tags carry streams, binary data and development-only debug info. Inside the JSON, strings that start with `$` carry meaning.

| Encoding | Meaning |
|---|---|
| `["$", type, key, props]` | A React element |
| `"$1"` | The value stored in row 1 |
| `"$L1"` | A lazy reference to row 1. React suspends there until that row, a client module or late content, arrives |
| `"$@4"` | A promise, resolved when row 4 arrives |
| `"$h2"` | A Server Function reference (section 8) |
| `"$Q2"`, `"$W2"` | A `Map` or a `Set` whose entries sit in row 2 |
| `"$D…"`, `"$n…"`, `"$S…"` | A date, a bigint, a global symbol from `Symbol.for` |

### Streaming: rows arrive when their data does

Save this as `stream.cjs`. It prints each flush with its time.

```js
const React = require("react");
const { renderToPipeableStream, registerClientReference } = require("react-server-dom-webpack/server");
const h = React.createElement;

const Comments = registerClientReference(function () {}, "./Comments.js", "Comments");
const manifest = { "./Comments.js#Comments": { id: "./Comments.js", chunks: [], name: "Comments" } };
const wait = (ms, value) => new Promise((resolve) => setTimeout(() => resolve(value), ms));

async function Slow() {
    return h("p", null, await wait(500, "slow part"));
}

function Page() {
    const comments = wait(1000, ["first!"]); // not awaited: passed down as a promise
    return h("main", null,
        h("h1", null, "fast part"),
        h(React.Suspense, { fallback: h("p", null, "loading") }, h(Slow)),
        h(Comments, { comments }));
}

const start = Date.now();
const stream = renderToPipeableStream(h(Page), manifest);
stream.pipe(new (require("node:stream").Writable)({
    write(chunk, _encoding, done) {
        const ms = Math.round((Date.now() - start) / 250) * 250; // round off startup noise
        process.stdout.write(`+${ms}ms ${chunk}`);
        done();
    },
}));
```

```text role="output"
+0ms 1:"$Sreact.suspense"
3:I["./Comments.js",[],"Comments"]
0:["$","main",null,{"children":[["$","h1",null,{"children":"fast part"}],["$","$1",null,{"fallback":["$","p",null,{"children":"loading"}],"children":"$L2"}],["$","$L3",null,{"comments":"$@4"}]]}]
+500ms 2:["$","p",null,{"children":"slow part"}]
+1000ms 4:["first!"]
```

Row `1` holds the Suspense type as a global symbol, and the element type `"$1"` points at it. The first flush carries everything ready, including the fallback and a hole, `"$L2"`, for the slow part. Row `2` lands after half a second and the promise row `4` after one.

The browser shows the fallback at once and swaps in each row as it arrives. SSR HTML streams the same way (section 7), and since React 19.2 it briefly batches Suspense reveals so several appear together.

</MarginNote>

Render `Counter` twice inside `Post` and run `flight.cjs` again. You should see one `I` row and two `"$L1"` references, because React writes one `I` row per Client Component per response.

```bash

```

## 7. First load and navigation: RSC, SSR and hydration

Server Components, server-side rendering and hydration all sound like rendering on the server. They are three different steps.

### The short version

On the first load, the RSC render runs Server Components and streams the payload. **Server-side rendering** (SSR) reads that payload and renders it, with each Client Component's first markup, into HTML. The user sees content before any JavaScript runs.

**Hydration** then attaches state and event handlers to that HTML in the browser, for Client Components only. Server Components never hydrate, because they have nothing to attach. Later navigations skip HTML: the browser fetches a new payload and updates the tree in place.

### The first-load pipeline

```jsx
// Simplified teaching version of a framework's first-load handler.
import { renderToReadableStream as renderFlight } from "react-server-dom-webpack/server";
import { createFromReadableStream } from "react-server-dom-webpack/client";
import { renderToReadableStream as renderHtml } from "react-dom/server";

async function handleRequest(request) {
    const flight = renderFlight(<App url={request.url} />, clientManifest); // 1. RSC render
    const [forSsr, forBrowser] = flight.tee();

    const tree = createFromReadableStream(forSsr, { serverConsumerManifest }); // 2. SSR decodes the payload
    const html = await renderHtml(<Root tree={tree} />); // and renders it to HTML

    return new Response(inlinePayload(html, forBrowser)); // 3. HTML plus payload, streamed
}
```

In a real framework, steps 1 and 2 run in separate module graphs, because step 1 needs the `react-server` build of React.

### In the browser

```jsx
// Simplified teaching version of the browser entry.
import { hydrateRoot } from "react-dom/client";
import { createFromReadableStream } from "react-server-dom-webpack/client";

const tree = createFromReadableStream(readInlinedPayload()); // no second request
hydrateRoot(document, <Root tree={tree} />);
```

React loads the Client Component chunks, rebuilds the tree from the payload and walks the existing DOM. At each client reference, it attaches state and handlers to the nodes already there. Next.js inlines the payload in the HTML as `self.__next_f.push` scripts, so no extra request is needed.

<MarginNote note="the same reason they ship no code">

A Server Component has no browser behaviour to attach. Its HTML stays cheap static content for the life of the page, which cuts the client's work on load.

</MarginNote>

A Client Component renders twice on the first load, and that is why purity and cleanup discipline matter here too. A render that reads `Date.now()` or `window` can differ between the two runs, and React reports a hydration mismatch.

<GuideFigure figure="rs-first-load" />

In Next.js, a later navigation requests the route's payload with an `rsc` header, not an HTML document. React and the client chunks are already loaded, so only the new tree description travels. Next.js also prefetches payloads for links and caches them.

### Try it

Disable JavaScript in DevTools and load a Next.js page. The content should still appear, because SSR produced HTML, but nothing interactive works. That separates "HTML exists" from "it became interactive". Then enable JavaScript, view the page source, and search for this.

```text
self.__next_f.push
```

Each match is a chunk of the inlined payload, in the row format from section 6. Finally, click a link and find the request with an `rsc` header in the Network tab. Its response is rows, not HTML.

## 8. Server Functions: calling the server from the client

Writing data still meant an API route, a `fetch`, loading and error state, then a refresh. Could client code call the server directly?

### The short version

A **Server Function** is an `async` function marked with `"use server"` that runs on the server but can be called from client code. Its body never ships. The client gets a server reference, a stub that knows its id. Calling it sends the arguments in a POST and returns the serialized result.

So a local-looking call is a network round trip. A Server Function can be a prop, because only the reference crosses, and as a form `action` it works before JavaScript loads. React called all of these Server Actions until September 2024.

### Marking a Server Function

```js
// actions.js: every export becomes a Server Function
"use server";

export async function savePost(formData) {
    await db.posts.update({ title: formData.get("title") }); // runs on the server
}
```

```jsx
// Inline, inside a Server Component
export default function Page({ id }) {
    async function publish() {
        "use server";
        await db.posts.publish(id); // id is captured and sent along with the reference
    }
    return <PublishButton onPublish={publish} />;
}
```

At the top of a file, `"use server"` marks every export. At the top of an async function body, it marks that one function. It never marks components. "Server Action" now means a Server Function used as an action, such as a form's `action`.

### What the client receives

Save this as `server-ref.cjs`. It does by hand what a bundler does for `"use server"`.

```js
const React = require("react");
const { renderToPipeableStream, registerClientReference, registerServerReference } = require("react-server-dom-webpack/server");

const LikeButton = registerClientReference(function () {}, "./LikeButton.js", "LikeButton");
const manifest = { "./LikeButton.js#LikeButton": { id: "./LikeButton.js", chunks: [], name: "LikeButton" } };

// What a bundler generates for a "use server" export, written by hand.
async function like(postId) {
    return postId;
}
registerServerReference(like, "./actions.js", "like");

const tree = React.createElement(LikeButton, { postId: 7, onLike: like.bind(null, 7) });
renderToPipeableStream(tree, manifest).pipe(process.stdout);
```

```text role="output"
1:I["./LikeButton.js",[],"LikeButton"]
2:{"id":"./actions.js#like","bound":"$@3"}
0:["$","$L1",null,{"postId":7,"onLike":"$h2"}]
3:[7]
```

The function body appears nowhere. `onLike` became `"$h2"`, and row 2 holds the function's id plus its `bind` arguments, which React turns into a stub in the browser.

### Calling it is a POST

```js
// Simplified teaching version of the client stub (createServerReference in react-client).
function createServerReference(id, callServer) {
    return (...args) => callServer(id, args);
}

// The framework supplies callServer. The endpoint and header here are made up.
async function callServer(id, args) {
    const response = await fetch("/server-functions", {
        method: "POST",
        headers: { "x-function-id": id },
        body: await encodeReply(args), // the same serialization rules, in reverse
    });
    return createFromFetch(Promise.resolve(response)); // the result comes back as Flight rows
}
```

<MarginNote note="it looks local but it is a network call">

Every call pays a round trip and serializes its arguments. Treat it like a request.

</MarginNote>

The server decodes the arguments with `decodeReply` and runs the function. In Next.js the POST goes to the page that invoked the action. Next.js also runs Server Actions one at a time per client, so `Promise.all` will not parallelize them.

### Forms that work before JavaScript

```jsx
import { savePost } from "./actions";

export default function Editor() {
    return (
        <form action={savePost}>
            <input name="title" />
            <button>Save</button>
        </form>
    );
}
```

Before hydration, this is a plain HTML form. React adds a hidden field named `$ACTION_ID_` plus the function's id, and the server's `decodeAction` finds the function from it. After hydration, React intercepts the submit and calls the function without a reload.

This is **progressive enhancement**: the form works first, and JavaScript makes it nicer. In Next.js, a form inside a Client Component queues an early submit until it hydrates.

| Hook | Problem it solves | Returns |
|---|---|---|
| `useActionState(action, initialState)` | Replaces `useState` for the result, an `onSubmit` handler and a loading flag | `[state, dispatchAction, isPending]` |
| `useFormStatus()` | A child inside a form, like a submit button, needs the form's status without prop drilling | `{ pending, data, method, action }` |
| `useOptimistic(value, reducer)` | The UI should change at once while the action runs, then settle on the real result | `[optimisticState, setOptimistic]` |

```jsx
"use client";
import { useActionState } from "react";
import { saveTitle } from "./actions"; // "use server": (previous, formData) => message

export function TitleForm() {
    const [message, formAction, isPending] = useActionState(saveTitle, "");
    return (
        <form action={formAction}>
            <input name="title" />
            <button disabled={isPending}>Save</button>
            <p>{message}</p>
        </form>
    );
}
```

### Try it

In a Next.js app, import this into a `"use client"` component and call it from a button.

```js
"use server";

export async function ping(message) {
    console.log("server got", message);
    return message.toUpperCase();
}
```

The log should appear in your terminal, though in development React may also echo it in the browser console, marked as server output. The Network tab should show a POST. Then disable JavaScript and submit the `Editor` form above. It should still save.

## 9. Keeping the server side safe

Server code now feels like component code, and that comfort is the risk. One import can leak a secret, and a Server Function is a public endpoint.

### The short version

Two rules keep the server side safe. First, a Server Function's arguments are client-controlled, and anyone can send its POST without your UI. A login check on the page that renders the form does not protect it. So each function validates input and checks authentication and authorization itself.

Second, keep server-only code out of client modules. Importing the `server-only` package turns that mistake into a build error, and Next.js sends only `NEXT_PUBLIC_` environment variables to the client. Next.js adds its own protections, but they never replace your checks.

### Every Server Function checks its caller

```js
"use server";

export async function deletePost(postId) {
    const session = await auth(); // who is calling?
    if (!session) throw new Error("Unauthorized");

    if (typeof postId !== "string") throw new Error("Bad input"); // never trust the shape
    const post = await db.posts.find(postId);
    if (post.authorId !== session.userId) throw new Error("Forbidden"); // may this caller do this?

    await db.posts.delete(postId);
}
```

<Mark kind="underline" wraps>Treat every Server Function as a public HTTP endpoint</Mark>. Authentication asks who is calling. Authorization asks whether that caller may touch this post. Without it, any logged-in user can delete anyone's post, a bug called an insecure direct object reference.

Next.js accepts only POST for actions. It blocks **cross-site request forgery** (CSRF), where another site makes the user's browser send the POST, by checking that `Origin` matches `Host`. It caps bodies at 1MB, encrypts action ids and captured variables, and strips unused actions. The docs still say to check every caller yourself.

### Keeping secrets out of the bundle

```js
// lib/data.js
import "server-only"; // importing this file from client code fails the build

export async function getData() {
    const response = await fetch("https://api.example.com/data", {
        headers: { authorization: process.env.API_KEY },
    });
    return response.json();
}
```

Without that import, a Client Component could import `getData` by accident. Next.js would bundle it with `process.env.API_KEY` replaced by an empty string, and the call would fail confusingly. The `client-only` package marks the opposite case.

Props leak too. Everything passed to a Client Component is readable in the payload, so pass the fields it needs, not a whole user record.

### Try it

Create `lib/secret.js` with `import "server-only"` at the top, then import it from a client file.

```js
"use client";
import "../lib/secret"; // the build should fail here
```

The Next.js build should fail and name the file. Then right-click one of your action requests in the Network tab and choose "Copy as cURL". Replay it with another user's post id, and confirm your check rejects it.

## 10. What React owns and what the framework owns

Much of what people call RSC behaviour is Next.js behaviour, and caching is the biggest example. Knowing the owner tells you which docs to read.

### The short version

React defines the model, and a framework turns it into an app with files, a router, HTTP endpoints and caching. RSC needs a bundler to create client references, which is why real apps run through a framework.

Caching shows the split. React's only caching primitive here is `cache()`, which shares a result within one server request. Anything that lasts across requests, like `"use cache"` or `revalidatePath`, is Next.js. So read the React docs for the why, and the framework docs for the how.

### Who owns what

| React core (react.dev, stable in React 19) | Your framework (Next.js here) |
|---|---|
| Server Components, Client Components and the boundary | File conventions and where routes live |
| `"use client"`, `"use server"` and their meaning | How an `await` in a component is tied to a request |
| Server Components as the default | The router, and navigations that fetch payloads instead of HTML |
| The payload format and the serialization rules | The HTTP endpoint a Server Function lives at, and how forms post to it |
| Server Functions, `use`, `useActionState`, `useFormStatus`, `useOptimistic` | Caching, revalidation and most performance behaviour |
| Progressive enhancement as a design goal | The mechanism that delivers it |
| `cache()` for one request | `"use cache"`, `cacheLife`, revalidation and the router cache |

### React's cache lasts one request

```js
import { cache } from "react";

export const getUser = cache(async (id) => {
    return db.users.find(id); // runs once per id per request
});
```

Two Server Components that call `getUser(1)` in one render share a single query. React drops the cache when the request ends, and `cache` works only in Server Components.

### Next.js caches across requests

```js
import { cacheLife } from "next/cache";

export async function getProducts() {
    "use cache";
    cacheLife("hours");
    return db.products.all();
}
```

With Cache Components, a Next.js setting enabled in `next.config`, `"use cache"` keeps a result across requests, keyed by its arguments. After a mutation, calls such as `revalidatePath` choose what to refresh.

### Try it

Wrap a data function in `cache`, log inside it, and call it from two Server Components on one page.

```jsx
export default function Page() {
    return (
        <>
            <UserName id={1} />
            <UserAvatar id={1} />
        </>
    );
}
```

It should log once per request. Remove `cache`, and it should log twice.

## 11. Same engine, new input: debugging the boundary

Does RSC replace fibers, reconciliation and the commit phase? And when something breaks, where do you look first?

### The short version

RSC does not replace the rendering engine. It gives it a new input: part of the element tree arrives pre-rendered as the payload. The host elements a Server Component returned become fibers, but the Server Component itself never exists in the browser.

Client Components run hooks and re-render as before. A new payload is diffed against the current tree, so client state survives where type and position match. When something breaks, ask which side this code is on, and whether it does something only the other side can.

### What the browser actually holds

```jsx
// What the browser builds from row 0 of the payload in section 6.
<article>
    <h1>Hello</h1>
    <Counter start={3} tags={new Set(["a"])} at={new Date(0)} />
</article>
```

`Post` is not in this tree, so it has no fiber, no hooks and no re-render. The `article` and `h1` become host fibers and commit like any DOM elements. `Counter` is a normal Client Component, so bailouts, effect timing and keys apply as before. <Mark kind="marker">Same engine, new input.</Mark>

A Next.js navigation or refresh brings a new payload, which React reconciles with the usual rules: same type at the same position, keys for lists. So a Client Component in a shared layout keeps its state.

### A procedure for boundary bugs

1. Trace imports up to the nearest `"use client"` file to find the side.
2. Server territory has no state, effects, events or browser APIs.
3. Client territory has no database, files or secrets.
4. Fix a violation by moving the piece, often into a small client leaf.

### Pitfalls

| Pitfall | Do this instead | Section |
|---|---|---|
| A heavy client bundle, because `"use client"` sits too high or was added "just in case" | Put it on the interactive leaf | 2, 4 |
| `"use server"` to make a Server Component | Add no directive | 3, 8 |
| Believing `"use client"` means browser-only | It still renders to HTML on the server | 4 |
| A serialization error, because a function or class instance was passed down | Pass data, and define the function in the Client Component | 5 |
| Importing server-only code into a client file | Pass server content down as `children` | 2, 5 |
| Reading Context in a Server Component | Put the provider in a Client Component | 3 |
| A Server Function without its own checks | Validate and authorize inside it | 9 |
| Passing a whole database record as props | Pass only the fields needed | 9 |
| Fetching in an effect out of habit | Fetch in a Server Component during render | 1, 3 |

The React DevTools Profiler shows Client Components rendering as usual. Server Components never re-render in the browser, so they never appear there as re-rendering.

### Try it

Audit one real page. Mark each component's side and ask whether it needs to be there. Then move one `"use client"` deeper.

```diff
- "use client"; // at the top of app/page.js
+ "use client"; // only at the top of app/LikeButton.js
```

Compare the JavaScript transferred in the Network tab before and after. Then record an interaction in the React DevTools Profiler, and confirm only Client Components render.

## The whole thing in one list

1. RSC splits one tree at `"use client"` boundaries in the module graph, fixed at build time.
2. Server Components are the default: they run only on the server, can `await` data, and ship no code.
3. Never running in the browser, they have no state, effects, handlers, browser APIs or Context.
4. Client Components ship to the browser, render to HTML on the server first, then hydrate.
5. Props must serialize, and server content enters Client Components as `children`.
6. The payload is Flight: streamed rows of JSON, client references and late-filling promises.
7. On first load RSC feeds SSR, which feeds hydration, and navigations fetch payloads.
8. Server Functions turn a client call into a POST, so each must validate and authorize its caller.
9. Caching across requests belongs to the framework, while React offers per-request `cache()`.
10. Reconciliation still processes the result in the browser: same engine, new input.
