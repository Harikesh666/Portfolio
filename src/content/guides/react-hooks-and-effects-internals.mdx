A chat room shows a notification when it connects. You switch the theme, and the chat disconnects and reconnects. You remove `theme` from the dependency array, and the linter complains. You silence the linter, and the notification uses yesterday's theme.

```jsx
function ChatRoom({ roomId, theme }) {
    useEffect(() => {
        const connection = createConnection(roomId);
        connection.on("connected", () => showNotification("Connected!", theme));
        connection.connect();
        return () => connection.disconnect();
    }, [roomId, theme]); // switch the theme, and the chat reconnects
}
```

Each part of that bug comes from a few mechanisms. React keeps your hooks in a list on an internal object. Each render sees a frozen copy of state. An effect compares its dependencies with `Object.is`, and every setup has a cleanup.

This guide shows those mechanisms as React's source implements them. By the end you can derive the rules of hooks, and section 13 fixes the chat room.

> Current as of React 19.2 and 19.3, with React Compiler 1.0. The hook model dates from React 16.8, and `useEffectEvent` became stable in 19.2.

## 1. Hooks live in a list on the fiber

Everyone repeats the rules of hooks. Call them at the top level, never inside a condition, a loop or after an early return. Call them only from components or other hooks.

A rule you cannot derive is a rule you will break by accident. So where do these rules come from?

### The short version

A function component has no `this` and no object to keep state on. So React keeps one internal object per component instance, its **fiber**, and stores your hooks there as a linked list.

React matches each hook call to a list node <Mark kind="circle">only by order</Mark>: the first call gets node one, the second gets node two. It never sees your variable names. Call a hook conditionally and the order shifts, so a call reads another hook's node.

The rules are not style. They are the only thing that works with storage by position. Before each render React installs a mount or update version of every hook, and after it a version that throws.

### A toy hooks runtime

This teaching version runs in Node. It keeps hooks in an array and finds them with a cursor.

```js
// Simplified teaching version: hooks found by position, not by name.
let fiber = null; // the component being rendered
let cursor = 0; // which hook slot we are up to

function useState(initial) {
    const owner = fiber;
    const slot = cursor++;
    if (owner.hooks.length <= slot) owner.hooks.push(initial); // first render: allocate
    const setState = (value) => {
        owner.hooks[slot] = value;
    };
    return [owner.hooks[slot], setState];
}

function render(component, f, props) {
    fiber = f;
    cursor = 0;
    return component(props);
}
```

Now break rule one on purpose.

```js
function Form({ showAge }) {
    const [name] = useState("Ada");
    if (showAge) {
        const [age] = useState(36); // a conditional hook: the bug
    }
    const [city] = useState("London");
    return `${name}, ${city}`;
}

const formFiber = { hooks: [] };
console.log(render(Form, formFiber, { showAge: true }));
console.log(render(Form, formFiber, { showAge: false }));
```

```text role="output"
Ada, London
Ada, 36
```

On the second render, the `city` call reaches slot two, which holds the age. Nothing knew the names, so nothing noticed.

### The real hook node

React links nodes instead of using an array, starting at the fiber's `memoizedState` field.

```ts
// The Hook type in ReactFiberHooks.js, React 19.
type Hook = {
    memoizedState: any; // this hook's value
    baseState: any; // the state before any skipped update (section 5)
    baseQueue: Update | null; // skipped updates waiting to replay (section 5)
    queue: any; // the update queue, for useState and useReducer
    next: Hook | null; // the next hook called in this component
};
```

`memoizedState` holds something different for each kind of hook.

| Hook | The node's `memoizedState` holds | `queue` |
|---|---|---|
| `useState`, `useReducer` | The current state | An update queue |
| `useEffect`, `useLayoutEffect`, `useInsertionEffect` | An effect object `{ tag, create, deps, inst }` | `null` |
| `useMemo` | `[value, deps]` | `null` |
| `useCallback` | `[callback, deps]` | `null` |
| `useRef` | The ref object `{ current }` | `null` |
| `useContext`, `use()` | No node at all | n/a |

<GuideFigure figure="hk-hook-nodes" />

React works in two phases. The render phase calls your components to compute the new UI, and the **commit** phase applies the result to the DOM. On the first render, `mountWorkInProgressHook` appends a node per call. Later renders walk the list with `updateWorkInProgressHook`, copying each node from the last committed fiber.

### The errors a broken order produces

```text
Rendered more hooks than during the previous render.
Rendered fewer hooks than expected. This may be caused by an accidental early return statement.
Should have a queue. You are likely calling Hooks conditionally, which is not allowed.
```

React throws the first when a render calls more hooks than the stored list holds, and the second when a render stops early. It throws the third when a `useState` call lands on a node without an update queue, such as an effect's node.

In development it first warns about a change in the order of hooks. Some mismatches throw nothing and read the wrong node, so never count on the error.

### The dispatcher swap

```js
// From renderWithHooks in ReactFiberHooks.js, React 19.2 (production branch, simplified).
ReactSharedInternals.H =
    current === null || current.memoizedState === null
        ? HooksDispatcherOnMount // first render: allocate nodes
        : HooksDispatcherOnUpdate; // later renders: read nodes

let children = Component(props, secondArg);

ReactSharedInternals.H = ContextOnlyDispatcher; // after render: hooks throw
```

A **dispatcher** is an object holding one implementation of every hook. The `useState` you import forwards to whichever dispatcher React installed, so one line creates a node on mount and reads it on update.

| Dispatcher | When React installs it | What `useState` does there |
|---|---|---|
| `HooksDispatcherOnMount` | The fiber's first render | `mountState`: create the node and its queue |
| `HooksDispatcherOnUpdate` | Later renders | `updateState`: walk to the node and fold its queue |
| `HooksDispatcherOnRerender` | A re-run after a render-phase update, or after `use()` suspends (waits on a promise) | `rerenderState`: apply the render-phase updates |
| `ContextOnlyDispatcher` | Outside any render | Throws "Invalid hook call" |

That last row is rule two: call a hook from an event handler, and the throwing dispatcher answers. `eslint-plugin-react-hooks` checks both rules statically, and its `recommended` preset also reports diagnostics from React Compiler, the build tool that adds memoization (section 14).

`use()` is the one exception to rule one. It takes no node, so it may sit inside a condition (section 17).

### Try it

Run the toy in Node and confirm the city comes out as 36. Then, in a React app, call `useState(1)`, then `if (props.flag) useState(2)`, then `useEffect(...)`. Toggle `flag` from a parent and watch the warning, then the crash.

Turning `flag` on usually gives "Should have a queue", because the second `useState` reads the effect's node. Move the second `useState` above the `if` to fix it.

## 2. Every render is a snapshot

You call `setCount(count + 1)` and log `count` on the next line. The log shows the old value. A `setInterval` created once logs the same count forever. It looks as if `count` missed an update.

### The short version

Each time React calls your component, it produces one render. That render has its own props, its own state and its own functions, all fixed at that call's values. `count` is not a live variable you read "now". It is a constant for the whole life of one render.

A setter does not change that constant. It queues an update and asks React for a new render, which reads a new constant. <Mark kind="marker" wraps>Closures capture the render they were born in.</Mark> So a callback that outlives its render keeps that render's values. React chose this because a render that never changes midway can be paused, restarted or thrown away safely.

### One render, one set of constants

```jsx
function Counter() {
    const [count, setCount] = useState(0);

    function handleClick() {
        setCount(count + 1);
        console.log(count); // this render's value, not the new one
    }

    useEffect(() => {
        const id = setInterval(() => {
            console.log(count); // render zero's count, forever
        }, 1000);
        return () => clearInterval(id);
    }, []);

    return <button onClick={handleClick}>{count}</button>;
}
```

Think of a flipbook. Each render is one drawing, and the `count` on page three is 3 for good. React does not edit page three. It draws page four.

| What you see | Why |
|---|---|
| `console.log(count)` after `setCount` logs the old value | The setter schedules a new render instead of reassigning this one's constant |
| A click handler sees the state of one render | Each render makes a new `handleClick` that closes over its own `count` |

### Watch two renders in Node

```js
// Simplified teaching version: each render is a fresh call with fresh constants.
const store = { count: 0 };
const buttons = [];

function Counter() {
    const count = store.count; // a constant for this render
    function handleClick() {
        store.count = count + 1; // stands in for setCount(count + 1)
        console.log("this handler sees count =", count);
    }
    buttons.push(handleClick);
}

Counter(); // render 1
buttons[0](); // click the button that render 1 drew
Counter(); // render 2
buttons[0](); // render 1's handler, still alive
buttons[1](); // render 2's handler
```

```text role="output"
this handler sees count = 0
this handler sees count = 0
this handler sees count = 1
```

Render 1's handler still sees 0 after render 2 exists. It belongs to a render that already happened.

<GuideFigure figure="react-render-snapshot" />

### Why React chose snapshots

React could have made `count` a live value. With snapshots, the same props and state always give the same UI. Concurrent React, which can render in pieces, relies on that.

So do not ask "what is `count` now?". Ask "which render's snapshot does this code close over?".

### Try it

In a React app, build the `Counter` above. Click several times: the screen climbs while the console keeps logging 0. Add `count` to the effect's dependency array, and the rebuilt closure makes the log track the screen.

## 3. Stale closures: the bug in long-lived callbacks

A timer, a subscription or a listener keeps acting on old data. Adding the value to the dependency array fixes it, but sometimes the timer then resets every second. You want to reason about this instead of guessing.

### The short version

A **stale closure** is section 2 in action: a function that outlives its render keeps seeing that render's values. Timers, subscriptions and listeners live longest, so they go stale most often. There are three fixes, and the right one depends on what the code needs.

If it only needs the previous state, use the updater form `setCount(c => c + 1)`. If the work changes with the value, list it as a dependency. If the code reads the value but should not react to it, use `useEffectEvent`. The wrong fix trades a stale value for an effect that keeps restarting.

### The broken counter

```jsx
useEffect(() => {
    const id = setInterval(() => {
        setCount(count + 1); // count is frozen at the render that ran this effect
    }, 1000);
    return () => clearInterval(id);
}, []); // runs once, so its closure is render zero's
```

This counts to 1 and stops. Every tick computes `0 + 1`, because the callback closed over render zero and React never rebuilds it.

### Fix A: stop depending on the value

```jsx
useEffect(() => {
    const id = setInterval(() => {
        setCount((c) => c + 1); // React passes the latest state in
    }, 1000);
    return () => clearInterval(id);
}, []);
```

The updater `c => c + 1` does not close over `count`. React hands it the current value when it processes the queue (section 4). The effect truly does not depend on `count`, so it should not list it.

### Fix B: rebuild the effect when the value changes

```jsx
useEffect(() => {
    const id = setInterval(() => {
        setCount(count + 1);
    }, 1000);
    return () => clearInterval(id);
}, [count]); // a fresh effect, and closure, after every change
```

This also works, at a cost. Every change runs the cleanup and a new setup, so the interval clock restarts each tick. Fix B is right when the work really should be rebuilt, such as reconnecting a socket for a new `roomId`.

### Fix C: mark the value as non-reactive

When the effect must read the latest value but a change should not re-run it, use `useEffectEvent` (section 13).

| Fix | What it does | Re-runs the effect? | Use it when |
|---|---|---|---|
| A: updater form or a ref | Stops reading the stale value | No | The code only needs the previous state |
| B: honest dependencies | Rebuilds the closure on change | Yes, every change | The work differs for each value |
| C: `useEffectEvent` | Reads the latest value at call time | No | The value is read but is not a trigger |

### Try it

In a React app, build the broken counter and confirm it stops at 1. Apply Fix A and watch it count. Apply Fix B with a `console.log` in the cleanup, and watch cleanup and setup fire every second.

## 4. Setting state queues an update

You call `setCount(count + 1)` three times in one handler, and the count goes up by one. Three calls to `setCount(c => c + 1)` go up by three. And nothing changes until your function runs again. What is the model?

### The short version

A setter does not change a variable. It creates an update object, adds it to that hook's **update queue**, and asks React to schedule a render. On the next render, `useState` folds the queue: it starts from the previous state and applies each update in order. A plain value replaces the running result, and an updater function receives it.

So three `setCount(count + 1)` calls all hold the value 1, from the same snapshot, and land on 1. Three `setCount(c => c + 1)` calls compose to 3. React renders once for all three, because it renders later, in a microtask or a task, after your handler has finished.

### The fold

`basicStateReducer` below is React's real function. The `fold` around it is a simplified teaching version of the loop in `updateReducerImpl`.

```js
function basicStateReducer(state, action) {
    return typeof action === "function" ? action(state) : action;
}

function fold(baseState, updates) {
    let state = baseState;
    for (const update of updates) state = basicStateReducer(state, update.action);
    return state;
}

const count = 0; // this render's snapshot
const valueForm = [{ action: count + 1 }, { action: count + 1 }, { action: count + 1 }];
const updaterForm = [{ action: (c) => c + 1 }, { action: (c) => c + 1 }, { action: (c) => c + 1 }];
console.log(fold(count, valueForm));
console.log(fold(count, updaterForm));
```

```text role="output"
1
3
```

In a component, the same two handlers look like this.

```jsx
function handleClick() {
    setCount(count + 1); // count is 0 in this render, so the update holds 1
    setCount(count + 1); // still 0, still 1
    setCount(count + 1); // the queue folds 0 -> 1 -> 1 -> 1
}

function handleClickComposed() {
    setCount((c) => c + 1); // the update holds a function
    setCount((c) => c + 1);
    setCount((c) => c + 1); // the queue folds 0 -> 1 -> 2 -> 3
}
```

If your next state depends on the previous state, use the updater form.

### The queue is a circular list

```js
// Simplified teaching version of how React links updates into queue.pending.
function enqueue(queue, update) {
    if (queue.pending === null) {
        update.next = update; // the first update is a ring of one
    } else {
        update.next = queue.pending.next; // the new last points at the first
        queue.pending.next = update; // the old last points at the new one
    }
    queue.pending = update; // pending always points at the newest update
}

const queue = { pending: null };
for (const action of ["a", "b", "c"]) enqueue(queue, { action });

const order = [];
const first = queue.pending.next; // the oldest update
let update = first;
do {
    order.push(update.action);
    update = update.next;
} while (update !== first);
console.log(order.join(" -> "));
```

```text role="output"
a -> b -> c
```

`queue.pending` points at the newest update, and its `next` is the oldest. One pointer gives React both ends, so adding an update and starting the walk each take one step. Each update carries more than your action.

```ts
// The Update type in ReactFiberHooks.js, React 19.2 (a gesture field omitted).
type Update<S, A> = {
    lane: Lane; // how urgent the update is (section 5)
    revertLane: Lane; // used by useOptimistic (section 17)
    action: A; // your value or updater function
    hasEagerState: boolean; // computed before render? (section 6)
    eagerState: S | null;
    next: Update<S, A>; // the next update in the ring
};
```

Every update first waits in a side buffer, `concurrentQueues`. React links the buffer into the ring when the next render starts, so the ring never changes under a render that is reading it.

### What a setter does

```js
// Simplified teaching version of dispatchSetState (ReactFiberHooks.js).
function dispatchSetState(fiber, queue, action) {
    const lane = requestUpdateLane(fiber); // how urgent, read from context
    const update = { lane, action, hasEagerState: false, eagerState: null, next: null };
    const root = enqueueConcurrentHookUpdate(fiber, queue, update, lane); // join the queue
    scheduleUpdateOnFiber(root, fiber, lane); // mark the lane, then schedule the root
}
```

It never touches the value your render holds. `requestUpdateLane` picks a **lane**, a bit that says how urgent the update is. A click gives `SyncLane`, a timer `DefaultLane`, and `startTransition` a transition lane.

A **transition** is an update you mark as not urgent with `startTransition`, so React may render it later and interrupt it. [The scheduler and lanes guide](/articles/react-scheduler-and-lanes-internals) covers lanes in full.

### Batching

```jsx
setTimeout(() => {
    setCount((c) => c + 1);
    setFlag((f) => !f);
    setName("Ada");
}, 0); // createRoot: one render for all three
```

React 18 and later batch every update, from handlers, timeouts, promises and native listeners alike. Rendering waits for a later microtask or task, so same-tick updates all join the queue first. Updates from one context also share a lane.

The old `ReactDOM.render` roots, removed in React 19, rendered such updates at once. An `await` splits the work into separate renders.

```jsx
async function save() {
    setStatus("saving"); // renders after this event
    await api.save();
    setStatus("saved"); // a later tick, so a later render
    setDirty(false); // batched with "saved"
}
```

### flushSync: the escape hatch

```jsx
import { flushSync } from "react-dom";

function addItem(item) {
    flushSync(() => setItems((items) => [...items, item]));
    listRef.current.lastChild.scrollIntoView(); // the new row is in the DOM already
}
```

`flushSync` renders and commits its updates before it returns, opting out of batching. Use it only when the next line must read the committed DOM.

### Lazy initial state

```jsx
const [rows, setRows] = useState(buildRows()); // buildRows runs on every render
const [lazyRows, setLazyRows] = useState(() => buildRows()); // runs once, on mount
```

React uses the initial value only on mount, but the first line still calls `buildRows()` every render and discards the result. Pass a function, and `mountStateImpl` calls it once.

### Try it

In a React app, put three `setCount(count + 1)` calls in one handler and a `console.log` in the component body. Confirm one render and an increase of one. Switch to `setCount(c => c + 1)` and confirm an increase of three. Then wrap one call in `flushSync` and watch an extra render appear.

## 5. Inside the queue: lanes, skipped updates and rebasing

A transition and a click can update the same state. React renders the click first and the transition later. The click must not lose the transition's update, and the transition must not undo the click. How does one queue serve two renders?

### The short version

Each update carries the lane it was created with, and each render processes only some lanes, its `renderLanes`. When `useState` folds the queue, it skips any update whose lane is not in the render. It saves the state just before the first skip as the hook's `baseState`. It keeps the skipped update, and every update after it, in `baseQueue`.

The urgent render shows a result without the skipped work. When the skipped lane renders later, React replays the kept updates from `baseState`, in their original order. This is **rebasing**. The final state is the same as if every update had applied in the order you made them.

### A toy rebase

```js
// Simplified teaching version of the skip-and-rebase loop in updateReducerImpl.
const reducer = (state, action) => (typeof action === "function" ? action(state) : action);
const isSubset = (set, lane) => (set & lane) === lane; // NoLane (0) is in every set

function processQueue(hook, renderLanes) {
    let state = hook.baseState;
    let newBaseState = state;
    const kept = [];
    for (const update of hook.baseQueue) {
        if (!isSubset(renderLanes, update.lane)) {
            if (kept.length === 0) newBaseState = state; // the state before the first skip
            kept.push(update); // skipped: replay it later
            continue;
        }
        if (kept.length > 0) kept.push({ ...update, lane: 0 }); // applied now, replayed later too
        state = reducer(state, update.action);
    }
    hook.memoizedState = state;
    hook.baseState = kept.length > 0 ? newBaseState : state;
    hook.baseQueue = kept;
    return state;
}
```

Queue a transition update, then a click, on one string.

```js
const SyncLane = 0b10;
const TransitionLane = 0b100000000;
const hook = {
    baseState: "",
    baseQueue: [
        { lane: TransitionLane, action: (s) => s + "T" }, // a transition appends T
        { lane: SyncLane, action: (s) => s + "S" }, // then a click appends S
    ],
};

console.log(JSON.stringify(processQueue(hook, SyncLane))); // the urgent render
console.log(JSON.stringify(processQueue(hook, TransitionLane))); // the transition render, later
```

```text role="output"
"S"
"TS"
```

The click shows `"S"` at once. The transition render replays both updates from the empty base and ends at `"TS"`, the order you made them. Applying `T` on top of `"S"` would give `"ST"`, an order no user caused.

### The real bookkeeping

| Field | What it holds after a render |
|---|---|
| `memoizedState` | The state this render shows |
| `baseState` | The state before the first skipped update |
| `baseQueue` | The skipped update and every later one, as a ring |
| `fiber.lanes` | The skipped lanes, so React knows this fiber still has work |

```js
// From updateReducerImpl in ReactFiberHooks.js, React 19.2 (simplified).
const shouldSkipUpdate = !isSubsetOfLanes(renderLanes, updateLane);
if (shouldSkipUpdate) {
    // clone it into the new base queue; the first skip also fixes newBaseState
    currentlyRenderingFiber.lanes = mergeLanes(currentlyRenderingFiber.lanes, updateLane);
    markSkippedUpdateLanes(updateLane);
} else {
    newState = update.hasEagerState ? update.eagerState : reducer(newState, update.action);
}
```

An applied update that follows a skip is cloned with `NoLane`, which is 0. Zero is a subset of every lane set, so React never skips that clone. Marking the skipped lane on the fiber brings the later transition render back to this component.

Rebasing has a consequence you can feel. An updater after a skipped update runs in the urgent render and again in the replay. So updaters and reducers must be pure: same input, same output, no side effects.

When two transition updates hit the same queue, `entangleTransitionUpdate` ties their lanes together, so React renders them together.

## 6. Bailouts and render-phase updates

Setting state to the value it already has should cost nothing, yet sometimes React still calls your component. And sometimes React calls it twice in a row with no commit between. Both come from the queue.

### The short version

When you call a `useState` setter and the fiber has no other pending updates, React computes the next state at once, outside any render. This is the **eager state**. If it is `Object.is`-equal to the current state, React keeps the update but schedules no render at all.

If the fiber already has pending work, React cannot know the current state yet. So it renders the component, finds the same state and skips the children. `useReducer` never takes the eager path. A setter called during your own component's render is different again. React stashes the update and calls your component again at once, up to 25 times.

### The eager path

```js
// Simplified teaching version of dispatchSetStateInternal, React 19.2.
function dispatchSetStateInternal(fiber, queue, action, lane) {
    const update = { lane, action, hasEagerState: false, eagerState: null, next: null };
    const nothingPending = fiber.lanes === NoLanes && (fiber.alternate === null || fiber.alternate.lanes === NoLanes);
    if (nothingPending && queue.lastRenderedReducer !== null) {
        const current = queue.lastRenderedState;
        const eager = queue.lastRenderedReducer(current, action); // compute it now
        update.hasEagerState = true;
        update.eagerState = eager;
        if (Object.is(eager, current)) {
            enqueueConcurrentHookUpdateAndEagerlyBailout(fiber, queue, update); // kept for a rebase
            return false; // no render scheduled
        }
    }
    const root = enqueueConcurrentHookUpdate(fiber, queue, update, lane);
    scheduleUpdateOnFiber(root, fiber, lane);
    return true;
}
```

React keeps two copies of each fiber, the committed one and a work-in-progress one. The other copy is called the **alternate**, and React checks both for pending lanes.

| Condition for the eager path | Why |
|---|---|
| A `useState` setter, not `useReducer`'s `dispatch` | Only `dispatchSetState` has this path |
| Not called during this component's own render | Render-phase updates go another way |
| No pending updates on the fiber or its alternate | Otherwise the current state is not known yet |
| `queue.lastRenderedReducer` is set | `useOptimistic` sets it to `null` on purpose |

If the eager state differs, React stores it on the update and uses it during the fold instead of calling your updater again. If computing it throws, React swallows the error, and render throws it again. A Node toy shows the outcomes.

```js
// Simplified teaching version of the eager check in dispatchSetStateInternal.
const reducer = (state, action) => (typeof action === "function" ? action(state) : action);
const queue = { lastRenderedState: 5, lastRenderedReducer: reducer };
const fiber = { lanes: 0 }; // 0 means no pending updates

function setState(action) {
    if (fiber.lanes === 0 && queue.lastRenderedReducer !== null) {
        const eager = queue.lastRenderedReducer(queue.lastRenderedState, action);
        if (Object.is(eager, queue.lastRenderedState)) return "bail out, no render";
    }
    fiber.lanes |= 0b10; // the update is pending now
    return "render scheduled";
}

console.log(setState(5)); // same value, nothing pending
console.log(setState(6)); // a real change
console.log(setState(5)); // same as the committed value, but work is pending
```

```text role="output"
render scheduled
render scheduled
```

### The bailout during render

Without the eager path, React must render to find out.

### Render-phase updates

```jsx
function List({ items }) {
    const [prevItems, setPrevItems] = useState(items);
    const [selection, setSelection] = useState(null);
    if (items !== prevItems) {
        setPrevItems(items); // a render-phase update
        setSelection(null); // reset derived state when the prop changes
    }
    // ...
}
```

Calling your own component's setter during its render is allowed for one pattern: adjusting state when a prop changes. `isRenderPhaseUpdate` spots the call, and `enqueueRenderPhaseUpdate` stashes it. As soon as your function returns, React calls it again with the rerender dispatcher, before it renders any child.

```js
// From renderWithHooksAgain in ReactFiberHooks.js, React 19.2 (simplified).
const RE_RENDER_LIMIT = 25;
let numberOfReRenders = 0;
do {
    didScheduleRenderPhaseUpdateDuringThisPass = false;
    if (numberOfReRenders >= RE_RENDER_LIMIT) {
        throw new Error("Too many re-renders. React limits the number of renders to prevent an infinite loop.");
    }
    numberOfReRenders += 1;
    ReactSharedInternals.H = HooksDispatcherOnRerender;
    children = Component(props, secondArg);
} while (didScheduleRenderPhaseUpdateDuringThisPass);
```

An unconditional `setCount(count + 1)` in the body never settles, so it hits the limit. Guard every render-phase update with a condition, as `List` does. Setting a different component's state during render is not allowed, and React warns about it.

## 7. useState and useReducer

Your component has grown five `useState` calls that must change together, and one keeps updating without its partner. People say "use a reducer", but when does it pay off?

### The short version

`useState` is `useReducer` with a reducer you did not write. Its built-in `basicStateReducer` calls a function action on the previous state, and uses any other action as the new state. With `useReducer` you write the reducer yourself and dispatch actions such as `{ type: "submit" }`.

Both hooks share the node, the queue, the fold and the rebasing, so the choice is about clarity, not speed. Reach for a reducer when one event changes several fields at once, or when you want every transition in one pure, testable function. Both hooks return a function with a stable identity.

### useState is useReducer

```js
// updateState from ReactFiberHooks.js, React 19.2. That is the whole function.
function updateState(initialState) {
    return updateReducer(basicStateReducer, initialState);
}
```

A setter queues a value or an updater. `dispatch` queues an action, and the fold runs your `(state, action) => newState` on each one.

### A reducer you can test without React

```js
function formReducer(state, action) {
    switch (action.type) {
        case "submit":
            return { ...state, isSubmitting: true, errors: {} };
        case "submit_failed":
            return { ...state, isSubmitting: false, errors: action.errors };
        default:
            return state;
    }
}

const before = { values: { email: "" }, errors: {}, isSubmitting: true };
const after = formReducer(before, { type: "submit_failed", errors: { email: "required" } });
console.log(after.isSubmitting, after.errors.email, before.isSubmitting);
```

```text role="output"
false required true
```

One `submit_failed` case updates both fields in one step, and the old state object is untouched.

| Signal | With several `useState` calls | With `useReducer` |
|---|---|---|
| One event changes several fields | Easy to update three fields and forget the fourth | One case returns the whole new state |
| The next state depends on current fields | You must remember the updater form | The reducer always receives the latest state |
| You want the logic testable | Setter calls spread across handlers | One pure function, tested with plain values |

A reducer is also the usual way to write a state machine in React: named states and the allowed moves between them.

### A stable dispatch

```js
// From mountReducer: dispatch is created once and kept on the queue.
const dispatch = (queue.dispatch = dispatchReducerAction.bind(null, currentlyRenderingFiber, queue));
```

Every later render returns `queue.dispatch`, the same function, and `useState`'s setter is bound the same way. So listing either in a dependency array never re-runs an effect, and passing either through context is safe. `useReducer(reducer, initialArg, init)` calls `init(initialArg)` only on mount, like a lazy initializer.

The reducer must be pure. Rebasing may run it again (section 5), and Strict Mode calls it twice in development (section 18). A reducer that misbehaves only in Strict Mode is not pure.

### Try it

In a React app, rewrite a component with three or four related `useState` calls as one `useReducer`. The handlers shrink to `dispatch({ type: "..." })`. Then test the reducer in Node with plain objects.

## 8. Effects synchronize with the outside world

Many people learn effects as `componentDidMount`, `componentDidUpdate` and `componentWillUnmount` rolled into one. So they write `useEffect(..., [])` for "on mount" and use refs to detect "did this prop change". It half works, and the bugs are always about timing.

### The short version

An effect does not mark a moment in a component's life. It describes a **synchronization**: keep some external system in step with values from this render. The external system is anything React does not manage, such as a socket, a timer, `document.title` or a chart library.

You give React three things: a setup function, the cleanup it returns, and a dependency array. After a commit, if a dependency changed, React runs the old cleanup and then the new setup. Mount is just the first setup, and unmount is the last cleanup. If you cannot name the external system, you probably do not need an effect.

### "Be in sync", not "do on mount"

```jsx
useEffect(() => {
    document.title = `Inbox (${unreadCount})`; // bring the title into sync
}, [unreadCount]); // it depends on unreadCount, and only that
```

There is no "on mount" or "on update" here, only "the title should equal this, given `unreadCount`".

<MarginNote note="forget mount and unmount as the model">

React keeps the DOM in step with your render for you. An effect extends that promise to things React has never heard of. You describe the target, and React works out when to reach it again.

</MarginNote>

```jsx
useEffect(() => {
    const connection = createConnection(roomId); // setup: connect to this room
    connection.connect();
    return () => connection.disconnect(); // cleanup: undo exactly that
}, [roomId]); // the synchronization depends on roomId
```

You did not write "if `roomId` changed, reconnect". You wrote "be connected to `roomId`", and React derived the reconnect.

| Moment | What React runs |
|---|---|
| First commit | Setup |
| A later commit, a dependency changed | The previous cleanup, then the new setup |
| A later commit, no dependency changed | Nothing |
| Unmount | The last cleanup |

### You might not need an effect

```jsx
// Wrong: an effect that copies props into state.
const [fullName, setFullName] = useState("");
useEffect(() => {
    setFullName(first + " " + last); // a second render, with a stale name in between
}, [first, last]);

// Right: compute it during render.
const name = first + " " + last;
```

```jsx
// Wrong: a request sent by an effect that watches a flag.
// Right: the click caused it, so the click handler sends it.
function handleSubmit() {
    post("/api/register", form);
}
```

Effects are for systems outside React. If the work computes something from props or state, do it during render. If it responds to a user action, do it in the event handler. The linter's `set-state-in-effect` rule flags the first pattern, and the docs page "You Might Not Need an Effect" covers the rest.

### Try it

Take an effect you wrote in the lifecycle style. Name the external system it keeps in sync and list the values it reads. If you cannot name a system, move the code into render or a handler.

## 9. The dependency array

The dependency array feels like an incantation. An empty array means once, no array means every time, and a list means "sometimes". Get it wrong and you get a loop or a stale value. What is the array, physically?

### The short version

Think of it this way: <Mark kind="marker" wraps>the dependency array is a cache key for your synchronization.</Mark> During render, React compares each new element with the previous one, using `Object.is`. If every element matches, React skips the effect at commit. If any differs, or there is no array, React runs cleanup then setup.

An empty array matches every time after the first, so the effect runs once and cleans up on unmount. The array is not "when to run". It is the set of values the effect reads. Leave one out and you get a stale value. List one with a new identity every render, and the effect re-runs every render.

### areHookInputsEqual

```js
// areHookInputsEqual from ReactFiberHooks.js, React 19.2, without its DEV warnings.
function areHookInputsEqual(nextDeps, prevDeps) {
    if (prevDeps === null) return false;
    for (let i = 0; i < prevDeps.length && i < nextDeps.length; i++) {
        if (Object.is(nextDeps[i], prevDeps[i])) continue;
        return false;
    }
    return true;
}

console.log(areHookInputsEqual([], [])); // an empty array
console.log(areHookInputsEqual([1, "room-a"], [1, "room-a"])); // equal primitives
console.log(areHookInputsEqual([{ id: 1 }], [{ id: 1 }])); // a new object each render
console.log(areHookInputsEqual([1], null)); // no previous deps
```

```text role="output"
true
true
false
false
```

That loop is the whole dependency mechanism. In development, React also warns when the array changes length between renders.

### Where the comparison happens

```js
// Simplified teaching version of updateEffectImpl (ReactFiberHooks.js, React 19.2).
function updateEffectImpl(fiberFlags, hookFlags, create, deps) {
    const hook = updateWorkInProgressHook();
    const nextDeps = deps === undefined ? null : deps;
    const inst = hook.memoizedState.inst; // one instance for the effect's whole life
    if (nextDeps !== null && areHookInputsEqual(nextDeps, currentHook.memoizedState.deps)) {
        hook.memoizedState = pushSimpleEffect(hookFlags, inst, create, nextDeps); // no HasEffect: skip
        return;
    }
    currentlyRenderingFiber.flags |= fiberFlags; // this fiber has effect work
    hook.memoizedState = pushSimpleEffect(HasEffect | hookFlags, inst, create, nextDeps);
}
```

The comparison happens during render, not after the commit. Each render pushes a fresh effect object, with or without the `HasEffect` bit, and the commit runs only effects that carry it.

The effect object holds `tag`, `create` (your setup), `deps` and `inst`. The `inst` object lives as long as the effect and keeps the cleanup in `inst.destroy`. React also links a component's effects into a ring at `fiber.updateQueue.lastEffect` for the commit to walk.

| What you wrote | `nextDeps` | Result |
|---|---|---|
| `[]` | `[]` | Equal after the first run: runs once, cleans up on unmount |
| No array | `null` | Never compared: runs after every commit |
| `[a, b]` | `[a, b]` | Runs whenever `a` or `b` changes under `Object.is` |

### Stale values and infinite loops

If an effect reads `count` but does not list it, React never sees `count` change and never re-runs the effect. You told React the synchronization does not depend on `count`, and React believed you.

```jsx
function Results({ id }) {
    const [data, setData] = useState(null);
    const options = { id, limit: 20 }; // a new object every render
    useEffect(() => {
        fetchResults(options).then(setData); // setData renders, which builds a new options
    }, [options]); // which never compares equal: a loop
}
```

A dependency with a new identity every render always compares as changed. If the effect also sets state, the new render builds another object and runs the effect again. Section 10 shows the fixes.

The `exhaustive-deps` lint rule computes the true set of reactive values an effect reads: props, state and anything derived from them. When it complains, `areHookInputsEqual` is about to give the wrong answer, and silencing the rule ships the bug.

### Object.is, not ===

```js
console.log(NaN === NaN, Object.is(NaN, NaN));
console.log(0 === -0, Object.is(0, -0));
```

```text role="output"
false true
true false
```

They differ only for `NaN` and for `0` and `-0`.

## 10. Referential stability

You wrapped a child in `React.memo`, and it still re-renders. You wrote a correct dependency array, and the effect still fires every render. Both times the value "looks the same". You have met identity.

### The short version

JavaScript compares objects, arrays and functions by identity, not by contents, so two literals that look the same are different values. Your component body runs on every render, so every literal written inside it gets a new identity each time. React's checks all use `Object.is`: dependency arrays, `React.memo` props, and `useMemo` and `useCallback` deps.

So a fresh object in a dependency array re-runs the effect every render, and a fresh function prop defeats `React.memo`. Primitives compare by value and stay stable when equal. Fix it by depending on primitives, by moving constants out of the component, or by keeping an identity with `useMemo` or `useCallback`.

### Identity in plain JavaScript

```js
console.log({ a: 1 } === { a: 1 }); // two objects
console.log([1, 2] === [1, 2]); // two arrays
console.log((() => {}) === (() => {})); // two functions
console.log(1 === 1, "x" === "x"); // primitives compare by value

const config = { a: 1 };
console.log(config === config); // the same object
```

```text role="output"
false
false
false
true true
true
```

React inherits this rule from JavaScript. "The same value" for a primitive means equal, but for an object it means the very same object.

```jsx
function Parent({ userId }) {
    const config = { userId }; // a new object every render
    const handleClick = () => doThing(); // a new function every render
    const items = data.map((d) => d.name); // a new array every render
    // ...
}
```

### The memo symptom

`React.memo` skips a re-render when every prop is `Object.is`-equal to the last one. Pass a memoized child an inline object or function, and that prop is new every time, so the child always renders. "I added `React.memo` and nothing improved" usually means an unstable prop.

| Fix, in order of preference | Example | Why it works |
|---|---|---|
| Depend on or pass primitives | List `userId`, not `config` | Equal primitives are stable |
| Move constants out of the component | `const DEFAULTS = {...}` at module scope | One identity for the program's life |
| Keep an identity with `useMemo` or `useCallback` | `useMemo(() => ({ userId }), [userId])` | The same object until `userId` changes |

### The extreme case: a component defined inside a component

```jsx
function Page() {
    function Row() {
        return <li>row</li>;
    } // a new component type on every render
    return <Row />; // React remounts it, losing its state and DOM
}
```

The inner function is a new component type each render, so React remounts its subtree. The `static-components` lint rule flags it. That and an over-firing effect are one phenomenon at two scales: a fresh identity where React expected a stable one.

Do not over-correct. Most props and dependencies are primitives and already stable. Identity matters only for values that feed an equality check, and React Compiler (section 14) handles most of it.

### Try it

In a React app, make a `React.memo` child that logs when it renders. Pass it `style={{ color: "red" }}` and watch it render with every parent render. Move the object to a module constant and watch the child go quiet.

## 11. Cleanup: setup and cleanup come in pairs

You set up a subscription in an effect and know you should clean it up, but the timing confuses you. Does cleanup only run on unmount? Why does a handler fire twice, or a fetch show stale results?

### The short version

The function your effect returns is its cleanup, and it is not an unmount handler. React runs it to undo one synchronization before starting the next. When dependencies change, React calls the previous render's cleanup, then this render's setup. On unmount it calls the last cleanup, with no setup after it.

For layout and passive effects, React runs every due cleanup before any setup, so a new setup never overlaps a stale one. The model is simple: <Mark kind="underline" wraps>each render's effect cleans up the previous render's effect</Mark> before it starts its own. Write the cleanup so it exactly undoes the setup above it, and leaks and races disappear.

### The pairing

```jsx
useEffect(() => {
    const subscription = source.subscribe(roomId, onMessage);
    return () => subscription.unsubscribe(); // undo THIS subscription
}, [roomId]);
```

When `roomId` changes from A to B, React runs A's cleanup, then subscribes to B. Treat cleanup as unmount-only, and you stay subscribed to both, so `onMessage` fires twice. The leak and the double message are one bug: a setup without its cleanup.

<GuideFigure figure="hk-cleanup" />

React stores each cleanup in `inst.destroy` and calls it before the next `create`, your setup.

### The fetch race

```jsx
useEffect(() => {
    let ignore = false;
    fetchUser(userId).then((data) => {
        if (!ignore) setUser(data); // only the latest effect may win
    });
    return () => {
        ignore = true; // the superseded request is ignored
    };
}, [userId]);
```

If `userId` changes quickly, two requests are in flight, and without the flag the last to answer wins. The cleanup flips `ignore` on the superseded effect, so its late answer is dropped. This Node toy simulates the race.

```js
// Simplified teaching version: two requests, and the older one answers last.
function fakeFetch(id, ms) {
    return new Promise((resolve) => setTimeout(() => resolve(`user ${id}`), ms));
}

let shown = null;
function runEffect(id, ms) {
    let ignore = false;
    fakeFetch(id, ms).then((data) => {
        if (!ignore) shown = data;
    });
    return () => {
        ignore = true; // the cleanup
    };
}

const cleanupA = runEffect("A", 50); // slow request
cleanupA(); // userId changes, so React cleans up A first
runEffect("B", 10); // fast request
setTimeout(() => console.log(shown), 100);
```

```text role="output"
user B
```

Delete the `if (!ignore)` check and it prints `user A`. If your request API supports it, cleanup can cancel the request instead.

```jsx
useEffect(() => {
    const controller = new AbortController();
    fetch(`/api/users/${userId}`, { signal: controller.signal })
        .then((response) => response.json())
        .then(setUser)
        .catch((error) => {
            if (error.name !== "AbortError") throw error;
        });
    return () => controller.abort(); // cancel the superseded request
}, [userId]);
```

### What you can rely on

You can rely on the pairing: an effect's cleanup always runs before its next setup, and on unmount. Do not rely on the order between sibling components. Section 12 places each kind of effect around the browser's paint. In development, Strict Mode adds one extra cleanup and setup on mount to test the pairing (section 18).

### Try it

In a React app, write the `roomId` subscription and comment out the cleanup. Change `roomId` a few times and log inside `onMessage`: the handlers stack up. Restore the cleanup and confirm one subscription stays active.

## 12. When effects run: insertion, layout and passive

You position a tooltip in a `useEffect`, and for one frame it flashes in the wrong place. `useLayoutEffect` fixes it. What is the real difference, and why not use `useLayoutEffect` everywhere?

### The short version

React commits in phases. First it changes the DOM, and during that phase it runs `useInsertionEffect`, then the cleanups of changed layout effects. Next, still <Mark kind="circle">before paint</Mark>, it attaches refs and runs `useLayoutEffect` setups. Passive effects, from `useEffect`, come last.

After most renders React runs passive effects in a separate task, so the browser usually paints first. After a discrete render, such as a click, it runs them at the end of the commit instead. State set in a layout effect re-renders before paint. State set in a passive effect renders at default priority, so a paint can come first.

Layout effects block paint, so default to `useEffect` and keep layout effects for preventing a visible flicker, and keep them cheap.

### The commit, step by step

| Step | What runs | Can the browser paint before it? |
|---|---|---|
| 1. Mutation | DOM inserts, updates and removals. Insertion effect cleanups and setups. Layout effect cleanups. Old refs detach. | No |
| 2. Layout | Layout effect setups. New refs attach. | No |
| 3. Paint | The browser draws the frame | n/a |
| 4. Passive | All passive cleanups, then all passive setups | Usually yes, but not after a discrete render |

Each effect's `tag` combines its kind with the `HasEffect` bit from section 9.

```js
// ReactHookEffectTags.js, React 19: one bit per effect kind.
export const HasEffect = /* */ 0b0001; // dependencies changed: fire this time
export const Insertion = /* */ 0b0010;
export const Layout = /*    */ 0b0100;
export const Passive = /*   */ 0b1000;
```

The commit asks for exact combinations, such as `Layout | HasEffect`. React also flags the fiber so it can skip subtrees with no effect work: `useEffect` sets `Passive`, and the other two set `Update`.

```js
// Simplified teaching version of the commit for one function component.
function commitMutation(fiber) {
    commitHookEffectListUnmount(Insertion | HasEffect, fiber);
    commitHookEffectListMount(Insertion | HasEffect, fiber);
    commitHookEffectListUnmount(Layout | HasEffect, fiber); // old layout cleanups
}

function commitLayout(fiber) {
    commitHookEffectListMount(Layout | HasEffect, fiber); // new layout setups
}

// Later, for the whole tree: commitPassiveUnmountEffects, then commitPassiveMountEffects.
```

### When passive effects run in React 19

```js
// From commitRoot in ReactFiberWorkLoop.js, React 19.2 (simplified).
if (includesSyncLane(pendingEffectsLanes)) {
    flushPendingEffects(); // a discrete render: run passive effects now, before paint
}
// otherwise a NormalPriority scheduler task runs flushPassiveEffects later
```

A source comment gives the reason: after a discrete render, the effects' results must be observable at once.

| What caused the render | When its passive effects run |
|---|---|
| A click or key press (`SyncLane`) | At the end of the commit, before paint |
| A timer, a network response or a transition | In a later scheduler task, usually after paint |
| Anything, if a new render starts first | Just before that render begins |

If an effect must wait for paint after a click, as with an `alert()`, defer it with `setTimeout`.

### State updates inside effects

```jsx
useLayoutEffect(() => {
    const { width } = tipRef.current.getBoundingClientRect();
    setLeft(anchorX - width / 2); // SyncLane: re-renders before paint
}, [anchorX]);

useEffect(() => {
    const { width } = tipRef.current.getBoundingClientRect();
    setLeft(anchorX - width / 2); // at most DefaultLane: a paint can come first
}, [anchorX]);
```

React runs the commit at discrete priority, so a setter in a layout effect gets `SyncLane` and renders before the commit returns. Passive effects run with priority lowered to at most `DefaultLane`, so their updates render in a scheduler task. That is the flash: the browser paints the first position, then your correction.

<GuideFigure figure="hk-layout-effect" />

Layout effects suit measurements that must appear in the first paint: tooltips, popovers, sizing from a measured element and restoring scroll.

### useInsertionEffect and server rendering

```jsx
useInsertionEffect(() => {
    const style = document.createElement("style");
    style.textContent = rule; // in place before any layout effect measures
    document.head.appendChild(style);
    return () => style.remove();
}, [rule]);
```

`useInsertionEffect` exists for CSS-in-JS libraries. It runs in the mutation phase, so injected styles exist before any layout effect measures.

No effect runs on the server, and React 19's server renderer treats `useLayoutEffect` as a no-op. A layout-dependent component may jump after **hydration**, when React attaches to the server's HTML. Render such components only on the client.

## 13. useEffectEvent: read the latest without reacting

Back to the opening chat room. The effect should reconnect when `roomId` changes, but it also reads `theme`. With `theme` listed, a theme change reconnects. Without it, the notification goes stale.

### The short version

`useEffectEvent`, stable since React 19.2, splits an effect into two kinds of logic. Reactive logic, like connecting to `roomId`, must re-run when its values change. Non-reactive logic, like a notification in the current `theme`, should use the latest value without being a trigger.

Wrap the non-reactive part in an **Effect Event**. When it runs, it sees the latest committed props and state, yet it stays out of the dependency array. Its identity changes every render. You omit it because the linter knows it is non-reactive, not because it is stable. Call it only from effects, never during render.

### The fix

```jsx
function ChatRoom({ roomId, theme }) {
    const onConnected = useEffectEvent(() => {
        showNotification("Connected!", theme); // the latest theme, read at call time
    });

    useEffect(() => {
        const connection = createConnection(roomId);
        connection.on("connected", () => onConnected());
        connection.connect();
        return () => connection.disconnect();
    }, [roomId]); // only roomId is a trigger now
}
```

<MarginNote note="the honest way to leave a value out">

The effect reconnects only when `roomId` changes, and the notification still uses the current theme. Every "disable the linter here" instinct points at this situation, and an Effect Event names it in a way the linter understands.

</MarginNote>

### How it works

```js
// Simplified teaching version of mountEvent and updateEvent (ReactFiberHooks.js, React 19.2).
function useEffectEvent(callback) {
    const hook = mountOrUpdateWorkInProgressHook();
    if (hook.memoizedState === null) hook.memoizedState = { impl: callback };
    const ref = hook.memoizedState; // one box for the component's whole life
    queueSwapAtCommit(ref, callback); // during commit: ref.impl = callback
    return function eventFn(...args) {
        if (isRendering()) throw new Error("A function wrapped in useEffectEvent can't be called during rendering.");
        return ref.impl(...args); // always the latest committed callback
    };
}
```

The hook keeps a box, `{ impl }`, for the component's whole life. Each render returns a new wrapper, which is why the identity changes, and the wrapper calls whatever `impl` holds.

React writes the new callback into `impl` during the commit, before any layout or passive effect of that commit runs. So an effect that fires sees this render's `theme`. React 19.2 swaps it just before DOM mutation, and 19.3 during it.

| Rule | Why |
|---|---|
| Call it only from effects or other Effect Events | "The latest committed value" only has a meaning when effects run. During render it throws. |
| Never pass it to another component or hook | It belongs to the effect beside it, and the linter enforces this |
| Call `useEffectEvent` at the top level | It is a hook, so it obeys section 1 |
| Never use it to hide a real dependency | If the work should repeat for each value, that value is a trigger |

### The abuse to avoid

```jsx
// Wrong: url decides the work, so url is reactive.
const onVisit = useEffectEvent(() => logVisit(url));
useEffect(() => onVisit(), []); // logs only the first url

// Right: url is a dependency, the cart count is not.
const onVisitUrl = useEffectEvent((visitedUrl) => logVisit(visitedUrl, cartCount));
useEffect(() => onVisitUrl(url), [url]);
```

### The ref pattern it replaces

```jsx
const latestTheme = useRef(theme);
useLayoutEffect(() => {
    latestTheme.current = theme; // the older workaround
});
```

That works, but it separates a value from its use, and the linter cannot follow it. Before 19.2, `useEffectEvent` shipped only in experimental builds, so older apps still use the ref.

### Try it

In a React app, build `ChatRoom` with `theme` in the dependency array and log in connect and disconnect. Toggle the theme and watch it reconnect. Move the notification into `useEffectEvent` and drop `theme`: toggles stop reconnecting. Then move `roomId` into the Effect Event too, and watch the room stop reconnecting when it should.

## 14. useMemo, useCallback and the Compiler

You have sprinkled `useMemo` and `useCallback` around "for performance", and you have heard that React Compiler does this for you. What do these hooks cache, and when do they earn their keep?

### The short version

`useMemo` caches a computed value, and `useCallback` caches a function. Each stores `[value, deps]` on its hook node and compares deps with the same `areHookInputsEqual` as effects. Their main job is keeping an identity stable, so a downstream dependency array or `React.memo` boundary sees "unchanged". Their second job is skipping truly expensive work.

Still, <Mark kind="underline" wraps>they are not a correctness tool</Mark>, because React may throw a cache away. React Compiler 1.0, stable since October 2025, inserts equivalent memoization at build time. With it on, most hand-written `useMemo` and `useCallback` calls become unnecessary.

### updateMemo

```js
// updateMemo from ReactFiberHooks.js, React 19.2 (its Strict Mode branch removed).
function updateMemo(nextCreate, deps) {
    const hook = updateWorkInProgressHook();
    const nextDeps = deps === undefined ? null : deps;
    const prevState = hook.memoizedState; // [value, deps]
    if (nextDeps !== null && areHookInputsEqual(nextDeps, prevState[1])) {
        return prevState[0]; // a cache hit
    }
    const nextValue = nextCreate();
    hook.memoizedState = [nextValue, nextDeps];
    return nextValue;
}
```

`updateCallback` is the same, except it stores your function instead of calling one. So `useCallback(fn, deps)` behaves like `useMemo(() => fn, deps)`.

### The main job: stable identity

```jsx
const filterOptions = useMemo(() => ({ status, sortBy }), [status, sortBy]);
useEffect(() => {
    loadRows(filterOptions);
}, [filterOptions]); // stable until status or sortBy changes

const handleSelect = useCallback((id) => onSelect(id), [onSelect]);
return <MemoizedRow onSelect={handleSelect} />; // the memo boundary holds
```

This is the third fix from section 10, and it is about identity, not CPU.

### The second job: expensive work

```jsx
const visible = useMemo(() => sortRows(rows, sortKey), [rows, sortKey]); // only when inputs change
const total = useMemo(() => a + b, [a, b]); // slower than just adding
```

Memoization has its own cost: storing the value and comparing deps every render. Wrapping trivial work makes code slower and noisier, so measure first.

Memoization never promises two things. First, the cache can vanish, for example when you edit the file in development or when a component suspends on its first mount. So never use `useMemo` to store state or to run something once. Use state or a ref. Second, an unstable dependency defeats it.

### What the Compiler changes

```jsx
// What you write with React Compiler on.
function Row({ item, onSelect }) {
    const label = formatLabel(item);
    return <MemoButton onClick={() => onSelect(item.id)}>{label}</MemoButton>;
}
// The compiler caches label and the arrow, so MemoButton sees stable props.
```

The Compiler analyzes components at build time and memoizes values and functions by what each part of the UI depends on. Compiled code calls an internal hook, `useMemoCache`, which keeps an array of cached slots per component. With it on, stop adding `useMemo` and `useCallback` by reflex.

You might keep a manual one where an effect needs an identity you want to state openly. The lint rule `preserve-manual-memoization` warns when the Compiler cannot keep yours. Without the Compiler, the manual rules above still apply.

### Try it

In a React app, compare `useMemo(() => a + b, [a, b])` with plain `a + b` in the Profiler. The memo buys nothing. Then, in a project with the Compiler on, delete a defensive `useCallback` that feeds a `React.memo` child, and confirm the child stays quiet.

## 15. useRef and ref callbacks

You need to remember an interval ID without causing a render, or reach a DOM node to focus it. `useRef` does both, and its "no re-render" part seems to break everything else about React.

### The short version

`useRef(initial)` returns an object, `{ current: initial }`, stored on the hook node and returned unchanged on every render. Writing `ref.current` creates no update, joins no queue and schedules no render. That suits two jobs: holding a DOM node, which React writes into `current` during commit, and keeping a mutable value you never render.

Do not read or write `ref.current` during render, except to set it up once. Renders can run twice or be thrown away. React 19 lets a ref callback return a cleanup function, and passes `ref` to function components as an ordinary prop.

### All of useRef

```js
// mountRef and updateRef from ReactFiberHooks.js, React 19.2.
function mountRef(initialValue) {
    const hook = mountWorkInProgressHook();
    const ref = { current: initialValue };
    hook.memoizedState = ref;
    return ref;
}

function updateRef(initialValue) {
    const hook = updateWorkInProgressHook();
    return hook.memoizedState;
}
```

The screen changes only when something else renders, and that render reads the latest `current`.

### Job one: reaching the DOM

```jsx
const inputRef = useRef(null);
useEffect(() => {
    inputRef.current.focus(); // the node exists by the time effects run
}, []);
return <input ref={inputRef} />;
```

React detaches old refs during the mutation phase and attaches new ones during the layout phase. Children commit before parents, so a component's layout and passive effects already see its DOM refs. `current` is `null` before the first commit and after the node is removed.

### Job two: a mutable value you do not render

```jsx
const intervalRef = useRef(null);

function start() {
    intervalRef.current = setInterval(tick, 1000); // remembered, with no render
}

function stop() {
    clearInterval(intervalRef.current);
}
```

Interval IDs, an `ignore` flag, the previous value of a prop and a counter that should not paint all belong in refs.

### Ref callbacks with cleanup

```jsx
<div
    ref={(node) => {
        const observer = new ResizeObserver(() => measure(node));
        observer.observe(node);
        return () => observer.disconnect(); // React 19: runs when the ref detaches
    }}
/>
```

React stores the returned function on the fiber as `refCleanup` and calls it on detach. Return nothing, and React keeps the old behavior of calling your callback with `null`.

An inline callback is a new function each render, so React cleans up the old one and calls the new one every time. Strict Mode adds one extra attach and cleanup on mount (section 18).

### ref is a prop in React 19

```jsx
function TextInput({ ref, ...props }) {
    return <input ref={ref} {...props} />; // no forwardRef needed
}
```

`useImperativeHandle` lets a parent's ref receive a custom object instead of a raw node.

```jsx
function VideoPlayer({ ref, src }) {
    const videoRef = useRef(null);
    useImperativeHandle(ref, () => ({ play: () => videoRef.current.play() }), []);
    return <video ref={videoRef} src={src} />;
}
```

React runs it as a layout effect, so the parent's ref is set before the parent's own layout effects.

### The rule, and its one exception

```jsx
const playerRef = useRef(null);
if (playerRef.current === null) {
    playerRef.current = new VideoPlayer(); // runs once, and running it twice is harmless
}
```

Rendering must be a pure function of props and state. Strict Mode calls render twice, and concurrent React can discard a render and start again. So a ref write during render can happen zero, one or two times. Keep ref reads and writes in effects and handlers.

The exception, shown above, is lazy initialization that is **idempotent**: doing it twice has the same result as doing it once. The `refs` lint rule flags other reads and writes during render.

### Try it

In a React app, write to a ref from a button handler and log it: the log changes, the screen does not. Add a `useState` next to it and watch only the state cause a render. Then give a `<div>` an inline ref callback that logs on attach and on cleanup. Both fire on every render.

## 16. Custom hooks: sharing logic, not state

Custom hooks feel like they create something shared. Do two components using the same custom hook share state? Do the rules of hooks apply inside one? What is actually reused?

### The short version

A custom hook is a function whose name starts with `use` and that calls other hooks. It has no fiber and no instance of its own. When a component calls it, the hooks inside run during that component's render, and their nodes join the component's own list at that spot.

So two components calling the same custom hook get independent state. They share logic, never data. The same positional list explains why the rules of hooks apply inside custom hooks too. The `use` prefix is how the linter and React Compiler know to treat a function as a hook.

### One list per component

```jsx
function useToggle(initial = false) {
    const [on, setOn] = useState(initial); // a node in the CALLER's list
    const toggle = useCallback(() => setOn((o) => !o), []); // also the caller's
    return [on, toggle];
}

function Panel() {
    const [open, toggleOpen] = useToggle(); // useToggle's two nodes go here
    const [count, setCount] = useState(0); // then this one
    // Panel's list: useToggle's useState, useToggle's useCallback, count's useState
}
```

<MarginNote note="as if you pasted the calls into the component">

There is no `useToggle` instance and no boundary in storage. The calls run inside `Panel`'s render, so their nodes join `Panel`'s list in the order they ran.

</MarginNote>

The toy runtime from section 1 shows that two components get two copies.

```js
// Reuses the toy useState and render from section 1.
function useToggle(initial = false) {
    const [on, setOn] = useState(initial);
    return [on, () => setOn(!on)];
}

function Panel() {
    const [open, toggle] = useToggle();
    return { open, toggle };
}

const panelFiber = { hooks: [] };
const sidebarFiber = { hooks: [] };
const panel = render(Panel, panelFiber);
render(Panel, sidebarFiber);
panel.toggle(); // toggle the panel only
console.log(render(Panel, panelFiber).open, render(Panel, sidebarFiber).open);
```

```text role="output"
true false
```

### Three consequences

| Question | Answer | Why |
|---|---|---|
| Do two callers share state? | No | Each call runs on a different fiber and creates its own nodes |
| Do the rules of hooks apply inside? | Yes | Its calls join the caller's list, and there is only one list |
| Can custom hooks call custom hooks? | Yes | Every call flattens into the same list, in execution order |

To share state between components, lift it up or put it in context. [The state management guide](/articles/react-state-management-architecture) covers both. A function that calls no hooks should not have the `use` prefix.

Return an array when callers will rename the values, like `useState`, and an object for several named values. Either way, the logic gets a name and one home, and you can test it in a small test component.

### Try it

In a React app, use `useToggle` in two sibling components. Toggle one and confirm the other does not move. Then wrap the `useState` inside `useToggle` in an `if` and watch the error appear in the calling component.

## 17. The newer hooks: use, Actions and optimistic state

React 19 ships `use`, `useOptimistic`, `useActionState`, `useFormStatus` and more. How do they connect to the machinery you now know?

### The short version

Most newer hooks sit on the same list, queue and lanes. `use(resource)` reads a promise or a context without taking a hook node, which is why it may sit in a condition. A pending promise suspends the component until it resolves. An **Action** is a function React runs inside a transition, often an async one.

`useOptimistic` shows a temporary value during an Action. It queues a `SyncLane` update that React drops once the Action's transition lane renders. `useActionState` keeps an Action's result, runs queued calls one after another and tracks `isPending`. `useTransition` and `useDeferredValue` move work onto transition lanes. The rest cover external stores, IDs and DevTools labels.

### use(): no node, so no rule one

```jsx
function Comments({ commentsPromise }) {
    const comments = use(commentsPromise); // suspends until the promise resolves
    return comments.map((comment) => <p key={comment.id}>{comment.text}</p>);
}

function Heading({ showTheme }) {
    if (showTheme) {
        const theme = use(ThemeContext); // allowed: use() takes no hook node
        return <h1 className={theme}>Hello</h1>;
    }
    return <h1>Hello</h1>;
}
```

```js
// use from ReactFiberHooks.js, React 19.2 (one branch for 19.3 omitted).
function use(usable) {
    if (usable !== null && typeof usable === "object") {
        if (typeof usable.then === "function") return useThenable(usable); // a promise
        if (usable.$$typeof === REACT_CONTEXT_TYPE) return readContext(usable); // a context
    }
    throw new Error("An unsupported type was passed to use(): " + String(usable));
}
```

Neither branch calls `mountWorkInProgressHook`, so `use()` never shifts the hook list. Promises get their own counter, `thenableIndexCounter`, which matches each promise to its call on replay.

If the promise resolves while React is still waiting, React replays the component with the rerender dispatcher, reusing the hooks that already ran. Otherwise the nearest Suspense boundary shows its fallback, and React renders the component again later.

Create the promise in a parent, a cache or a Server Component, not during render. The [Suspense guide](/articles/react-suspense-internals) covers what happens after a component suspends.

### useOptimistic

```jsx
function Thread({ messages, sendMessage }) {
    const [optimistic, addOptimistic] = useOptimistic(messages, (state, text) => [...state, { text, sending: true }]);

    async function formAction(formData) {
        addOptimistic(formData.get("text")); // shows at once
        await sendMessage(formData); // when the Action ends, messages updates and the temp row goes
    }

    return <form action={formAction}>{/* render optimistic, plus an input */}</form>;
}
```

```js
// Simplified teaching version of the update dispatchOptimisticSetState queues.
const update = {
    lane: SyncLane, // the optimistic value commits right away
    revertLane: requestTransitionLane(transition), // and disappears when the Action's lane renders
    action,
};
```

The fold applies the optimistic update until `renderLanes` contains its `revertLane`. Then it skips it, as if it never happened, and the real `messages` show. Every render, `useOptimistic` also resets its base state to the value you pass in, so optimistic updates rebase on the latest real state (section 5).

Call the setter inside an Action. Outside one, React logs a development warning and the value only flashes.

### useActionState

```jsx
async function addToCart(previousCount, itemId) {
    await post("/cart", itemId);
    return previousCount + 1;
}

function AddButton({ itemId }) {
    const [count, dispatchAction, isPending] = useActionState(addToCart, 0);
    return (
        <button onClick={() => startTransition(() => dispatchAction(itemId))}>
            Add {isPending ? "..." : count}
        </button>
    );
}
```

`useActionState` allocates three hook nodes: the state, `isPending` held as optimistic state, and a queue of pending calls. React runs queued calls one at a time and passes each the previous result. The action can be a plain client function, as here, or a Server Function. [The Server Components guide](/articles/react-server-components-internals) covers the server side.

`dispatchAction` has a stable identity. Call it from an Action, through `startTransition` or a form's `action` prop. The action function may have side effects, so Strict Mode never calls it twice.

### The rest, as a map

| Hook | What it gives you | Mechanism |
|---|---|---|
| `useTransition` | `[isPending, startTransition]` | A transition lane, plus an urgent optimistic `isPending` |
| `useDeferredValue` | A value that may lag | During an urgent render, a second render on a deferred transition lane |
| `useSyncExternalStore` | A value from a store outside React | Re-checks the snapshot before commit, to avoid **tearing** |
| `useId` | An ID that matches on server and client | Derived from the component's place in the tree |
| `useDebugValue` | A custom hook's DevTools label | Does nothing outside DevTools |
| `useFormStatus` | The parent form's pending state | Reads the nearest `<form>` Action, from `react-dom` |

Tearing is one screen showing two versions of the same value. `useId` is for accessibility attributes such as `aria-describedby`, never for list keys.

### Try it

In a React app, wire `useActionState` to an async action that waits one second. Click three times quickly and confirm the calls run one after another, each starting from the previous result.

## 18. Strict Mode runs your code twice

In development, your component logs twice, and a chat connects, disconnects and connects again. Nothing is broken. `<StrictMode>` is doing this on purpose.

### The short version

In development, `<StrictMode>` calls code that should be pure twice, to expose code that is not. React calls your component body twice and keeps one result. It also doubles initializers, updaters, reducers and `useMemo` functions.

In React 19, the second component call reuses the hook state of the first, so `useMemo` and `useCallback` return the first call's results. On mount, React also runs one extra cleanup and setup for every effect and ref callback. Correct code behaves the same. A missing cleanup or a side effect in render breaks visibly, in development.

### How React doubles the render

```js
// From renderWithHooks in ReactFiberHooks.js, React 19.2 (simplified).
const shouldDoubleRenderDEV = __DEV__ && (workInProgress.mode & StrictLegacyMode) !== NoMode;
shouldDoubleInvokeUserFnsInHooksDEV = shouldDoubleRenderDEV; // first call: double the user functions
let children = Component(props, secondArg);
shouldDoubleInvokeUserFnsInHooksDEV = false;
if (shouldDoubleRenderDEV) {
    children = renderWithHooksAgain(workInProgress, Component, props, secondArg); // reuses hook state
}
```

| What React doubles | How | What it catches |
|---|---|---|
| The component body | Called twice, the second call reuses the first call's hooks | Side effects and ref writes during render |
| State initializers, updaters and reducers | Called twice during the first call | Mutating state instead of returning new state |
| `useMemo` callbacks | Called twice during the first call, reused in the second | Impure computations |
| Effects | One extra cleanup and setup on mount | A missing or partial cleanup |
| Ref callbacks | One extra cleanup and attach on mount, new in React 19 | A missing ref cleanup |
| `useActionState` action functions | Never doubled | Nothing, because they may have side effects |

### What a double render exposes

```jsx
function StoryTray({ stories }) {
    const items = stories; // not a copy
    items.push({ id: "create", label: "Create Story" }); // mutates a prop
    return <ul>{items.map((story) => <li key={story.id}>{story.label}</li>)}</ul>;
}
```

In Strict Mode "Create Story" appears twice, because the second call pushes into the same array again. Copy first with `[...stories, ...]`, and both calls agree. With React DevTools installed, logs from the second call appear dimmed.

### What the extra effect cycle exposes

```text
Connecting to "general"
Disconnected from "general"
Connecting to "general"
```

The extra cycle simulates a component that unmounts and mounts again, as when a Suspense fallback replaces it or the user navigates away and back.

A correct effect ends in the same state: one connection. A leaky one ends with two. "It only breaks in Strict Mode" always means a real bug, usually a missing cleanup. Fix the pair, and Strict Mode goes quiet.

### Try it

In a React app, wrap the root in `<StrictMode>` and log in a component body, an updater, a `useMemo` callback and an effect. Count each log on first mount. Then remove an effect's cleanup and watch the extra cycle leave a second subscription behind.

## 19. Debugging hooks and effects

An effect fires constantly, or never. A value is stale. A memoized child re-renders anyway. You want a procedure that turns "React is being weird" into "I know which mechanism this is".

### The short version

Almost every hook bug is one of a few mechanisms from this guide. Ask three questions in order. Which render's snapshot did the bad value come from? Does the dependency array match what the effect reads, as the linter reports? Is the misbehaving value a primitive or an identity?

Those three resolve most cases. For timing bugs, ask a fourth: which commit phase runs this code, and was the render discrete? The React DevTools Profiler shows why each component rendered. Performance Tracks, new in React 19.2, show render and effect time per component in Chrome's Performance panel.

### Making identity visible

```js
function useWhyDidYouUpdate(name, props) {
    const previous = useRef(props);
    useEffect(() => {
        const changed = Object.keys(props).filter((key) => !Object.is(props[key], previous.current[key]));
        if (changed.length > 0) console.log(name, "changed:", changed);
        previous.current = props;
    });
}
```

This small hook logs which props changed identity since the last commit. A stale value is never random: it is a closure pinned to a render. "Looks the same but is treated as different" is always identity.

### Symptoms and causes

| Symptom | Mechanism | Section |
|---|---|---|
| An effect runs after every render | A dependency with a fresh identity | 10 |
| An effect loops forever | It sets state that rebuilds its own dependency | 9 |
| A stale value in a timer or subscription | A closure over an old render | 3 |
| Setup, cleanup, setup on mount in development | Strict Mode testing the cleanup | 18 |
| "Rendered more hooks" after a condition | A desynced hook list | 1 |
| "Too many re-renders" | An unguarded setter in the body | 6 |
| State "did not update" right after a set | The snapshot | 2 |
| Three value setters added only one | All read one snapshot | 4 |
| A `React.memo` child re-renders anyway | An unstable prop from the parent | 10 |
| A one-frame flicker | Layout read in a passive effect | 12 |
| A ref callback runs on every render | An inline callback is a new function | 15 |

## The whole thing in one list

1. Hooks are a linked list on the fiber, matched by call order, which is why the rules of hooks exist.
2. React swaps dispatchers: mount creates nodes, update reads them, and outside render hooks throw.
3. Each render is a snapshot, and every closure keeps the render that created it.
4. A setter adds an update to a circular queue, and the next render folds it, so updaters compose.
5. Updates carry lanes, and React replays skipped updates from `baseState` in their original order.
6. A same-value `useState` update can bail out before render, and render-phase updates re-run the component at once.
7. Effects synchronize with outside systems, and React decides during render, with `Object.is`, whether each one fires.
8. Cleanup always runs before the next setup, and fresh identities over-fire effects and defeat memoization.
9. Insertion and layout effects run before paint, and passive effects usually run after it, but not after a click.
10. `useEffectEvent`, refs, the Compiler, `use()`, Actions and Strict Mode all build on the same list and queue.

[ReactFiberHooks.js](https://github.com/facebook/react/blob/main/packages/react-reconciler/src/ReactFiberHooks.js) holds nearly everything in this guide, and [ReactFiberWorkLoop.js](https://github.com/facebook/react/blob/main/packages/react-reconciler/src/ReactFiberWorkLoop.js) holds the commit and the passive flush.

### Two classic essays

Dan Abramov's [A Complete Guide to useEffect](https://overreacted.io/a-complete-guide-to-useeffect/) and [React as a UI Runtime](https://overreacted.io/react-as-a-ui-runtime/) explain the snapshot model and identity. Both predate `useEffectEvent` and the Compiler, so read them for the model, not the API.
